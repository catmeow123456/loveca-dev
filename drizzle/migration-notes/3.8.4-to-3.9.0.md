# 3.8.4 到 3.9.0 停机迁移说明

> 文档类型：迁移运行说明
> 适用范围：从生产 `v3.8.4` 升级到 `v3.9.0`
> 当前状态：发布候选；尚未在生产执行

## 变更范围

本次发布包含两个 Drizzle schema 迁移：

1. `drizzle/0010_add_ranked_system.sql`
   - 新增赛季、排位对局、当前积分、软重置种子与追加式积分流水表；
   - 为公共牌桌票据和预留增加休闲/排位队列类型与赛季绑定；
   - 为玩家占用增加 `RANKED_QUEUE`，为对局来源增加 `RANKED`；
   - 不创建赛季、不回填历史对局积分，也不自动开放排位候场。
2. `drizzle/0011_add_match_replay_retention.sql`
   - 允许 `match_records.completeness` 使用 `METADATA_ONLY`；
   - schema 迁移本身不删除历史回放。删除超过保留期的回放子记录必须另行运行数据清理脚本，并视为独立、不可逆的维护动作。

本次还扩展了卡牌同步层的 Heart 颜色口径：Loveca Excel、CloudBase 与 llocg_db 的 `orange` 写为独立 `ORANGE`，`GRAY` 无色与 `RAINBOW` All Heart 继续保持不同语义。部署代码不会自动改写生产 `cards` 数据；只有已审核的数据源确实包含需要同步的橙色 Heart 或其他卡牌变更时，才执行本说明中的可选同步步骤。

专题细节见：

- `drizzle/migration-notes/ranked-system.md`
- `drizzle/migration-notes/3.8.4-to-3.9.0-match-replay-retention.md`
- `docs/matchmaking-and-ladder/RANKED_INITIAL_IMPLEMENTATION.md`
- `docs/card-data-sync/design.md`

## 发布前提

本次按停机迁移执行，不在运行时保留旧新结构 dual-read：

1. 在预发布环境使用最新生产备份完整演练本说明，并保存命令输出和验证结果。
2. 确认发布提交、`v3.9.0` tag、API 镜像 revision 和前端产物 build ID 指向同一提交。
3. 暂停 API、公共牌桌/排位运行时任务、对局记录写入和所有卡牌同步任务。
4. 完成 PostgreSQL dump，记录文件位置、校验和与恢复命令；如计划同步卡图，同时备份对象存储 bucket。
5. 确认数据库迁移基线已经到 `0009_magenta_nightcrawler`，且没有手工预建同名排位表或列。
6. 在具备源码、devDependencies 和生产 `DATABASE_URL` 的发布环境执行迁移；API runtime 镜像不包含 Drizzle CLI。
7. 准备 3.9.0 前后端/API 同版部署。迁移完成后不得恢复 v3.8.4 写入服务。

不要使用 `pnpm db:push`，不要修改已经共享的历史 SQL。

## 迁移演练与正式执行

Drizzle 当前没有用于本流程的生产 dry-run 命令。所谓 dry-run 是在生产备份恢复出的隔离数据库中执行真实迁移并完成全部验证：

```bash
DATABASE_URL='postgres://<staging-clone>' pnpm db:migrate
```

预发布演练通过、生产停写和备份确认后，再在生产执行：

```bash
DATABASE_URL='postgres://<production>' pnpm db:migrate
```

`pnpm db:migrate` 应按 journal 顺序执行 `0010`、`0011`。任一步失败都保持停机，不部署 API，不手工跳过 migration journal；先保存错误与数据库状态，再决定修复后重试或从发布前 dump 恢复。

## 迁移后验证

### Schema 与初始数据

排位表应完整存在：

```sql
SELECT tablename
FROM pg_tables
WHERE schemaname = 'public'
  AND tablename IN (
    'ranked_seasons',
    'ranked_matches',
    'ranked_player_ratings',
    'ranked_player_seeds',
    'ranked_rating_events',
    'ranked_rating_event_steps'
  )
ORDER BY tablename;
```

预期返回 6 张表。迁移不会自动创建赛季或积分数据：

```sql
SELECT
  (SELECT count(*) FROM ranked_seasons) AS seasons,
  (SELECT count(*) FROM ranked_matches) AS matches,
  (SELECT count(*) FROM ranked_rating_events) AS rating_events;
```

三个值均应为 `0`。

既有公共牌桌票据和预留只能被规范化为休闲队列，且不绑定赛季：

```sql
SELECT queue_kind, season_id IS NULL AS season_is_null, count(*)
FROM public_table_tickets
GROUP BY queue_kind, season_id IS NULL
ORDER BY queue_kind, season_id IS NULL;

SELECT queue_kind, season_id IS NULL AS season_is_null, count(*)
FROM public_table_reservations
GROUP BY queue_kind, season_id IS NULL
ORDER BY queue_kind, season_id IS NULL;
```

迁移前已有行只能出现 `CASUAL / true`。

确认回放完整度约束已经允许 `METADATA_ONLY`：

```sql
SELECT pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'match_records'::regclass
  AND conname = 'match_records_completeness_check';
```

结果应包含 `FULL`、`PARTIAL`、`INCOMPLETE` 与 `METADATA_ONLY`。

### 应用 smoke

部署 3.9.0 API 与前端后，在恢复公开流量前至少验证：

- `/api/health` 可响应，API 日志没有 schema、约束或迁移错误；
- 登录、卡组列表、卡图读取与普通房间创建可用；
- 休闲公共牌桌仍使用 `CASUAL`，不会误入排位赛季；
- 管理员能读取排位赛季页，尚未创建首季时玩家页安全显示无可用赛季；
- 创建草稿赛季、开放候场、结算更正等管理员流程只按另行批准的首季演练执行，不在发布 smoke 中直接开放生产赛季；
- 最近完整历史记录仍可读取回放，迁移后没有记录被自动清理。

## 可选卡牌数据同步

仅部署 3.9.0 不要求重跑卡牌同步。如果生产数据源已经出现 `orange`，或本次另有明确的数据发布范围，按“llocg_db 基础字段 → Loveca Excel/CloudBase 补强”的顺序执行，并对每一步单独审核。

先验证本地源文件转换：

```bash
pnpm exec tsx src/scripts/sync-cards-llocg.ts --dry-run
pnpm exec tsx src/scripts/sync-cards-loveca-excel.ts \
  --xlsx=docs/card-data-sync/sources/<已审核的-loveca-源文件>.xlsx \
  --dry-run
```

需要从 CloudBase 读取补强数据时，使用受控凭据运行：

```bash
pnpm exec tsx src/scripts/sync-cards-loveca-excel.ts \
  --source=cloudbase \
  --cloudbase-collection=loveca \
  --dry-run
```

正式写入前应保存 dry-run 报告，明确卡牌数量、字段差异、`ORANGE` 映射和图片策略。优先在可交互 TTY 中运行正式命令并逐项确认；非交互环境的 `--yes` 会跳过人工确认，只能在报告已经审核且另行授权后使用。`sync-cards-cloudbase-new.ts --upload-images --yes` 还会写入对象存储，不属于本次默认发布动作。

同步完成后抽查 `cards.hearts`、`cards.blade_hearts`、`cards.requirements` 中的 `ORANGE`，并确认 `GRAY` 未被改写为 `RAINBOW`。如果本次没有已审核的新来源数据，明确记录“未执行卡牌数据同步”。

## 回放保留数据清理

`0011` 只提供 `METADATA_ONLY` schema 能力。发布当天默认不执行历史数据删除。后续如经独立维护授权清理超过 10 天的已封存回放，必须先停写、备份并 dry-run：

```bash
DATABASE_URL='postgres://<production>' pnpm exec tsx \
  drizzle/data-migrations/purge-expired-match-replay-data.ts \
  --dry-run --retention-days=10 --batch-size=100
```

只有报告中的对局和子记录数量经人工确认后，才可在独立授权下执行 `--apply --yes`。该动作会永久删除时间线、检查点、事件、决策和卡组明细；应用层无法恢复。

## 部署顺序与兼容边界

1. 停止旧 API 和所有写入任务。
2. 完成备份并在隔离副本验证恢复能力。
3. 执行 `pnpm db:migrate`，完成 SQL 校验。
4. 部署 3.9.0 API 镜像与 3.9.0 前端静态产物。
5. 完成应用 smoke 后恢复流量。
6. 首季创建/开放、卡牌数据同步、回放数据清理分别走独立授权，不与代码部署捆绑自动执行。

前端与 API 应同版部署；旧 API 不得连接迁移后的 schema 继续写入。生产首季开放前还必须完成预发布排位演练、告警渠道、运营指标、首季时间窗口与 POC 判断口径。

## 回滚边界

- 在生产迁移前失败：可继续运行 v3.8.4，不涉及数据库恢复。
- 迁移完成但尚未恢复写入：停止部署，从发布前 dump 恢复数据库，再回滚 API 与前端到 v3.8.4。
- 已恢复写入但尚未产生排位数据、卡牌同步或回放清理：仍优先停机后从发布前 dump 恢复；不得假设 v3.8.4 可以安全连接新 schema。
- 一旦产生正式排位数据：不得删表、删列或手改积分；应用层更正只能使用追加式 `VOID / REPLACEMENT`。如果必须整体回滚 schema，只能停写并从发布前 dump 恢复，同时接受发布后的新增业务数据丢失，或先制定人工合并方案。
- 一旦执行卡牌数据同步或回放清理：代码/前端/API 可以在同 schema 的兼容版本间单独回滚，但数据本身不会随代码回滚。错误卡牌数据需按审核后的反向同步或备份恢复处理；已清理回放只能从发布前数据库备份恢复。
- 对象存储若有写入，按发布前 bucket 备份恢复对应 key，并刷新代理/CDN 缓存。

任何回滚后都要重新执行 API、前端、图片、普通联机与历史记录 smoke，并记录恢复的版本标签和镜像 digest。

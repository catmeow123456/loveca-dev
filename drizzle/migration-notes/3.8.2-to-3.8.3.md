# 3.8.2 至 3.8.3 发布迁移说明

- 适用发布：`v3.8.3`
- 适用 SQL：`drizzle/0009_magenta_nightcrawler.sql`

## 变更范围

- 新增 `public.email_change_tokens`，用于保存待确认邮箱换绑的一次性 token 摘要、新邮箱、
  过期时间和用户关联。
- `user_id` 与 `token` 均为唯一值；用户删除时通过外键级联删除待确认记录。
- 新增 token 与过期时间索引。
- 更新 `public.cleanup_expired_tokens()`，将过期的邮箱换绑 token 纳入统一清理。
- 新增个人中心资料、密码与邮箱换绑 API/前端流程；邮箱确认成功后更新账号邮箱并撤销现有可续期会话。
- 本次不转换既有用户数据，不需要重跑卡牌数据或其他数据同步脚本，也不修改对象存储内容。
- 本次没有新增生产环境变量。若启用邮箱换绑，必须沿用并核对现有
  `EMAIL_ENABLED=true`、`SMTP_HOST`、`SMTP_PORT`、`SMTP_USER`、`SMTP_PASS`、`SMTP_FROM`
  与正确的 `FRONTEND_URL`；未启用邮件时前端不应提供邮箱换绑入口。

`0009` 是新增表与函数替换，不会改变旧 API 已使用的表结构，因此旧 API 可以短时连接已迁移
schema 以处理故障回退；但新 API 在迁移前不能安全提供邮箱换绑。发布仍必须使用停机维护窗口，
先迁移数据库，再切换同一提交构建的 API 与 `client/dist`，不允许长期前后端混跑。

## 发布前置与执行顺序

1. 停止 `v3.8.2` API、定时清理任务和其他生产写入，进入维护窗口。
2. 完成 Postgres dump，记录备份文件、校验结果与恢复命令；按生产 runbook 同时确认对象存储快照
   可用，尽管本次不修改对象存储。
3. 确认发布环境包含完整源码与 devDependencies，并核对生产 `DATABASE_URL`；不得在 API runtime
   镜像内猜测执行迁移，也不得使用 `pnpm db:push`。
4. 在生产数据库执行：

   ```bash
   DATABASE_URL='postgres://...' pnpm db:migrate
   ```

5. 执行下方迁移后 SQL 检查。任一检查不符合预期时保持停机，不部署新 API。
6. 部署 `v3.8.3` API 镜像，随后立即部署同一提交构建的 `client/dist`，再恢复流量。
7. 若生产启用邮件，确认 SMTP 凭据通过安全环境变量注入，且 `FRONTEND_URL` 指向正式 HTTPS 域名。

## 发布前验证

发布前确认 3.8.2 基线中尚无邮箱换绑表，并记录当前清理函数定义：

```sql
SELECT to_regclass('public.email_change_tokens') AS email_change_tokens;

SELECT pg_get_functiondef('public.cleanup_expired_tokens()'::regprocedure);
```

从未提前应用 `0009` 的 3.8.2 数据库中，第一条应返回 `NULL`。如果表已经存在，停止发布并先核对
Drizzle migration 记录、表结构、索引和函数定义；不要直接重复执行 migration SQL。

## 迁移后验证

确认表、列、约束和索引存在：

```sql
SELECT to_regclass('public.email_change_tokens') AS email_change_tokens;

SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'email_change_tokens'
ORDER BY ordinal_position;

SELECT constraint_name, constraint_type
FROM information_schema.table_constraints
WHERE table_schema = 'public'
  AND table_name = 'email_change_tokens'
ORDER BY constraint_name;

SELECT indexname
FROM pg_indexes
WHERE schemaname = 'public'
  AND tablename = 'email_change_tokens'
ORDER BY indexname;
```

预期：

- relation 为 `email_change_tokens`；
- 列包含 `id`、`user_id`、`new_email`、`token`、`expires_at`、`created_at`；
- 存在主键、`user_id`/`token` 唯一约束和指向 `users(id)` 的外键；
- 存在 `idx_email_change_tokens_token` 与 `idx_email_change_tokens_expires_at`。

确认清理函数已包含新表，并做不修改数据的定义检查：

```sql
SELECT position(
  'DELETE FROM public.email_change_tokens'
  IN pg_get_functiondef('public.cleanup_expired_tokens()'::regprocedure)
) > 0 AS cleans_email_change_tokens;

SELECT count(*) AS pending_email_changes
FROM public.email_change_tokens;
```

第一条应返回 `true`；刚完成迁移且尚未恢复流量时，第二条通常应为 `0`。

## 发布后 smoke

按生产 runbook 完成容器、API health、前端 `version.json`、manifest 与图片代理检查，并至少验证：

1. 已登录账号可以打开个人中心，更新用户名与显示名称；用户名冲突返回明确错误。
2. 修改密码时必须验证当前密码；成功后旧密码失效，新密码可登录。
3. 启用邮件的生产环境中，使用测试账号发起邮箱换绑，确认新邮箱收到正式域名链接。
4. 打开一次有效确认链接，确认账号邮箱更新、旧会话被撤销且需要重新登录。
5. 重复使用或使用过期确认链接应失败，且不会再次修改邮箱。
6. 调用既有 token 清理任务后，过期 `email_change_tokens` 记录会被删除。
7. 完成联机房间、局内聊天和一局基础对战的最小 smoke，确认 API 与前端为同一版本。

## 同步脚本与人工审核

- 本次不需要运行卡牌、用户、对局记录、对象存储或图片同步脚本。
- 不需要 `--yes` 类批量数据写入，也没有需人工审核的源文件导入。
- 不要为了验证迁移而在生产执行 `pnpm db:push` 或手工修改已共享的 Drizzle migration。

## 回滚边界

- 若迁移成功但尚未恢复生产写入，新表为空；可以先回滚 API 与前端到 `v3.8.2`。旧 API 会忽略
  这张新增表，但这不等于 schema 已回滚。
- 若恢复流量后仅 API/前端出现问题，可停止写入并将 API 与前端一并回滚到 `v3.8.2`；发布期间
  创建的邮箱换绑 token 不会被旧版本消费，应视为失效，后续重新发布时由用户重新发起。
- 仓库没有 `0009` 的 down migration。若要求数据库精确回到发布前状态，或迁移/数据出现异常，
  必须停止 API 写入并从发布前 Postgres dump 恢复；不要手工删除共享 migration 记录。
- 本次不修改对象存储；只有同时发生与本次无关的对象损坏时，才使用发布前对象存储快照恢复。

> 文档类型：人工发布 runbook（不是 Drizzle 可执行迁移）
> 适用范围：从 3.9.4 升级到 3.9.5

> 赛季公告专题：[`drizzle/migration-notes/ranked-season-announcement.md`](ranked-season-announcement.md)

## 结论与部署边界

- 本版本包含 `0017_add_ranked_rating_revisions.sql`、`0018_add_ranked_season_announcement.sql`、`0019_add_player_badges.sql`、`0020_add_ranked_deck_observations.sql`。生产迁移历史当前截至 `0016`，发布 3.9.5 前必须执行 `pnpm db:migrate` 并确认 `0017` 至 `0020` 全部登记成功。
- `0017`、`0018` 只增加评分参数修订和赛季公告所需结构，不会自动修订既有赛季评分、修改算法配置或写入公告。`0019`、`0020` 只增加徽章与精简卡组观察结构，不会自动补发首届赛季徽章，也不会自动回填历史排位对局。
- 首届赛季会在 3.9.5 上线前由 3.9.4 结束，因此本次采用两个停写窗口：先在原始回放仍处于 10 天保留窗口内完成结构迁移和首轮环境观察回填；首届赛季结束后再完成增量观察回填、徽章事后补发和新版部署。两个窗口之间继续运行 3.9.4，但必须保持回放清理暂停。
- 3.9.5 新版排位开局依赖 `ranked_deck_observations`；不得在 `0020` 尚未落地时部署新版 API。API 与前端必须使用同一 3.9.5 release SHA 构建并同版部署。
- 本版本不新增生产环境变量，不包含卡牌基础数据同步、对象存储上传或卡图同步；不得执行 `pnpm db:push`、任何卡牌同步 apply 命令或手工修改 Drizzle journal。本次不包含 Android APK/AAB，Android 版本字段和签名材料保持不变。

## 窗口一：结构迁移与首轮环境观察回填

1. 记录 3.9.5 release SHA、候选 API 镜像标签及 digest、前端产物来源、操作者和回滚负责人；确认 exact-SHA `Quality Gates`、API 候选镜像 runtime 检查和 `Release Tag Integrity` 均已成功。
2. 停止 API、排位开局、结算、评分参数修订和回放清理，等待在途事务收束后创建并验证完整 PostgreSQL 备份。
3. 在 3.9.5 release SHA 的完整源码和锁文件上使用生产 `DATABASE_URL` 执行 `pnpm db:migrate`；确认 `0017` 至 `0020` 全部登记成功，并核对四份专题迁移说明要求的表、列、约束和索引。
4. 对首届赛季执行环境观察 dry-run：

   ```bash
   DATABASE_URL=... pnpm ranked:environment:backfill -- --season-key=<首赛季-key>
   ```

5. 默认只接受 `blockers=[]`、`irrecoverableMatchCount=0` 的完整历史分支。保持停写，复制 dry-run 的 `ledgerRevision` 执行：

   ```bash
   DATABASE_URL=... pnpm ranked:environment:backfill -- --season-key=<首赛季-key> \
     --apply --yes --expected-ledger-revision=<dry-run-ledgerRevision>
   ```

   若可验证备份也无法恢复少量已清理对局，必须严格按赛季环境专题说明固定 `irrecoverableMatchCount`、`irrecoverableMatchHash` 和 ledger revision，并由维护者书面接受永久覆盖率缺口；不得用例外参数绕过任何 `blockers`。

6. 再次 dry-run，完整历史分支应满足 `blockers=[]`、`irrecoverableMatchCount=0`、`wouldInsertObservationCount=0`、`alreadyCompleteMatchCount=matchCount`。核对结果后恢复 3.9.4 API 与前端及排位服务，但继续暂停 10 天回放清理，直至窗口二完成。

## 窗口二：赛季收口、增量回填与 3.9.5 部署

1. 使用 3.9.4 按既定流程结束首届赛季。再次停止 API、排位开局、结算、评分参数修订和回放清理，等待在途事务收束后创建并验证新的完整 PostgreSQL 备份。
2. 重复执行首届赛季环境观察 dry-run，并按窗口一相同的完整历史或已批准例外分支完成增量 apply；再次 dry-run，确认没有新的可回填记录、硬阻塞或未经批准的永久缺口。
3. 对已结束的首届赛季执行徽章 dry-run，核对来源赛季、资格门槛、候选玩家、已授予玩家、`wouldAwardCount` 和 `ledgerRevision`：

   ```bash
   DATABASE_URL=... pnpm badges:first-ranked:backfill -- --season-key=<首赛季-key>
   ```

4. 保持停写，使用 dry-run 返回的 ledger revision 完成事后补发：

   ```bash
   DATABASE_URL=... pnpm badges:first-ranked:backfill -- --season-key=<首赛季-key> \
     --apply --yes --expected-ledger-revision=<dry-run-ledgerRevision>
   ```

5. 再次执行徽章 dry-run，预期 `wouldAwardCount=0`，且规则绑定、候选数、已授予数和流水版本一致。首届徽章完全按已结算历史补发，不需要重开赛季或制造测试对局。
6. 部署与 release SHA 一致的 `ghcr.io/catmeow123456/loveca-api:v3.9.5`（或已记录 digest）和前端产物；确认 `/api/health`、首页、`version.json`、PWA manifest、排位赛季页和图片代理版本一致。
7. 检查排位公告读取、运营概览、对局处理、玩家环境 Top 30 与覆盖率、个人中心徽章展示；抽查新排位对局双方各有一条身份和卡组来源一致的精简观察事实。
8. 完成登录、卡组读取/保存、普通联机房间、公共牌桌首次对局与重开猜拳、排位候场/开局/结算及一局基础对战 smoke。全部门禁通过后恢复所有服务，再恢复 10 天回放清理；确认清理不会删除长期精简观察，且缺少完整排位观察时会整体阻断。

## 回滚

- `pnpm db:migrate` 执行前失败：保持 3.9.4 服务和数据库不变，修复原因后重新准备发布。
- 任一迁移或回填失败：保持全部写入停止，不部署 3.9.5，也不要手工补表、改 Drizzle journal、删除既有授予或观察记录；根据已执行步骤和已验证备份决定向前修复或整库恢复。
- `0017` 至 `0020` 均为向后兼容的新增结构。窗口一完成后可继续运行 3.9.4，但必须保持回放清理暂停，并不得使用 3.9.5 新功能写入生产事实。
- 数据回填成功后不得通过删表或删记录回滚。若窗口二需要回到 3.9.4，应停止全部写入、保留已经写入的徽章和观察事实，只回滚 API 与前端；恢复服务前验证旧版不会破坏这些新增表。
- 若数据库与 3.9.5 API 健康而仅前端静态产物异常，可在验证接口兼容后单独回滚前端；GitHub tag、Release 和不可变镜像标签不得覆盖或重写。

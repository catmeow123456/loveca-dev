# 3.8.1 至 3.8.2 发布迁移说明

- 适用发布：`v3.8.2`
- 适用 SQL：无新增 Drizzle migration

## 变更范围

- 公共牌桌配对房间新增双方到场确认与 60 秒超时结束语义；超时会在既有
  `public_table_reservations.failure_reason` 中记录 `OPENING_ARRIVAL_TIMEOUT`。
- 联机房间投影新增 `openingArrivalExpiresAt`、`endInfo` 与 `ENDED` 状态；对局投影新增公开的
  `endInfo`，用于认输和正常结束后的结果展示。
- 规则模式的 LIVE 设置阶段新增撤回本轮盖牌命令；联机认输会以既有对局记录结构封存为
  `SURRENDERED`。
- 公共牌桌 heartbeat 宽限从 90 秒收紧到 45 秒，API runtime cleanup 默认间隔从 60 秒收紧到
  10 秒；没有新增生产环境变量。
- 本次不修改数据库 schema，不转换历史数据，不需要重跑卡牌数据、对象存储或其他同步脚本。

新前端依赖上述新增投影字段与房间状态，旧 API 不提供完整协议；旧前端也不具备新的到场门禁和
结束页交互。发布时必须在同一维护窗口切换 `v3.8.2` API 与 `client/dist`，不允许长期混跑。

## 发布前置与执行顺序

1. 确认生产当前已完成 `v3.8.1` 对应的 `drizzle/0008_add_public_table_beta.sql`，并完成
   Postgres dump；记录恢复命令和备份位置。对象存储虽无本次变更，仍按生产 runbook 确认快照可用。
2. 停止旧版本 API、公共牌桌候场与其他新对局写入，避免维护窗口内继续创建仅存在于旧进程内存的
   房间运行态。
3. 本次没有新增 migration，因此无需执行 `pnpm db:migrate`；不得执行 `pnpm db:push`。
4. 部署 `v3.8.2` API 镜像，随后立即部署同一提交构建的 `client/dist`，再恢复流量。
5. 确认生产仍显式提供既有 JWT、数据库、对象存储、`FRONTEND_URL` 与可选邮件配置；本次无需新增
   环境变量。

## 发布前后验证

发布前确认 `v3.8.1` 公共牌桌底座仍存在：

```sql
SELECT
  to_regclass('public.gameplay_participations') AS gameplay_participations,
  to_regclass('public.public_table_tickets') AS public_table_tickets,
  to_regclass('public.public_table_reservations') AS public_table_reservations;

SELECT column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'public_table_reservations'
  AND column_name = 'failure_reason';
```

第一条应返回三个非空 relation，第二条应返回一行 `failure_reason` 文本列。本次发布前后结果应一致，
因为 `v3.8.2` 不改变 schema。

部署后按生产 runbook 检查 API health、前端 `version.json`、manifest 与图片代理，并至少完成：

1. 两个测试账号通过公共牌桌完成候场、确认、双方进入房间、猜拳和首个对局快照。
2. 仅一方进入公共牌桌房间时，确认 60 秒后房间显示到场超时结束，且 reservation 的
   `failure_reason` 为 `OPENING_ARRIVAL_TIMEOUT`。
3. 联机对局完成一次主动认输，确认双方结果页正确，历史记录状态为 `SURRENDERED`。
4. 在规则模式 LIVE 设置阶段盖牌后撤回，确认仅能撤回本轮仍为里侧的 LIVE 卡。

## 回滚边界

- 本次无 schema 或批量数据迁移；若仅 API / 前端异常，可停止写入后把 API 镜像和前端静态产物
  一并回滚到 `v3.8.1`，无需恢复数据库。
- 已写入的 `OPENING_ARRIVAL_TIMEOUT` 只是既有可空文本列中的新原因值，不要求清理；回滚后的旧
  API 不应继续复用发布期间的内存房间运行态。
- 若发布期间同时发生与本次无关的数据损坏，停止 API 写入并按生产 runbook 使用发布前 dump
  恢复；不要把应用回滚等同于数据库恢复。

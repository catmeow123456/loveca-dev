# 3.9.2 → 3.9.3 生产迁移说明

> 文档类型：人工发布 runbook（不是 Drizzle 可执行迁移）
> 适用范围：从 3.9.2 升级到 3.9.3
> 通用生产发布流程：[`docs/production-release-runbook.md`](../../docs/production-release-runbook.md)
> 独立排位迁移：[`docs/matchmaking-and-ladder/RANKED_V3_ACTIVE_SEASON_MIGRATION.md`](../../docs/matchmaking-and-ladder/RANKED_V3_ACTIVE_SEASON_MIGRATION.md)

## 结论与部署边界

- 本版本没有 schema SQL 变化，不新增 Drizzle migration，生产发布无需执行 `pnpm db:migrate`。
- 本版本不包含数据修复、卡牌数据同步、对象存储上传或图片同步；不得为了本次发布临时执行 `pnpm db:push` 或任何卡牌同步 apply 命令。
- 本版本不新增生产环境变量。发布前仍需按通用 runbook 核对数据库、JWT、对象存储、前端域名及按需启用的邮件配置。
- API 与前端必须使用同一 3.9.3 release SHA 构建并同版部署。排位候场准入不再因为活动赛季期间发布卡池变化而关闭，但赛季生命周期、开放窗口、候场开关和评分配置校验保持不变。
- 活动赛季 `GLICKO1_PER_MATCH_V2` → V3 的停机迁移不属于本次普通版本发布，不会自动执行。若生产仍需该迁移，必须继续按独立 runbook 取得授权并完成停写、备份、dry-run、apply 和二次 dry-run；不得把部署 3.9.3 当作迁移完成。
- 本次不包含 Android APK/AAB；`android/twa/loveca/twa-manifest.json` 的 Android 版本字段和签名材料保持不变。

## 发布前准备

1. 记录 3.9.3 release SHA、`v3.9.3` API 镜像标签及 digest、前端产物来源、操作者和回滚负责人。
2. 确认 exact-SHA `Quality Gates`、API 候选镜像 runtime 检查和 `Release Tag Integrity` 均已成功；父提交、PR head 或其他 SHA 的结果不能复用。
3. 检查工作树与发布差异，确保本地卡图、研究报告、导出 CSV、Android 测试包和 keystore 未进入发布提交或产物。
4. 即使没有 schema 迁移，也应确认最近一次 Postgres 备份可恢复，并记录当前 API/前端版本和上一版 `v3.9.2` 镜像 digest。对象存储本次无写入，不要求额外同步快照。
5. API 进程内对局运行态尚未完整持久恢复。部署应选择低峰维护窗口，提前停止新对局入口并等待进行中对局收束；不得把容器重启视为无感滚动更新。

## 部署顺序与验证

1. 不执行数据库迁移或卡牌同步。按生产 runbook 将 `LOVECA_API_IMAGE` 固定为已验证的 `ghcr.io/catmeow123456/loveca-api:v3.9.3` 或记录的 digest，再拉取并启动 API；生产机不得重新构建镜像。
2. 部署同一 release SHA 构建的 `client/dist`，同时更新 manifest、Service Worker、`version.json` 和 PWA 图标静态产物；本次不分发 Android 安装包。
3. 检查容器状态、API 日志和 `/api/health`，再检查首页、`manifest.webmanifest`、图片代理和 `version.json` 的版本/buildId。
4. 完成最小 smoke：登录、卡组读取与卡图、普通联机房间创建/加入、移动端局内状态栏与聊天入口、私有房间赛后重开/离房，以及一局包含声援 DRAW 与 LIVE 判定的基础流程。
5. 如活动赛季处于开放状态，核对赛季页和候场状态；发布卡池变化不得再造成“当前版本与赛季环境不一致”的准入错误。不要在本次 smoke 中执行评分算法迁移或重建。

## 回滚

- API 或前端异常且数据库未被其他运维动作修改时，回滚到已记录的 3.9.2 API digest 和同 SHA 前端产物，并重新执行健康检查与最小 smoke。
- 本次没有 schema 或数据迁移，因此不需要数据库回滚；若发布窗口中另行执行了排位 V3 迁移、卡牌同步或其他写入，必须使用对应独立 runbook 的回滚边界，不能套用本说明的无迁移结论。
- 回滚 `latest` 时不要猜测标签内容；生产部署应固定到上一版不可变标签或已记录 digest。GitHub tag 和 Release 保留作为审计记录，不覆盖或重写。

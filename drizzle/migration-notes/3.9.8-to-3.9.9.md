# 3.9.8 -> 3.9.9 生产迁移说明

> 文档类型：人工发布 runbook（不是 Drizzle 可执行迁移）
> 适用范围：从 3.9.8 升级到 3.9.9
> 通用生产发布流程：[`docs/production-release-runbook.md`](../../docs/production-release-runbook.md)
> 专题说明：[`season-admin-role.md`](season-admin-role.md)、
> [`maintenance-mode-three-state.md`](maintenance-mode-three-state.md)

## 结论与部署边界

- 本版本包含 `0028_add_season_admin_role.sql`、
  `0029_maintenance_mode_three_state.sql` 与
  `0030_add_global_battle_timeout_config.sql`。从 3.9.8 升级时必须在停写窗口执行
  `pnpm db:migrate`，并确认三条迁移均登记成功。
- `0028` 扩展 `profiles.role` 的约束并创建 `management_audit_logs` 骨架，但不会自动授予
  `season_admin`。赛季写操作持久审计、破坏性操作原因和完整权限 E2E 尚未完成，本次部署后不得为真实运营账号分配
  `season_admin`。
- `0029` 将平台状态收敛为 `NORMAL`、`RESTRICTING_NEW_GAMES`、`MAINTENANCE`。旧
  `SCHEDULED`、`COMPLETED`、`POSTPONED`、`CANCELLED` 会转换为 `NORMAL` 并清空旧维护字段；
  旧计划和历史语义必须在迁移前转存为公告，运行时不提供旧值兼容读取。
- `0030` 为平台配置增加操作超时和断线重连期限，默认分别为 180 秒和 60 秒。新对局在开局时冻结当时配置；已有
  进行中对局不应因后台调整而改变。当前自动操作超时和断线裁定仍只在已启用对应裁定的排位路径执行。
- 3.9.9 首次部署独立公开维护快照。生产必须新增宿主持久目录
  `PUBLIC_SITE_STATUS_SNAPSHOT_DIR`，并让反向代理把其中同一文件映射为禁止缓存的
  `/site-status.json`；该目录不得位于 `client/dist`。生产 compose 会把目录挂载到 API 容器内固定路径。
- API、前端和迁移必须来自同一 3.9.9 release SHA。本版本不执行卡牌数据同步、卡图重传、对象存储写入或回放保留
  清理；新增的数据维护页面与匿名分析导出只是运维能力，任何清理 apply 仍需独立预览和授权。
- 本版本不包含 Android APK/AAB。Android 版本字段、正式签名和 assetlinks 保持不变。

## 发布前环境、备份与维护窗口

1. 记录 3.9.9 release SHA、API 候选镜像标签与 digest、固定生产平台 `linux/amd64`、前端产物来源、
   GHCR `latest` 起始快照、操作者和回滚负责人。确认 exact-SHA `Quality Gates`、候选镜像 runtime 检查和
   `Release Tag Integrity` 均按发布 runbook 通过。
2. 确认 3.9.8 生产数据库已经按顺序应用 `0001` 至 `0027`，并审查 `0028`、`0029`、`0030` 与
   Drizzle journal；不得修改已共享迁移或使用 `pnpm db:push`。
3. 迁移前只读盘点并保存：

   ```sql
   SELECT role, count(*) FROM profiles GROUP BY role ORDER BY role;
   SELECT lifecycle, count(*) FROM site_status_config GROUP BY lifecycle ORDER BY lifecycle;
   SELECT id, lifecycle, title, summary, updated_by, updated_at
   FROM site_status_config
   ORDER BY id;
   ```

   如果存在旧的计划、延期、取消或完成状态，先把仍需保留的用户可见信息转存为公告并人工核对，不得依赖迁移后的旧字段。

4. 在宿主机创建独立持久目录，配置 `PUBLIC_SITE_STATUS_SNAPSHOT_DIR`，并让反向代理将同一目录中的
   `site-status.json` 暴露为 `/site-status.json`。响应必须包含 `Cache-Control: no-store, max-age=0`，且不能
   回退到 API、SPA index 或前端发布目录。
5. 首次切换三态协议时，使用 3.9.9 release SHA 的离线工具先写入维护快照，再从未登录和无痕窗口验证深链进入维护页：

   ```bash
   pnpm site-status:snapshot \
     --status=MAINTENANCE \
     --path=/srv/loveca/site-status/site-status.json \
     --title='舞台正在整备' \
     --summary='版本更新期间暂时无法进入。'
   ```

   上述路径只是示例，必须替换为生产 `PUBLIC_SITE_STATUS_SNAPSHOT_DIR` 中的实际文件。确认公开快照可达且禁止缓存后，
   停止旧 API、后台任务、公共/排位/娱乐模式候场与开局、赛季管理及其他数据库写入，并等待在途事务收束。

6. 创建并验证完整 PostgreSQL 备份，记录备份位置、校验结果和恢复命令。至少单独核对 `profiles`、
   `site_status_config`、排位运行表、主题赛季运行表和对局记录根表。数据库仍在停写时保留迁移前汇总结果。

## 停机迁移与部署顺序

1. 在 3.9.9 release SHA 的完整源码、锁文件、devDependencies 和生产 `DATABASE_URL` 上执行：

   ```bash
   pnpm db:migrate
   ```

   不得使用 `pnpm db:push`，不得手工补表、约束或 Drizzle journal。

2. 在仍保持停写时核对迁移结果：

   ```sql
   SELECT role, count(*) FROM profiles GROUP BY role ORDER BY role;

   SELECT conname, pg_get_constraintdef(oid)
   FROM pg_constraint
   WHERE conname IN (
     'profiles_role_check',
     'site_status_config_lifecycle_check',
     'site_status_config_player_action_timeout_check',
     'site_status_config_reconnect_grace_period_check'
   )
   ORDER BY conname;

   SELECT id, lifecycle,
          player_action_timeout_seconds,
          reconnect_grace_period_seconds,
          updated_by, updated_at
   FROM site_status_config
   ORDER BY id;

   SELECT to_regclass('public.management_audit_logs') AS management_audit_logs;
   ```

   现有 `user` / `admin` 数量必须与迁移前一致，`season_admin` 必须为 0；状态只能是三种新值；默认时限应为
   180/60，除非本次维护窗口已记录并批准其他平台级值。

3. 部署与 release SHA 一致的 `ghcr.io/catmeow123456/loveca-api:v3.9.9`（或发布记录中的不可变
   digest）和同一 SHA 的前端静态产物。生产机只拉取镜像并以 `--no-build` 启动，不重新构建 API。
4. 保持公开快照为 `MAINTENANCE`，检查 `/api/health` 与 `/api/ready`。`/api/ready` 未成功前不得开放；同时
   核对 API 容器挂载的快照路径与反向代理读取的是宿主机上的同一文件。
5. 由平台管理员通过维护页运营入口进入平台配置，保存 `NORMAL`。确认数据库状态已开放且 API 原子写出 `OPEN` 快照；
   不得只用离线脚本写 `OPEN` 来绕过数据库恢复流程。
6. 从普通、无痕和已安装 PWA 检查首页、深链、`version.json`、PWA manifest、图片代理和
   `/site-status.json`。确认公开快照禁止缓存，且 API 暂停时维护/故障页面不会依赖卡图或远程资源。
7. 做最小业务 smoke：登录、卡组读取、普通房间、公共牌桌、排位候场与一局受控对局；确认平台后台显示 180/60
   时限或批准后的值，新排位对局冻结对应配置，终局能区分主动认输、断线超时与操作超时。
8. 核对数据维护页的回放清理预览和赛季匿名分析 ZIP 只读生成路径。不要在本次发布窗口执行清理 apply；以后执行时必须
   固定 cutoff，确认 `blockedRankedMatchCount=0`，并单独取得删除授权。
9. 继续保持 `season_admin` 未分配。赛季写操作审计、破坏性操作原因、完整负向权限矩阵和 E2E 全部完成并另行审核前，
   不得把开发基线描述为可生产委派。

## 回滚边界

- 数据库迁移前失败：数据库尚未变化；保持维护快照和停写，修复环境后重新进入迁移流程。
- 数据库迁移失败：保持全部写入停止，不部署 3.9.9，不手工补表、约束或 journal；根据失败点向前修复，或恢复迁移前
  PostgreSQL 备份。
- 数据库迁移成功而新应用部署失败：不要启动 3.9.8 接受流量。`0028`–`0030` 不提供旧应用运行时兼容；如无法修复
  并重新部署同一 3.9.9 SHA，恢复迁移前数据库备份，并同时回滚 API 与前端。
- 已产生 `season_admin`、新三态配置、管理审计或新时限配置后，不得通过手改约束回退到 3.9.8。先保持停写，审核
  数据保留与角色恢复策略，再决定修复 3.9.9 或从已确认的备份整体恢复。
- GitHub tag、Release 和不可变 `v3.9.9` / `sha-*` 镜像标签不得覆盖或重写；`latest` 回滚使用提升前记录的旧
  digest，生产 API 回滚优先使用部署前从实际旧容器捕获的不可变 RepoDigest。

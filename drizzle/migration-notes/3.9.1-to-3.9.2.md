# 3.9.1 → 3.9.2 生产迁移说明

> 文档类型：人工发布 runbook（不是 Drizzle 可执行迁移）
> 适用范围：从 3.9.1 升级到 3.9.2
> 详细排位迁移步骤：[`docs/matchmaking-and-ladder/RANKED_V3_ACTIVE_SEASON_MIGRATION.md`](../../docs/matchmaking-and-ladder/RANKED_V3_ACTIVE_SEASON_MIGRATION.md)
> 通用生产发布流程：[`docs/production-release-runbook.md`](../../docs/production-release-runbook.md)

## 结论与部署边界

- 本版本没有 schema SQL 变化，不新增 Drizzle migration，生产发布无需执行 `pnpm db:migrate`。
- 本版本包含独立的活动赛季 `GLICKO1_PER_MATCH_V2` → V3 停机数据迁移。它不是 schema migration，不能因“无需 `db:migrate`”而跳过；生产迁移尚未执行，必须另行取得生产操作授权。
- 迁移会追加 V3 `REPLACEMENT`（平台无结果为 `VOID`）指令并重建积分投影、对局算法标记、赛季冻结配置和竞技环境；不会删除或改写旧评分事件与步骤。
- API 与前端必须以 3.9.2 同版部署。迁移完成后不得启动旧 3.9.1/V2 API 连接新数据；新版 API 启动和恢复候场是迁移后的两个独立动作。
- 本版本不新增生产环境变量；迁移 CLI 仍会加载既有服务端完整配置，不能只提供 `DATABASE_URL`。
- 本次不要求、也不会自动执行卡牌数据同步、对象存储上传或图片同步。排位迁移只读取当前已发布卡池身份并要求其与赛季冻结身份一致；不一致时应停止并调查，不能用同步动作绕过 blocker。

## 发布前准备

1. 安排完整停机窗口，记录目标提交、`v3.9.2` 镜像标签及 digest、活动赛季 ID、操作者 ID 和恢复负责人。
2. 准备 3.9.2 目标提交的完整源码和锁文件，并安装完整依赖。生产 API runtime 镜像只含 `dist/server/index.js`，不含迁移 CLI、`tsx` 或 devDependencies，不能在该镜像中运行迁移。应在受控迁移主机从目标提交执行 `pnpm install --frozen-lockfile`，再运行 `pnpm ranked:v3:migrate`；不得从其他提交拼接脚本或依赖。
3. 为迁移进程提供与生产 API 相同且完整的配置：`DATABASE_URL`、`JWT_SECRET`、`JWT_REFRESH_SECRET`、`MINIO_ENDPOINT`、`MINIO_PORT`、`MINIO_ACCESS_KEY`、`MINIO_SECRET_KEY`、`MINIO_BUCKET`、`MINIO_USE_SSL`、`FRONTEND_URL`、`EMAIL_ENABLED`，以及明确的 `NODE_ENV=production`。如 `EMAIL_ENABLED=true`，还需提供 `SMTP_HOST`、`SMTP_PORT`、`SMTP_USER`、`SMTP_PASS`、`SMTP_FROM`；即使迁移逻辑不发送邮件，配置模块仍必须完整、真实且与目标环境一致。所有秘密仅通过受控环境注入，不写入仓库、命令行、报告或聊天记录。
4. 先保留旧 V2 应用运行，通过既有管理操作把赛季候场设为 `PAUSED`；等待已配对/已开局对局结束，并由旧版可靠结算路径把所有 `PENDING` 排空。
5. 确认没有新排位运行态进入后，停止旧版 API、排位清理任务和全部其他写入者，再创建完整 Postgres dump；记录备份文件、校验值和已验证的恢复命令。停机后、新版启动前不得恢复任何写入。

## dry-run、apply 与二次 dry-run

在受控迁移主机、3.9.2 目标提交源码根目录中执行；报告路径必须位于加密或访问受控的运维目录，且使用全新的文件名（CLI 拒绝覆盖已有报告）。
即使提供 `--report`，CLI 仍会把同一份完整 JSON 报告写到 stdout，因此不得在公开 CI、可公开检索的终端录制或未受控日志系统中运行。

```bash
pnpm ranked:v3:migrate -- --season-id=<uuid> \
  --report=/安全路径/v3-dry-run.json
```

审核 `sourceLedgerRevision`、`targetLedgerRevision`、`appendedDirectiveCount`、`materializedMatchCount`、`playerChanges`，并确认全部 blocker 为 0，尤其是逐场冻结环境漂移 `rankedMatchEnvironmentMismatches` 与权威记录规则漂移 `matchRecordRulesMismatches` 均为空。报告包含用户标识、积分变化、赛季/流水修订等敏感运营数据，不得提交到 Git、上传公开附件、粘贴到公开 Release 或聊天；只向获授权的发布人员提供必要摘要，并按生产数据保留策略保存和销毁原文件。

维持停机与 `PAUSED`，使用已审核 dry-run 的源 revision 显式 apply：

```bash
pnpm ranked:v3:migrate -- --season-id=<uuid> --apply \
  --expected-ledger-revision=<dry-run sourceLedgerRevision> \
  --admin-user-id=<uuid> --report=/安全路径/v3-apply.json
```

apply 成功后仍不得启动应用，立即以新报告路径再次 dry-run：

```bash
pnpm ranked:v3:migrate -- --season-id=<uuid> \
  --report=/安全路径/v3-post-apply-dry-run.json
```

二次 dry-run 必须返回 `alreadyApplied=true`、追加数 0、全部 blocker 为 0，并确认：赛季和全部 `ranked_matches` 已标记 V3；每个有评分流水的对局最新指令为 V3；旧事件与旧步骤数量未减少；玩家积分、排名和最近 delta 与 apply 报告一致。任何一项不满足都保持停机，不得手工改积分或删除迁移事件。

## 部署与发布后检查

1. 二次 dry-run 通过后，按生产 runbook 部署 `ghcr.io/catmeow123456/loveca-api:v3.9.2`（或已记录 digest）及同一 3.9.2 提交构建的 `client/dist`；生产机只拉取镜像，不重新构建。
2. 启动只接受完整 `ratingScale` 配置的 3.9.2 API，检查容器日志、`/api/health`、首页、PWA 静态资源和图片代理。
3. 在候场仍为 `PAUSED` 时，只读核对赛季页、排行榜、个人积分与最近对局 delta；最小验证普通房间/公共牌桌基础流程未受影响。
4. 经单独运营确认后，再通过既有管理操作将候场恢复为 `OPEN`。迁移 CLI 不会自动恢复候场，部署成功也不代表获得该操作授权。
5. `OPEN` 后验证排位检索、确认、开局、服务端权威结算和后续积分变化；保存脱敏发布记录。不要在本次部署中自动运行任何卡牌同步脚本。

## 回滚

- apply 前失败：修复 blocker 后重新 dry-run；数据库未写入，可继续保持旧 V2 应用停机或按发布决策恢复旧服务。
- apply 已成功后：不能只把 API 镜像切回 3.9.1。旧 V2 API 不允许读取 V3 赛季冻结配置、V3 指令链与重建后的投影；若决定回滚旧 API，必须停止全部写入并从迁移前完整 Postgres dump 恢复整库，同时回滚前端/API，明确接受备份时点之后的数据丢失。
- 若迁移成功但 3.9.2 应用无法启动，优先保持停机并用 apply 报告修复部署；只有经过单独回滚决策才执行整库恢复。不得通过手改赛季 JSON、积分投影或删除追加事件来制造 V2 兼容状态。
- 仅前端静态产物故障且 3.9.2 API 与 V3 数据均健康时，可单独修复或回滚前端，但不能让旧前端继续承担未经验证的 V3 排位操作；恢复服务前仍需完成同版兼容确认。

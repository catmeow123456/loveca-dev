# 3.10.0 -> 3.10.1 生产迁移说明

> 文档类型：人工迁移说明（不是 Drizzle 可执行迁移）
> 适用范围：从 3.10.0 升级到 3.10.1
> 当前状态：发布准备中；尚未在生产执行
>
> 本文只记录 3.10.1 特有的数据迁移。通用停机部署流程见
> [`docs/production-release-runbook.md`](../../docs/production-release-runbook.md)。
> 活动徽章子流程的权威说明见 [`activity-badges.md`](./activity-badges.md)。

## 当前生产状态

- 生产数据库已按 journal 应用到 `0033_harden_card_sync`。
- 生产 API 仍运行 3.10.0 事故期间的本地临时镜像 `loveca-api:3.10.0-hotfix-dotenv`（见 [`3.9.9-to-3.10.0.md`](./3.9.9-to-3.10.0.md) 的事故记录）。该本地镜像没有 registry RepoDigest；部署前只能按 runbook 第 4.1 节捕获容器 ID 与镜像 ID 作为回滚记录，无法得到可回滚的 RepoDigest。此限制只阻塞部署前的回滚基线完整性，不阻塞本版本发布产物本身。
- 3.10.0 部署时按负责人明确要求未创建数据库备份，当前没有 3.9.9 数据库回滚点。本次迁移前备份默认必需；若再次放弃，必须记录“迁移后只能向前修复”。

## 迁移内容

按 Drizzle journal 顺序一次执行：

1. `0034_add_activity_covers.sql`：新增 `activity_cover_configs` 表，保存排位赛季与娱乐模式活动大封面的主图、宽图、紧凑图对象键与裁剪焦点。纯新增表，无存量数据改写。
2. `0035_add_activity_badges.sql`：扩展 `player_badge_rules` / `player_badges` 支持活动徽章；把既有 `ranked-first-season-qualified` 规则指向冻结对象键 `activity-badges/1f16f56b-3d54-4b10-a0e5-034e26cd4bf5/badge.webp`；若发现其他未审计旧规则会直接失败，必须先逐条制定迁移方案。
3. `0036_add_theme_deck_choice.sql`：`theme_table_versions` 增加 `deck_choice_count`（默认 1，正整数约束），支持娱乐模式匹配后候选选组。

禁止手工执行单条 SQL、伪造 journal、使用 `pnpm db:push` 或重新执行 `docker/init.sql`。

本版本没有卡牌数据同步或卡图重同步；活动封面与徽章素材由管理员在后台上传，不属于迁移窗口。

## 迁移前门禁

- 应用确认为 3.10.0（当前以本地 hotfix 镜像运行），Drizzle journal 已到 `0033`，且未部分执行 0034-0036。
- API、前端、迁移源码和 `scripts/seed-activity-badge-assets.ts` 来自同一 release SHA；`assets/badges/first-ranked-season.png` 必须来自同一 checkout，它是 0035 冻结对象键的唯一素材输入。
- 候选 `ghcr.io/catmeow123456/loveca-api:v3.10.1` 镜像已按通用 runbook 第 2 节通过 `node --check dist/server/index.js` 与 production-only 运行时 import 检查（`dist/scripts/sync-cards-cloudbase-new.js`）。
- `.env` 中存在现有 `DATABASE_URL` 与 MinIO 配置；本版本不新增环境变量，只检查是否存在，不输出值。徽章与封面对象写入现有公开 `MINIO_BUCKET`。
- 平台已经进入 `MAINTENANCE`，旧 API、前端和所有数据库写入任务已停止。

数据库备份默认必需。当前已经没有 3.9.9 回滚点；若再放弃本次备份，0035 改写徽章规则后将完全没有数据库回滚能力，失败只能保持维护模式并向前修复。

## 执行

### 1. 迁移 schema

```bash
cd /root/loveca
pnpm install --frozen-lockfile
pnpm db:migrate
```

确认 journal 最新顺序为 0034 -> 0035 -> 0036，并核对：

- `activity_cover_configs` 表存在，主键为 `(activity_type, activity_id)`。
- `player_badge_rules` 的 `image_object_key` / `image_sha256` / `revision` / `last_idempotency_key` / `last_request_fingerprint` 均为 NOT NULL。
- `badge_key = 'ranked-first-season-qualified'` 的规则指向冻结对象键，`revision = 1`。
- `theme_table_versions.deck_choice_count` 存在，现有行全部为默认值 1。

### 2. 补传首届徽章素材（按需）

仅当环境曾执行首届排位徽章补发时需要。先预览：

```bash
DATABASE_URL=... pnpm badges:activity-assets:seed
```

核对 `objectKey`、`sha256`（必须为 `1662921b3edf6f56cd1449f5bb6f1000229ef46a72fabd6adb87d499eb42e768`）、`bytes`；保持停机并执行：

```bash
DATABASE_URL=... pnpm badges:activity-assets:seed -- --apply --yes
```

再次预览确认 `alreadyExists=true`；从对象存储读取该键并核对为规范化后的徽章图。全新环境没有历史规则时脚本返回 `notApplicable=true`，跳过本步。

### 3. 部署和验收

按通用 runbook 部署同一 SHA 的 API 与前端（前端在生产机同一 SHA 构建）。本版本功能要求前后端同版：新手教程、活动徽章/封面读取、候选选组都依赖两侧同时上线。

最小业务 smoke：

- `/api/health`、`/api/ready` 通过；`version.json` 版本与 commit SHA 正确。
- 管理员登录；排位与娱乐模式活动徽章、大封面读取正常（未配置时应回退默认展示）。
- 执行一次徽章替换上传与一次封面上传，确认对象键格式与预览裁剪正常。
- 完整走一遍共享牌桌新手教程至完成；验证教程完成状态写入。
- 娱乐模式匹配后出现候选选组流程，确认 `deck_choice_count` 生效。
- 平台状态与站点快照读取正常后恢复 `NORMAL`。

## 回滚边界

- 0034-0036 前失败：恢复旧应用（本地 hotfix 镜像）即可。
- schema 迁移或素材 apply 失败：保持维护和停写，不手工改表或 journal。
- 有迁移前备份：可恢复数据库、旧 API 镜像和旧前端；注意旧应用为本地 hotfix 镜像，无 RepoDigest，只能按记录的镜像 ID 恢复。
- 无迁移前备份：不得把旧 API 直接接回已变化的数据库；保持维护并向前修复。
- 已发布的 `v3.10.1` tag 与镜像 tag 不得覆盖；修复应发布新的 patch 版本。

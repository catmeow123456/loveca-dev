# 3.9.3 → 3.9.4 生产迁移说明

> 文档类型：人工发布 runbook（不是 Drizzle 可执行迁移）
> 适用范围：从 3.9.3 升级到 3.9.4
> 通用生产发布流程：[`docs/production-release-runbook.md`](../../docs/production-release-runbook.md)
> PT 限制表专题说明：[`drizzle/migration-notes/deck-point-tables.md`](deck-point-tables.md)

## 结论与部署边界

- 本版本包含 `0012_add_deck_point_tables.sql` 至 `0016_allow_deck_point_table_admin_control.sql` 五个 Drizzle migration，生产发布必须先执行 `pnpm db:migrate`，再切换 API 和前端。
- 迁移新增版本化 PT 限制表、条目和审计日志，为卡组、公共牌桌票据及对局卡组快照回填不可变 PT 校验事实，并补齐 PT 表编辑、发布、排期激活、替换和废弃的生命周期约束。
- 迁移会按执行时刻初始化 `2026-04-03` 与 `2026-08-08` 两张 PT 表。若在北京时间 2026-08-08 00:00 前执行，新表先进入 `SCHEDULED`；到点后的 current 读取会在单事务内将新表激活、旧表退役并写入审计。若在该时刻后执行，新表直接初始化为 `ACTIVE`。
- 本版本不新增生产环境变量，不包含卡牌基础数据同步、对象存储上传或图片同步；不得执行 `pnpm db:push` 或任何卡牌同步 apply 命令。
- API 与前端必须使用同一 3.9.4 release SHA 构建并同版部署。本次不包含 Android APK/AAB，Android 版本字段和签名材料保持不变。

## 发布前准备

1. 记录 3.9.4 release SHA、`v3.9.4` API 镜像标签及 digest、前端产物来源、操作者和回滚负责人。
2. 确认 exact-SHA `Quality Gates`、API 候选镜像 runtime 检查和 `Release Tag Integrity` 均已成功；不得复用父提交、PR head 或其他 SHA 的检查结果。
3. 停止新对局入口并等待进行中对局收束，暂停会写入卡组、公共牌桌票据或对局快照的 API 实例，再创建并验证完整 Postgres 备份。
4. 检查迁移前数据库中不存在与初始 PT 表 UUID 或版本 `2026-04-03`、`2026-08-08` 冲突的手工记录；确认 Drizzle journal 尚未登记 `0012` 至 `0016`。
5. 检查发布差异，确保本地卡图、导出数据、Android 测试包、keystore 和任何生产数据报告未进入发布提交或产物。

## 迁移、部署与验证

1. 在 3.9.4 release SHA 的完整源码和锁文件上安装依赖，使用与生产 API 相同的 `DATABASE_URL` 执行 `pnpm db:migrate`；不得从 runtime 镜像或其他提交拼接迁移文件执行。
2. 迁移完成后、恢复写入前，确认 `0012` 至 `0016` 全部登记成功；`deck_point_tables` 有且仅有一条 `ACTIVE`，并且最多一条 `SCHEDULED`，两张初始表的条目数量与专题说明中的权威来源一致。
3. 抽查既有 `decks.validated_point_table_version`，以及 `public_table_tickets`、`match_deck_snapshots` 的 `point_table_version`、`point_total`、`point_limit` 均已回填且非空；核对总点数没有负值。
4. 部署与 release SHA 一致的 `ghcr.io/catmeow123456/loveca-api:v3.9.4`（或已记录 digest）和前端产物，再检查容器日志、`/api/health`、首页、`version.json`、PWA manifest 与图片代理。
5. 调用玩家可见 current PT 表接口，确认返回版本与数据库 `ACTIVE` 一致；分别验证卡组保存、公共牌桌准入和正式对局快照使用同一 PT 版本及点数上限。
6. 若迁移发生在北京时间 2026-08-08 00:00 前，跨过生效边界后再次读取 current 接口，确认 `2026-08-08` 原子切换为 `ACTIVE`、旧表以 `REPLACED` 退役，并存在 `SCHEDULE_ACTIVATED` 与 `RETIRED_BY_REPLACEMENT` 审计记录。
7. 完成登录、卡组读取/保存、普通联机房间、公共牌桌、卡图加载和一局基础对战 smoke；再按本批卡效回归清单抽查新增卡效交互。

## 回滚

- `pnpm db:migrate` 执行前失败：保持 3.9.3 服务和数据库不变，修复原因后重新准备发布。
- 任一迁移失败：保持全部写入停止，不启动 3.9.4，也不要手工补表、改 Drizzle journal 或执行 `db:push`；根据已执行到的迁移和备份决定向前修复或整库恢复。
- `0012` 至 `0016` 成功后，不得只把 API 回滚到 3.9.3。新增的非空列没有旧版写入默认值，旧 API 创建或更新卡组、公共牌桌票据及对局快照时可能失败。需要回滚旧版时，应停止全部写入、恢复迁移前完整 Postgres 备份，再同步回滚 API 与前端，并明确接受备份时点后的数据丢失。
- 若数据库与 3.9.4 API 健康而仅前端静态产物异常，可在验证接口兼容后单独回滚前端；GitHub tag、Release 和不可变镜像标签不得覆盖或重写。

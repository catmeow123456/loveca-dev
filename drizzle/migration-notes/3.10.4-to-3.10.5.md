# 3.10.4 -> 3.10.5 生产迁移说明

> 文档类型：版本迁移说明
> 适用范围：生产环境从 `v3.10.4` 升级到 `v3.10.5`
> 发布身份：`v3.10.5` / `ebc289344c90afde8b50a57f0845d0948094667b`
> 权威通用流程：[`docs/production-release-runbook.md`](../../docs/production-release-runbook.md)
> 补充状态：`v3.10.5` 公开 tag 先于本文创建且不得改写；本文属于发布后补充的迁移材料，不表示该文件已经包含在原 tag 中

本次升级没有新增 Drizzle SQL migration，也没有修改 `src/server/db/schema.ts`、`drizzle/meta/_journal.json` 或 `docker/init.sql`。生产 schema 的最新既有迁移仍为 `0038_add_matchmaking_bgm_library.sql`。但是，新卡同步任务的既有 JSONB 字段增加了新的持久化语义，部署前必须排空旧版活动任务；卡组分类 YAML 导入、候场 BGM 批量上传和卡效重构也需要按本文核对数据兼容与回滚边界。

本文不授权或执行生产迁移、卡牌同步、对象存储上传、管理员操作或部署。

## 1. 迁移结论

### 1.1 数据库结构

- 无新增或修改的 SQL migration；不要创建空迁移、修改已共享 SQL 或手工伪造 Drizzle journal。
- 仍须在维护窗口按通用 runbook 执行一次 `pnpm db:migrate`，确认目标库没有遗漏的既有迁移。若生产已完整部署 `v3.10.4`，该命令不应应用新文件。
- 禁止使用 `pnpm db:push`，也禁止重新执行 `docker/init.sql`。后者只用于新库初始化，不能作为已有生产库的升级步骤。

### 1.2 数据转换

- 没有需要全表重写、离线 backfill 或一次性数据脚本处理的业务记录。
- `card_sync_runs.source_summary` 的新字段只要求活动任务切换治理，不要求回填已经结束的历史 PREVIEW／APPLY 记录。
- 卡组分类 YAML 导入只在管理员确认后创建新的既有格式样板，不转换旧样板、既有分类发布或历史 observation。
- 候场 BGM 批量上传仍逐首创建既有 `matchmaking_bgm_tracks` 记录和内容寻址对象，不改写旧曲目或玩家偏好。
- 卡效与共享 workflow 重构不改写 `cards`、对局历史、checkpoint 或回放记录，也不要求同步基础卡牌数据。

### 1.3 配置与对象存储

- 无新增生产环境变量。
- 无新增 bucket、代理路径或对象 key 格式。候场 BGM 继续使用既有公开 bucket 的 `music/` 与 `matchmaking-bgm/` key；新卡同步继续使用既有卡图路径。
- 本版本不会自动上传 BGM、卡图或其他对象。对象写入只会在部署后的明确管理员操作中发生。

## 2. 数据重构与兼容边界

### 2.1 上游新卡同步任务

`v3.10.5` 继续复用 `0031_add_card_sync_jobs.sql` 和 `0033_harden_card_sync.sql` 创建的表，没有新增列。变化位于现有 `card_sync_runs.source_summary` JSONB 与 `card_sync_run_items` 的写入语义：

- PREVIEW 仍保存完整候选项。
- 新建 APPLY 时，`source_summary.previewCandidateCardCodes` 保存预览的完整候选卡号集合。
- `source_summary.selectedCardCodes` 保存管理员本次实际选择的非空子集。
- APPLY 的 `APPLY_RESULT` items 只为选中卡牌创建。
- worker 执行前重新读取上游，以完整候选集核对来源未漂移，再只处理选中子集。

这项变化有以下迁移含义：

1. `v3.10.4` 创建的活动 APPLY 不包含上述两个 JSONB 字段，不能直接交给 `v3.10.5` worker。部署前必须让旧 worker 将所有 `QUEUED`／`RUNNING` APPLY 处理到终态。
2. 已经处于 `SUCCEEDED`、`PARTIAL` 或 `FAILED` 的历史 APPLY 不会再被 worker 认领，可以保留原样，不得为了补字段而重写审计历史。
3. 旧 PREVIEW 可以保留。若仍在 15 分钟有效期内，`v3.10.5` 在创建新 APPLY 时会从其 CANDIDATE items 重建完整候选集并写入新语义；无需修改 PREVIEW 历史行。
4. 旧幂等键对应的 APPLY 缺少 `selectedCardCodes` 时，新版不会把它误认成一次相同的选择；发生冲突应重新预览并使用新幂等请求，不手工修改旧任务。
5. 回滚到 `v3.10.4` 前也必须排空由 `v3.10.5` 创建的活动 APPLY。旧 worker 不理解“完整候选集＋选中子集”的分离语义，不能承接新版未完成任务。

维护前使用只读 SQL 确认没有活动 APPLY：

```sql
SELECT
  id,
  status,
  created_at,
  started_at,
  updated_at,
  jsonb_typeof(source_summary -> 'previewCandidateCardCodes') AS preview_codes_type,
  jsonb_typeof(source_summary -> 'selectedCardCodes') AS selected_codes_type
FROM card_sync_runs
WHERE kind = 'APPLY'
  AND status IN ('QUEUED', 'RUNNING')
ORDER BY created_at ASC, id ASC;
```

结果必须为 0 行。若存在记录：

- 保持 `v3.10.4` API／worker 运行，让合法任务完成；不要先启动 `v3.10.5` worker。
- 若任务无法完成，保持维护状态并按现有卡牌同步故障流程调查租约、逐卡结果及对象引用；不要直接把状态改成成功，也不要删除任务行。
- 对已经写入的 DRAFT 卡牌和被引用卡图按任务结果逐项审查；部署或回滚不会自动删除它们。

部署后创建的新 APPLY 应满足以下只读一致性检查。该查询只检查任务元数据，不触发同步：

```sql
SELECT
  run.id,
  jsonb_array_length(run.source_summary -> 'previewCandidateCardCodes') AS preview_count,
  jsonb_array_length(run.source_summary -> 'selectedCardCodes') AS selected_count,
  count(item.id) FILTER (WHERE item.kind = 'APPLY_RESULT') AS apply_item_count
FROM card_sync_runs AS run
LEFT JOIN card_sync_run_items AS item ON item.run_id = run.id
WHERE run.kind = 'APPLY'
  AND run.created_at >= TIMESTAMPTZ '<本次部署开始时间>'
GROUP BY run.id, run.source_summary
ORDER BY max(run.created_at) DESC;
```

对每个新任务，`selected_count` 应大于 0 且等于 `apply_item_count`，`preview_count` 应大于等于 `selected_count`。正式 APPLY 仍需单独管理员授权；本次部署 smoke 默认只做到预览，不自动导入卡牌。

### 2.2 卡组分类样板

历史排位候选和 YAML 导入复用既有 `ranked_deck_observations`、`deck_archetypes`、`deck_archetype_templates` 与管理审计结构：

- 历史候选查询只读已封存排位对局与长期 observation；回放清理不会删除已保留的 observation。
- 从历史对局导入时重新核对对局已结束、席位属于真实用户且 observation 仍存在。
- YAML 预览和保存都会重新解析主卡组；不同罕度按基础编号合并，能量卡与其他导出字段不进入分类样板。
- YAML 保存使用既有 `MANUAL` source kind、既有 cards JSON 数组和既有构筑指纹，没有新持久化格式，也不转换旧样板。
- 导入只改变草稿；必须另行发布分类 release 后才会影响玩家侧分类结果。

部署前必须确认目标库已经应用既有 `0020_add_ranked_deck_observations.sql` 与 `0032_add_deck_classifier.sql`。如果缺失，先按既有 [`3.9.9-to-3.10.0.md`](3.9.9-to-3.10.0.md) 和 [`ranked-deck-classifier-production.md`](ranked-deck-classifier-production.md) 执行，不得把首次结构迁移、种子导入或分类发布臆写成本版本已完成事项。

可使用以下只读检查确认依赖结构存在：

```sql
SELECT
  to_regclass('public.ranked_deck_observations') AS observations,
  to_regclass('public.deck_archetypes') AS archetypes,
  to_regclass('public.deck_archetype_templates') AS templates,
  to_regclass('public.deck_classifier_releases') AS releases;
```

四列都必须非空。不要为本版本批量重算旧构筑指纹、修改历史样板来源或自动发布新分类版本。

### 2.3 候场 BGM

本次批量上传是前端串行调用既有单文件接口，不是新的批量事务或批量表结构：

- 每首 MP3 仍独立完成文件校验、内容寻址对象上传和 `matchmaking_bgm_tracks` 写入。
- 某首失败不会回滚已经成功的其他曲目；管理页面会保留逐首结果并允许只重试失败项。
- 上传尝试限额从每用户／每地址 10 分钟 `6 / 12` 提高到 `30 / 60`，累计字节上限仍为 `60 MiB / 120 MiB`，单文件仍不超过 `20 MiB`。
- 已有曲目、默认子集和 `profiles.matchmaking_bgm_track_ids` 不需要转换。

目标库必须已经应用 `0037_add_matchmaking_audio_preferences.sql` 和 `0038_add_matchmaking_bgm_library.sql`。对象存储仍使用既有公开 bucket；本版本不迁移或复制旧 MP3。

### 2.4 卡效、对局与历史记录

- 新增卡效 definition、workflow、modifier 与查询 helper 都是运行时代码重构，不增加权威状态字段，不改变 checkpoint 序列化格式。
- 历史对局 `userId` 修复只改变查询条件组合，不重写 `match_records` 或 participant 数据。
- 不需要对旧 checkpoint、timeline、public/private events、decision records 或现有卡效次数记录做 backfill。
- 生产部署仍必须先结束活动对局和写入任务，再同时切换 API 与前端；不要让旧进程继续承接新版规则结算。
- 本版本不会修改 `cards` 表中的基础卡文或数值，不运行 Excel、CloudBase 或 llocg_db 同步。卡效代码发布与卡牌数据同步是两个独立动作。

## 3. 发布前清单

1. 核对 API 镜像、前端源码、tag 与本说明目标 release SHA；生产必须使用不可变镜像引用，不使用 `latest`。
2. 按平台状态机进入 `NORMAL -> RESTRICTING_NEW_GAMES -> MAINTENANCE`，确认没有活动对局、排位／主题配对或其他写入任务。
3. 确认上节活动 APPLY 查询返回 0 行；记录最近任务状态供部署后对照。
4. 完成 PostgreSQL 备份并验证恢复命令。若明确放弃备份，部署记录必须注明没有数据库回滚能力。
5. 核对现有环境变量仍包含数据库、JWT、CloudBase 与 MinIO 所需配置，但不要打印秘密值。本版本没有新增变量。
6. 核对 `assets/card/`、`assets/images/`、`llocg_db` 和 `trigger` 没有临时或未发布 diff；本次镜像与前端产物不得混入测试资产。
7. 记录既有业务数据基线，至少包括卡牌同步活动任务数、分类样板数、候场曲目数和玩家自选候场曲目人数：

   ```sql
   SELECT count(*) AS active_card_sync_runs
   FROM card_sync_runs
   WHERE kind = 'APPLY' AND status IN ('QUEUED', 'RUNNING');

   SELECT count(*) AS classifier_templates
   FROM deck_archetype_templates;

   SELECT count(*) AS matchmaking_bgm_tracks
   FROM matchmaking_bgm_tracks;

   SELECT count(*) AS profiles_with_custom_bgm
   FROM profiles
   WHERE matchmaking_bgm_track_ids IS NOT NULL;
   ```

## 4. 推荐执行顺序

### 4.1 停止写入与数据库校验

按通用 runbook 停止 API 与前端后，在具有完整源码、devDependencies 和生产 `DATABASE_URL` 的发布环境执行：

```bash
pnpm install --frozen-lockfile
pnpm version:check
pnpm db:migrate
```

`pnpm db:migrate` 应成功结束。若生产已完整应用 `v3.10.4` 所需迁移，本次不应新增 journal 行；当前源码 journal 的最后一项仍应为 `0038_add_matchmaking_bgm_library`。可抽查：

```sql
SELECT id, hash, created_at
FROM drizzle.__drizzle_migrations
ORDER BY created_at DESC
LIMIT 5;
```

发现生产 journal 落后时，停止把“无新增迁移”解释为“无需迁移”；应先阅读所有尚未应用版本的迁移说明，按实际跨度补齐，不能只挑 `0038` 手工执行。

### 4.2 部署应用

1. 使用 `ghcr.io/catmeow123456/loveca-api:v3.10.5` 或其已验证 digest 部署 `linux/amd64` API。
2. 在前端停止后，从同一 release SHA 构建前端；不要让新前端长期连接旧 API，或让旧前端长期连接新 API。
3. 启动 API 和前端后先保持维护模式，完成健康、ready、版本、静态资源和结构化日志检查。
4. 本次不执行卡牌同步 APPLY、分类发布、BGM 上传或其他生产数据写入，除非这些动作在当前维护窗口另有明确授权和审查记录。

## 5. 发布后验收

除通用 runbook 的健康检查外，至少完成以下窄 smoke：

- 普通用户读取既有候场曲库与自己的声音偏好，确认旧选择未丢失；平台管理员页面只读加载既有曲目和默认子集。真实上传属于独立对象存储写入验收，不因部署自动执行。
- 卡组分类管理只读加载既有分类、样板和发布；预览一份受控 YAML，确认主卡组数量、基础编号合并、能量排除和重复构筑提示。保存样板或发布分类属于独立管理写操作。
- 历史对局使用 `userId`、双方玩家、关键词和日期组合筛选，确认分页结果稳定。
- 上游新卡同步第一次只执行“检查新卡”，核对默认选择、warning 候选、全选／清空与选择数量。PREVIEW 会写本地 PostgreSQL 任务记录但不会写 `cards` 或对象存储；正式 APPLY 需要再次明确确认。
- 使用受控测试对局验证本批卡效的代表性登场、LIVE 开始、常时 modifier、成员下方移动和状态变化流程；不得在生产管理员页面通过脚本绕过正常入口。

验收后再次执行发布前的数据基线查询，确认没有意外批量改写。若只做上述只读／预览检查，分类样板数、候场曲目数和玩家偏好人数不应因部署本身变化。

## 6. 回滚边界

- 本次没有 schema migration；未执行额外数据写入时，可在停止写入后将 API 与前端一起回滚到 `v3.10.4`，通常无需恢复数据库。
- 回滚前必须排空 `v3.10.5` 创建的 `QUEUED`／`RUNNING` APPLY，不允许 `v3.10.4` worker 接管新版部分选择任务。
- `v3.10.5` 已完成的新卡同步任务不会被代码回滚撤销。已写入的 DRAFT 卡牌和卡图按任务记录保留并单独审查，不批量删除。
- 新增的 YAML 分类样板使用旧版可识别的 `MANUAL` 格式，代码回滚不会自动删除；如业务决定撤销，应通过正常草稿管理和审计流程处理。
- 批量 BGM 上传中已经成功的独立曲目不会因后续曲目失败或代码回滚而自动删除。需要移除时使用正常管理员入口并记录对象清理结果。
- 卡效运行时回滚只影响之后创建或恢复的对局。回滚前结束新版活动对局，避免在同一局中混用两版规则语义。
- 如果维护窗口另外执行了卡牌同步、分类发布、BGM 上传、对象存储写入或人工 SQL，这些都超出本版本默认迁移范围，必须按各自备份与审计记录单独判断回滚。

## 7. 本次明确不执行

- 不修改或覆盖公开 `v3.10.5` tag、GitHub Release 对应 SHA 或不可变镜像标签。
- 不新增空 SQL migration，不修改 `0038` 及更早迁移历史。
- 不执行 `pnpm db:push`，不重新执行 `docker/init.sql`。
- 不回填终态卡牌同步任务的 JSONB 摘要。
- 不自动导入上游新卡，不同步卡文或卡图，不发布卡组分类，不上传候场 BGM。
- 不构建或分发 Android APK/AAB。

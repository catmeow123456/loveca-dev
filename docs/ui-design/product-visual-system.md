# Loveca 产品视觉系统与页面统一规范

> 文档类型：视觉设计与页面系统规范
> 适用范围：公开首页、认证、玩家大厅、卡组、游戏准备、联机、排位、观战、历史、账户、管理后台及对局外层 UI
> 当前状态：现行产品视觉规范；具体实现与差距以对应页面、专题文档为准
> 不覆盖：游戏规则、卡效交互语义、权威状态结构以及 `GameBoard` 内部区域规则
> 最后更新：2026-10-24

## 1. 文档职责

本文回答以下问题：

- Loveca 应当呈现怎样的产品气质；
- 公开首页和功能子页面如何属于同一个产品；
- 页面外壳、导航、排版、颜色、组件和状态如何统一；
- 用户从首页选择任务后，如何连续进入认证、卡组或对局；
- 如何判断视觉、交互与页面体验是否达到设计目标。

与其他 UI 文档的边界：

发生冲突时：

1. 规则正确性与权威状态边界优先；

5. 历史设计稿只作背景参考。

品牌、语义、业务契约与可访问性要求应保持清晰。页面原型、密度和强调方式是结合场景使用的基线；设计与实现的顺序由问题决定，不要求所有页面采用相同结构、步骤或组件数量。

## 2. 产品定位与视觉方向

### 2.1 服务对象

Loveca 面向三类玩家：

- 想快速测试卡组和卡效的构筑者；
- 想和真人完成正式对局的玩家；
- 想观战、回看或管理比赛环境的参与者。

### 2.2 页面共同任务

页面围绕玩家的连续任务组织：

> 帮助玩家把一副卡组可靠地带到一张可操作、可理解的对战桌上。

典型主流程为：

```text
了解产品 → 准备卡组 → 选择对战方式 → 进入对局 → 查看结果
```

### 2.3 视觉命题

Loveca 的视觉命题是：

> 舞台感存在于真实卡牌和对战桌中；工具界面像一套安静、精确的演出后台。

因此：

- 题材识别来自真实卡图、桌面区域、Heart 与 LIVE 规则信号；
- 功能页依靠清楚的版式、细边框、纸面和深梅色建立统一感；
- 不用大量粒子、光晕、渐变和漂浮卡片制造“游戏感”；
- 不把所有页面都做成舞台海报，也不把所有页面都做成管理后台。

## 3. 设计原则

视觉服务于任务完成与体验质量。结合新手与熟练用户、操作频率、内容密度、设备和输入方式，重点判断：

- 用户能否发现入口、理解模式和状态、完成操作并确认结果；
- 层级、分组和信息密度是否便于扫描与比较，减少不必要的阅读和记忆；
- 字体、色彩、比例、间距、图形和动效是否协调，传达 Loveca 的身份与适当的情感体验；
- 操作反馈是否及时，失败是否可恢复，布局、焦点和常用入口是否稳定；
- 深浅主题、窄屏、文字缩放、键盘、触控与读屏下，关键任务是否仍可完成。

轻快感来自清晰层级、适量信息、适当视觉体量和及时响应。减少装饰与文字时仍要保留操作可发现性及决定所需的信息；美观、感知易用与实际任务表现分别判断，不以容器数量或留白大小代替质量。

### 3.1 真实产品内容优先

卡图、卡组、房间状态、对局桌面和真实数据是主要视觉材料。插画、抽象光效和装饰图形只能补充，不能替代内容。

### 3.2 行动层级与当前任务相称

流程页应让当前下一步突出；列表、编辑器和多任务大厅按区域与上下文组织操作，无需强行设置全页唯一 CTA。次操作、辅助入口与危险操作通过位置和样式形成可理解的层级。

首页可以呈现多个用户目标，但不能把所有入口都画成主 CTA。

### 3.3 结构不全部依赖卡片

使用以下方式区分内容：

- 页面区域背景；
- 分隔线；
- 栏目标题；
- 列表与表格；
- 少量真正需要独立边界的面板。

禁止把每个标题、状态、说明和按钮都包装进相同的白色圆角卡片。

### 3.4 氛围强度分层，身份保持一致

公开首页和对局可以使用深色舞台画布；卡组、认证和管理页可以使用浅色纸面。两者必须共享品牌色、字体角色、间距、边框、按钮和导航语言。

统一不等于每页同一种背景。

### 3.5 用户意图必须跨页面保留

“管理卡组”“开始对局”“观战”不是三个通往登录页的别名。

- 需要认证时，应说明为什么登录；
- 登录或注册后，应继续到用户原先选择的目标；
- 不需要认证的功能不得强制经过登录；
- 离线能力和云端能力必须在入口处说清楚。

### 3.6 强调来自内容的重要性

视觉重点应帮助理解当前任务，避免多个无关区域竞争注意力。例如：

- 公开首页：真实对战桌预览；
- 卡组详情：卡组封面卡/核心卡组构成；
- 游戏准备：当前所选对局方式；
- 排位：当前赛季与个人竞技状态；
- 对局：正在发生的规则事件。

功能页通常保持克制；重点的数量、规模与位置由内容和状态决定，不要求每页必须有且只有一个强视觉，也不为凑主视觉添加装饰。

### 3.7 入口文案保持短而直接

入口说明用户此刻可以做什么；规则、权限和流程在影响决定的位置解释，避免上下游重复。

- 标题使用动作或任务名，例如“对战大厅”“管理卡组”；
- 说明优先用短句补充影响当前选择的事实，长度取决于理解与决策所需；
- 标题已经表达的动作，不在说明中换一种说法重复；
- 仅影响后续步骤的细节在该步骤说明；影响准入、数据丢失或当前选择的条件提前可见；
- 状态标签只表达当前可用性或结果，不承担第二段功能介绍。

## 4. 品牌视觉基础

| Stage Ink    | `#1D1321` | 深色主画布、品牌顶栏、对局外层 |
| Stage Plum   | `#35192F` | 深色次表面、重要深色区块       |

### 4.4 色彩约束

- 普通页面以统一的主强调色建立行动层级；状态色按真实含义使用，不为装饰增加颜色，也不为限制颜色数量丢失状态区别；
- 主按钮使用 Coral，不使用粉橙渐变；
- Orange 不与 Coral 竞争主行动，只用于次强调和时点提示；
- Aqua 只用于“在线、就绪、同步成功”等状态，不作为普通链接色；
- 大面积背景不使用多色渐变；
- 文本与必要的非文本界面信息满足适用的 WCAG AA 对比度要求；按实际背景与状态检查透明层、卡图和选中态，不能只凭肉眼选色。状态不只依赖颜色。

## 5. 字体与排版

### 5.1 字体角色

字体系统分为三种角色：

| 角色       | 建议字体                         | 使用范围                                 |
| ---------- | -------------------------------- | ---------------------------------------- |
| 展示标题   | 系统 UI / CJK sans，500/600      | 公开首页品牌标题；其他关键页面标题       |
| 产品正文   | 系统 UI / CJK sans，400/600      | 导航、正文、表单、按钮、列表             |
| 逐字符数据 | `ui-monospace` / `Cascadia Code` | 卡号、房间号、日志等需要逐字符辨识的内容 |

当前产品正文和展示标题共享 `system-ui` / `-apple-system` / `Segoe UI` / `PingFang SC` / `Microsoft YaHei` 等系统 UI/CJK sans fallback 栈。展示标题应与正文保持相近的字形气质，避免使用倾斜或过度装饰的字体。中英文组合时优先统一笔画粗细和视觉重心，并通过字号、明度和间距建立层级。

引入 webfont 时须覆盖所需字形、字重并在项目内托管，评估加载成本，不由各页面分别引入字体。当前 `assets/fonts/NotoSansSC-600-loveca.ttf` subset 资产及其 `@font-face` 为预留，默认 UI 不引用；在补齐所需字形和字重前，不得将其作为产品正文或展示标题字体。

### 5.2 字阶

以下为排版参考范围；按内容和视口选择层级，关键标签与操作不因空间不足降为难以辨认的小字。文字缩放后保留内容、操作和合理重排。

| Token        | 桌面         | 移动端       | 用途                 |
| ------------ | ------------ | ------------ | -------------------- |
| `display-xl` | 72–96 / 0.98 | 48–64 / 1.0  | 仅公开首页等品牌首屏 |
| `display-md` | 40–56 / 1.12 | 32–40 / 1.15 | 赛季、关键任务页     |
| `heading-lg` | 28–34 / 1.25 | 24–28 / 1.3  | 页面主标题           |
| `heading-md` | 20–24 / 1.35 | 18–22 / 1.35 | 区块标题             |
| `body-lg`    | 16–18 / 1.75 | 15–17 / 1.7  | 主要说明             |
| `body-md`    | 14–15 / 1.65 | 14–15 / 1.6  | 普通正文             |
| `caption`    | 11–12 / 1.5  | 11–12 / 1.5  | 次要信息             |
| `utility`    | 9–11 / 1.4   | 9–11 / 1.4   | 卡号、状态、步骤标签 |

中文标题和正文默认使用正常字距。全大写英文只用于短状态或数据标签。

### 5.3 字重、字距与等宽字体边界

- 正文默认使用 400；导航、按钮、字段标签、普通强调、页面与区块标题使用 600。大型标题主要依靠字号和留白建立层级，必要时可降至 500。
- 700 只保留给比分、结算结果和确实需要强烈强调的短数据，不作为普通标题默认值。
- 不使用 750、800、850、900 等非标准或过重字重，也不依赖浏览器合成粗体。
- 中文正文、控件和标题字距为 0；仅纯拉丁展示标题允许轻微收紧。
- 装饰性英文 eyebrow 可以使用至多 `0.08em` 的正字距，但中英文混排时回到正常字距。
- 等宽字体只用于房间号、卡号、回合编号、checkpoint、日志、YAML/JSON 等需要逐字符辨识的数据；阶段名、区域名、按钮和普通中文标签使用产品正文字体。

## 6. 空间、形状与层次

### 6.1 间距

继续使用 4px 基础网格：

```text
4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96
```

- 控件内部：8–16；
- 同组元素：8–12；
- 面板内部：16–24；
- 页面区块：32–64；
- 品牌落地页大区块：64–112。

普通产品页使用以下密度基线：

| 项目                 | 基线                        |
| -------------------- | --------------------------- |
| 页面主体顶部间距     | 16–24px，默认 20px          |
| 普通面板内边距       | 18–24px，默认 20px          |
| 面板或同级区块间距   | 12–18px，默认 16px          |
| 主按钮和标准输入高度 | 44px                        |
| 页面标题栏高度       | 64–76px，不额外叠加大块留白 |

公开首页品牌段、沉浸式对局和明确的开局演出可以使用专项密度，但普通任务页不能以 `vh` 留白、空装饰舞台或重复标题占据首屏。

基线用于保持同类页面协调，具体密度按内容与设备调整。控件的可见填色、边框面积与实际命中区域可以不同；紧凑切换和行内操作不必画成大块按钮，但仍须容易发现、聚焦和触达。

### 6.2 圆角

| 元素                 | 圆角                     |
| -------------------- | ------------------------ |
| 输入框、按钮、标签页 | 6–8px                    |
| 普通面板、列表容器   | 8–10px                   |
| 抽屉、模态框         | 12–14px                  |
| 状态 pill            | 999px，仅限真正的短状态  |
| 卡牌图片             | 尊重卡面比例，通常 6–8px |

禁止默认使用 20–24px 大圆角。大圆角只能服务于明确的移动端底部抽屉或特殊实体。

圆角按角色和显示尺寸选择，同一密集视图先用对齐、间距和少量必要边界表达分组，再决定是否需要容器。小型牌桌缩略图不机械套用普通面板的圆角；标题和数量也不因“统一”而全部装进胶囊。

依据：[Fluent 2 Shapes](https://fluent2.microsoft.design/shapes/)和 [Atlassian Radius](https://atlassian.design/foundations/radius/)按角色及尺寸区分形状与圆角。Palmer 的 [Common region（1992）](<https://doi.org/10.1016/0010-0285(92)90014-S>)表明包围区域会影响知觉分组；据此减少无业务含义的重复外框，是本项目的设计推论。Bar 与 Neta 的[轮廓偏好实验（2007）](https://doi.org/10.1016/j.neuropsychologia.2007.03.008)使用物品和图案的喜好判断，并未验证游戏界面的最佳圆角或容器数量；[曲率偏好综述（2016）](https://www.frontiersin.org/journals/human-neuroscience/articles/10.3389/fnhum.2015.00712/full)也讨论了语境、文化及机制方面的未决问题，不能将其简化为“圆角越多越好”。

### 6.3 阴影

- 页面结构主要靠色面和边框，不靠阴影；
- 普通面板默认无阴影；
- 悬浮菜单、抽屉、模态和拖拽对象可以使用阴影；
- 不使用彩色发光阴影表达普通 hover；
- 悬浮层级反映真实覆盖关系，避免多个无关区块同时突出；嵌套菜单、模态与详情按交互关系处理层叠和焦点。

### 6.4 共享视觉原语

普通业务页优先从 `client/src/components/common/VisualPrimitives.tsx` 复用以下窄组件：

| 组件             | 职责                                             |
| ---------------- | ------------------------------------------------ |
| `Panel`          | 普通表面、语义色调和统一内边距；默认不带硬阴影   |
| `SectionHeading` | 区块标题、可选说明、eyebrow 和右侧操作的稳定布局 |
| `ActionButton`   | 主、次、轻量和图标按钮的高度、圆角、字重与状态   |
| `StatusBadge`    | 成功、警告、错误、信息等真正的短状态             |
| `TextInput`      | 标准输入框外观和 `aria-invalid` 语义             |

异步状态复用 `client/src/components/common/AsyncFeedback.tsx` 的 `LoadingState`、`EmptyState` 与 `ErrorNotice`，统一加载、空结果与局部错误／重试。页面提供业务内容和恢复动作；外部间距与滚动由所在布局负责。

这些组件不决定业务流程、文案、权限、数据格式或页面信息架构。模式选择卡、列表行、长错误提示、移动端 bottom sheet 和对局演出仍使用各自的专用边界，不能为了“统一”塞进 `Panel` 或 `StatusBadge`。

## 7. 产品外壳与导航

### 7.1 全站导航模型

桌面登录后主导航固定为：

```text
Loveca | 大厅 | 卡组 | 对战 | 观战 | 历史        公告 | 主题 | 账户 | 退出登录
```

管理员能力进入账户菜单或独立“管理”入口，不与玩家主任务平级。

未登录公开导航使用同一产品顶栏，并替换为访客任务：

```text
Loveca | 卡组 | 对战 | 观战 | 最新商品 | 公告     登录 | 创建账号
```

### 7.2 App Frame

公开首页与登录后页面共享 `ProductHeader`；除沉浸式对局、全屏编辑器和特殊回放外，子页面再由 `ProductFrame` 提供标题栏与内容外壳：

```text

├──────────────────────────────────────────────────┤
```

约束：

- 全局导航和页面标题是两层不同职责；
- 公开首页与登录后顶栏使用同一产品正文字体、字号和 600 字重，不允许页面私自改用合成粗体；
- 页面标题栏使用整宽细边框，不做漂浮圆角卡片；
- 页面级主要操作在标题栏右侧或内容首行，移动端可下沉到底部操作区；
- Logo 返回大厅；返回按钮回到明确的父任务；
- 按钮文案优先写具体目标，如“返回卡组列表”，避免只有“返回”。
- 桌面端必须直接提供可发现的退出登录操作；移动端可将其收入主导航菜单。

## 8. 页面原型

以下概括当前页面的任务与组织方式。重设计可按任务组合或调整结构，保留已确认的导航、业务和交互契约；无需为套用某个原型改变用户目标。

### 8.1 公开产品页

主要任务：说明 Loveca 能做什么，并把访客带到正确任务。

```text
全站导航
产品命题 + 一个主 CTA | 真实桌面/卡牌内容
对战 / 卡组 / 观战三个真实入口
开始对局的简短说明
官方发售与活动消息
登录或注册收口
```

要求：

- 主视觉必须来自真实卡牌或桌面；
- 对战、卡组、观战进入不同后续路径；
- 认证后恢复原任务；
- 公开首页“对战”和“开始对战”认证后进入新版对战大厅，与登录后顶部导航一致；离线模式进入练习与调试的卡组准备。
- 不使用营销数字墙、无依据的覆盖率或装饰性“01/02/03”。
- 当前商品区使用一项重点商品与两项紧凑商品的非对称版式；
- 官方消息只引用 Bushiroad 等权威来源，并显示发布日期和原文链接；
- Loveca 产品公告与官方卡牌消息必须明确分区，不得混淆来源；
- 当前商品摘要维护于 `PublicHomePage.tsx`，图片使用本地静态资源；展示来源、商品日期与“整理于”日期，不暗示自动实时同步；
- 官方原文链接只在玩家主动点击后打开，页面运行时不依赖境外图片请求；
- 没有可核实来源时不展示消息，不用过期内容冒充实时资讯。

维护商品内容时，以[官方商品页](https://llofficial-cardgame.com/products/)和 [Bushiroad 官方商店](https://bushiroad-store.com/pages/llofficial-cardgame)核对名称、分类、发售日与已公开信息，不补造未公布日期。图片使用 `assets/images/official-products/` 下的 WebP 资源，按仓库资产维护边界处理，并同步来源和整理日期。

### 8.2 认证页

主要任务：完成认证并继续先前任务。

```text
品牌顶栏 / 返回公开首页
本次登录目的说明 | 表单
账号辅助操作
```

要求：

- 必须说明“登录后继续做什么”；
- 卡组管理等云端任务不显示可用的离线替代；
- 登录成功后不统一跳大厅；
- 注册、找回密码、邮箱验证共享同一认证外壳。

### 8.3 玩家大厅

主要任务：让已登录玩家继续最可能的下一步。

```text
全站导航
欢迎回来，玩家 / Loveca 大厅
继续中的房间/对局（存在时为主操作）
玩法目录                 | 当前一副卡组与进入所选玩法
可自定义的常用入口       | 个人最近一场对局
公告与服务状态（影响任务时提示）
```

要求：

- 采用已确认的 [C 方案](prototypes/player-home/index.html?variant=c)：桌面为玩法目录与紧凑准备区两列，手机按玩法、卡组准备、常用入口、最近对局排列。正式行为以 `HomePage` 与既有服务边界为准，原型中的账号与数据只作示例。
- 页头使用“Loveca 大厅”；桌面玩法行约 90px，选中态由浅粉背景、左侧强调线和勾号共同呈现。右侧准备卡以单行图标与玩法名称响应选择，介绍集中在左侧目录；构筑状态放在准备卡标题旁，查看与更换集中在卡组摘要中。正常三种玩法切换维持准备卡的基础高度与最近对局位置，局部标题过渡尊重 reduced-motion。
- 大厅主按钮使用加深的 Coral 底与暖白文字、箭头，深浅主题保持一致；悬停时底色略加深。普通与悬停状态的文字对比度均不低于 4.5:1，禁用态沿用主题语义。
- 主页显示当前一副卡组摘要，并按所选模式呈现可用性；名称、封面和“查看构筑”均可打开只读详情（统计含 PT，以及成员、LIVE、能量卡列表），详情标题旁可直接“编辑卡组”，打开同一副云端或本地卡组的既有编辑器；“更换卡组”按需打开共享 `DeckSelector`，标题旁提供“卡组管理”。打开选组时按既有过期策略自动读取，不常驻刷新按钮，读取失败时保留明确的重试操作。卡组总数增长不增加主页列表。
- 首页选组是 UI 状态；进入对战大厅、排位或本地准备时，将选中卡组写入对应的既有浏览器选组偏好，下一页仍按当前卡池与 PT 重新校验。卡组被删除或失效后重新从有效投影选择，不自动修改账号卡组。
- 对战大厅使用自组卡组，区分「标准模式」与「娱乐模式」，区别仅在总 PT 门槛；具体准入和偏好见[大厅需求 FR9](../online-mode/community-lobby-requirements.md#fr9-标准与娱乐模式)。赛季排位与「主题牌桌」是独立入口，遵守平台开关，不虚构开放状态；主题牌桌使用平台预组，不要求自建卡组。离线模式展示对墙打与双人调试，联网入口保留明确的不可用原因。
- 大厅房间等待加入时以已入座／虚线空席的双人图示表达状态，配小号状态、公开或链接加入方式及等候时间；沿用现有图标、圆角和主题色，不使用大字等待口号。确认开局等需要玩家响应的状态保留明确文字。
- 当前房间以有宽度约束的共享面板样式构成视觉主体：邀请靠近等待状态，卡组变更入口跟随卡组摘要，观战设置与结束等待的操作在底部分组。切换模式和取消等待直接可见，切换前明确说明结束等待的后果。公共列表保持平面层级，已有房间时其空状态不再引导创建房间。
- 无可用自建卡组时提供构筑或调整入口，需要自建卡组的主按钮禁用；平台预组与教程仍可达。首次读取失败、加载中与保留旧数据的刷新失败分别反馈，不把同步失败显示为“没有卡组”。
- 保存房间存在时优先“返回房间”；另开本地对局保留在房间区的“其他操作”中，继续使用现有重新核验与认输／离房流程。
- 最近一场只读取个人历史接口，展示最近已结束的记录并可进入对应详情；没有记录、读取失败与离线各有反馈。管理员权限不会把该区域扩大为全站历史。
- 正常状态不展示常驻系统诊断；公告仅在影响任务时升级为横幅，运营工具按原权限保留在低频区域。

常用入口定制：

- 默认显示新手教程、观战、历史对局、对墙打；卡组管理、双人调试与开发环境开放的联机调试可在“自定义”中启用。教程在主页只保留此处入口；玩法入口已在目录中，不再重复为常用入口。
- “自定义”打开可滚动弹层，通过复选框增减入口、上移／下移按钮排序，支持键盘、Escape、保存、取消与恢复默认。编辑是草稿，保存后才生效；恢复默认也需保存。支持隐藏全部入口。
- 隐藏项沿用 `loveca.home.hiddenEntries` 的既有读取与对象写入；旧数组的既有读取保留。排序独立保存在 `loveca.home.entryOrder`，按稳定入口 ID 记录，不跨设备同步，不写入账号；新排序缺失或无效时回落到默认顺序。存储失败时保留当前页面选择并提示。
- 平台、权限或环境不允许的候选不出现；暂不可用的可见入口保留原因。个人设置不改变平台开关或玩法准入。
- 使用主题语义 token，保持浅色、深色、窄屏与弹层焦点可读。不为正常入口添加用途或宣传式副标题。

设计依据：[NN/g 的定制建议](https://www.nngroup.com/articles/customization/)强调保留良好默认体验、让定制按需发生；[Chrome 快捷入口设置](https://support.google.com/chrome/answer/11032183?hl=zh-Hans)提供明确的显示控制。本页据此采用按需编辑、显式保存和可恢复的默认设置。文案遵循 [NN/g 极简设计原则](https://www.nngroup.com/articles/aesthetic-minimalist-design/)和 [Material 文案指南](https://m1.material.io/style/writing.html)，只保留帮助当前操作的信息，异常提示按需展示。

#### 桌面区域标签、数量与小操作

区域名、牌数（包括能量 `5/5`）与小操作使用同一套 `battle-zone-label` / `battle-mini-action` 样式，覆盖 PC、手机和对手查看层。

| 项目       | 规范                                                                                                                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 字体       | 产品正文字体，12px / 500，16px 行高；数字使用 tabular-nums，不切换等宽字体                                                                                         |
| 名称与数量 | 使用主、次文字色等量混合的柔和文字色，取消字形描边；标题背后使用局部主题色半透明层与模糊，边缘渐隐，不加实体边框。叠在牌堆上的数量保留小型磨砂底，以免卡面干扰数字 |
| 小操作     | 沿用现有磨砂表面、轻描边与 6px 圆角，目标至少 28×28 CSS px；不以绿色、橙色或发光区分普通整理动作                                                                   |
| 状态       | hover 增强磨砂表面，按下使用 overlay；键盘焦点有 2px 外轮廓；禁用用次级文字和明确禁用行为，不整体降低控件透明度                                                    |
| 对比度     | 普通文字至少 4.5:1，小字优先留足余量；必要的控件边界和焦点指示至少 3:1；计算字旁的实际背景，包含透明度和祖先 opacity                                               |
| 交互       | 名称与数量保持信息属性，不伪装成按钮；状态切换在原位置反馈，不隐式重排；小操作保留可访问名称与不可操作原因                                                         |

卡垫与卡面是复杂、可变背景。保持原有背景、透明分区和配色，不为解决文字问题替换为整块白色或深色底板。区域标题的局部遮罩在字形范围内保持完整强度，向外渐隐；小操作和牌堆数量使用局部磨砂底。计算对比度时应包含透明背景的合成结果，不能把模糊或阴影当成达标证据。对手查看层也不整体淡化标签与控件。尺寸约束应通过区域布局处理，不把数量或操作文字压成更小字号。

依据：[WCAG 文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)及 [G18 图像背景方法](https://www.w3.org/WAI/WCAG22/Techniques/general/G18)要求检查局部文字背景；[WCAG 目标尺寸](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)给出 24px 的 AA 基线及例外，本组件采用 28px，不代表全桌面已完成可访问性认证。[NN/g 一致性原则](https://www.nngroup.com/articles/consistency-and-standards/)支持共用组件及稳定语义。Rosenholtz、Li、Nakano 的 [Measuring visual clutter（2007）](https://pubmed.ncbi.nlm.nih.gov/18217832/)讨论杂乱对遮挡、辨识与视觉搜索的影响；据此减少无信息意义的配色与装饰，是本项目的设计推论，不是该研究指定的配色或像素参数。

Sawyer 等的 [Glanceable, legible typography over complex backgrounds（2020）](https://www.bendsawyer.com/wp-content/uploads/2025/05/Sawyer-et-al_2020_Glanceable-legible-typography-over-complex-backgrounds.pdf)比较了局部遮罩、模糊、阴影与描边：实验 III 中阴影优于所测试的描边方案。实验使用拉丁字体、静态图片与短时辨认任务，不能直接确定中文牌桌的参数。当前选择局部柔和遮罩，是结合用户偏好与浏览器截图作出的设计判断；透明度与文字色另做合成对比度检查。

#### 牌桌尺寸与圆角分配

`battle-table` 内按信息角色分配尺寸，牌面始终保持 5:7，横置时为 7:5。成员承担主要操作与辨识，成功 LIVE 保持可辨认的完整牌面，资源与能量使用较小缩略图；不以统一尺寸代替层级。

| 对象                        | 尺寸与圆角                                                                                                                                                       |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 成员、LIVE、成功 LIVE、手牌 | 普通牌面圆角 4px；正面、背面、选中层继承同一轮廓，效果外沿按外扩距离增加圆角                                                                                     |
| 成功 LIVE                   | 手机横牌 84×60px，PC 横牌 112×80px 至 126×90px；共用三个叠放槽，沿同一竖轴向下叠放，手机相邻槽位下移 12–14px、PC 下移 36–45px；手机标题行 18px，保留支持区总高度 |
| 主卡组、休息室、能量卡组    | 同级牌堆尺寸一致；PC 为 40×56px，手机按可用高度在 40–72px 高之间适配，圆角 3px                                                                                   |
| 能量                        | 活跃牌 36×50.4px，待机横置；圆角 3px，叠放间距不随数量变化                                                                                                       |
| 按钮                        | 圆角 6px；小操作至少 28px 高，手机底部工具栏为 32px 高                                                                                                           |
| 普通分区与浮层              | 分区 8px、底部抽屉 12px；保留原背景和轻透明表面，标题及比例数字不独立加框                                                                                        |

成员槽等包围牌面的边界按牌面圆角和边框外扩量处理，例如 4px 牌面外的 2px 边框使用 6px 圆角。这些是当前牌桌的工程参数，遵循 6.2 的角色、尺寸与嵌套关系原则，不作为其他页面的固定像素要求。

判定、检视、休息室、换牌、效果选择与卡牌详情沿用同一套形状规则。`battle-table` 作用域将常用圆角映射到上述层级；通过 portal 渲染的判定、休息室、操作菜单和详情根节点也必须保留该作用域，避免回退到全站的 14px 牌面轮廓。原生图片缩略牌、背面、翻牌动画统一使用 4px 牌面裁切；独立浮层使用 12px，内部信息分区使用 8px，选择与操作控件使用 6px。数字不另加无交互含义的胶囊，选中勾号、头像等有明确语义的圆形保留。

PC 优先给成员牌分配主战场高度。窗口变矮时，手牌预留高度由 112px 连续收紧至 96px，LIVE 行占用的布局高度由 80px 收紧至 70px，成员牌再根据实际剩余空间和列宽适配；避免在高度断点突然缩小成员牌。LIVE 横牌约 95×68px 至 116×83px，区域朝 VS 延伸 8px，并用负外边距收回增加的高度，成员测量包含这部分外边距；对手所需 Hearts 放在靠成员的上沿。手机使用独立的可用高度计算。

## 9. 组件规范

### 9.1 按钮

| 类型        | 用途                     | 同屏数量            |
| ----------- | ------------------------ | ------------------- |
| Primary     | 当前页面默认下一步       | 通常 1 个           |
| Secondary   | 合法但次要的替代操作     | 可多个              |
| Text        | 导航、低频辅助操作       | 按需                |
| Destructive | 删除、退出房间、认输     | 与普通操作分区      |
| Icon-only   | 主题、关闭等高度通用动作 | 必须有 `aria-label` |

按钮名称让用户预判操作结果，优先使用“选择对局方式”“保存卡组”“加入房间”。流程上下文已经明确时可用“继续”；高影响或跨模式操作应写清具体动作，避免歧义。视觉体量按所在层级选择，保持点击、键盘焦点与触控反馈可辨。

### 9.2 表面

- `PageSection`：靠留白和分隔线形成页面区块；
- `Panel`：需要独立边界的工作区域；
- `ListRow`：重复数据的默认容器；
- `Callout`：维护、错误或规则提醒；
- `OverlaySurface`：菜单、抽屉、模态。

禁止 `Panel` 内无意义地继续嵌套多个相同 `Panel`。

### 9.3 状态

状态按理解和恢复需要组合标签、说明与动作。简单状态可以只用短标签；需要恢复的错误可使用：

```text
[云端不可用] 无法读取你的云端卡组。  重试
```

- 颜色只辅助，不单独承载含义；
- 禁用原因与恢复条件在上下文中可理解，必要时补充说明；
- 错误说明下一步；
- 空状态提供首个有效动作；
- 加载使用骨架或局部进度，不让整页反复闪回启动屏。

### 9.4 表单

- 标签始终可见；
- 帮助文本靠近字段；
- 校验错误显示在对应字段附近；
- 主要提交按钮沿流程保持同一名称；
- 手机软键盘出现时字段和提交按钮仍可访问。

### 9.5 卡牌图像

- 卡图用于展示真实内容，不作为无关背景贴图；
- 功能页使用与显示尺寸相符的图片规格；
- 图片失败必须有稳定卡背或占位；
- 卡图网格支持键盘焦点与触控详情；
- 生产页面不得依赖本地测试补图。

## 10. 动效

### 10.1 时长

当前共享 token 为 `--duration-fast: 150ms`、`--duration-normal: 250ms`、`--duration-slow: 500ms`、`--duration-dramatic: 2500ms`，具体定义以 `index.css` 为准。它们是复用基线，实际时长按变化距离、信息量和操作频率选择；规则事件、LIVE 结果与对局结束遵循专项动效设计，不把长时长套用到普通操作。

### 10.2 使用原则

- 公开首页允许一次编排式入场；
- 功能子页面不为每个 section 重复上浮；
- 列表 hover 不默认位移；
- 拖拽和区域移动遵循对局 motion 规范；
- 所有非必要动画支持 `prefers-reduced-motion`；
- 动画不能延迟真实操作结果。

## 11. 文案与命名

### 11.1 导航词汇固定

统一使用：

- 大厅
- 卡组
- 对战
- 观战
- 历史
- 账户
- 管理

同一目的不要在不同页面混用“主页 / 首页 / 大厅”“游戏 / 对局 / 开局”等多个导航名称。产品导航使用“大厅”，公开站点根页使用“首页”。

自组对战统一使用「标准模式」「娱乐模式」完整名称，平台预组活动使用「主题牌桌」，避免把两种不同入口统称为娱乐模式。

### 11.2 状态文案

- 面向玩家描述结果，不暴露状态机、批次或内部服务名；
- 用主动语态；
- 不使用“奇怪解释文案”替代卡牌原文；
- 空状态不写情绪性标语，直接告诉用户如何开始；
- 操作成功后的反馈沿用按钮动词，如“保存卡组”→“卡组已保存”。

### 11.3 中文表达原则

Loveca 的界面文案以简体中文玩家为主要读者，同时尊重作品、卡牌与规则中已经形成的专有名词。目标不是把所有外语强行翻译成中文，而是让句子自然、操作明确、术语稳定。

- 从玩家要完成的事出发，不描述系统结构。例如写“开始对战”，不写“进入规则桌面”；
- 一个按钮只写一个明确动作，优先使用“开始对战”“管理卡组”“进入观战”等动宾短语；
- 标题说明目的，正文补充条件与结果。不要在标题中塞入所有模式或实现细节；
- 使用日常、完整的中文句式，避免“可以上桌的构筑”“选择场合”“规则状态已载入”等直译或工程化表达；
- “构筑”优先作动词或规则概念使用，如“构筑卡组”“构筑规则”；表示一副牌时使用“卡组”；
- 面向玩家时使用“卡牌效果”，代码、调试界面或紧凑规则标签中才可使用“卡效”；
- 不用宣传口号替代产品事实。首屏应说明可以构筑卡组、寻找对手和进行对局；
- 中文与英文、数字之间保留一个半角空格；已经固定组合的卡牌术语按卡面与规则原文书写。

推荐句式：

| 场景     | 使用                        | 避免                         |
| -------- | --------------------------- | ---------------------------- |
| 对战入口 | 开始对战 / 选择对战方式     | 选择场合 / 进入规则桌面      |
| 卡组状态 | 卡组符合构筑规则            | 合法构筑 / 可以上桌的构筑    |
| 卡组动作 | 构筑卡组 / 管理卡组         | 整理我的构筑                 |
| 对局动作 | 开始对局 / 进入房间         | 坐下开局 / 启动游戏实例      |
| 离线入口 | 进入离线模式 / 体验离线对局 | 离线模式游玩 / 先离线试桌    |
| 加载状态 | 当前可使用 2,032 张卡牌     | 2,032 张卡牌已载入           |
| 登录衔接 | 登录后继续刚才的操作        | 登录后把你带到刚才选择的地方 |

## 12. 避免无任务依据的装饰

以下做法容易增加视觉负担，不能仅为填满页面或制造特色而采用；是否适合应由内容、层级和任务决定：

- 大号居中标题 + pill eyebrow + 三张完全相同功能卡；
- 深色背景 + 多个发光渐变球 + 玻璃卡片；
- 没有真实业务含义的 `01 / 02 / 03`；
- 用大数字统计填补空白；
- 每个区块都使用圆角、描边、阴影和 hover 上浮；
- 用六色 Heart 装饰与规则无关的页面；
- 为每张卡片加入独立入场动画；
- 用内部实现说明冒充产品文案。

产品辨识度来自真实内容与连贯的视觉语言。通用表单和工具栏可沿用成熟模式，不为追求独特而增加装饰、隐藏入口或改变熟悉操作。

## 13. 主题策略

### 13.1 一套结构，两套色彩

浅色与深色主题共享：

- 布局；
- 字阶；
- 间距；
- 圆角；
- 组件状态；
- 导航模型；
- 交互行为。

只替换语义颜色和必要阴影。

### 13.2 页面默认主题

- 公开首页可以固定使用品牌深色首屏，但正文仍需与系统主题协调；
- 工作台、认证和管理页尊重用户主题；
- 对局桌面可以使用独立的规则画布，但 chrome 尊重主题；
- 主题切换不改变信息结构。

### 13.3 固定视觉回归基线

非对局产品页使用独立 [Playwright 配置](../../client/playwright.visual.config.ts)维护截图差异比较，当前覆盖公开首页、玩家大厅、对局准备、卡组管理与对战大厅。固定矩阵为：

- 390px 浅色；
- 768px 深色；
- 1024px 浅色；
- 1440px 浅色；
- 1440px 深色。

截图测试固定时间、时区、locale、主题、reduced motion、mock 数据和设备像素比，等待字体及首屏图片稳定后使用 `toHaveScreenshot`。截图按运行平台分目录保存，浏览器与字体环境保持一致，不能跨平台替换基线。

这套矩阵用于重复比较；当前改动应覆盖哪些页面和项目由影响决定，新增问题可补充相应状态或视口。截图不能替代键盘、触控、焦点、异步反馈及任务结果的验证。执行与基线维护见[前端验证规范](standard.md#83-按影响选择验证)。

## 14. 设计判断与完成质量

设计、调研、原型、实现与验证的顺序和深度按任务选择。复杂、反复修改仍难收敛的问题可依据 [frontend-design skill](../../.agents/skills/frontend-design/SKILL.md#复杂问题与研究)查阅学术研究与工业实践，学习适用的机制和评估方式，再结合本产品的内容、用户与工程边界作判断。

完成质量围绕受影响的用户任务判断：

- **任务与控制**：入口可发现，模式与后果可理解，操作路径真实可用；涉及认证时延续原任务，等待、空、禁用和错误有适当反馈与恢复路径。
- **视觉与阅读**：品牌、字体、色彩、间距、形状和动效协调，重点与信息重要性相称；长内容不挤掉操作，也不隐藏决定所需的信息。
- **情境与无障碍**：目标视口、主题与文字缩放下关键内容可读、操作可达；焦点可见，语义与名称完整，关键操作不只依赖颜色或 hover，reduced-motion 下功能完整。
- **响应与稳定**：真实内容规模下操作及时，布局、浏览位置与焦点稳定；不会因动画或整页重载反复阻断任务。
- **工程与证据**：复用合适的 token、组件与权威状态，按影响完成浏览器复核和相关检查，清理被替代的旧实现。评估体验时结合任务结果与用户反馈，不把截图通过或主观审美当作可用性改善的证明。

交付说明实际变化、关键取舍、已验证内容和未覆盖边界。具体命令、维护成本与提交范围遵循前端规范和仓库约定，临时验证截图不默认提交。

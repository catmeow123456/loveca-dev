# Loveca 产品视觉系统与页面统一规范

> 文档类型：视觉设计与页面系统规范
> 适用范围：公开首页、认证、玩家大厅、卡组、游戏准备、联机、排位、观战、历史、账户、管理后台及对局外层 UI
> 当前状态：目标态权威文档；后续子页面重设计必须以本文为视觉依据
> 不覆盖：游戏规则、卡效交互语义、权威状态结构以及 `GameBoard` 内部区域规则
> 最后更新：2026-08-01

## 1. 文档职责

本文回答以下问题：

- Loveca 应当呈现怎样的产品气质；
- 公开首页和功能子页面如何属于同一个产品；
- 页面外壳、导航、排版、颜色、组件和状态如何统一；
- 用户从首页选择任务后，如何连续进入认证、卡组或对局；
- 旧页面应按什么顺序迁移，怎样判断迁移完成。

与其他 UI 文档的边界：

| 文档                                                       | 负责内容                                             |
| ---------------------------------------------------------- | ---------------------------------------------------- |
| 本文                                                       | 产品视觉方向、页面原型、导航系统、组件外观与迁移目标 |
| [前端 UI 开发规范](standard.md)                            | React、CSS token、布局、浮层、文案等实现约束         |
| [移动端适配需求](mobile-adaptation-requirements.md)        | 断点、触控、窄屏重排和移动端验收                     |
| [游戏桌 UI 现状](game-table/current-state.md)              | `GameBoard` / `PlayerArea` 当前布局和交互事实        |
| `battle-interaction-design` / `motion-system-design` skill | 对局交互和动作反馈的专项设计                         |

发生冲突时：

1. 规则正确性与权威状态边界优先；
2. 具体页面需求和已确认交互契约优先；
3. 本文决定视觉与页面系统；
4. `standard.md` 决定实现方式；
5. 历史设计稿只作背景参考。

## 2. 产品定位与单一设计命题

### 2.1 服务对象

Loveca 面向三类玩家：

- 想快速测试卡组和卡效的构筑者；
- 想和真人完成正式对局的玩家；
- 想观战、回看或管理比赛环境的参与者。

### 2.2 页面共同任务

所有非对局页面共同完成一件事：

> 帮助玩家把一副卡组可靠地带到一张可操作、可理解的对战桌上。

设计不围绕“展示功能模块”组织，而围绕玩家的连续任务组织：

```text
了解产品 → 准备卡组 → 选择场合 → 进入对局 → 查看结果
```

### 2.3 视觉命题

Loveca 的视觉命题是：

> 舞台感存在于真实卡牌和对战桌中；工具界面像一套安静、精确的演出后台。

因此：

- 题材识别来自真实卡图、桌面区域、Heart 与 LIVE 规则信号；
- 功能页依靠清楚的版式、细边框、纸面和深梅色建立统一感；
- 不用大量粒子、光晕、渐变和漂浮卡片制造“游戏感”；
- 不把所有页面都做成舞台海报，也不把所有页面都做成管理后台。

## 3. 设计原则

### 3.1 真实产品内容优先

卡图、卡组、房间状态、对局桌面和真实数据是主要视觉材料。插画、抽象光效和装饰图形只能补充，不能替代内容。

### 3.2 一页只有一个默认行动

每个页面必须有一个视觉上最明确的下一步。其他操作根据重要性降为次按钮、文字按钮或局部菜单。

首页可以呈现多个用户目标，但不能把所有入口都画成主 CTA。

### 3.3 结构不全部依赖卡片

使用以下方式区分内容：

- 页面区域背景；
- 分隔线；
- 栏目标题；
- 列表与表格；
- 少量真正需要独立边界的面板。

禁止把每个标题、状态、说明和按钮都包装进相同的白色圆角卡片。

### 3.4 氛围强度分层，身份保持一致

公开首页和对局可以使用深色舞台画布；卡组、认证和管理页可以使用浅色纸面。两者必须共享品牌色、字体角色、间距、边框、按钮和导航语言。

统一不等于每页同一种背景。

### 3.5 用户意图必须跨页面保留

“管理卡组”“开始对局”“观战”不是三个通往登录页的别名。

- 需要认证时，应说明为什么登录；
- 登录或注册后，应继续到用户原先选择的目标；
- 不需要认证的功能不得强制经过登录；
- 离线能力和云端能力必须在入口处说清楚。

### 3.6 大胆只用在一个地方

每个页面最多设置一个强视觉：

- 公开首页：真实对战桌预览；
- 卡组详情：卡组封面卡/核心卡组构成；
- 游戏准备：当前所选对局方式；
- 排位：当前赛季与个人竞技状态；
- 对局：正在发生的规则事件。

其余区域保持安静。

### 3.7 入口文案保持短而直接

入口只说明用户此刻可以做什么，不重复下一页才需要解释的规则、权限和流程。

- 标题使用动作或任务名，例如“房间观战”“管理卡组”；
- 说明最多补充一个会影响当前选择的事实，优先使用一个短句；
- 标题已经表达的动作，不在说明中换一种说法重复；
- “只读”“选择玩家视角”等下游规则，应在进入对应任务后、真正需要决策的位置说明；
- 状态标签只表达当前可用性或结果，不承担第二段功能介绍。

## 4. 品牌视觉基础

### 4.1 核心色板

以下是目标品牌原色。实现时必须映射到全局语义 token，不应继续保留为页面私有变量。

| 名称         | 色值      | 用途                           |
| ------------ | --------- | ------------------------------ |
| Stage Ink    | `#1D1321` | 深色主画布、品牌顶栏、对局外层 |
| Stage Plum   | `#35192F` | 深色次表面、重要深色区块       |
| Paper        | `#F8F3ED` | 浅色页面主画布                 |
| Card White   | `#FFFDF9` | 浅色表面、表单和主要内容区     |
| Loveca Coral | `#E95678` | 主行动、焦点和品牌识别         |
| Cue Orange   | `#F29862` | 次强调、时点、提示和暖色信号   |
| Ready Aqua   | `#6FCBD0` | 在线、READY、同步完成等窄状态  |

Heart 粉、红、黄、绿、蓝、紫、橙、灰和 All 色仍是规则语义色，不进入普通页面装饰色板。

### 4.2 浅色语义映射

```css
--canvas: #f8f3ed;
--surface: #fffdf9;
--surface-subtle: #f1e9e5;
--surface-strong: #e9deda;
--text-primary: #1d1321;
--text-secondary: #655865;
--text-muted: #948894;
--border-subtle: rgb(29 19 33 / 10%);
--border-default: rgb(29 19 33 / 18%);
--action-primary: #e95678;
--action-primary-hover: #d84d6e;
--action-secondary: #35192f;
```

### 4.3 深色语义映射

```css
--canvas: #1d1321;
--surface: #281629;
--surface-subtle: #301a30;
--surface-strong: #35192f;
--text-primary: #fffdf9;
--text-secondary: #c9bec8;
--text-muted: #928493;
--border-subtle: rgb(255 253 249 / 10%);
--border-default: rgb(255 253 249 / 18%);
--action-primary: #e95678;
--action-primary-hover: #f06b89;
--action-secondary: #f29862;
```

### 4.4 色彩约束

- 普通页面最多同时出现一个主强调色和一个状态色；
- 主按钮使用 Coral，不使用粉橙渐变；
- Orange 不与 Coral 竞争主行动，只用于次强调和时点提示；
- Aqua 只用于“在线、就绪、同步成功”等状态，不作为普通链接色；
- 大面积背景不使用多色渐变；
- 文本和交互状态必须满足 WCAG AA 对比度，不能只凭肉眼选色。

## 5. 字体与排版

### 5.1 字体角色

目标字体系统分为三种角色：

| 角色       | 建议字体                          | 使用范围                           |
| ---------- | --------------------------------- | ---------------------------------- |
| 展示标题   | 系统 UI / CJK sans，500/600       | 公开首页品牌标题；其他关键页面标题 |
| 产品正文   | 系统 UI / CJK sans，400/600       | 导航、正文、表单、按钮、列表       |
| 规则与数据 | `IBM Plex Mono` / `Cascadia Code` | 卡号、房间号、步骤、状态缩写、数值 |

当前产品正文和展示标题共享 `system-ui` / `-apple-system` / `Segoe UI` / `PingFang SC` / `Microsoft YaHei` 等系统 UI/CJK sans fallback 栈。展示标题应与正文保持相近的字形气质，避免使用倾斜或过度装饰的字体。中英文组合时优先统一笔画粗细和视觉重心，并通过字号、明度和间距建立层级。

只有决定引入覆盖所需字形和字重的 webfont 时，才要求在项目内本地托管，且其他页面不得各自引入未经确认的字体。当前 `assets/fonts/NotoSansSC-600-loveca.ttf` subset 资产及其 `@font-face` 仅为兼容/预留保留，默认 UI 不引用；在补齐所需字形和字重前，不得将其作为产品正文或展示标题字体。

### 5.2 字阶

| Token        | 桌面         | 移动端       | 用途                 |
| ------------ | ------------ | ------------ | -------------------- |
| `display-xl` | 72–96 / 0.98 | 48–64 / 1.0  | 仅公开首页等品牌首屏 |
| `display-md` | 40–56 / 1.12 | 32–40 / 1.15 | 赛季、关键任务页     |
| `heading-lg` | 28–34 / 1.25 | 24–28 / 1.3  | 页面主标题           |
| `heading-md` | 20–24 / 1.35 | 18–22 / 1.35 | 区块标题             |
| `body-lg`    | 16–18 / 1.75 | 15–17 / 1.7  | 主要说明             |
| `body-md`    | 14–15 / 1.65 | 14–15 / 1.6  | 普通正文             |
| `caption`    | 11–12 / 1.5  | 11–12 / 1.5  | 次要信息             |
| `utility`    | 9–11 / 1.4   | 9–11 / 1.4   | 卡号、状态、步骤标签 |

中文标题和正文默认使用正常字距。全大写英文只用于短状态或数据标签。

### 5.3 字重、字距与等宽字体边界

- 正文默认使用 400；导航、按钮、字段标签、普通强调、页面与区块标题使用 600。大型标题主要依靠字号和留白建立层级，必要时可降至 500。
- 700 只保留给比分、结算结果和确实需要强烈强调的短数据，不作为普通标题默认值。
- 不使用 750、800、850、900 等非标准或过重字重，也不依赖浏览器合成粗体。
- 中文正文、控件和标题字距为 0；仅纯拉丁展示标题允许轻微收紧。
- 装饰性英文 eyebrow 可以使用至多 `0.08em` 的正字距，但中英文混排时回到正常字距。
- 等宽字体只用于房间号、卡号、回合编号、checkpoint、日志、YAML/JSON 等需要逐字符辨识的数据；阶段名、区域名、按钮和普通中文标签使用产品正文字体。

## 6. 空间、形状与层次

### 6.1 间距

继续使用 4px 基础网格：

```text
4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96
```

- 控件内部：8–16；
- 同组元素：8–12；
- 面板内部：16–24；
- 页面区块：32–64；
- 品牌落地页大区块：64–112。

普通产品页使用以下密度基线：

| 项目                 | 基线                        |
| -------------------- | --------------------------- |
| 页面主体顶部间距     | 16–24px，默认 20px          |
| 普通面板内边距       | 18–24px，默认 20px          |
| 面板或同级区块间距   | 12–18px，默认 16px          |
| 主按钮和标准输入高度 | 44px                        |
| 页面标题栏高度       | 64–76px，不额外叠加大块留白 |

公开首页品牌段、沉浸式对局和明确的开局演出可以使用专项密度，但普通任务页不能以 `vh` 留白、空装饰舞台或重复标题占据首屏。

### 6.2 圆角

| 元素                 | 圆角                     |
| -------------------- | ------------------------ |
| 输入框、按钮、标签页 | 6–8px                    |
| 普通面板、列表容器   | 8–10px                   |
| 抽屉、模态框         | 12–14px                  |
| 状态 pill            | 999px，仅限真正的短状态  |
| 卡牌图片             | 尊重卡面比例，通常 6–8px |

禁止默认使用 20–24px 大圆角。大圆角只能服务于明确的移动端底部抽屉或特殊实体。

### 6.3 阴影

- 页面结构主要靠色面和边框，不靠阴影；
- 普通面板默认无阴影；
- 悬浮菜单、抽屉、模态和拖拽对象可以使用阴影；
- 不使用彩色发光阴影表达普通 hover；
- 同一视图最多允许一个明显悬浮层级。

### 6.4 共享视觉原语

普通业务页优先从 `client/src/components/common/VisualPrimitives.tsx` 复用以下窄组件：

| 组件             | 职责                                             |
| ---------------- | ------------------------------------------------ |
| `Panel`          | 普通表面、语义色调和统一内边距；默认不带硬阴影   |
| `SectionHeading` | 区块标题、可选说明、eyebrow 和右侧操作的稳定布局 |
| `ActionButton`   | 主、次、轻量和图标按钮的高度、圆角、字重与状态   |
| `StatusBadge`    | 成功、警告、错误、信息等真正的短状态             |
| `TextInput`      | 标准输入框外观和 `aria-invalid` 语义             |

这些组件不决定业务流程、文案、权限、数据格式或页面信息架构。模式选择卡、列表行、长错误提示、移动端 bottom sheet 和对局演出仍使用各自的专用边界，不能为了“统一”塞进 `Panel` 或 `StatusBadge`。

## 7. 产品外壳与导航

### 7.1 全站导航模型

桌面登录后主导航固定为：

```text
Loveca | 大厅 | 卡组 | 对战 | 观战 | 历史        公告 | 主题 | 账户 | 退出登录
```

管理员能力进入账户菜单或独立“管理”入口，不与玩家主任务平级。

未登录公开导航使用同一产品顶栏，并替换为访客任务：

```text
Loveca | 卡组 | 对战 | 观战 | 最新商品 | 公告     登录 | 创建账号
```

### 7.2 App Frame

公开首页与登录后页面共享 `ProductHeader`；除沉浸式对局、全屏编辑器和特殊回放外，子页面再由 `ProductFrame` 提供标题栏与内容外壳：

```text
┌──────────────────────────────────────────────────┐
│ 品牌 / 主导航                         公告 / 账户 │
├──────────────────────────────────────────────────┤
│ 返回 / 面包屑       页面标题          页面级操作 │
├──────────────────────────────────────────────────┤
│                                                  │
│ 页面主体                                         │
│                                                  │
└──────────────────────────────────────────────────┘
```

约束：

- 全局导航和页面标题是两层不同职责；
- 公开首页与登录后顶栏使用同一产品正文字体、字号和 600 字重，不允许页面私自改用合成粗体；
- 页面标题栏使用整宽细边框，不做漂浮圆角卡片；
- 页面级主要操作在标题栏右侧或内容首行，移动端可下沉到底部操作区；
- Logo 返回大厅；返回按钮回到明确的父任务；
- 按钮文案优先写具体目标，如“返回卡组列表”，避免只有“返回”。
- 桌面端必须直接提供可发现的退出登录操作；移动端可将其收入主导航菜单。

### 7.3 移动端外壳

```text
┌────────────────────────┐
│ Loveca          账户/菜单│
├────────────────────────┤
│ ← 父页面        页面标题 │
├────────────────────────┤
│                        │
│ 主内容                 │
│                        │
├────────────────────────┤
│ 当前步骤的唯一主操作    │  仅流程页需要
└────────────────────────┘
```

- 主导航折叠为菜单，但当前任务必须可见；
- 不把所有桌面导航图标塞进顶栏；
- 流程页允许固定底部主操作，并处理安全区；
- 页面保持单一主滚动容器。

## 8. 页面原型

### 8.1 公开产品页

单一任务：说明 Loveca 能做什么，并把访客带到正确任务。

```text
全站导航
产品命题 + 一个主 CTA | 真实桌面/卡牌内容
对战 / 卡组 / 观战三个真实入口
开始对局的简短说明
官方发售与活动消息
登录或注册收口
```

要求：

- 主视觉必须来自真实卡牌或桌面；
- 对战、卡组、观战进入不同后续路径；
- 认证后恢复原任务；
- 不使用营销数字墙、无依据的覆盖率或装饰性“01/02/03”。
- 首页首版以最新商品为主，使用一项重点商品与两项紧凑商品的非对称版式；
- 官方消息只引用 Bushiroad 等权威来源，并显示发布日期和原文链接；
- Loveca 产品公告与官方卡牌消息必须明确分区，不得混淆来源；
- 商品缩略图与中文摘要由 Loveca 服务端或自有静态资源缓存提供，页面运行时不得依赖日本官网、GitHub 等境外资源；
- 官方原文链接只在玩家主动点击后打开；同步失败时继续展示最后一次成功缓存及其同步日期；
- 没有可靠数据源时隐藏消息模块，不用手写内容长期冒充“最新消息”。

商品信息维护方法：

1. 先查看 Loveca 官网的[商品列表](https://llofficial-cardgame.com/products/)，再打开候选商品页核对官方名称、分类、发售日和已公开卖点；只有月份、尚无具体日期的预告也要记录为预告，不能自行补日期。
2. 官网直连异常时，可用 `curl -x http://127.0.0.1:7890 -L --max-time 30 <URL>` 经本机 7890 代理复查。若仍出现异常 404 或超时，使用限定 `site:llofficial-cardgame.com/products/` 的搜索索引读取官方页，并以 [Bushiroad 官方商店](https://bushiroad-store.com/pages/llofficial-cardgame) 交叉核对；搜索摘要可能滞后，不能单独作为最终依据。
3. 商品图只取官网或 Bushiroad 官方商店，转为 WebP 后保存到 `assets/images/official-products/`；前端继续引用本地 `/images/official-products/...`，不在运行时请求境外图片。
4. 更新 `client/src/components/pages/PublicHomePage.tsx` 的商品卡、预告和“整理于”日期后，至少运行 `pnpm --dir client exec tsc -b`；商品卡顺序或图片变化较大时再补桌面和移动端截图检查。

### 8.2 认证页

单一任务：完成认证并继续先前任务。

```text
品牌顶栏 / 返回公开首页
本次登录目的说明 | 表单
账号辅助操作
```

要求：

- 必须说明“登录后继续做什么”；
- 卡组管理等云端任务不显示可用的离线替代；
- 登录成功后不统一跳大厅；
- 注册、找回密码、邮箱验证共享同一认证外壳。

### 8.3 玩家大厅

单一任务：让已登录玩家继续最可能的下一步。

```text
全站导航
继续中的房间/对局（存在时为主操作）
当前卡组准备状态 | 开始新对局
排位 / 观战 / 历史
公告与服务状态
```

要求：

- 正常状态不让系统诊断信息占据主视觉；
- 无卡组时主任务改为创建卡组；
- 有保存房间时主任务改为返回房间；
- 公告只在真正影响任务时升级为横幅。

### 8.4 工作台页

适用于卡组管理、卡组编辑、卡牌管理和大部分后台。

```text
App Frame
标题 + 主要操作
紧凑工具栏（搜索 / Tabs / 筛选）
列表、表格或主编辑区
详情抽屉 / 局部菜单
```

要求：

- 使用列表和分隔线组织重复内容，不默认一项一卡片；
- 工具栏保持 1–2 行；
- 主要内容有明确滚动边界；
- 批量操作和危险操作与普通操作分离。

### 8.5 任务流程页

适用于游戏准备、联机房间、公共牌桌、排位候场和重开流程。

```text
App Frame
当前任务标题 + 进度
当前一步的选择或状态
必要的上下文摘要
上一步             唯一下一步
```

要求：

- 一屏只强调当前步骤；
- 已完成信息收为摘要；
- 等待态展示下一步将由谁、在什么条件下触发；
- 手机端主操作稳定在拇指可达区。

### 8.6 沉浸式对局

`GameBoard` 不套普通页面内容框，但共享品牌 token、字体、按钮和覆盖层规范。

```text
轻量对局 chrome
对手区域
共享桌面
己方区域
上下文操作 / 效果处理
```

要求：

- 规则语义色优先于品牌色；
- 不在桌面之上重复全站主导航；
- 离开、重开、设置和聊天进入轻量 chrome；
- 对局前、对局后页面重新回到 App Frame。

## 9. 组件规范

### 9.1 按钮

| 类型        | 用途                     | 同屏数量            |
| ----------- | ------------------------ | ------------------- |
| Primary     | 当前页面默认下一步       | 通常 1 个           |
| Secondary   | 合法但次要的替代操作     | 可多个              |
| Text        | 导航、低频辅助操作       | 按需                |
| Destructive | 删除、退出房间、认输     | 与普通操作分区      |
| Icon-only   | 主题、关闭等高度通用动作 | 必须有 `aria-label` |

按钮必须写结果：“选择对局方式”“保存卡组”“加入房间”，不用“提交”“继续”这类缺少上下文的词。

### 9.2 表面

- `PageSection`：靠留白和分隔线形成页面区块；
- `Panel`：需要独立边界的工作区域；
- `ListRow`：重复数据的默认容器；
- `Callout`：维护、错误或规则提醒；
- `OverlaySurface`：菜单、抽屉、模态。

禁止 `Panel` 内无意义地继续嵌套多个相同 `Panel`。

### 9.3 状态

状态由“短标签 + 明确说明 + 可执行动作”组成：

```text
[云端不可用] 无法读取你的云端卡组。  重试
```

- 颜色只辅助，不单独承载含义；
- 禁用状态必须解释恢复条件；
- 错误说明下一步；
- 空状态提供首个有效动作；
- 加载使用骨架或局部进度，不让整页反复闪回启动屏。

### 9.4 表单

- 标签始终可见；
- 帮助文本靠近字段；
- 校验错误显示在对应字段附近；
- 主要提交按钮沿流程保持同一名称；
- 手机软键盘出现时字段和提交按钮仍可访问。

### 9.5 卡牌图像

- 卡图用于展示真实内容，不作为无关背景贴图；
- 功能页使用与显示尺寸相符的图片规格；
- 图片失败必须有稳定卡背或占位；
- 卡图网格支持键盘焦点与触控详情；
- 生产页面不得依赖本地测试补图。

## 10. 动效

### 10.1 时长

| Token    | 时长       | 用途                      |
| -------- | ---------- | ------------------------- |
| Fast     | 120–160ms  | hover、按压、颜色         |
| Normal   | 180–240ms  | 菜单、局部面板            |
| Slow     | 300–420ms  | 抽屉、模态、单次页面入场  |
| Dramatic | 按专项设计 | LIVE 结果、阶段、游戏结束 |

### 10.2 使用原则

- 公开首页允许一次编排式入场；
- 功能子页面不为每个 section 重复上浮；
- 列表 hover 不默认位移；
- 拖拽和区域移动遵循对局 motion 规范；
- 所有非必要动画支持 `prefers-reduced-motion`；
- 动画不能延迟真实操作结果。

## 11. 文案与命名

### 11.1 导航词汇固定

统一使用：

- 大厅
- 卡组
- 对战
- 观战
- 历史
- 账户
- 管理

同一目的不要在不同页面混用“主页 / 首页 / 大厅”“游戏 / 对局 / 开局”等多个导航名称。产品导航使用“大厅”，公开站点根页使用“首页”。

### 11.2 状态文案

- 面向玩家描述结果，不暴露状态机、批次或内部服务名；
- 用主动语态；
- 不使用“奇怪解释文案”替代卡牌原文；
- 空状态不写情绪性标语，直接告诉用户如何开始；
- 操作成功后的反馈沿用按钮动词，如“保存卡组”→“卡组已保存”。

### 11.3 中文表达原则

Loveca 的界面文案以简体中文玩家为主要读者，同时尊重作品、卡牌与规则中已经形成的专有名词。目标不是把所有外语强行翻译成中文，而是让句子自然、操作明确、术语稳定。

- 从玩家要完成的事出发，不描述系统结构。例如写“开始对战”，不写“进入规则桌面”；
- 一个按钮只写一个明确动作，优先使用“开始对战”“管理卡组”“进入观战”等动宾短语；
- 标题说明目的，正文补充条件与结果。不要在标题中塞入所有模式或实现细节；
- 使用日常、完整的中文句式，避免“可以上桌的构筑”“选择场合”“规则状态已载入”等直译或工程化表达；
- “构筑”优先作动词或规则概念使用，如“构筑卡组”“构筑规则”；表示一副牌时使用“卡组”；
- 面向玩家时使用“卡牌效果”，代码、调试界面或紧凑规则标签中才可使用“卡效”；
- 不用宣传口号替代产品事实。首屏应说明可以构筑卡组、寻找对手和进行对局；
- 中文与英文、数字之间保留一个半角空格；已经固定组合的卡牌术语按卡面与规则原文书写。

推荐句式：

| 场景     | 使用                        | 避免                         |
| -------- | --------------------------- | ---------------------------- |
| 对战入口 | 开始对战 / 选择对战方式     | 选择场合 / 进入规则桌面      |
| 卡组状态 | 卡组符合构筑规则            | 合法构筑 / 可以上桌的构筑    |
| 卡组动作 | 构筑卡组 / 管理卡组         | 整理我的构筑                 |
| 对局动作 | 开始对局 / 进入房间         | 坐下开局 / 启动游戏实例      |
| 离线入口 | 进入离线模式 / 体验离线对局 | 离线模式游玩 / 先离线试桌    |
| 加载状态 | 当前可使用 2,032 张卡牌     | 2,032 张卡牌已载入           |
| 登录衔接 | 登录后继续刚才的操作        | 登录后把你带到刚才选择的地方 |

## 12. 明确禁止的模板化设计

以下组合容易产生明显的生成式设计痕迹，除非内容本身确实需要，否则不得使用：

- 大号居中标题 + pill eyebrow + 三张完全相同功能卡；
- 深色背景 + 多个发光渐变球 + 玻璃卡片；
- 没有真实业务含义的 `01 / 02 / 03`；
- 用大数字统计填补空白；
- 每个区块都使用圆角、描边、阴影和 hover 上浮；
- 用六色 Heart 装饰与规则无关的页面；
- 为每张卡片加入独立入场动画；
- 用内部实现说明冒充产品文案；
- 将所有未登录操作都重定向到同一个通用登录页。

自检问题：

> 如果把 Loveca、卡图和文案替换掉，这个页面是否可以原样用于任意 SaaS、AI 工具或其他 TCG？

如果答案是“可以”，说明视觉仍不够具体。

## 13. 主题策略

### 13.1 一套结构，两套色彩

浅色与深色主题共享：

- 布局；
- 字阶；
- 间距；
- 圆角；
- 组件状态；
- 导航模型；
- 交互行为。

只替换语义颜色和必要阴影。

### 13.2 页面默认主题

- 公开首页可以固定使用品牌深色首屏，但正文仍需与系统主题协调；
- 工作台、认证和管理页尊重用户主题；
- 对局桌面可以使用独立的规则画布，但 chrome 尊重主题；
- 主题切换不改变信息结构。

### 13.3 固定视觉回归基线

非对局产品页使用独立 Playwright 配置维护真实截图差异比较，避免与数据驱动的 E2E 项目交叉相乘。固定矩阵为：

- 390px 浅色；
- 768px 深色；
- 1024px 浅色；
- 1440px 浅色；
- 1440px 深色。

测试必须固定时间、时区、locale、主题、reduced motion、mock 数据和设备像素比，并等待字体及首屏图片稳定后使用 `toHaveScreenshot`。截图按运行平台分目录保存；启用 Linux CI 必须先在统一 Chromium 与 CJK 字体镜像中生成 Linux 基线，不能拿 macOS 系统字体截图直接充当 Linux 基线。

## 14. 迁移路线

### Phase 0：设计系统底座

- 将公开首页私有颜色提升为全局品牌/语义 token；
- 确认并应用统一系统字体栈；
- 建立 `AppFrame`、全站导航、页面标题栏和移动端菜单；
- 收敛 Button、Panel、ListRow、Status、EmptyState、Callout；
- 建立桌面/移动端/深浅主题截图基线。

### Phase 1：入口与认证

| 页面                         | 目标原型   | 首要改造                                   |
| ---------------------------- | ---------- | ------------------------------------------ |
| `PublicHomePage`             | 公开产品页 | 改用全局 token 与 App Frame 导航           |
| `LoginPage` / `RegisterPage` | 认证页     | 延续任务说明、统一品牌边缘、减少孤立表单卡 |
| `HomePage`                   | 玩家大厅   | 重组为继续任务、卡组准备和次级入口         |
| `GameSetupPage`              | 任务流程页 | 统一步骤、摘要和底部主操作                 |

### Phase 2：卡组工作台

| 页面             | 目标原型   | 首要改造                              |
| ---------------- | ---------- | ------------------------------------- |
| `DeckManager`    | 工作台     | 列表化、统一工具栏、明确创建/导入层级 |
| `CardEditor`     | 全屏工作台 | 卡牌库、卡组抽屉和详情的稳定区域关系  |
| `SharedDeckPage` | 只读工作台 | 作者、构筑摘要、复制动作和登录续接    |

### Phase 3：对局入口与记录

| 页面                       | 目标原型        | 首要改造                         |
| -------------------------- | --------------- | -------------------------------- |
| `OnlineRoomPage`           | 任务流程页      | 房间状态、锁组、准备和唯一下一步 |
| `PublicTablePage`          | 任务流程页      | 候场、确认、恢复和错误状态       |
| `RankedPage`               | 任务首页 + 流程 | 赛季状态、个人结果和候场入口     |
| `OnlineSpectatorLobbyPage` | 紧凑任务页      | 房间号输入与授权说明             |
| `MatchRecordsPage`         | 工作台          | 筛选、记录列表和回放入口         |

### Phase 4：账户与后台

- `AccountCenterPage` 使用标准表单与安全操作分区；
- 管理页使用密度更高的工作台，不复刻玩家大厅；
- 表格、筛选、批量操作和危险操作统一；
- 管理入口从玩家主导航降级。

### Phase 5：对局外层

- 只统一 `GameBoard` 外层 chrome、按钮、抽屉、模态和结果页；
- 不因视觉统一改写权威状态或桌面规则布局；
- 卡牌移动、LIVE、声援、检视和卡效反馈按专项 motion/interaction 规范验收。

## 15. 每页迁移流程

每个页面按相同顺序改造：

1. 写出页面的单一任务；
2. 列出主操作、次操作和危险操作；
3. 选择本文中的页面原型；
4. 确认进入来源和离开目标；
5. 先改 App Frame 与信息结构；
6. 再换 token 和组件；
7. 最后添加该页唯一的强视觉；
8. 验证深色、浅色、390、430、768、1024 和桌面宽度；
9. 验证键盘、触控、reduced motion、加载、空、错误和维护状态；
10. 删除旧样式，而不是长期 dual-style。

不允许先制作高保真视觉，再补按钮落点和状态分支。

## 16. 完成定义

一个页面只有同时满足以下条件，才算完成统一改造：

- 使用全局品牌与语义 token，没有新增页面私有主题；
- 归属于一个明确页面原型；
- 复用统一 App Frame 或有记录在案的沉浸式例外；
- 主操作明确且后续路径真实可用；
- 认证后恢复原任务；
- 加载、空、禁用、错误、维护状态完整；
- 深浅主题可读；
- 主要视口无全局横向溢出；
- 关键操作不依赖 hover；
- 焦点可见、图标按钮有可访问名称；
- reduced motion 下功能完整；
- 没有重复旧组件或兼容样式分支；
- focused tests、截图审查和生产构建通过。
- 受影响的代表页面通过上述固定矩阵的截图差异比较。

## 17. 设计评审清单

评审每个页面时回答：

### 产品

- 用户为什么来到这里？
- 默认下一步是什么？
- 页面是否保留了进入时的意图？
- 是否把系统限制错误地放在产品价值之前？

### 结构

- 这个页面属于哪一种原型？
- 是否存在卡片套卡片？
- 工具栏、列表和详情的滚动边界是否明确？
- 移动端是否重新排序，而不是简单缩窄？

### 视觉

- 强视觉是否只有一个？
- 视觉是否来自 Loveca 的真实内容？
- Heart 色是否只在表达规则？
- 去掉品牌名后是否仍像任意模板？

### 交互

- 每个按钮是否准确描述结果？
- 认证、离线和云端边界是否在操作前说明？
- 返回、关闭和撤销是否有稳定锚点？
- 空、错、加载和等待状态是否告诉用户下一步？

### 工程

- 是否复用 token 和通用组件？
- 是否引入页面私有色板或一次性布局组件？
- 是否完成深浅主题、响应式、键盘和 reduced-motion 验证？
- 是否保留了本可删除的旧样式 fallback？

---

这套系统追求的不是“所有页面看起来一样”，而是让玩家在任何页面都能感受到同一个产品：知道自己在哪里、正在准备什么，以及下一步会被带到哪张桌子。

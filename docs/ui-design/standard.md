# Loveca 前端 UI 开发规范

> 文档类型：编码标准
> 适用范围：React 组件、主题 token、页面布局、覆盖层和产品文案
> 当前状态：现行规范，需与 `client/src/index.css`、`client/src/lib/theme.ts` 和实际页面组件同步维护
> 视觉依据：[产品视觉系统与页面统一规范](product-visual-system.md)

本文约束 UI 的实现质量与工程边界，目标是让操作正确、可访问、响应稳定，并降低修改与维护成本。产品视觉语言由视觉系统定义；设计目标、研究与取舍方法见 [frontend-design skill](../../.agents/skills/frontend-design/SKILL.md)。具体工作顺序和验证范围按当前问题决定。

## 1. 总原则

### 1.1 以任务结果和实现质量判断

- 用户能找到操作、理解当前状态、完成任务并确认结果；等待和失败有反馈，恢复不丢失有效输入。
- 结构、文案和视觉共同建立清晰层级，同类操作保持一致；紧凑布局仍保留可读性与可操作性。
- 键盘、触控、读屏、主题和文字缩放下保留主要任务；输入响应、滚动和布局保持稳定。
- 复用已有组件与语义 token，保持职责清晰；权威状态、权限及隐藏信息边界不因 UI 修改而改变。

按任务影响安排设计、实现和验证，不规定先改结构还是先做视觉探索。局部收益应与改动范围、复杂度和运行成本相称。

### 1.2 用户语言优先，禁止实现说明文案进入产品界面

文案帮助用户理解位置、可做的操作及后果。控件和上下文已经说明的内容无需重复；影响当前决定的规则、权限、风险和恢复方法应在需要时可见。

“当前入口已经迁到统一主题体系”“这个页面使用新版工作台布局”等实现说明留在文档，不进入产品界面。

### 1.3 操作位置与焦点保持可预测

高频开关尽量保持位置，展开与收起入口应容易找到。抽屉、模态可以沿用已有关闭位置，不机械要求开关坐标相同。状态更新避免无关重排或焦点丢失；关闭覆盖层后，将焦点恢复到触发入口或合适的后续任务位置。

## 2. 视觉系统规范

### 2.1 必须使用语义化 token，不允许业务组件继续写旧主题硬编码

优先使用：

- `var(--bg-*)`
- `var(--text-*)`
- `var(--border-*)`
- `var(--accent-*)`
- `var(--semantic-*)`

优先复用：

- `surface-panel*`
- `workspace-*`
- `modal-*`
- `button-*`
- `input-field`
- `status-pill`
- `chip-badge`

禁止在业务组件里继续扩散：

- `bg-[#2d2820]`
- `bg-[#3d3020]`
- `text-orange-*`
- `bg-slate-*`
- 旧 `cute-*` 风格

规则：

- 品牌色、页面原型、氛围强度和页面外壳以 `product-visual-system.md` 为准
- 新页面不得新增一套私有配色语言
- 修改涉及的旧样式应收敛到现有 token，处理顺序按问题决定
- 同类角色复用相同的组件、状态语义和样式来源；不同密度通过明确变体表达

### 2.2 按信息角色保持一致

- 同级计数保持字号、对齐与数字格式一致；普通数量可用纯文本，需要隔离复杂背景时再加局部底色。
- 状态使用稳定的语义色，并配合文字或图形；标题、分类、计数不因统一风格而全部变成胶囊。
- 可操作控件与静态信息应可区分；按钮的可见体量可以轻量，实际命中区域仍须满足触控与无障碍要求。

### 2.3 优先复用 typed 视觉原语

普通业务页的面板、区块标题、按钮、状态和单行输入分别优先使用 `Panel`、`SectionHeading`、`ActionButton`、`StatusBadge` 与 `TextInput`。它们统一 10px 面板圆角、8px 控件圆角、44px 默认控件高度和 400/600 字重角色。

这些是共享默认值。列表内操作、紧凑切换和专用桌面按角色选择已有变体；调整视觉体量时保留可辨识状态、焦点和足够的操作区域。

边界：

- `Panel` 不负责选择页面信息架构，也不应用于卡片套卡片；
- `StatusBadge` 只表达短状态，不能包装作者名、分类或整句说明；
- 房间号、卡号等数据可以在 `TextInput` 上额外使用等宽字体，普通输入不得使用；
- 对局桌、开局演出、移动端 bottom sheet、模态和抽屉保留专项组件；
- 不为一次性 7px、14px 圆角或硬偏移阴影绕过共享 token。

标准字重为正文 400，普通强调、按钮及普通标题 600；700 仅用于比分、结算结果等短而强烈的信息。中文正文、控件和标题字距均为 0；仅纯拉丁展示标题可轻微收紧。等宽字体仅用于逐字符辨识的数据。

### 2.4 当前共享组件入口与复用边界

组件统一从 `client/src/components/common` 导出，按职责使用：

| 层次 | 当前模块 | 职责 |
| --- | --- | --- |
| 视觉基础 | `VisualPrimitives.tsx` | `ActionButton`、`TextInput`、`Panel`、`SectionHeading`、`StatusBadge`；标题通过 `size="compact"` 支持紧凑工具区 |
| 异步反馈 | `AsyncFeedback.tsx` | `LoadingState`、`EmptyState`、`ErrorNotice`；统一可读状态、空结果和可选重试入口 |
| 页面外壳与通用交互 | `ProductFrame`、`ProductHeader`、`PageHeader`、`ConfirmDialog`、`SelectMenu` | 导航、页面标题、确认与选择交互 |
| 业务组件 | `DeckSelector`、`DeckStats`、`CasualRuleSelector` | 卡组、构筑与模式等领域展示，复用基础控件 |
| 交互行为 | `hooks/useDialogAccessibility.ts` | 对话框焦点、Escape 与背景交互隔离 |

基础组件不读取接口、不维护业务请求或决定重试动作。调用方提供状态内容、`onRetry` 和 `retryDisabled`；`EmptyState` 的后续操作通过 `action` 传入。加载和空状态可选 `plain` / `panel` 外观，外部间距由调用方控制。历史页与卡组选择器已共用这组异步反馈。

`panel` 状态使用轻量底色、实线细边框和面板圆角，不用深色占位块或虚线扩大视觉重量。模式、来源等分类优先使用普通辅助文字；真正的完成、警告与错误状态复用 `StatusBadge`。历史页的节点切换和手机回放入口复用 `ActionButton`，不另设按钮字阶。

页面 CSS 只设置页面结构与业务布局，不用宽泛的 `button`、`input`、`h2` 后代选择器覆盖共享组件的尺寸、排版和状态。原生选择条目仍可保留专用组件，不为统一外观将所有可点击内容都改成普通操作按钮。优先扩展已有组件的明确变体，出现实际复用需求时再提取组件，不为一次性结构建立通用配置框架。

## 3. 布局规范

### 3.1 工具栏默认紧凑，避免“大而空”的控制区

编辑器、管理页、检索页优先将空间留给内容。相关的搜索、切换和筛选可成组排列，低频扩展项按需展开；高频入口和影响选择的条件应容易发现。

行数由内容、视口和文字缩放决定，不为压成一两行缩小触控区域、挤掉标签或隐藏关键操作。手机允许重排和换行，检查软键盘及安全区对可见内容的影响。

### 3.2 布局稳定性依赖显式高度链

涉及 `flex`、侧栏、抽屉、卡牌列表、滚动区域时，必须明确高度关系。

要求：

- 需要滚动的容器自己声明 `overflow`
- `flex` 子元素缺省检查 `min-h-0`
- 抽屉和浮层内部滚动区单独拆出，不要让整个容器既承担定位又承担滚动
- 面板外露把手时，外层容器必须允许 `overflow-visible`

### 3.3 不要依赖“看上去差不多”的定位

如果一个浮层应当居中，就必须使用稳定的居中结构，而不是靠试偏移值。

推荐结构：

外层固定覆盖全屏并负责居中，内层动画元素只负责进入、退出和内容动画。

不要把“居中定位”和“动画 transform”写在同一个 `motion.div` 上。

原因：

- Framer Motion 会覆盖 `transform`
- `translate(-50%, -50%)` 很容易失效
- 最终表现就是弹窗跑到屏幕下方或右下角

## 4. 弹窗与浮层规范

### 对战桌面的工具栏与辅助区

- 桌面端房间、日志、聊天、模式控制及设置统一由 `GameBoard` 的顶部工具栏承载，并实际占用布局高度。联机、观战与回放通过桌面入口插槽接入，避免在外层另加左上角悬浮工具条。
- 常规桌面工具栏实际高度为 48px：主入口和状态组最高 40px，上下内边距各 3.5px，含 1px 底边框；窄屏必要时换行增高。紧凑样式只作用于工具栏内标记的入口，不压缩菜单内容和手机控件。
- 应援/判定、公开日志和调试日志使用工具栏下方的左侧辅助区，同一时刻展示一个大型面板。切换日志保留判定查看玩家；重新打开判定区时切回判定面板。
- 当前桌面容器宽度达到 1440px 时，420px 辅助区与牌桌并排；更窄的桌面使用抽屉，保持顶部工具入口可用。后续调整阈值需要同时验证三成员槽与两侧资源区的最小可用宽度。
- 判定标题、玩家切换和确认操作不随内容滚动；仅面板内容区独立滚动。移动端判定使用模态面板，背景桌面不可操作，键盘焦点遵循共享对话框规则；房间入口保持在阶段浮层上方，但仍随背景桌面受判定模态隔离。
- 顶部工具栏占位后，桌面玩家信息放在手牌两侧，不再独占整行挤压舞台。成员优先使用牌区剩余高度，保持最大 140px 宽并约束窄桌面的三列宽度；成员的拖拽与详情容器必须填满槽位，不能由图片原始尺寸决定大小。
- LIVE 正面与背面共用横牌比例，空槽与实卡切换保持布局稳定。手牌、成员、LIVE 与需求心图标不得相互遮挡；不要整体缩放牌桌或改变卡牌的规则 orientation。
- 成员优先使用可用高度，手牌与 LIVE 区随窗口高度适配；手机沿用独立的尺寸与触控布局。具体参数统一见[牌桌尺寸与圆角分配](product-visual-system.md#牌桌尺寸与圆角分配)与[游戏桌 UI 现状](game-table/current-state.md)，此处不维护另一套尺寸副本。
- 主题、对战特效等低频设置收在对战设置菜单，本地退出与重开收在房间菜单；关键规则操作继续放在对应效果面板或阶段控制区。

### 4.1 弹窗默认使用 portal

只要是全屏遮罩弹窗、居中 modal、跨区域浮层，默认挂到 `document.body`。

适用场景：

- 检视卡组顶
- 休息室展开
- 详情模态框
- 中央确认框

原因：

- 组件挂在局部树内时，容易被父级布局、`overflow`、`transform`、层叠上下文影响
- `fixed` 不一定真的相对视口定位

### 4.2 外层负责定位，内层负责动画

规范：

- 外层容器负责 `fixed`、`inset-0`、`items-center`、`justify-center`
- 内层 `motion.div` 只做 `opacity/scale/y` 动画

不要反过来。

### 4.3 浮层要分级，不要所有东西都做成 modal

按层级分为：

- `overlay`: 卡牌 hover 详情
- `drawer`: 判定区、详情抽屉
- `modal`: 检视卡组顶、休息室、确认框
- `workspace panel`: 编辑器、管理页、侧栏

不同层级不要混用同一交互逻辑。

## 5. 交互规范

### 5.1 模式、权限与权威状态

仅属于调试模式的调试日志、控制条在其他模式不渲染。当前任务中暂不可用、但用户需要知道如何解锁的操作，可保留禁用状态并说明条件；不要混淆无关功能与暂不可用功能。

条件渲染不替代权限校验。对战状态通过 `GameSession` / `GameService` / command 层改变；React 展示投影并提交命令，隐藏信息在投影与服务边界隔离，不先传给前端再隐藏。

### 5.2 面板开关必须成对设计

任何可展开/收起结构都要同时检查：

- 打开入口在哪
- 收起入口在哪
- 位置是否稳定、关系是否容易理解，关闭后焦点是否恢复
- 收起按钮是否会被裁切、遮挡、覆盖

### 5.3 hover 操作不能成为唯一操作路径

卡牌操作悬浮菜单可以存在，但关键操作不能只依赖 hover 才能发现。

对于移动端或窄屏：

- 必须有替代入口
- 或至少保证核心操作仍可通过按钮、面板完成

### 5.4 可访问性是交互约束

优先使用原生按钮、链接、表单与单选等语义；自定义控件补齐对应的名称、角色、状态与键盘行为。图标按钮有可访问名称，焦点清晰且不被遮挡，状态变化不只依赖颜色。

模态打开时管理焦点与背景交互，关闭后恢复焦点；普通浮层不套用模态的焦点限制。异步结果、错误与必要进度应能被读屏感知，避免重复播报。检查文字缩放、目标尺寸、实际背景对比度和 reduced-motion，适用要求参照视觉系统与移动端规范。

### 5.5 反馈、恢复与异步一致性

操作被接受后及时反馈，进行中避免重复提交；失败保留有效输入，说明原因与可执行的恢复方式。取消、返回和撤销遵守业务规则，权限错误不伪装为成功。

处理请求竞态、卸载和模式切换，避免旧结果覆盖当前选择；加载、空数据、失败和刷新旧数据应正确区分。保留浏览位置和有效上下文，避免每次刷新都清空整页。

## 6. 表单规范

### 6.1 高频字段优先可见

主要输入和提交入口应容易发现，字段分组与任务顺序一致。必填、可选及格式要求清楚，标签不依赖 placeholder；低频设置可按需展开，错误靠近对应字段并提供修正方法。

### 6.2 区分编辑与浏览的长文本需求

编辑中的备注、描述保留可用输入宽度，空间不足时重排字段。列表中的长备注可单行截断，并提供键盘和触控均可访问的全文入口；详情按内容需要换行。不要让辅助内容无限撑高列表，也不截掉决定操作所必需的信息。

## 7. 文案与图标规范

### 7.1 少用 emoji 作为界面主表达

emoji 可以用于临时调试，不应作为正式 UI 的主图标系统。

优先使用统一图标库，例如 `lucide-react`。

### 7.2 图标与文字共同帮助辨识

模式切换等含义不够通用的操作使用明确名称，图形辅助快速区分；选中态同时有位置、形状或标记。关闭等熟悉动作可以只展示图标，但必须有可访问名称。`aria-label` 服务辅助技术，不能替代普通用户需要的可见说明；`title` 也不能作为触屏上唯一的解释。

## 8. 维护性规范

### 8.1 让修改范围与问题相称

复用已有组件、token 与状态来源，移除被本次实现替代的旧样式和重复逻辑。同一共享原因影响多处时，在共同来源修复并覆盖相关调用方；独立问题不借局部修改扩成整站重构。组件抽象、依赖和缓存应有实际收益，不为外观增加重复业务状态。

### 8.2 性能与视觉稳定性

按真实内容规模检查加载、输入响应、滚动和内存占用。大列表、图片和动效按瓶颈选择分页、延迟加载或其他优化，保留完整搜索与键盘访问能力；不预先叠加优化机制。

图片、异步内容和反馈预留合适空间，避免布局跳动、焦点丢失或操作入口漂移。结合实际设备和网络判断性能，不以动画时长或单一评分代替任务体验。

### 8.3 按影响选择验证

- UI 变化在真实浏览器中检查代表性内容与操作结果；根据影响覆盖视口、主题、长文本、加载和错误状态。
- 行为或状态变化运行相关 focused tests；类型或编译链路变化运行对应 TypeScript 检查。构建、完整视觉回归和 E2E 由影响范围决定，纯文档修改检查格式、链接与声明一致性。
- 共享视觉组件或 token 变化覆盖受影响的代表页面；固定截图矩阵见[视觉回归基线](product-visual-system.md#133-固定视觉回归基线)。截图审查与交互验证互相补充。

独立视觉回归入口如下，可按页面用例与项目筛选范围：

```bash
pnpm --dir client test:e2e:visual
```

先审查差异、确认变化符合任务意图，再更新需要调整的基线；不要为了消除失败直接运行 `pnpm --dir client test:e2e:visual:update`。该命令更新全部快照，局部变更应筛选用例与项目。基线按平台隔离，浏览器与字体环境保持一致，测试卡牌使用本地确定性占位图。

临时截图、录屏和报告留在本地验证目录，不默认纳入提交；基线变更遵循用户明确要求与仓库约定。交付说明实际检查结果和未覆盖边界，不以自动化通过宣称用户体验已经验证改善。

## 9. 发布与版本规范

### 9.1 版本号必须单一来源

产品版本由根目录 `VERSION` 维护，`package.json` 和 `client/package.json` 通过 `pnpm version:check` 保持一致。`client/vite.config.ts` 读取 `VERSION` 注入前端版本；构建身份另外使用 build ID / commit SHA，以识别同版本的不同构建。

版本号应同时驱动：

- 首页显示
- 页脚显示
- PWA 缓存版本

### 9.2 缓存更新必须与版本联动

应用更新统一由 `client/src/lib/appUpdateCoordinator.ts` 和 `appUpdateRegistration.ts` 管理，Service Worker 使用 `prompt` 注册模式：

- Service Worker 与 `version.json` 发现更新时只标记可用，不自动导航或刷新。
- 进行中对局和未保存编辑期间不提供会丢失任务的更新操作；玩家在安全页面确认后才应用更新，且只刷新一次。
- Workbox 管理旧 precache；更新流程不枚举清空卡图、表情等运行时缓存，也不把 SW 接管事件作为独立刷新入口。
- 当前部分资源缓存按产品版本命名，内容寻址表情缓存使用稳定名称；具体缓存策略以 `client/vite.config.ts` 为准。

当前实现与验收边界见[前端外层架构需求与设计](../frontend-app-architecture/requirements-and-design.md)和[阶段 A 观测基线](../frontend-app-architecture/phase-a-observability-baseline.md)。

## 10. 完成质量

以受影响的任务与状态判断：操作结果正确，入口和反馈清楚，布局与焦点稳定，目标设备和输入方式可用，权限及数据边界保持正确。实现复用合适的共享能力，没有引入无必要的复杂度；按影响选择的检查通过，未解决的问题明确说明。具体实施顺序由开发者或 agent 判断。

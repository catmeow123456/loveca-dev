# 轮换主题牌桌策划与设计

> 文档类型：设计文档
> 适用范围：轮换主题牌桌的产品边界、玩家流程、分配模型、运营约束与第一版实现
> 当前状态：权威设计；第一版开发闭环已落地，尚未开放生产活动
> 产品定位：固定时段、非计分、由服务端提供预组的公共牌桌活动

## 1. 决策与目标

建议将玩家提出的“大乱斗”实现为**轮换主题牌桌**，而不是在公开匹配或排位中强制随机玩家卡组。

目标是：让所有卡牌已开放的环境中，玩家能以低学习和构筑成本体验不同体系、降低连续撞见相似引擎的疲劳，并验证“预组主题对局”是否提高休闲对局的趣味与复玩。

它不承担以下职责：

- 不修复某一体系过强、卡效错误或禁限用问题；
- 不改变排位的自组合法卡组、单一候场池与计分公平性；
- 不按玩家自组卡组强度配对，也不惩罚玩家使用热门卡组；
- 不建设第三套规则桌面、对局记录或匹配状态机。

## 2. 模式边界

| 项目     | 轮换主题牌桌                                   | 休闲公共牌桌     | 赛季排位         |
| -------- | ---------------------------------------------- | ---------------- | ---------------- |
| 卡组     | 服务端冻结的预组                               | 玩家自带合法卡组 | 玩家自带合法卡组 |
| 开放方式 | 固定短时段，避开排位核心窗口                   | 常规开放         | 固定赛季开放窗口 |
| 结果     | 不计分                                         | 不计分           | 计入赛季 rating  |
| 配对原则 | 独立主题活动池；按已验证的对局组合分配双方卡组 | 单一 FIFO        | 单一 FIFO        |
| 目标     | 尝试、发现、对局多样性                         | 自由对战         | 公平竞技         |

首期建议只在每周固定的 1～2 个短窗口运行，并与排位核心时段错开；不要在验证前全天常驻，以免进一步拆分有限候场人数。

## 3. 玩家流程

1. 玩家在活动页看到本期主题、开放时间、全部预组名称、完整卡表、玩法标签、难度与“本局随机分配”的明确提示。
2. 玩家选择“加入主题牌桌”后进入复用公共牌桌状态机的**独立主题活动池**；此时不上传、不选择也不修改个人卡组。
3. 双方确认后，服务端在创建房间前的同一权威事务中选择一个已批准的**对局组合**，再以 50/50 概率交换双方所持预组，并持久化本次分配。
4. 服务端只在分配记录已成功冻结后创建现有正式联机房间，将本局分配的预组作为权威锁定卡组写入快照；猜拳、隐藏信息、`RULES` / `FREE` 协商、认输、历史记录与普通正式对局一致。
5. 对局结束后只展示活动结果与可选反馈，不写入排位、日常任务门槛或高价值奖励进度。

“先选对局组合、再随机座位”是首版的核心公平规则。不能让两名玩家分别从“主流卡组表”独立抽一副：那会制造未经测试的极端对局，也会令某些组合被重复抽到。

分配前，玩家只知道本期公开预组池和“随机分配”的规则；分配后，玩家在进入正式开局房间时看到自己本局使用的预组。若玩家在分配后、开局前主动离开，按公共牌桌的开局前离场口径处理；无过错对手必须能够恢复候场或获得等价的明确处理结果。该恢复能力未闭环前，主题牌桌不得上线，不能以“非计分”降低这一要求。

## 4. 预组池与配对矩阵

### 4.1 预组不是“主流卡组列表”

每一期推荐 6～8 副预组。选池应同时满足：

- 玩法差异清楚，进入前可由一句玩法标签说明；
- 卡效自动化与规则流程已可接受，不把玩家当测试人员；
- 预组在当前活动规则环境下有可玩的展开与反制空间；
- 有少量高认知度主流构筑作为入口，同时有当前使用率较低的体系；
- 每副均有可公开的完整成员、LIVE、能量清单与版本号。

当前数据支持把 Cerise Bouquet、Edel Note、DOLLCHESTRA、5yncri5e! 视为“玩家熟悉的候选锚点”，而非自动全部入池；A・ZU・NA、QU4RTZ、AZALEA、CatChu!、Mira-Cra Park! 等可作为差异化候选。最终入池必须以本期完整牌表和实测结果为准，不能只按线上份额或社区热度决定。

### 4.2 每一期必须冻结的对象

| 对象                  | 必填内容                                                                                            | 目的                               |
| --------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `themeTableVersion`   | 主题名、规则环境、全局卡牌目录版本/哈希、开始/结束时间、公告文案、分配算法版本                      | 区分不同活动、规则与算法           |
| `prebuiltDeckVersion` | 预组 ID、显示名、完整成员/LIVE/能量表、规范内容哈希、玩法标签、难度、来源、规则完整性检查与审阅记录 | 可复盘每局实际使用的卡表           |
| `matchupPairVersion`  | 两副预组 ID、允许方向、权重、测试记录、启用状态                                                     | 防止独立随机产生未测组合           |
| 本期可选组合快照      | 启用的 `matchupPairVersion`、权重及其规范哈希                                                       | 使抽签集合可重建，不受后来停用影响 |
| 分配记录              | 对局/预留 ID、主题/预组/组合版本、双方预组 ID、算法版本、可审计熵结果或等价承诺                     | 回放、投诉审查与活动分析           |

预组由服务端所有，不能引用某位玩家的云端卡组；活动启用后不可原地修改。需要修正时创建新版本、停止旧版本继续发牌，并保留历史对局关联。随机种子若用于审计，必须连同算法版本、可选组合快照和服务端熵来源一起保存；单独保存一个可由运营者任意指定的种子，不构成可审计的公平性证明。

### 4.3 配对矩阵的建立方法

1. 先对每副候选预组做规则完整性检查和内部试打，记录先后手、完成率、明显不可逆卡死与人工处理负担。
2. 只把通过检查的双方组合放入矩阵；相同预组镜像也必须单独测试，而不是默认安全。
3. 对每个组合记录双方方向的实测结果；若存在明显优势，优先调整预组或从矩阵移除，而非降低玩家随机到该预组的概率。
4. 上线后按组合而非仅按单副预组监控。出现异常时立即停用该组合，活动仍可用剩余矩阵继续运行。

首版可以用等权重的已批准组合；只有在多期稳定数据后，才评估有限权重调节。不得对某个玩家、昵称、个人自组卡组或历史胜率做定向抽签。

### 4.4 曝光目标与首期矩阵规模

“每个组合内 50/50 交换座位”只保证该组合中双方取得任一预组的概率相同；如果某副预组出现在更多组合中，或组合权重不同，它在全池的曝光仍会偏高。因此每个 `themeTableVersion` 必须另行冻结：

- 启用组合及权重所推导出的每副预组**预期边际曝光率**；
- 允许的曝光偏差和统计口径（按已分配局、已开局局或已完成局）；
- 组合选择算法，以及配置发布前的可复算校验结果。

首期不要求把 6～8 副候选预组做成完整 round-robin。6 副含镜像已有 21 组、8 副已有 36 组，短窗口下难以取得每组可解释的样本。首期可以公开 6～8 个候选，但应只启用少量已试打、能满足曝光目标的组合；或缩小为 4～5 副核心预组。扩大矩阵必须作为后续版本变更，而不是在活动运行中静默加组。

### 4.5 队列与原子分配契约

主题牌桌复用公共牌桌的候场、确认、租约、房间引导和玩家占用机制，但必须拥有独立的 `THEME` 队列上下文与 `themeTableVersion` 环境身份，不能借用普通 `CASUAL` 队列或让玩家个人锁组进入活动池。主题票据的卡组字段在入队时表示“尚未分配”；确认成功后才由服务端写入已冻结预组。

形成主题对局时，服务端必须在单一事务/可恢复的幂等边界内完成以下动作：读取仍启用的本期组合快照、选择组合与座位、写入不可变分配记录、将两份预组锁定到对应票据或预留，并取得创建房间所需的租约。任何一步失败都不得产生“已匹配但没有可审计卡组”的房间；失效配置、组合池为空或预组校验失败时，应释放预留并按既有无过错恢复口径处理双方。

## 5. 运营规则与界面文案

活动页必须在候场前明确：

- 本活动不计入排位，且使用平台提供的预组；
- 本期预组与完整卡表的可见入口；
- 随机的是“已验证对局组合中的双方位置”，不是随机抽取无关的热门卡组；
- 当前开放时间、关闭后的下一次时间，以及不开放时可去休闲公共牌桌或排位；
- 若某预组含更复杂的规则或未完全自动化的交互，要在玩法标签中事先说明。

首版不提供预组二选一、重抽、禁用卡组、投票 ban 或按卡组筛选队列。这些都会增加候场状态、降低配对密度并损害“直接体验”的目标。若活动数据证明玩家明显需要掌控感，后续只评估“同强度档二选一、双方同时锁定、开局揭示”这一种低复杂度扩展。

## 6. 需要复用与新增的系统边界

复用既有公共牌桌候场、双方确认、正式联机房间、权威对局、卡组锁定快照、观战、认输、重连和历史记录。主题牌桌的新增责任仅包括：

- 活动窗口与活动版本读取；
- 服务端预组注册表和配对矩阵；
- 在确认成功后进行可审计的组合/座位分配；
- 将活动、预组和配对版本随对局快照保存；
- 独立的活动指标聚合与管理员停用入口。

前端不得自行随机或持有权威预组。即使客户端提前展示候选预组，也必须由服务端在形成对局时决定并返回锁定结果。管理员“停用组合”只影响尚未分配的新预留；已冻结的分配与已开始对局保持原版本，以免运行时改写玩家本局规则事实。

## 7. 指标、停开条件与首期判定

### 7.1 每个活动窗口采集

- 候场人数、等待时间、确认率、房间创建成功率、开局率、完成率、认输/断线/`FREE` 使用；
- 各预组曝光次数、获胜次数、先后手、镜像率与每个预组组合的样本量；
- 预组组合层面的完成率、异常处理率和胜率，而非只看单副预组总胜率；
- 每副预组的实际边际曝光率相对本期冻结目标的偏差，并按“分配 / 开局 / 完成”三个分母分别显示；
- 同窗口休闲公共牌桌与排位的等待、完成与对局量变化；
- 参加者在 7 / 14 天内的再次对局、活动前后本人对局量变化，以及自愿反馈中的“理解玩法”“想再玩”“不公平”“等待过长”。

### 7.2 首期的继续、调整与停止

首期只验证可玩性和增量参与，不以高参与数或单次好评直接常驻化。

| 判断                                                                                               | 建议动作                                                                 |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 分配、锁定或房间引导出现不可审计结果；无过错对手无法得到既定恢复结果                               | 立即暂停新入队，保留证据并先修复公共牌桌/分配链路                        |
| 某组合达到预先冻结的最小完成样本后，胜率区间越过容忍范围、完成率低于下限，或产生超过上限的人工处理 | 立即从配对矩阵停用，复测预组；不改成按玩家定向抽签                       |
| 单副预组实际曝光持续偏离本期目标且超过允许偏差                                                     | 暂停该版本的新分配，校验矩阵、权重和算法；不得通过面向特定玩家的抽签修正 |
| 活动明显拉低同窗口休闲/排位的完成率，或使等待时间不可接受                                          | 缩短窗口、移到其他时段或暂停，而非再开一个队列                           |
| 预组曝光符合目标、完成率可接受、玩家复玩和人均对局量提升，且未只是搬运原有对局                     | 保留并以新池轮换进行第二期验证                                           |
| 平台数据发现某体系跨自组模式长期压制                                                               | 单独启动竞技环境、卡效正确性与禁限用审查；主题牌桌不掩盖该问题           |

在首期开始前，运营应填写具体的最小样本、可接受等待时间、组合胜率容忍范围、完成/异常处理下限、曝光偏差上限和基线窗口，并冻结在活动记录中，避免事后修改成功定义。基线至少固定同星期、相邻时段的对照窗口、观察回溯长度、测试/管理员账号排除规则和“净新增”的计算方式；主题桌的局数不能单独当作增量参与。

## 8. 上线顺序

1. 先收束公共牌桌的开局前离场无过错恢复、进行中房间恢复和指标聚合；主题桌不以非计分为由绕过这些前提。
2. 建立可审计的主轴/核心组件标签与快照质量原因码，保证活动外的环境基线可信。
3. 选出 6～8 个候选预组，冻结完整清单并做规则与少量对局组合试打。
4. 建立独立主题队列上下文、活动版本、服务端预组、配对矩阵、原子分配/锁定记录、曝光校验和管理员停用能力。
5. 用短时段进行首期非计分试验；窗口避开排位核心时段。
6. 依据冻结指标决定保留、调整、暂停或进入第二期；不从首期直接推广为全天常驻模式。

## 10. 2026-08-02 第一版落地评估与实现状态

总体判断：产品边界与随机分配原则合理，可以进入实现；首期应继续保持短窗口、非计分和服务端预组，不应加入玩家二选一、独立抽牌或高价值奖励。当前方案最重要的正确点是把“组合选择”和“座位交换”分开冻结，同时公开完整卡表、限制候选组合，并把活动身份与卡组快照留在服务端。

第一版已经落下以下基础闭环：

- 新增独立 `THEME` 队列上下文和 `THEME_QUEUE` 玩家占用，不与休闲或排位候场混用；
- 新增活动版本、服务端预组版本、组合版本和不可变分配记录；
- 主题票据入队时不上传个人卡组，双方确认后才在同一数据库事务中选择已启用组合、50/50 交换双方位置、冻结候选集合哈希与随机证明，并把两副预组写入对应票据；
- 只有分配冻结成功后才进入现有房间创建租约；房间继续复用正式联机、权威规则、卡组快照、观战、认输和历史记录；
- 玩家页可查看本期说明、开放状态、全部预组、玩法/难度标签和完整成员/LIVE/能量卡表，并可候场、确认、跨页面保活和进入已创建房间；
- 数据迁移为 `drizzle/0026_add_theme_table_v1.sql`，主题分配可通过 `reservationId` 与最终 `matchId` 审计。

第二实施批次继续完成：

- 新增受管理员权限保护的活动编排 API 和工作台，按“活动 → 预组 → 组合 → 发布”推进；活动草稿冻结当前规则版本、卡牌目录哈希和分配算法，至少两副合法预组及一个实测组合后才能发布；
- 数据库只允许一个 `ACTIVE` 版本。发布后不能原地修改活动事实、预组或新增/重新启用组合，只能即时停用组合；停用最后一个组合会在同一数据库语句中自动暂停新入队；
- “已创建房间、尚未开局”阶段一方主动离开、未到场或整体开局超时后，责任方票据终止；无过错方在活动仍开放时取得新票据、保留原 FIFO `joined_at`，并以 `requeued_from_ticket_id` 留下审计链；
- 管理工作台已展示入队、分配、开局、完成、无过错回队以及按组合权重推导的目标/实际预组曝光。首期成功定义随活动冻结，不允许事后改口径。

当前实现仍只适合开发/内测环境：尚未建立首期真实预组池和实测配对矩阵；进行中房间跨进程恢复、完整等待/确认/组合胜率与异常率聚合、曝光偏差告警、主题身份历史详情和 focused 双浏览器验收仍未闭环。环境调研中的主流/特色体系不能直接当作已批准活动卡表；完成真实试打和上述上线前置前，不得发布生产 `ACTIVE` 版本。

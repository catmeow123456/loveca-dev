# 赛季内评分参数修订与全量回算

> 文档类型：设计与运维 Runbook
> 适用范围：进行中 V3/V4 排位赛季的参数预览、维护期回算、审计与恢复
> 当前状态：已实现；必须在暂停匹配且排位运行态归零后应用
> 最后更新：2026-08-09

## 1. 不可变边界

`GLICKO1_PER_MATCH_V1`–`V4` 仍是已发布的冻结算法身份，管理员调整不会覆盖这些配置，也不会把新参数继续写成原 `algorithmVersion`。每次应用都生成唯一的 `<base>_REV_<revisionId>` 身份，完整新旧 config、哈希、竞技环境 ID、操作人、原因、流水版本和预览摘要保存在 `ranked_rating_revisions`。

V3 修订只能调整 `ratingScale / minimumRatingDeviation / placementMatchCount`，不能凭空加入 V4 成长公式。V4 除上述参数外，提供五项成长设置：启用开关、成长基准分、最大单局注入/回收总分、高分局胜方回收比例和过渡宽度；关闭时只让成长项归零，另外四项数值仍随修订保存。参数都由服务端白名单和数值范围校验，不接受任意公式、代码或完整 JSON config 上传。

| 参数                                | 适用版本 | 允许范围       | 说明                                             |
| ----------------------------------- | -------- | -------------- | ------------------------------------------------ |
| `ratingScale`                       | V3/V4    | 200–2000       | 调整预期胜率曲线对分差的敏感度                   |
| `minimumRatingDeviation`            | V3/V4    | 30–200         | 限制长期活跃玩家 RD 的最低值                     |
| `placementMatchCount`               | V3/V4    | 1–30 的整数    | 同步更新定级和参榜场次；正式 V4 基准仍为 5       |
| `growthPool.enabled`                | V4       | `true / false` | 关闭后保留其余成长参数，但回算结果不叠加成长项   |
| `growthPool.centerRating`           | V4       | 1400–2400      | 决定成长项由正和转为负和的中心分                 |
| `growthPool.maximumTotalAdjustment` | V4       | 1–50           | 限制一场对局双方合计最多注入或回收的分数         |
| `growthPool.negativeWinnerShare`    | V4       | 0.5–1          | 高分负和局由胜方承担的回收比例，败方自动承担余量 |
| `growthPool.transitionWidth`        | V4       | 50–1000        | 数值越小，中心分附近从正和切换到负和越快         |

## 2. 预览契约

预览只读取当前赛季、追加式积分流水、seed 和投影，先用当前冻结配置重放并核对投影，再按新参数重放。响应包含新旧 config、有效/变化对局数、受影响玩家数、积分和名次最大变化、单局加减分最大差异、seed RD 夹取数以及所有 blocker。

预览令牌由服务端签名，有效期 15 分钟，并绑定 `seasonId`、修订 ID、新旧 config 哈希、`ledgerRevision`、参数、原因和过期时间。任意字段被篡改、过期，或预览后又有新结算/更正，应用都会被拒绝并要求重新预览。

## 3. 应用保护

应用只允许 `ACTIVE + PAUSED`，且必须同时满足：没有 `PENDING` 或进行中排位对局；没有活动排位票据、配对预留、玩家占用；所有对局的规则、卡池、卡组政策、评分算法和对局记录规则版本与赛季当前冻结环境一致；赛季保存的规则、卡池、卡组政策和源评分配置必须能重新生成同一个冻结竞技环境 ID。回算始终沿用赛季冻结卡池，不会因操作时恰好发布了另一版卡池而改写历史环境。

应用在一个 `SERIALIZABLE` 事务中锁定赛季和相关对局/流水/投影。对每场对局的最新指令追加新修订版本的 `REPLACEMENT / VOID`，然后原子重建全部玩家投影和每场 before/after 快照，统一更新对局/赛季算法身份、参榜门槛、竞技环境和流水 revision。任一 SQL 或复核失败都会回滚全部改动。

如果提高最低 RD，历史 seed RD 会在新参数回放输入边界确定性夹到新下限，夹取人数在预览中显示；同时只在必要时上调冻结配置的 `softResetMinimumDeviation`，不改动其他软重置语义。

## 4. 维护期步骤

1. 在管理页填写新参数和原因，生成预览，保存关键差异供运营确认。
2. 暂停排位匹配，等待票据、预留、占用、进行中和待结算对局全部归零。
3. 重新生成预览；确认 `canApply=true`、blocker 全为 0，再勾选确认并应用。
4. 核对赛季流水 revision、排行榜、玩家最近对局加减分和修订历史，再重新开放匹配。
5. 如需恢复，在历史中选择旧参数，依然按“预览→暂停→全量回算”创建新不可变修订，不删除旧修订或旧积分事件。

数据库结构由 `0017_add_ranked_rating_revisions.sql` 提供；首次部署、验证和不可逆边界见 `drizzle/migration-notes/ranked-rating-revisions.md`。

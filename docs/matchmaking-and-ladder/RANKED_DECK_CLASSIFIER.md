# 赛季排位卡组分类与环境饼图

> 适用范围：长期排位卡组观察、卡组分类运营、发布与重分类、玩家环境统计
>
> 当前状态：代码与迁移已实现；生产数据库迁移、初始种子导入和首次发布需由部署者显式执行
>
> 最后更新：2026-08-23

## 1. 玩家统计口径

登录玩家通过 `GET /api/ranked/environment/decks?seasonId=<uuid>` 读取当前生效分类版本下的赛季卡组环境。管理端将“展示什么”和“如何计权”分开配置：展示内容可任意复选使用占比、胜者构成和高排名玩家构成；全部取消时玩家页完全不渲染卡组环境模块，接口在读取发布快照和统计聚合前返回空结果。使用占比和胜者构成可选择 `PLAYER_EQUAL`、`MATCH_EQUAL` 或 `BOTH`；高排名玩家构成固定使用玩家等权。

- 玩家等权：每名玩家先归一化自己的卡组分布，再让每名玩家权重相同；胜者构成只在至少有一场胜利的玩家之间等权。
- 对局等权：使用占比中每个有效席位权重相同；胜者构成中每场有效对局的胜方权重相同。
- 高排名玩家构成：从当前排行榜中按 rating 选取已达到赛季排行榜最低场次的前 N 名，只统计这些玩家自己的赛季卡组席位；每名至少有一个可分析席位的玩家先归一化自己的赛季使用分布，再彼此等权。N 默认 30，管理员可在 10–100 之间即时调整。活跃赛季使用当前排名，关闭赛季自然使用最终排名。

“使用占比”回答环境由哪些卡组构成，“胜者构成”回答胜方使用了哪些卡组，“高排名玩家构成”回答当前榜单高排名玩家在本赛季使用了什么；三者都不直接证明卡组强度或等同于胜率。表格另行展示原始胜率、排除镜像对局后的非镜像胜率、出场席位数及已启用的使用率口径。图表显示前 8 个已识别分类，其余已识别分类合并为“其他已识别卡组”；`其他／未识别` 与 `分类冲突／待复核` 始终保持独立，不被视觉合并掩盖。分类可配置一张精确卡号的代表卡，玩家饼图会将对应卡图裁剪进分类扇区；未配置、图片缺失、其他、未知和冲突扇区使用分类颜色回退，图例与文字标签始终保留。

只有最终 `SETTLED`、双方长期观察完整、双方都具有当前发布版本可公开分类结果的对局进入饼图。`UNKNOWN` 和 `AMBIGUOUS` 进入统计分母，`EXCLUDED`、`INVALID` 和尚未分类的观察不进入。接口同时返回观察覆盖率、分类结果覆盖率、可分析对局数和玩家数。

## 2. 识别算法

分类输入只读取 `ranked_deck_observations.main_deck_cards`，按基础卡号合并印刷版本并验证 `48 MEMBER + 12 LIVE`。稳定构筑指纹版本为 `loveca-deck-v1`。当前算法依次执行：

1. 人工覆盖：全局覆盖适用于未来发布；版本覆盖只适用于指定发布。版本覆盖优先于同指纹的全局覆盖。
2. 精确样板：构筑指纹与启用样板相同；同一指纹不能同时成为两个启用样板。
3. 严格规则：规则只使用可序列化的包含、任一包含、禁止包含和卡号合计数量条件；数字越小优先级越高，只在最高优先级命中集内判断冲突。
4. 相似度：按卡数差的半 L1 距离（即需要替换的张数）计算，MEMBER 权重 `1`、LIVE 权重 `3`，最大距离 `42`，前两名最小间隔 `3`。
5. 不能可靠判断时保留 `UNKNOWN` 或 `AMBIGUOUS`，不强行归类。

分类算法版本、指纹版本、名称、样板、规则和四个距离参数全部冻结在发布快照中。任务执行和玩家读取都会校验 `config_hash`，不使用当前草稿或未来代码默认值替换历史发布参数。代表卡、备用颜色、展示内容、基础计权和高排名人数属于独立展示设置，不进入发布快照或 `config_hash`；修改后即时生效，不触发预览、重算或发布。玩家接口按发布快照中的稳定分类 ID 叠加数据库中的最新展示设置；未选择任何展示内容时会在读取发布快照和聚合统计前直接返回空结果。

## 3. 发布与任务状态

草稿名称、样板和规则可持续编辑，`draftRevision` 防止两个管理员用旧页面互相覆盖。发布会创建不可变快照及 `BUILDING` 版本，并排队执行全量分类：

```text
草稿 -> BUILDING -> 全量成功 -> ACTIVE
                  -> 任意失败 -> FAILED
旧 ACTIVE ---------------------> SUPERSEDED（仅在新版本成功时）
```

玩家始终只读取唯一 `ACTIVE` 版本。新版本的全部结果和状态切换在一个事务中提交；失败时旧版本继续服务。系统同一时间只允许一个 `BUILDING` 版本和一个 `RUNNING` 任务。发布切换、手动重分类和人工覆盖共用事务锁；构建期间后两类操作返回 409，避免覆盖落到即将退役的版本。失败的新增观察自动补分类任务可按相同幂等键重新排队。

服务进程启动后会运行持久任务 worker；超过 3 分钟没有心跳的 `RUNNING` 任务被标为失败。新增排位观察会自动为当前版本补分类，不需要管理员逐场触发。

## 4. 运营管理

“运营管理中心 → 对局与赛季 → 卡组分类”要求 `season.deck_classifier.manage`，`season_admin` 与 `admin` 均拥有该权限，普通玩家没有。该模块包括：

- 发布与口径：用下拉复选框任意组合使用占比、胜者构成和高排名玩家构成，选择基础计权并设置高排名人数；全部取消即完全隐藏。另可全量预览、发布新版本、重分类当前版本和查看任务状态。
- 分类名称：新增、修改、归档名称、分组和顺序；归档会停用其草稿样板与规则，但不改写历史发布快照。每个分类另有即时展示设置，可独立修改备用颜色和可选代表卡，不增加草稿修订号；代表卡必须是卡牌库中的精确 MEMBER／LIVE 卡号，图片不可用时回退到颜色。新增但尚未发布的分类即使设置代表卡也不会出现在玩家端。
- 样板库：从排位对局管理的双方长期卡组观察直接导入，或展开查看并编辑完整卡表、归属、名称、备注与启用状态；支持按卡组分类筛选、按基础卡号或卡名筛选，并可按分类、样板名称、创建/修改时间及启用状态排序。列表不展示仅供机器匹配的 SHA-256 指纹。来源绑定 `match_id + seat`；原观察删除后只清空来源指针，已复制的样板卡表仍保留。修改卡表会在服务端重新标准化并计算指纹，但只写入草稿，重新预览并发布成功后才影响玩家分类。
- 识别规则：常见的单卡数量、多卡合计数量与禁止包含条件可用直观表单维护，规则列表优先显示自然语言；无法被直观编辑器无损表达的 `includeAny` 等条件仍以受限 JSON 编辑和展示。两种方式最终使用同一数据条件词汇，不执行任意脚本或表达式。
- 待处理：按出现次数查看 `UNKNOWN / AMBIGUOUS` 的完整 MEMBER／LIVE 卡表、卡图、卡名和数量，不向管理员展示机器指纹；可人工指定分类、保持未知或排除，并可查看及撤销已生效覆盖。人工指定分类只锁定当前完整构筑指纹，不参与其他构筑的近似度对比；也可另选“加入样板库”，把当前完整卡表复制为启用的 `MANUAL` 草稿样板，之后可在样板库继续编辑，并在预览、发布成功后参与精确与近似匹配。加入样板本身不会立即改变玩家端分类结果。
- 人工分类、保持未知、排除、撤销锁定和手动全量重分类均由后台任务更新当前发布版本；管理端通过任务 ID 轮询状态，只有任务成功后才刷新待处理队列，避免把接口已受理误报为分类已经生效。轮询超时不会取消后台任务，页面会提示管理员稍后刷新；任务失败则展示持久化错误信息。

所有写操作要求原因；配置、发布、种子导入和人工覆盖写入 `management_audit_logs` 的 `DECK_CLASSIFIER` 范围。管理接口统一挂载于 `/api/admin/deck-classifier`，权限校验还会读取 `profiles.role` 拒绝降权后的旧 token。

## 5. 数据与初始种子

首次生产发布使用已收束的单一 `0032_add_deck_classifier.sql`：它一次性建立分类、样板、规则、发布、任务、人工覆盖和展示设置结构，同时包含完全隐藏、独立展示内容与高排名人数。新库的单例设置初始化为“完全不展示”，在种子导入、首次发布、代表卡配置与玩家口径验收完成前不向玩家显示卡组环境模块。开发期临时的 `0033/0034` 已在进入生产前压缩，生产只需执行最终 `0032`。若任一迁移已经在某个环境执行，则不得再改写该环境的历史；本规则仅利用了“三个开发迁移都尚未进入生产”这一前提。任何环境均使用 `db:migrate`，不使用 `db:push`。

`pnpm deck-classifier:import-seed -- --zip=<zip>` 默认只解析和校验 GPT Pro 离线校准包，不连接数据库。显式增加 `--apply --actor-user-id=<admin-or-season-admin-uuid> --reason=<原因>` 后才在单个可串行化事务中写入草稿和审计。初始包包含 41 个分类、366 个样板（343 个启用、23 个 provisional 停用）及 2 条严格规则；软签名只作离线提示，不导入为硬规则。导入完成后仍须由管理员预览并发布首次版本，玩家页才会出现饼图。

## 6. 本地集中验收 fixture

仅在 `localhost:5432/loveca` 测试数据库中，可用下列命令预览并生成约 50 场完整、已结算的排位 fixture。脚本通过 `MatchRecorderService`、`RankedRatingService` 和卡组观察捕获服务写入，不直接拼接排位结果；默认 dry-run，`--apply` 必须同时提供 `--yes`。它固定轮换三个本地测试账号，使用六个已导入精确样板，并额外构造稳定的 `UNKNOWN` 和规则冲突 `AMBIGUOUS` 卡组，以便同时验收玩家等权、对局等权、胜者构成、胜率、镜像和待复核展示。

```bash
DATABASE_URL='postgres://loveca:loveca_dev@127.0.0.1:5432/loveca' \
pnpm deck-classifier:seed-test-fixtures -- \
  --season-key=test-ranked-v4-growth \
  --match-count=50 \
  --run-key=classifier-pie-v1

DATABASE_URL='postgres://loveca:loveca_dev@127.0.0.1:5432/loveca' \
pnpm deck-classifier:seed-test-fixtures -- \
  --season-key=test-ranked-v4-growth \
  --match-count=50 \
  --run-key=classifier-pie-v1 \
  --apply --yes
```

脚本拒绝远程主机、非 `loveca` 库、非固定测试凭据、非 5432 端口和 `NODE_ENV=production`，同一 `run-key` 可幂等重跑；已存在但与计划不一致时会停止，绝不删除或覆盖历史。测试环境默认重启会重建 volume；希望保留 fixture 时使用 `bash scripts/start-test-env.sh --no-db-rebuild`。

# 赛季排位卡组分类与环境饼图

> 适用范围：长期排位卡组观察、卡组分类运营、发布与重分类、玩家环境统计
>
> 当前状态：卡组分类与独立卡牌环境口径已通过开发验收，管理员分类胜率与完整参赛者查询已进入开发基线；生产数据库迁移、初始种子导入和首次发布需由部署者显式执行
>
> 最后更新：2026-08-29

## 1. 玩家卡组、卡牌与积分查询口径

登录玩家通过 `GET /api/ranked/environment/decks?seasonId=<uuid>` 读取当前生效分类版本下的赛季卡组环境，通过 `GET /api/ranked/environment?seasonId=<uuid>` 读取不依赖分类发布的赛季卡牌环境。两个板块都可任意复选使用占比、胜者构成和高排名玩家构成，使用占比和胜者构成均可在自身板块内选择 `PLAYER_EQUAL`、`MATCH_EQUAL` 或 `BOTH`，高排名玩家构成固定使用玩家等权。卡组与卡牌的展示内容、基础计权必须独立保存，不得因为修改一个板块而连带修改另一个板块；两者只共享高排名玩家人数 N。任一板块全部取消展示内容时，只隐藏自身并在自身统计聚合前返回空结果。

- 玩家等权：每名玩家先归一化自己的卡组分布，再让每名玩家权重相同；胜者构成只在至少有一场胜利的玩家之间等权。卡牌榜单中“分布”表示该玩家的有效卡组中包含某基础卡号的比例。
- 对局等权：使用占比中每个有效席位权重相同；胜者构成中每场有效对局的胜方权重相同。卡牌榜单按“包含该基础卡号的席位或胜方卡组数 / 对应总样本数”计算。
- 高排名玩家构成：从当前排行榜中按 rating 选取已达到赛季排行榜最低场次的前 N 名，只统计这些玩家自己的赛季卡组席位；每名至少有一个可分析席位的玩家先归一化自己的赛季使用分布，再彼此等权。N 默认 30，管理员可在 10–100 之间即时调整。活跃赛季使用当前排名，关闭赛季自然使用最终排名。

“使用占比”回答环境由哪些卡组或卡牌构成，“胜者构成”回答胜方使用了哪些卡组或卡牌，“高排名玩家构成”回答当前榜单高排名玩家在本赛季使用了什么；三者都不直接证明卡组/卡牌强度，胜者构成尤其不是胜率。卡牌三类口径必须各自独立排序并只显示自己的 Top 30，不同罕度按基础卡号合并，平均张数不改变卡牌是否被采用的判定。卡组表格另行展示原始胜率、排除镜像对局后的非镜像胜率、出场席位数及已启用的使用率口径。卡组图表先独立展示前 12 个有正值的已识别分类；若剩余“其他已识别卡组”仍超过整张图的 15%，则逐项扩展，最多独立展示 16 个，余项继续精确汇总为“其他已识别卡组”。`其他／未识别` 与 `分类冲突／待复核` 始终保持独立，不计入 12–16 个已识别分类名额，也不被视觉合并掩盖。分类可配置一张精确卡号的代表卡，玩家饼图会将对应卡图裁剪进分类扇区；未配置、图片缺失、其他、未知和冲突扇区使用分类颜色回退，图例与文字标签始终保留。

只有最终 `SETTLED`、双方长期观察完整、双方都具有当前发布版本可公开分类结果的对局进入饼图。`UNKNOWN` 和 `AMBIGUOUS` 进入统计分母，`EXCLUDED`、`INVALID` 和尚未分类的观察不进入。接口同时返回观察覆盖率、分类结果覆盖率、可分析对局数和玩家数。

卡牌环境只要求最终 `SETTLED` 且双方长期观察完整、席位与用户身份一致，不 JOIN 分类 assignment，也不校验或要求 `ACTIVE` 发布版本。无分类发布、卡组板块全部隐藏或分类 worker 正在运行均不得阻断卡牌板块自身的可见统计。

管理员玩家积分查询在原有评分、RD、场数和榜单上下文之上，为目标及上下各最多 3 名玩家动态聚合胜场与负场，并在唯一 `ACTIVE` 分类版本下按每名玩家的已分类有效对局记录聚合最常用分类；三项数据直接作为排名上下文表的列展示，不只显示目标玩家。展示名称必须取自当前发布快照，不取当前草稿名称或玩家卡组名。并列第一、无发布版本、无已分类样本以及历史观察/分类缺失都使用结构化状态如实返回，不任意选择一个并列项，不伪造历史分类。

管理员排位概览通过 `GET /api/admin/ranked/deck-statistics?seasonId=<uuid>` 读取不受玩家展示
开关影响的分类运营统计。它与玩家卡组环境共用严格的双方可分析边界：对局当前最终投影必须为
`SETTLED`，双方长期观察完整，双方在唯一 `ACTIVE` 发布下均有 `CLASSIFIED / UNKNOWN /
AMBIGUOUS` assignment；`INVALID / EXCLUDED`、尚未分类与不完整观察只进入覆盖说明，不进入
胜率样本。追加式流水不作为累计来源，因此 `VOID` 会移除整场样本，`REPLACEMENT` 只按当前
胜方重算一次。

管理员统计中的“使用场次”按席位计算。普通对局为双方各自分类贡献 1 次使用；镜像对局为同一
分类贡献 2 次使用、1 胜和 1 负。分类及其嵌套玩家明细的胜率都按 `胜场 / 使用次数` 计算。
所有正式分类均返回，零使用显示 0；`其他／未识别` 与 `分类冲突／待复核` 仅在确有样本时出现。
响应中的名称、分组和发布顺序取不可变发布快照，颜色叠加允许即时调整的当前展示设置；不得
改用草稿身份或玩家卡组名。管理页默认只展示使用场次最高的 3 类，支持按分类名称、分组或分类键
搜索并展示全部匹配项，也可显式展开全部分类；分类内玩家明细仍按需展开。该管理员接口即使玩家端
卡组环境被完全隐藏也仍然可读。

管理员概览的完整参赛者表通过 `GET /api/admin/ranked/players` 分页读取全部
`ratedMatchCount > 0` 的赛季玩家，并动态附带当前 `ACTIVE` 发布下的最常用分类。搜索只过滤
已经完成参榜分区和全局名次计算的结果，不改变参榜玩家的真实名次；用户 ID、用户名或显示名称的
精确匹配优先于有界模糊候选返回，避免被更高榜位的同子串账号挤出首屏。并列分类、部分覆盖、无发布和无样本继续以结构化状态
返回。管理页默认收起且不读取玩家列表；搜索作为定位器，借助结果的全局列表位置读取目标上下
各 3 人的窗口并高亮目标，之后仍可继续加载更高或更低名次。旧的单玩家积分查询和上下各最多
3 名上下文接口保留，但不再承担纵览赛季玩家的主要职责。

## 2. 识别算法

分类输入只读取 `ranked_deck_observations.main_deck_cards`，按基础卡号合并印刷版本并验证 `48 MEMBER + 12 LIVE`，同一基础编号不得超过 4 张。草稿样板和识别规则在保存及发布前都会按 `cards` 权威目录核对基础编号是否存在、MEMBER／LIVE 类型是否一致；发布后的冻结快照不再依赖未来卡牌目录，保持历史可重放。稳定构筑指纹版本为 `loveca-deck-v1`。当前算法依次执行：

1. 人工覆盖：全局覆盖适用于未来发布；版本覆盖只适用于指定发布。版本覆盖优先于同指纹的全局覆盖。
2. 精确样板：构筑指纹与启用样板相同；同一指纹不能同时成为两个启用样板。
3. 严格规则：规则只使用可序列化的包含、任一包含、禁止包含和卡号合计数量条件；数字越小优先级越高，只在最高优先级命中集内判断冲突。
4. 相似度：按卡数差的半 L1 距离（即需要替换的张数）计算，MEMBER 权重 `1`、LIVE 权重 `3`，最大距离 `42`，前两名最小间隔 `3`。
5. 不能可靠判断时保留 `UNKNOWN` 或 `AMBIGUOUS`，不强行归类。

分类算法版本、指纹版本、名称、样板、规则和四个距离参数全部冻结在发布快照中。任务执行和卡组环境/管理员最常用分类读取都会校验 `config_hash`，不使用当前草稿或未来代码默认值替换历史发布参数。代表卡、备用颜色、卡组环境展示内容/基础计权、卡牌环境展示内容/基础计权和两者共享的高排名人数属于发布快照之外的即时展示设置，不进入 `config_hash`；修改后不触发分类预览、重算或发布。卡组接口按发布快照中的稳定分类 ID 叠加数据库中的最新卡组展示设置；卡牌接口只读取卡牌展示设置与共享 N，不读取发布快照。任一板块未选择任何展示内容时，会在自身重型读取前直接返回空结果。

## 3. 发布与任务状态

草稿名称、样板和规则可持续编辑，`draftRevision` 防止两个管理员用旧页面互相覆盖。发布会创建不可变快照及 `BUILDING` 版本，并排队执行全量分类：

```text
草稿 -> BUILDING -> 全量成功 -> ACTIVE
                  -> 任意失败 -> FAILED
旧 ACTIVE ---------------------> SUPERSEDED（仅在新版本成功时）
```

玩家始终只读取唯一 `ACTIVE` 版本。新版本的全部结果和状态切换在一个事务中提交；失败时旧版本继续服务。系统同一时间只允许一个 `BUILDING` 版本和一个 `RUNNING` 任务。发布切换、手动重分类和人工覆盖共用事务锁；构建期间后两类操作返回 409，避免覆盖落到即将退役的版本。失败的新增观察自动补分类任务可按相同幂等键重新排队。

服务进程启动后会运行持久任务 worker；超过 3 分钟没有心跳的 `RUNNING` 任务被标为失败。新增排位观察会自动为当前版本补分类，不需要管理员逐场触发。

## 4. 运营管理

“运营管理中心 → 对局与赛季 → 卡组分类”要求 `season.deck_classifier.manage`，`season_admin` 与 `admin` 均拥有该权限，普通玩家没有。该模块包括：

- 发布与口径：卡组环境与卡牌环境分别提供展示内容复选和基础计权，可分别选择使用占比、胜者构成和高排名玩家构成，只共用一个高排名人数 N；任一板块全部取消只会隐藏该板块。另可全量预览、发布新版本、重分类当前版本和查看任务状态。
- 排位概览：在经营数据后按使用次数展示全部正式分类及有样本的未知/冲突分类，可展开查看各玩家使用次数、胜负和胜率；该运营读取只要求 `season.ranked.manage`，不受本模块玩家端展示设置控制。
- 分类名称：新增、修改、归档名称、分组和顺序；归档会停用其草稿样板与规则，但不改写历史发布快照。每个分类另有即时展示设置，可独立修改备用颜色和可选代表卡，不增加草稿修订号；代表卡必须是卡牌库中的精确 MEMBER／LIVE 卡号，图片不可用时回退到颜色。新增但尚未发布的分类即使设置代表卡也不会出现在玩家端。
- 样板库：从排位对局管理的双方长期卡组观察直接导入，或展开查看并编辑完整卡表、归属、名称、备注与启用状态；支持按卡组分类筛选、按基础卡号或卡名筛选，并可按分类、样板名称、创建/修改时间及启用状态排序。列表不展示仅供机器匹配的 SHA-256 指纹。来源绑定 `match_id + seat`；原观察删除后只清空来源指针，已复制的样板卡表仍保留。修改卡表会在服务端重新标准化并计算指纹，未知基础编号、与权威卡牌类型不一致或同编号超过 4 张都会被拒绝；合法修改只写入草稿，重新预览并发布成功后才影响玩家分类。
- 识别规则：常见的单卡数量、多卡合计数量与禁止包含条件可用直观表单维护，规则列表优先显示自然语言；无法被直观编辑器无损表达的 `includeAny` 等条件仍以受限 JSON 编辑和展示。两种方式最终使用同一数据条件词汇，不执行任意脚本或表达式。所有规则卡号在保存和发布时都会规范化为基础编号；同一合计条件不得通过不同罕度重复引用同一基础编号，运行时也只按唯一基础编号求和。
- 待处理：按出现次数查看 `UNKNOWN / AMBIGUOUS` 的完整 MEMBER／LIVE 卡表、卡图、卡名和数量，不向管理员展示机器指纹；可人工指定分类、保持未知或排除，并可查看及撤销已生效覆盖。人工指定分类只锁定当前完整构筑指纹，不参与其他构筑的近似度对比；也可另选“加入样板库”，把当前完整卡表复制为启用的 `MANUAL` 草稿样板，之后可在样板库继续编辑，并在预览、发布成功后参与精确与近似匹配。加入样板本身不会立即改变玩家端分类结果。
- 人工分类、保持未知、排除、撤销锁定和手动全量重分类均由后台任务更新当前发布版本；管理端通过任务 ID 轮询状态，只有任务成功后才刷新待处理队列，避免把接口已受理误报为分类已经生效。轮询超时不会取消后台任务，页面会提示管理员稍后刷新；任务失败则展示持久化错误信息。

所有写操作要求原因；配置、发布、种子导入和人工覆盖写入 `management_audit_logs` 的 `DECK_CLASSIFIER` 范围。管理接口统一挂载于 `/api/admin/deck-classifier`，权限校验还会读取 `profiles.role` 拒绝降权后的旧 token。

## 5. 数据与初始种子

首次生产发布使用已收束的单一 `0032_add_deck_classifier.sql`：它一次性建立分类、样板、规则、发布、任务、人工覆盖和展示设置结构。本次规划的目标设置形状要求卡组/卡牌各自拥有完全隐藏、独立展示内容与独立基础计权，仅共用高排名人数。新库的卡组单例设置初始化为“完全不展示”，在种子导入、首次发布、代表卡配置与玩家口径验收完成前不向玩家显示卡组环境模块；卡牌板块的默认值和可见性独立于卡组首次发布。开发期临时的 `0033/0034` 已在进入生产前压缩，生产只需执行最终 `0032`。若任一迁移已经在某个环境执行，则不得再改写该环境的历史；本规则仅利用了“三个开发迁移都尚未进入生产”这一前提。任何环境均使用 `db:migrate`，不使用 `db:push`。

`pnpm deck-classifier:import-seed -- --zip=<zip>` 默认只解析和校验 GPT Pro 离线校准包，不连接数据库。显式增加 `--apply --actor-user-id=<admin-or-season-admin-uuid> --reason=<原因>` 后，脚本会先按目标数据库的 `cards` 权威目录复核全部样板与规则卡号，再在单个可串行化事务中写入草稿和审计；任一卡号不存在或类型错误都会整体回滚。初始包包含 41 个分类、366 个样板（343 个启用、23 个 provisional 停用）及 2 条严格规则；软签名只作离线提示，不导入为硬规则。导入完成后仍须由管理员预览并发布首次版本，玩家页才会出现饼图。

## 6. 本地集中验收 fixture

仅在 `localhost:5432/loveca` 测试数据库中，可用下列命令预览并生成约 50 场完整、已结算的排位 fixture。脚本通过 `MatchRecorderService`、`RankedRatingService` 和卡组观察捕获服务写入，不直接拼接排位结果；默认 dry-run，`--apply` 必须同时提供 `--yes`。它固定轮换三个本地测试账号，使用六个已导入精确样板，并额外构造稳定的 `UNKNOWN` 和规则冲突 `AMBIGUOUS` 卡组，以便同时验收卡组/卡牌的玩家等权、对局等权、胜者构成、高排名玩家、卡组胜率、镜像和待复核展示，并验证卡牌胜者构成不被误表达为卡牌胜率。

```bash
DATABASE_URL='postgres://loveca:loveca_dev@127.0.0.1:5432/loveca' \
pnpm deck-classifier:seed-test-fixtures -- \
  --season-key=test-ranked-v4-growth \
  --match-count=50 \
  --run-key=classifier-pie-v1

DATABASE_URL='postgres://loveca:loveca_dev@127.0.0.1:5432/loveca' \
pnpm deck-classifier:seed-test-fixtures -- \
  --season-key=test-ranked-v4-growth \
  --match-count=50 \
  --run-key=classifier-pie-v1 \
  --apply --yes
```

脚本拒绝远程主机、非 `loveca` 库、非固定测试凭据、非 5432 端口和 `NODE_ENV=production`，同一 `run-key` 可幂等重跑；已存在但与计划不一致时会停止，绝不删除或覆盖历史。测试环境默认重启会重建 volume；希望保留 fixture 时使用 `bash scripts/start-test-env.sh --no-db-rebuild`。

# Loveca 平台产品发展路线草案

> 文档类型：历史/计划文档
> 适用范围：公共牌桌、赛季排位与轮换主题牌桌的产品阶段判断和后续候选方向
> 当前状态：讨论稿；当前实现事实以系统设计、当前限制和对应专题文档为准
> 更新时间：2026-08-02
> 当前重点：在已经形成稳定使用习惯的公共牌桌之上，推出固定时段开放、简单可靠的赛季排位 Beta

## 1. 当前基线

以下能力已经具备，不再作为下一阶段的主要开发目标：

- 公共牌桌候场、确认和自动创建正式联机房间；
- 公共牌桌已经经过一段时间的实际使用观察，玩家愿意在统一入口持续候场，产品需求已经得到验证；
- 服务端权威对局、历史记录和主动认输；
- 云端合法卡组选择与锁定；
- 管理员公告。

公共牌桌的故障恢复和指标仍需继续补强，但不再作为阻止排位设计和基础实现的产品门槛。涉及积分可信度、赛季暂停和异常结算的必要能力仍必须在首个排位 Beta 开放前完成。

## 2. 下一阶段目标

推出一个排位 Beta：

- 管理员在新卡发售或其他合适节点开启新赛季；
- 玩家在赛季配置的晚间等核心活跃时段进入一个排位队列；
- 玩家在独立的赛季排位页查看自己的 rating、参榜进度、排名和本赛季战绩；
- 排位候场复用公共牌桌状态机，配对后复用正式联机房间和共享牌桌，不建设另一套对局流程；
- 完成对局后计算 rating，并提供赛季排行榜；
- 赛季结束时封存榜单，新赛季进行软重置。

首版优先让玩家容易开局。Loveca 同时候场人数有限，因此先通过固定开放时段集中参与者，再采用纯 FIFO：按 `joinedAt` 从早到晚配对，时间相同时按 ticket ID 排序，不因 rating 或上一位对手跳过任何有效票据。

房间号和公共牌桌继续提供不计分的休闲对局。赛季排位是玩家主动进入的可选玩法，不成为使用卡组、历史记录或其他普通功能的前提。

本阶段的 POC 假设是：固定活跃时段的轻量赛季排名能够增加真人对局参与和重复游玩，同时不显著损害休闲公共牌桌的可用性，也不让主要用户因 rating 压力降低游玩意愿。公共牌桌已经验证统一候场需求，但没有验证可见 rating、排名或赛季是否具有正向产品价值；首季仍是实验，不把排位需求写成已经验证的事实。

## 3. 开发顺序

### R1：制度契约与影子验证

- 固定赛季生命周期、候场准入、每日/每周开放窗口和窗口结束处理；
- 固定排位中的 `RULES` / `FREE` 协商、远程撤销、认输、断线弃权和平台故障口径；
- 固定正式对局开始后禁用整局重开，避免双方通过重开作废即将结束的计分对局；
- 采用 Glicko-1，保存 `rating + RD`，新玩家从 `1500 / RD 350` 开始；
- 固定即时更新、RD 时间变化、精度、上下限、软重置和算法版本；
- 用既有完整对局离线影子验证算法和榜单波动，不追溯修改玩家积分。

首轮生产影子报告已经回流：2026-07-24 至 29 日的 491 局合格公共牌桌对局覆盖 50 名玩家。样本未显示明显首后手偏差，支持继续使用每局即时 Glicko-1 和纯 FIFO；但 5 场资格会让仍高 RD 的短期连胜玩家直接进入榜首，因此当前候选提升为 `GLICKO1_PER_MATCH_SHADOW_V2`，将建议参榜门槛改为 10 场，其他数学参数不变。V1 继续保留以复现已生成报告，所有 `SHADOW` 版本都不能写入玩家可见积分。

临时生产脚本 `scripts/generate-ranked-shadow-report.mjs` 继续只读查询 `match_records` 并生成匿名 JSON/Markdown。其 V2 输出会分开统计卡牌数据版本与对局卡组数据哈希，并细分被排除记录的状态。现有 `match_records.cardDataHash` 是两副本局卡组快照的哈希，不是全局卡牌目录哈希；R2 不能复用它冻结赛季环境。详细判断见[首轮生产影子报告分析](./RANKED_SHADOW_REPORT_ANALYSIS_2026-07-30.md)。

### R2：Rating 流水与赛季运营

- 每局原子写入双方结算前后 rating / RD，并保证同一 `matchId + algorithmVersion` 只结算一次；
- 用追加式作废/替代流水处理确认的平台故障或错误结算，不删除原记录；
- 实现赛季创建、开始、暂停候场、恢复候场、进入 `FINALIZING` 和封存；
- 实现开放窗口配置、下一次开放时间投影和 `FINALIZING` 最长收口期限；
- 为赛季保存独立的全局卡牌目录/竞技环境版本与哈希，不复用对局级 `match_records.cardDataHash`；
- 提供有效对局、异常结算、重复对手、断线弃权、`FREE` 使用和平台故障等基础指标；
- 管理员在首个 Beta 开放前已经可以暂停新排位并收口异常赛季。

当前 R2 与首版 R3 闭环已经在代码和本地完整测试环境实现，但尚未部署生产：

- `ranked_seasons / ranked_matches / ranked_player_ratings / ranked_player_seeds / ranked_rating_events / ranked_rating_event_steps` schema 与单一 `0010_add_ranked_system.sql` 迁移；
- 排位来源 `RANKED`、独立全局卡牌目录哈希和完整 `competitiveEnvironmentId`；
- `DRAFT -> ACTIVE -> FINALIZING -> CLOSED`、独立准入开关和时区开放窗口服务；
- `SERIALIZABLE` 事务内的双方原子结算、初始结算幂等和赛季 revision；
- 追加式 `VOID / REPLACEMENT`、防分叉更正链和全赛季确定性重建；
- `/api/admin/ranked` 环境/赛季/异常对局/基础监控接口，以及带 revision 乐观锁的更正预览与执行；
- 独立排位票据、赛季/环境隔离、纯 FIFO 配对、确认和正式房间引导；
- 既有 `GLICKO1_PER_MATCH_V1` 与新赛季默认 `GLICKO1_PER_MATCH_V2` 正式算法；V2
  将新玩家初始 RD 从 350 轻微下调到 300；
- 首场积分回显、默认 10 场且可按赛季配置的参榜门槛、个人赛季战绩、最近对局和
  排行榜；
- 赛季激活时从最近封存赛季生成可审计软重置种子；
- 权威终局自动结算、延迟结算重试、计划结束自动收口和最长收口期限平台无结果处理；
- `FREE` 使用审计标记、单方 3 分钟断线弃权，以及无法区分先后的双方超时平台无结果；
- 精简的玩家赛季页和管理员“赛季 / 异常对局”页面；
- 管理员只能引用服务端算法注册表，不能从请求注入评分参数；
- 持久层拒绝 `SHADOW` 算法版本。

当前剩余的是上线与观察工作，而不是首版主流程施工：生产迁移尚未执行，告警渠道和更细的运营指标仍需补充，首季开放时段与成功/暂停口径也要在真实数据产生前冻结。详细实现见 [R2 数据与结算核心设计](./RANKED_R2_DATA_AND_SETTLEMENT_DESIGN.md)、[赛季排位管理员 API](./RANKED_ADMIN_API.md)和[首版实现与验收说明](./RANKED_INITIAL_IMPLEMENTATION.md)。

### R3：固定时段排位 Beta

- 增加排位入口和一个排位候场池；
- 增加赛季排位页，在未开放和开放时均可查看个人赛季资料；
- 开放时展示当前窗口剩余时间，未开放时展示下一次开放时间；
- 复用公共牌桌的候场、确认、房间创建和占用互斥；
- 按稳定的纯 FIFO 顺序尽快成局；
- 允许双方按正式联机现有协议协商开启 `FREE`，使用过 `FREE` 的可靠权威结果仍正常计分；
- 正常终局、主动认输和断线逾期弃权计分；
- 退出或断线时保留重连期限，逾期未恢复才由服务端判定弃权负；
- 只有权威状态不可恢复或存在可审计的平台故障时，整局不计分；
- 展示定位状态、整数 rating、排名、本赛季胜负/胜率、最近排位对局、赛后变化和排行榜；
- 匹配成功后继续进入现有正式联机房间，不在对局桌面持续突出双方排名。

### R4：首季观察与常驻评估

- 通过现有公告系统发布赛季周期、每日开放时段和规则说明；
- 首季建议持续 4～6 周，无高价值奖励或普通功能门槛；
- 比较排位与休闲公共牌桌的等待时间、确认率、开局率和完成率；
- 观察重复对手、`FREE` 使用、异常结算、断线弃权、首后手结果和玩家复用；
- 比较首季前后全站真人对局完成量与每名玩家的重复参与，不把休闲对局搬入排位本身视为净增长；
- 分别收集参与者和看见排位但未参加者对游玩动力、rating 压力、开放时段、结果可信度和规则自动化的反馈；
- 在开放前固定“继续 / 调整入口或时段 / 暂停实验”的判断口径和记录位置，不在数据产生后追改成功定义；
- 根据实际同时在线和等待数据决定第二季继续固定时段、扩大时段或改为全天开放。

### R5 候选：卡组多样性观测与轮换主题牌桌试验

轮换主题牌桌的完整产品与技术方案以[轮换主题牌桌策划与设计](./ROTATING_THEME_TABLE_DESIGN.md)为准。本节只保留它在整体路线中的阶段判断；候选预组、别称口径与完整构筑来源必须在每期活动配置和实测记录中另行冻结。

公开房间和赛季排位都可能因当前版本的强势体系而出现卡组同质化。Loveca 向所有玩家开放全部卡牌，消除了获取卡牌的门槛，也会让已验证的最优构筑快速扩散。这个问题有两个不同层面：构筑环境的强度集中，以及玩家缺少低成本尝试其他体系的机会。

随机分配卡组只能改善后一层，不能替代卡池平衡、禁限用判断或卡效规则完善；因此不得把它当作排位平衡补丁。排位继续允许玩家使用自己构筑的合法卡组，也不按卡组强度、体系或上一位对手改变配对。避免同类卡组的针对性匹配会进一步拆散本来有限的候场池，也容易被规避。

在首季排位有稳定参与和基础指标后，可以将“大乱斗”以独立、非计分的 **轮换主题牌桌** 进行小规模试验：

- 仅在固定的短时段开放，优先安排在排位核心窗口之外；不建设全天常驻的第三个候场池，也不影响房间号对局；
- 复用公共牌桌候场、确认、正式联机房间、权威对局、历史记录和共享牌桌，不为活动另建规则桌面；
- 玩家进入前可查看本轮主题、完整卡组池、每副卡组的玩法/难度简介与本期 `X 选 1` 规则；匹配后由服务端生成候选，玩家在候选中选择 1 副（`X = 1` 时自动锁定）；
- 候选按启用组合图确定性生成，双方任意交叉选择都必须落在经过内部测试的启用组合内，避免独立随机产生未测的极端对局；
- 主题桌复用公共牌桌状态机，但拥有独立的 `THEME` 队列上下文和活动环境身份；确认后、创建房间前原子冻结主题/组合/预组版本、双方最终选择、算法版本与可审计分配结果，不能让玩家个人锁组混入主题池；
- 运营预组池建议从 6～8 副开始，保留少量具有辨识度的热门体系，但重点选择玩法差异明显、强度可接受且当前使用率偏低的体系。卡组是否入池由对局质量、卡效自动化完整度和内部测试决定，不能仅按公开使用率或策划偏好决定；
- 不以高价值奖励、排位积分或普通功能门槛驱动参与。首版目标是发现不同卡组和提升休闲对局趣味，而不是制造新的必玩压力。

预组卡组、卡组池版本、活动规则环境、每局分配结果和本局锁定卡组都必须随权威对局快照保存。服务端提供预组，不能在运行时依赖某位玩家的云端卡组；管理员编排阶段可以从自己持有且通过构筑校验的云端卡组复制一次不可变服务端快照。对局开始后仍按现有隐藏信息、`RULES` / `FREE` 协商和历史记录规则处理。分配后、开局前的责任方离场与未到场已按公共牌桌占用边界为无过错对手生成保留原 FIFO 时间的新票据；进行中房间恢复和完整活动指标/告警未收束前，仍不开放生产主题桌。首次生产开放前该玩法已升级为 `X 选 1` 候选卡组选择（见设计文档第 11 节），不提供重抽或投票 ban。

在做活动前，先补齐不改变玩家体验的卡组多样性观测。精确卡组内容 hash 只适合锁定与重放，不能代表体系；应在服务端分析/运营层按卡组快照生成可审计的体系标签或核心组件标签，并至少按公共牌桌与排位分别观察：

- 各体系占比、前四体系占比、镜像率和多样性变化；
- 体系及主要对局组合的胜率、样本量与先后手差异；
- 各模式的等待时间、确认率、开局率、完成率、断线/`FREE` 使用和重复参与；
- 主题池每副预组的实际选用次数与占比，以及组合/分配/锁定异常；
- 主题牌桌玩家在活动后 7/14 天的再次参与，以及其是否回流普通构筑对局。

试验前必须冻结“继续 / 调整 / 停止”的判断口径，包括组合最小完成样本、胜率容忍范围、完成/异常处理下限、可接受等待时间，以及同星期相邻时段的基线与净新增计算方法。至少要求活动没有显著拉低同窗口的公共牌桌完成率或使整体等待时间失去可接受性，并以实际卡组多样性、人均对局和重复参与提升，而非仅将原有休闲对局搬入新入口，作为继续的依据。若样本显示个别体系在所有模式中长期显著压制其他体系，应另行评估竞技环境、卡效正确性和可能的禁限用制度；轮换主题牌桌不掩盖该判断。

### 以后再评估

只有排位 Beta 有稳定参与后，再考虑全天开放、可见段位、纪念奖励、更细的匹配策略或 Glicko-2。

## 4. 排位上线要求

- 排位对局必须绑定赛季、规则环境和 rating 算法版本；
- 只有赛季有效、当前处于开放窗口且候场准入为 `OPEN` 时才能创建新排位票据；
- 结果只能来自服务端封存的权威对局；
- 同一对局重试时不能重复加减分；
- 双方同意开启 `FREE` 后仍正常计分，单方不能开启；
- 模式请求、同意/拒绝、切换和恢复 `RULES` 具备可审计记录；
- 正式对局开始后不能通过双方协商整局重开来逃避当前计分结果；
- 正常失败、主动认输和断线逾期弃权按相同公式结算；
- 退出或短暂断线不能立即终止或作废对局；
- 只有权威状态不可恢复或可审计的平台故障可以使整局不计分；
- 管理员能够暂停新排位；
- rating 流水可以审计和重建；
- 赛季结束不能把进行中的对局切换到新赛季。

## 5. 首版明确不做

- 多个排位队列或地区分池；
- 默认全天开放的常驻排位；
- 任何基于 rating、上一位对手或其他偏好的跳过、重排和等待扩圈；
- 隐藏 MMR 与可见段位分双轨；
- 晋级赛、保级赛、连胜加倍或活跃度加分；
- 按卡组强度匹配；
- 高价值奖励；
- 玩家信用分或互评；
- 为排位另建牌桌和规则流程；
- 因每次公告或卡牌数据更新自动重置赛季。

## 6. 当前下一步

1. 在预发布数据库 dry-run 单一 `0010_add_ranked_system.sql`，验证备份、停写、迁移、约束和回滚边界；
2. 用管理员页面完整演练草稿、激活、候场开关、自动收口、异常更正和封存；
3. 补充告警渠道及候场、确认、开局、完成、结算延迟、断线弃权、`FREE` 与平台无结果指标面板；同时设计并验证可审计的卡组体系/核心组件标签和镜像率、体系占比、主要对局组合与先后手差异聚合，不把精确卡组内容 hash 误作体系统计；
4. 在真实数据产生前冻结首季 4～6 周周期、固定开放时段和“继续 / 调整 / 暂停”判断口径；
5. 经单独发布授权后执行生产迁移和部署，再创建首个赛季草稿；不要由迁移自动开放候场；
6. 通过管理员公告开启小规模排位 Beta，并同步观察休闲公共牌桌的等待与完成变化；
7. 根据真实参与、重复游玩、结果可信度、卡组多样性和用户反馈决定第二季是否扩大开放时段，并复核 RD 增长与软重置参数；
8. 主题桌的独立队列、冻结分配、管理员编排/停用、开局前无过错回队、基础漏斗与实际选用统计已落地；下一步在排位和公共牌桌指标稳定后，先补进行中房间恢复、完整组合指标/告警与双浏览器验收，再使用真实试打并冻结的预组卡组池和短时段运行一次非计分试验；比较其对整体等待、完成、体系多样性、人均对局与后续复玩的净影响，并核验组合公平性、锁定可审计性与实际选用分布，再决定是否投入常驻化。

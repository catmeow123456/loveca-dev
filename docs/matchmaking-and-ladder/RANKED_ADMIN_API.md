# 赛季排位管理员 API

> 文档类型：专题说明
> 适用范围：赛季排位管理员 HTTP 契约、权限边界与管理页面职责
> 当前状态：赛季/对局管理、运营概览、卡组分类统计、完整参赛者查询和 V3/V4 参数修订全量回算已实现；当前赛季使用 V3；V4 为新赛季默认
> 最后更新：2026-08-29

## 1. 边界

管理员接口统一挂载在 `/api/admin/ranked`，整组路由要求已登录且当前数据库角色拥有
`season.ranked.manage`；`season_admin` 与 `admin` 均可拥有该权限，降权后的旧 token 会被拒绝。
本批只提供赛季运营、异常结算和基础监控能力，不提供玩家排位入口，
也不允许管理员直接写玩家 rating、RD、场次或排行榜名次。

当前服务端注册表包含影子候选 `GLICKO1_PER_MATCH_SHADOW_V2`、历史正式 V1–V3 和新赛季默认 V4。V1–V3 继续冻结；V4 使用 `1500 / RD 300 / ratingScale 800 / minimumRD 100 / 5 场定级`，并在双方定级后叠加 1800 中心成长池。创建、编辑和激活
持久赛季只能引用正式版本。正式算法仍必须通过代码审查显式加入注册表，普通草稿创建/编辑请求不能上传完整评分参数；该边界唯一开放的赛季级评分参数是软重置策略。默认
`RESET_TO_INITIAL` 使用所选正式算法的初始积分/RD；管理员可在草稿期选择
`RETAIN_TOWARD_CENTER` 并配置中心值、原积分保留比例和重置后最小 RD。
这些参数写入 `ratingConfig`、参与竞技环境哈希并在激活后冻结。若运营在赛季内调整评分参数，必须使用独立的“预览→维护期全量回算”契约；服务端会创建新不可变修订身份，不覆盖 V3/V4 正式配置。

赛季另存 `leaderboardMinimumMatchCount`。V1–V3 仍允许 1–100 并可在普通运营边界修改；正式 V4 创建页默认并锁定为 5，服务端拒绝草稿、激活或普通进行中编辑的不一致值。它不参与单局积分数学，V4 将其锁定是为了让定级完成和进入排行榜使用同一语义；受保护的参数修订若改变 `placementMatchCount`，则会在全量回算事务中同步更新参榜门槛。

## 2. 接口

| 方法     | 路径                                          | 用途                                              |
| -------- | --------------------------------------------- | ------------------------------------------------- |
| `GET`    | `/environment`                                | 查看当前卡牌目录、Shadow/正式算法及其竞技环境身份 |
| `GET`    | `/seasons`                                    | 查看赛季列表及当前开放窗口、有效候场状态          |
| `GET`    | `/seasons/:seasonId`                          | 查看冻结环境与当前部署环境差异                    |
| `POST`   | `/seasons`                                    | 使用服务端正式算法创建 `DRAFT + PAUSED` 赛季      |
| `PUT`    | `/seasons/:seasonId/draft`                    | 全量编辑草稿并重新冻结当前环境                    |
| `DELETE` | `/seasons/:seasonId`                          | 永久删除未开始且没有任何排位关联数据的草稿        |
| `PUT`    | `/seasons/:seasonId/operations`               | 修改进行中赛季的名称、公告、开放窗口和参榜门槛    |
| `POST`   | `/seasons/:seasonId/activate`                 | 校验当前部署环境后进入 `ACTIVE + PAUSED`          |
| `PUT`    | `/seasons/:seasonId/admission`                | 在 `ACTIVE` 中切换 `OPEN / PAUSED`                |
| `POST`   | `/seasons/:seasonId/finalize`                 | 结束赛季，进入 `FINALIZING` 并停止新匹配          |
| `POST`   | `/seasons/:seasonId/close`                    | 无待计分对局和未开局预留时完成赛季结算            |
| `GET`    | `/seasons/:seasonId/rating-revisions`         | 读取历次不可变评分参数修订与当前版本              |
| `POST`   | `/seasons/:seasonId/rating-revisions/preview` | 只读回放新参数对全赛季积分、名次和单局差异的影响  |
| `POST`   | `/seasons/:seasonId/rating-revisions/apply`   | 在暂停且无 blocker 时原子应用已签名预览的全量回算 |
| `GET`    | `/overview?seasonId=<uuid>`                   | 查看指定赛季运行健康、经营统计及玩家分布          |
| `GET`    | `/deck-statistics?seasonId=<uuid>`            | 查看当前分类发布下的卡组使用、胜率及玩家明细      |
| `GET`    | `/players?seasonId=<uuid>`                    | 分页查看该赛季全部已有有效计分记录的参赛者        |
| `GET`    | `/players/search`                             | 按赛季搜索已有有效计分记录的玩家                  |
| `GET`    | `/players/:userId/context`                    | 查看玩家评分、进度及带胜负/最常用卡组的榜单上下文 |
| `GET`    | `/matches`                                    | 分页查看排位对局并按赛季、结算状态或用户搜索      |
| `GET`    | `/matches/:matchId`                           | 查看对局评分事件及双方长期主卡组                  |
| `POST`   | `/matches/:matchId/settle`                    | 幂等重试权威结果结算                              |
| `POST`   | `/matches/:matchId/corrections/preview`       | 只读回放 `VOID / REPLACEMENT` 的全赛季影响        |
| `POST`   | `/matches/:matchId/corrections`               | 追加并执行已经预览的更正                          |
| `GET`    | `/monitoring/summary`                         | 汇总各结算状态数量及最早结束时间                  |

赛季的 `queueAdmission=OPEN` 表示运营允许候场，不表示此刻一定可以入队。玩家侧
最终准入必须同时满足：

```text
lifecycle == ACTIVE
&& queueAdmission == OPEN
&& now 位于赛季起止时间和每周开放窗口内
```

因此管理员可以在开放窗口开始前恢复 `OPEN`，无需卡点操作；窗口外的有效准入仍
为关闭。

删除赛季只接受仍为 `DRAFT + PAUSED`、`ledgerRevision=0` 且不存在候场票据、配对预留、
对局、卡组观察、积分投影/流水/修订、软重置种子或徽章引用的空草稿。删除与开始赛季在同一
可串行化事务边界锁定赛季行；已经开始或出现任何关联事实后都返回冲突，不使用外键级联清理
历史数据。成功删除会写入带赛季标识、名称和管理员身份的结构化审计日志。

`GET /matches` 接受可选的 `seasonId`、`ratingStatus`、`userQuery`、`limit` 和
`offset`。`userQuery` 匹配双方的用户名、显示名称或用户 ID；响应中的 `data` 是当前
页，`total` 是应用相同筛选后的总数，供管理页面计算分页。已结算对局同时返回当前
评分流水投影下双方的单局加减分；待结算与已作废对局返回空值，不把旧流水或尚未发生的
变化误显示为 0。

`GET /matches/:matchId` 在对局基本信息和评分事件外，返回 `decks`：只从
`ranked_deck_observations` 读取双方长期保存的主卡组观察，并可附带卡组快照中保留的
卡组名称。同基础卡号的罕度和异画已合并；能量卡组与逐张实例不属于长期记录。功能上线前
或尚未完成历史回填的对局可返回空数组，管理页应明确显示记录缺失。

`GET /overview` 必须显式指定赛季。运行健康统计候场票据、活动匹配预留、进行中对局、
已结束但尚未完成计分的对局和其最早结束时间；进行中与待计分两项互不重叠。经营统计包含总参赛人数、完成定级人数、进入排行榜
人数、有效对局、今日/近 7 日对局、近 7 日活跃玩家、人均场次和排行榜最低分。参赛者
以当前有效评分流水中的 `ratedMatchCount > 0` 为准；完成定级使用算法冻结配置中的
`placementMatchCount`，参榜使用赛季 `leaderboardMinimumMatchCount`。今日按赛季平台
时区自然日计算，近 7 日按接口生成时刻向前滚动 7×24 小时。场次分布固定为
`1–4 / 5–9 / 10–19 / 20–39 / 40+`，积分分布使用 100 分区间；这些读取不修改赛季、
候场或评分状态。

`GET /deck-statistics` 必须显式指定赛季，只读取唯一 `ACTIVE` 分类发布和当前最终排位
投影。可分析对局必须为最终 `SETTLED`，双方长期卡组观察完整，且双方在该发布下都具有
`CLASSIFIED / UNKNOWN / AMBIGUOUS` assignment；任一方尚未分类、`INVALID` 或 `EXCLUDED`
都会让整场对局退出胜率样本，但仍在覆盖信息中如实反映。读取不扫描追加式评分事件：
`VOID` 后的对局自然移出样本，`REPLACEMENT` 按当前胜方重算，不重复累计历史结果。

该接口中的“使用场次”是卡组席位使用次数，不是去重后的对局数。镜像对局会为同一分类
贡献 2 次使用、1 胜和 1 负；分类胜率与嵌套玩家胜率均按 `胜场 / 使用次数` 计算。响应以
`available / release / sample / categories` 表达可用状态、当前发布、样本覆盖和分类结果；
`sample` 区分已结算、双方观察完整、最终可分析的对局数，以及观察、assignment、识别、非法、
排除的席位数与两级覆盖率。分类行返回 `appearanceCount`、`winnerCount`、`lossCount`、
`winRate` 与 `playerCount`，并嵌套采用相同场次与胜负字段的完整玩家明细。
正式分类即使零使用也会返回；`其他／未识别` 与 `分类冲突／待复核` 仅在有样本时返回。
分类按使用次数降序和发布顺序稳定排列，玩家按使用次数、胜场、用户名和用户 ID 稳定排列。
这是管理员运营统计，不受玩家端卡组环境展示内容或隐藏开关影响；无 `ACTIVE` 发布时返回无发布
状态：`available=false`、`release=null`、`categories=[]`，样本仅保留已结算对局数，不回退到
草稿或已退役版本。

`GET /players` 必须显式提供 `seasonId`，接受可选 `q`、`limit` 和 `offset`；`limit` 默认
50、范围 1–100，`offset` 必须为非负整数。范围固定为该赛季 `ratedMatchCount > 0` 的全部
参赛者：先返回满足参榜门槛的玩家，使用公开榜一致的 `rating DESC, userId ASC` 排序和真实
全局名次；未达参榜门槛者排在其后、名次为 `null`，但仍返回定级/参榜状态、rating、RD、
有效计分场数、胜负及当前 `ACTIVE` 发布口径下的最常用卡组分类。最常用分类保留并列、覆盖不全、
无发布和无样本等结构化状态，不任意选择并列项。每个玩家项还返回 1-based `listPosition`，
表示他在“参榜玩家在前、未参榜参赛者在后”完整列表中的全局位置；该字段不改变 `rank`
的语义，后者仅表示真实公开榜名次，未参榜者仍为 `null`。

搜索在完整列表的 `rank` 和 `listPosition` 生成后执行，匹配用户名、显示名称或用户 ID，因此筛选结果仍
保留玩家的真实全局名次和列表位置；`% / _` 按普通字符处理。响应同时返回规范化后的 `query`、筛选后的
`total`、当前页
`players`、`ledgerRevision`、`placementRequired`、`leaderboardMinimumMatchCount` 和当前
`classificationRelease`。管理页面追加分页时必须比较这些快照字段；
若活动赛季已变化，则丢弃本页并从第一页重新加载，不能把两个流水或分类版本拼接成一张表。
现有 `/players/search` 与 `/players/:userId/context` 继续保留兼容既有只读调用，但不再是概览页
的主要浏览路径。

`GET /players/search` 必须显式提供 `seasonId` 和非空 `q`，`limit` 最大为 10。搜索只覆盖
该赛季 `ratedMatchCount > 0` 的评分投影，可匹配用户名、显示名称或用户 ID，并把 `% / _`
按普通字符处理，不能借通配符空查枚举全体账号。响应只返回用户 ID、用户名和显示名称，
不返回邮箱、卡组、战绩或其他账号资料。

`GET /players/:userId/context` 必须显式提供 `seasonId`。服务端以单条数据库语句读取赛季
冻结配置、`ledgerRevision`、目标玩家评分投影和榜单窗口，返回 rating、RD、有效计分场数、
`placementRequired`、`leaderboardMinimumMatchCount`、定级完成与参榜资格两个独立布尔值，
以及接口生成时间。玩家满足参榜门槛时，再按玩家端相同的
`rating DESC, userId ASC` 稳定顺序返回目标名次和上下各最多 3 名；榜首或榜尾不补齐。返回的每一行都包含胜场、负场和当前 `ACTIVE` 分类口径下的最常用卡组分类及覆盖状态。
V1–V3 的两个门槛可以独立配置，因此仍在定级的玩家若已经满足较低的参榜门槛，也必须
返回真实公开名次；状态标签不能替代这两个独立判断。该接口是管理员只读查询，不提供
批量导出，也不能直接改写任何 rating、RD、场次或名次。

草稿创建/编辑请求中的软重置配置形态为：

```json
{
  "softReset": {
    "mode": "RESET_TO_INITIAL",
    "center": 1500,
    "retention": 0.5,
    "minimumDeviation": 200
  }
}
```

`RESET_TO_INITIAL` 不读取公式参数，直接使用所选正式算法的初始积分和初始 RD；
字段仍完整保存，便于管理员切换到 `RETAIN_TOWARD_CENTER`。保留模式按
`center + retention × (旧积分 - center)` 计算新积分，并把 RD 提升到至少
`minimumDeviation`、同时限制在算法允许范围内。服务端拒绝超出正式算法边界的参数。

## 3. 更正安全契约

更正分为两个明确步骤：

1. 预览接口读取当前 `ledgerRevision`，构造未落库的 `VOID` 或
   `REPLACEMENT`，确定性重放整个赛季，并返回受影响玩家的 rating、RD、场次差异、
   当前目标事件和服务端签名的预览令牌。
2. 执行接口必须携带预览返回的 `currentLedgerRevision` 作为
   `expectedLedgerRevision`，同时原样提交 `expectedTargetEventId`、`previewToken`、
   动作、替代胜方、替代结果类型，并提供原因和稳定幂等键。

若预览后有任何新结算或其他更正推进了流水版本，执行会返回
`RANKED_CORRECTION_PREVIEW_STALE`，要求管理员重新预览；目标事件、动作、胜方或结果
类型与签名预览不一致时同样拒绝执行。相同幂等键的成功请求可安全重试；若同一幂等键
被用于不同对局、动作、胜方、结果类型或原因，服务端返回冲突。执行仍只追加
`VOID / REPLACEMENT` 事件并重建派生投影，不修改或删除历史流水。

赛季状态变化、候场开关、结算重试和更正执行都会写结构化
`ranked_admin` 应用日志；评分更正还在不可变事件中保存管理员、原因和幂等键。

进行中赛季的运营编辑使用独立白名单接口，只接受
`name / announcement / openWindows / leaderboardMinimumMatchCount`。`announcement`
是可留空、最多 2000 字的纯文本，换行原样展示，不接受富文本。赛季标识、平台时区、起止
时间、最晚结算时间、规则、卡池、卡组政策、算法和竞技环境均不进入该请求，也不会被
对应 SQL 更新。`FINALIZING / CLOSED` 赛季不再接受此类修改。

## 4. 管理页面

管理员首页提供“赛季排位管理”入口。页面保留三个一级区域：

- “概览”：按赛季展示实际匹配状态、候场/预留/进行中/待计分健康信息、核心经营统计，
  以及玩家场次数和积分分布；经营数据后提供卡组分类统计，摘要展示分类的使用场次、玩家数、
  胜负、胜率与最常使用者（最高次数并列时如实展示），默认只展示使用场次最高的 3 类，可按
  分类名称、分组或分类键搜索，也可展开全部；
  每个分类展开后查看完整玩家使用明细。下方全部参赛者表默认收起且不发起玩家列表请求；直接
  展开时读取前 50 人，搜索则作为定位器使用：唯一或精确匹配时读取目标上下各 3 人组成的 7 人
  窗口，将目标置于第 4 行并高亮，靠近榜首或榜尾时自然缩短一侧。模糊搜索命中多人时先展示
  候选，选定后再定位；定位完成后仍可继续加载更高或更低名次，清空搜索恢复完整列表；运行异常时
  直接提示最老待计分时间；
- “赛季”：创建、编辑或经二次确认永久删除空的未开始赛季，开始赛季、修改开放中赛季的名称、公告、开放时段与参榜
  场次门槛、开放/暂停匹配、结束赛季和完成结算；草稿和进行中赛季均可新增、修改或删除多个互不重叠的独立开放时段；进行中 V3/V4 赛季另有“调整积分参数”高风险工具，可编辑受限参数、查看新旧玩家/名次/单局差异、复用历史参数，并仅在安全校验通过后确认应用；V4 工具另提供成长补偿启用开关、基准分、最大单局注入/回收总分、高分局胜方回收比例，以及高级选项中的过渡宽度；
- 每个开放时段都允许以“次日”语义跨越午夜；提交时分别拆为当日至 `24:00` 与次日从 `00:00` 开始的合法 `openWindows`，并在保存前检查拆分后的窗口数量和重叠。回显时会在多个独立时段中逐对合并可无损还原的规范跨日窗口，其余底层窗口仍逐项可编辑；
- “对局处理”：默认分页查看全部赛季的排位对局，也可按赛季、计分状态筛选或按用户名、
  显示名称、用户 ID 搜索；列表直接显示双方胜负、双方加减分、胜方和结果类型，并可按需展开
  双方长期保存的主卡组。等待计分
  对局可重试计分，已结算对局可预览后执行不计分/改判。

普通赛季表单不直接展示完整算法参数或环境哈希；草稿和进行中表单可编辑受限长度的纯文本公告，
草稿表单另展示允许配置的软重置策略及其参数，这些审计详情仍由 API 和日志完整提供。概览切换
赛季或搜索条件时必须清空旧页并忽略迟到请求，卡组统计与参赛者列表使用独立加载、错误和空状态。

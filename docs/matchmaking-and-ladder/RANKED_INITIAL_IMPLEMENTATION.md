# 赛季排位首版当前状态与上线边界

> 文档类型：专题说明
> 适用范围：赛季排位首版玩家、匹配、结算、管理能力与上线边界
> 当前状态：V1 赛季已开放并使用 V3；V4 已实现且只供未来新赛季使用；管理员分类统计、完整参赛者浏览与定位、卡牌环境三 TAB 及活动徽章增量已实现并通过开发验收，尚待生产迁移与发布验收
> 最后更新：2026-08-30

## 1. 玩家闭环

玩家从首页进入“赛季排位”后可以：

- 查看当前或历史公开赛季；
- 查看开放状态、当前窗口结束或下次开放时间；
- 首场结算后查看积分和本局积分变化，达到赛季门槛后再显示排名；
- 选择合法云端卡组并加入独立排位候场；
- 跨页面维持候场、确认配对并自动进入现有正式联机房间；
- 在赛季页、候场状态和排位房间内随时查看赛季公告；
- 在对局只等待本人或对手推进且进入最后 1 分钟时看到操作超时提示；
- 查看最近排位对局和达到参榜场次门槛的排行榜；
- 查看当前或历史赛季的卡牌使用率 Top 30，以及有效样本量和数据覆盖率；本次规划将该板块升级为“使用占比 / 胜者构成 / 高排名玩家”三个 TAB，使用占比与胜者构成可分别按卡牌板块自身设置展示玩家等权、对局等权或两者；
- 按卡组环境自身的运营设置查看玩家等权、对局等权或两者并列的卡组使用占比与胜者构成饼图、高排名玩家构成，并查看胜率和非镜像胜率；卡组与卡牌的展示内容/基础计权互不影响，只共享高排名玩家人数 N，而卡牌统计不要求已发布卡组分类；
- 在已配置活动徽章的赛季达到 3 场有效计分对局后获得该赛季纪念徽章，并在个人中心查看。

页面只突出赛季状态、当前积分、参榜进度、卡组和一个主要操作。没有数据时不渲染空
排行榜。对局桌面继续复用现有 `GameBoard`，不持续强调双方排名。

玩家 API：

| 方法   | 路径                            | 用途                                                                 |
| ------ | ------------------------------- | -------------------------------------------------------------------- |
| `GET`  | `/api/ranked/seasons`           | 读取可见赛季                                                         |
| `GET`  | `/api/ranked/overview`          | 读取赛季、个人、候场、最近对局和排行榜                               |
| `GET`  | `/api/ranked/environment`       | 按 `seasonId` 读取卡牌使用占比、胜者构成、高排名玩家榜单与样本覆盖率 |
| `GET`  | `/api/ranked/environment/decks` | 按 `seasonId` 读取已发布的卡组分类环境                               |
| `POST` | `/api/ranked/queue/join`        | 以合法云端卡组加入排位候场                                           |
| `POST` | `/api/ranked/queue/heartbeat`   | 维持票据并读取最新状态                                               |
| `POST` | `/api/ranked/queue/confirm`     | 确认配对                                                             |
| `POST` | `/api/ranked/queue/cancel`      | 取消候场或放弃尚未开局的配对                                         |

排位纪念徽章不作为排行榜字段暴露；登录玩家通过 `GET /api/player-badges/me` 只读取自己的徽章，不提供查看其他玩家徽章的接口。赛季管理员通过受权限保护的活动徽章管理接口为具体赛季上传或替换图片，玩家不能写入徽章配置或授予记录。

## 2. 赛季与匹配

- 未来新赛季默认使用 `GLICKO1_PER_MATCH_V4`：初始 `1500 / RD 300`、`ratingScale=800`、最低 `RD 100`、5 场定级；双方均完成定级后，再叠加以双方赛前平均 1800 分为中心的平滑成长池。V4 的排行榜门槛固定与定级一致为 5 场。完整公式与分配规则见 [V4 评分设计](RANKED_V4_RATING_DESIGN.md)。V1–V3 配置继续冻结，用于旧赛季和流水重建。
- 新赛季软重置默认把回归玩家重置为该赛季的初始积分和初始 RD。草稿赛季可改为
  “向中心值保留”并配置中心值、原积分保留比例和重置后最小 RD；策略与参数随
  `rating_config` 冻结并参与竞技环境哈希，赛季激活后不可修改。
- 排位票据必须绑定 `seasonId + competitiveEnvironmentId`。
- 配对只在同一排位赛季和环境内按 `joinedAt + ticketId` 做稳定 FIFO。
- 排位和休闲公共牌桌共享底层状态机，但使用独立 `queueKind` 和跨模式玩家占用。
- 开放窗口结束或候场暂停后停止新票据并结束仍在等待的排位票据；已经形成的配对和
  已开局对局继续处理。
- 双方确认后的房间创建使用带代际校验的短租约；进程内开局按房间代际去重，租约过期
  后由清理任务有限重试，重试耗尽时无过错恢复仍活跃的候场票据。
- 排位房间来源固定为 `RANKED`，正式对局创建后依次绑定预留、赛季、玩家占用和双方
  票据；任一步失败都会补偿已完成步骤并删除刚创建的运行态对局。补偿无法完整完成时
  隔离该房间，阻止重复创建未计分的“伪排位”。
- 排位正式开局后拒绝整局重开。

## 3. 结算与运行时

- 权威记录完整封存后自动结算；失败保持 `PENDING`，运行时任务继续幂等重试。
- 正常终局、主动认输和断线弃权使用同一评分公式。排位对局重连期限取开局时冻结的
  平台配置，当前默认 1 分钟；仅一方超过期限时，该方判负。
- 断线判负先以 `PENDING` 状态和在线代际取得持久裁定权，再执行服务端权威认输命令；
  玩家在裁定等待窗口内恢复活动或命令失败时撤销临时标记并重试。
- 双方都超过期限且最后在线时间相差不超过 5 秒时，不判负、不计算胜者，记为
  `VOIDED / PLATFORM_NO_CONTEST`，不计入积分并保留结构化日志。
- 双方都超过期限且最后在线时间相差超过 5 秒时，最后在线时间较早的一方判负。
- 本局冻结的重连时限是权威裁定期限，不沿用休闲房间“双方离线后静默销毁对局”的语义。
  这三种断线裁定固定展示在赛季公告中；候场状态和局内房间菜单均可再次打开公告。
- 当权威状态明确只等待一名玩家推进时，该责任玩家超过本局冻结的平台操作时限仍没有
  成功游戏命令将因操作超时判负，当前默认时限为 3 分钟。轮询、被拒命令、聊天、观战和对手操作都不复位；双方同时可操作、系统自动
  推进以及任一参与者都可安全推进的公开展示不启动单方计时。
- 操作超时使用进程内截止时间和等待代际，不进入 `GameState`、checkpoint 或回放。清理任务
  取得排位持久裁定权后必须再次核对等待键、责任玩家、代际与截止时间，避免数据库等待期间
  已完成操作的玩家被旧窗口误判。进程恢复缺少计时运行态时，从恢复时刻重新给予完整期限。
- 玩家快照只投影责任席位、绝对截止时间和终局判负原因，不包含待决窗口的隐藏内容；共享
  对局桌面在最后 1 分钟显示非阻塞倒计时，终局明确区分主动认输、断线超时和操作超时。
- 对局时间线出现双方同意进入 `FREE` 的记录时，结算写入 `usedFree=true`；结果仍正常
  计分。
- 计划结束后赛季自动进入 `FINALIZING + PAUSED`；运行时任务先分批排空已经完整封存
  的可靠结果。到达最长收口期限后，只把仍无法形成可靠结果的 `PENDING` 对局转为
  平台无结果；仍在内存运行的对局必须先终止权威运行态，不能只改数据库状态。
- 进入 `FINALIZING` 前已经形成的配对允许继续确认和开局；这类尚未开局的预留消化完
  之前不能封存赛季，正式开局后由 `PENDING` 对局收口规则接管。
- 新赛季激活时，从最近封存赛季按冻结配置生成软重置种子；所有迟到结算和更正重建
  都从同一组种子开始。
- 每个排位赛季最多由一条持久徽章规则显式绑定。管理员首次上传图片时建立固定 3 场门槛
  并在同一事务补发已达标玩家；此后评分结算在更新赛季 ledger revision 后，以同一事务
  检查玩家当前有效计分场次。授予记录固定第 3 场有效对局、当时场次数和 revision；迟到
  结果或更正重建可以补发，图片替换不重复授予，已经授予的纪念徽章不会因后续 `VOID`
  自动撤回。首届既有规则通过停机迁移接入同一模型。

## 4. 管理闭环

管理员页面包含“概览”“赛季”和“对局处理”三个一级区域：

- 按赛季查看匹配开放状态、候场票据、活动预留、进行中对局、待计分积压和最老待计分时间；
- 查看总参赛、完成定级、进入排行榜、有效对局、今日/近 7 日对局、近 7 日活跃玩家、人均场次和排行榜最低分，并查看玩家场次数与积分分布；
- 查看当前 `ACTIVE` 发布下的卡组分类运营统计；严格样本按卡组席位聚合使用场次、玩家数、胜负与胜率，镜像对局贡献 2 次使用、1 胜和 1 负，分类可展开完整玩家使用明细，`INVALID / EXCLUDED` 与观察不完整只进入覆盖说明；
- 默认收起全部参赛玩家列表，并分页读取本赛季全部 `ratedMatchCount > 0` 的玩家；参榜玩家沿用公开榜名次，未参榜玩家置后且名次为空，每行展示评分、RD、场数、胜负、状态和当前发布下的最常用分类；
- 按用户名、显示名称或用户 ID 定位参赛者；精确匹配优先于最多 10 个模糊候选，定位后以目标上下各最多 3 人组成初始窗口并高亮目标，随后可继续加载更高或更低名次；分页拼接前校验 ledger revision、定级/参榜门槛和分类版本，快照变化时从当前定位或首屏重新读取；
- 旧单玩家搜索与上下各最多 3 名上下文接口继续保留兼容，但不再作为管理页纵览赛季玩家的主要路径；完整参赛者浏览不枚举零计分账号、不提供全体账号批量导出，也不允许覆写评分、场次或名次；
- 创建/编辑赛季草稿；
- 配置进入排行榜所需场次；
- 按赛季预览玩家实际会看到的赛季公告，核对积分、排行榜与断线裁定文案；
- 为任一赛季上传或替换纪念徽章，并在首次配置时补发已经达到 3 场门槛的玩家；
- 开始赛季；
- 修改进行中赛季的名称、纯文本公告、开放日、每日开放时段和参榜场次门槛；
- 开放或暂停匹配；
- 对进行中的 V3/V4 赛季预览受限积分参数变更，并在维护条件满足后执行全赛季回算或恢复历史参数；
- 结束赛季，并在所有对局计分后完成结算；
- 分页查看全部赛季的待结算与已结算对局，按赛季、计分状态筛选或按用户搜索，并直接核对双方胜负、加减分、胜方与结果类型；对局可按需展开双方长期保存的主卡组，早期缺失观察的历史对局显示明确缺失状态；
- 重试待结算对局；
- 预览并执行 `VOID / REPLACEMENT`，使用流水 revision、目标事件和签名预览令牌防止
  陈旧或被改写的预览落库；替代结算同时保留明确的结果类型。

参榜门槛只影响排行榜资格，不参与积分计算；V1–V3 赛季仍可通过普通运营编辑立即调整。正式 V4 新赛季默认并锁定为 5 场，普通运营编辑不能让“定级完成”和“允许参榜”分叉；若确需改变 V3/V4 的定级/参榜场次或其他评分参数，必须使用独立的签名预览与全赛季回算流程，并生成新的不可变修订身份。赛季时间等普通冻结字段仍不可经该流程修改。完整审计信息保留在 API、修订表和日志中。

## 5. 数据库迁移

排位基线由 `0010_add_ranked_system.sql` 提供；评分参数修订审计表和当前修订引用由 `0017_add_ranked_rating_revisions.sql` 提供；可编辑赛季公告字段由 `0018_add_ranked_season_announcement.sql` 提供；玩家徽章规则与授予记录由 `0019_add_player_badges.sql` 提供，`0035_add_activity_badges.sql` 再扩展为排位／娱乐模式统一活动来源、图片 revision 与幂等审计；长期卡组观察事实由 `0020_add_ranked_deck_observations.sql` 提供；卡组分类发布、assignment 与环境展示设置由 `0032_add_deck_classifier.sql` 提供。目标设置模型在同一单例中分别保存卡组/卡牌的展示内容和基础计权，仅共享高排名玩家人数 N。结构迁移不会自动认定首届赛季、上传旧静态徽章素材或回填历史卡组观察；必须在停写、备份和 dry-run 审核后执行对应的显式数据／对象迁移。执行与回滚边界见 `drizzle/migration-notes/ranked-rating-revisions.md`、`drizzle/migration-notes/ranked-season-announcement.md`、`drizzle/migration-notes/player-badges.md`、`drizzle/migration-notes/activity-badges.md` 和 `drizzle/migration-notes/ranked-season-environment.md`。

管理员完整参赛者浏览与分类运营统计直接复用 `0010` 已有的赛季、用户资料、当前评分投影与有效排位对局，并联合 `0020` 长期观察及当前 `ACTIVE` 分类 assignment 在 API 读路径派生胜负、最常用分类、分类胜率和玩家明细；不新增胜负/最常用/分类统计表或投影字段，也不持久化查询结果。

迁移不会创建赛季、不会回填旧公共牌桌积分，也不会自动开放玩家候场。`0010` 首季排位基线 schema 已在生产落地，且生产迁移历史已确认完成至 `0016`；`0017–0020` 与卡组分类增量尚未在生产执行，必须按各自迁移说明与第 6 节待办另行上线。`0010` 的原始执行与校验步骤见 `drizzle/migration-notes/ranked-system.md`。

首个赛季从 V2 迁移到 V3 的工具和步骤保留在 `RANKED_V3_ACTIVE_SEASON_MIGRATION.md`，仅用于历史审计和重现，不适用于 V4 或新的参数修订流程。

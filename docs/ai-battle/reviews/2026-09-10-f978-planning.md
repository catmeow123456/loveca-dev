## 实验版本边界

1. 共享 workflow 注册当前能力费用、支付自送后的目标与去向；AI adapter 只映射当前玩家可见对象。三族覆盖自送回手、付能回手、原槽登场。自送费用描述与真实 trigger-safe 支付共用同一入口；姬芽的同伴条件与回收 selector 从实际 resolver 复用。没有在 AI 层添加卡号规则或试执行候选。
2. 输入提供有限的登场条件收益、静态舞台逐色/总 HEART 与 BLADE 小计，以及可见 LIVE 候选和手牌对当前舞台的基础需求缺口。缺口复用共享判心规则，未计入其他 LIVE、玩家级修正、未知声援或完整连锁效果。
3. 运行时保留本回合最近 4 个已接受的策略选择、最近实际动作与前后资源。过去的 `modelIntent` 明确只是意图；失败和过期选择不写入。私密检视得到的已知顶牌只通过此前合法可见正面与公开移动位置记住；牌库移动、洗切、刷新、事件缺口/回退均清除，不利用隐藏实例 ID 跟踪牌序。
4. HTTP 输入无损去重完全相同的牌面与重复长卡文，保留候选、实例、所有数值和完整文本；有效值不同的同名/同号卡不会合并。原日志五份输入单独应用去重后，JSON 字节减少约 29%–38%，不是整份 HTTP 请求或 token 的缩减率。测试验证可无损还原，`SAMPLE` 与实际请求分别留存。
5. 教程、绿莲手册与控制提示要求比较完整能力路线、指定色和本轮 LIVE 收益；说明已知顶牌仍在牌库、设置后抽牌不能追加盖牌，以及保留能量需要具体用途。保留所有合法选择，没有强制花光能量。

实验未增加卡效完成范围。查询职责见[模块职责](../../card-effect-framework/module_boundaries.md#供动作选择读取的能力资源)。

## 最后版本 v4 的真实模型结果

使用专用 `qwen3.8-max`，`temperature=0.2`、`max_tokens=2048`、`enable_thinking=false`。这些是独立开发实验：固定局面只从原日志摘取己方手牌、休息室、顶层舞台、能量及对方公开舞台/成功区；不还原原局完整 checkpoint、成员下方堆叠、使用历史或隐藏牌序。卡牌事实来自现有冻结测试卡组，与原对局发布卡库来源不同。已知顶牌场景先脚本重做原捕获的选择，再请求模型，不把这段准备计为模型自主选择。

| 实验 | 最后版本实测结果 | 可以证明的范围 |
| --- | --- | --- |
| 111 / 149 / 151 / 已知顶牌，各 3 次 | 12/12 首次选择发动沙耶香，全部被接受 | 这些局面的首步不再直接空过 |
| 三个主要阶段连续执行 | 11 次模型选择；3 段均正常结束主要阶段 | 111、149 完成姬芽与「月夜见海月」路线；151 不虚构登场回收 |
| 自然绿莲镜像，AI 为 FIRST | T5 自然结束，AI 负；30 次模型、34 次机械接受 | 完整规则执行与当前策略的失败样本 |
| 自然绿莲镜像，AI 为 SECOND | T8 自然结束，AI 负；53 次模型、55 次机械接受 | 同上 |

两局使用正常 `GameSession`、AI runtime/client 和不同固定随机种子；对手是只读取自身可见输入的确定性测试策略，没有作者真人参与，也没有走 HTTP/数据库 recorder/页面链路。83 次整局模型调用全部 HTTP 200、`finish_reason=stop`，全部合法且被接受；无模型失败、兜底或人为终局。FIRST 等待中位数 2833.5ms、最大 3524ms；SECOND 中位数 2917ms、最大 26969ms。调用与其他实验并发，不能当成隔离性能基准。

仍存在明确的策略问题：

- 固定采样虽然首步正确，说明仍偶尔把姬芽数值记到费用 15「日野下花帆」上，把缺 5 绿说成缺 1 绿，或把尚在顶牌的 LIVE 当作本轮准备依据。连续实际执行后的三段说明有所改善，不代表这些错误已消失。
- FIRST 决定 81、113，以及 SECOND 决定 95、185，都曾以支付姬芽 LIVE 开始能力为由保留能量，实际舞台并没有姬芽。提供结构化事实与保留过去意图尚不能保证模型正确绑定能力来源。
- SECOND 决定 185 在对手已有两张成功 LIVE 的压力下，仍以“当前分数足够获胜”为由放弃加分路线；最终该局告负。单张基础需求达标不能证明赢得分数竞争，不能替代多 LIVE、条件加分和对手风险判断。

因此本次可以确认关键空过路线改善，不能宣布模型已达到合格真人对手的强度。下一轮策略验收应针对“能力来源绑定、手牌/顶牌时点、完整多 LIVE 分数与需求、保留费用的实际用途”，不再只统计首步是否发动能力。

## 1. 结论

这个想法可行，而且当前项目并不是从零开始。

现有系统已经具备 AI 对战最难替代的几块底层能力：服务端权威对局、语义化玩家命令、按座位生成的玩家视图、隐藏信息隔离、联机房间与命令管线、公共牌桌候场与配对、卡组快照、公共事件、对局记录和部分运行态恢复。面向模型的 Prompt 构造器、上下文管理器和策略模型应继续以对应座位的标准 `PlayerViewState` 为可见性来源，但不能直接序列化完整视图；必须经单一字段 allowlist 适配器生成版本化 `AiObservation`，只输出该座位依法可见的事实和脱敏决策契约。可信的服务端协调器和决策契约生成器可以读取权威状态以复用既有规则查询与校验。所有行动仍通过与真人相同的 `GameCommand` 入口进入权威校验。

形成初始分析时，距离“玩家能够稳定进入并完成一局 AI 对战”仍有中等偏大的工程距离；Phase 0～4 已按分层顺序补齐首版受控闭环。它并不是接入一次 LLM API、拼接一段 system prompt 就能完成的功能。下列清单保留初始分析时识别出的基础设施缺口，并显式标注当前状态：

- **已由 Phase 1A 解决**：初始版本没有面向机器决策的统一决策契约，权限投影不能完整表达可直接提交的具体动作、候选和约束。
- **已由 Phase 1B 解决（单实例范围）**：初始版本没有判断 AI 何时需要行动、取消过期思考和连续处理多步效果的调度能力。
- **已由 Phase 1B 解决（单实例范围）**：初始公开展示 deadline 主要由在线客户端定时请求推进，没有服务端 owner。
- **已由 Phase 1C 解决（认证卡组范围）**：初始版本没有只依赖合法决策契约、能够反复完成整局的随机合法机器人和 headless playout。
- **已由 Phase 1C 解决**：初始规则随机过程没有可注入测试源和完整事实带，无法仅靠机器人种子稳定复现整局失败。
- **已由 Phase 3/4 解决**：不可登录 AI 身份、精确专属卡组、Phase 2 策略版本以及模型/Prompt/provider/调用政策版本快照已进入正式 match runtime 与记录。
- **已由 Phase 2 解决（无 LLM 策略范围）**：初始版本缺少将压缩规则、固定卡组玩法、当前局面、合法决策和精选关键历史组合成稳定策略输入的对战上下文。
- **已由 Phase 4 解决**：provider-neutral request envelope、严格结构化返回、权威 contract 复验、有限 repair、服务端 LLM provider、超时、重试、取消、整局保守策略切换，以及成本、速率与并发治理均已落地。
- **当前最高优先级缺口**：Phase 4.5 已为主要阶段成员登场/换手、LIVE 设置、卡效来源/可选费用/目标选择补充语义后果，并加入完整卡组 system 知识、纯净精选历史和管理员实际请求上下文检查器；仍需覆盖更广卡效语义审计，完成真实 provider 新协议评测与真人抽样复盘。
- **独立入口已解决，公共补位仍缺少**：Phase 3 完成 SYSTEM 受控自动赛前和正式联机参与，Phase 4 增加登录玩家可用的独立入口；该赛前复用共享猜拳胜负规则，但不创建临时 `OnlineRoom` 或 presence。公共牌桌 AI 补位、presence 与多实例容量仍属于 Phase 5。
- **当前仍缺少**：进程重启后的进行中正式联机对局恢复闭环。
- **持续边界**：卡池自动裁判尚未完整覆盖；首版不需要追求全卡池，但进入 AI 对局的卡组必须在 `RULES` 中完成本局所需裁定，AI 不能依靠 Prompt 替规则引擎补做未实现卡效。

因此，当前适合先判断为：

- **技术可行性：高。**
- **直接把现有对墙打策略当成战术 AI 的可行性：低；复用其机械决策和自动推进能力的价值：中等。**
- **在少量专属、全自动化卡组上做受控 AI 对战的可行性：较高。**
- **立即开放任意卡组、AI 自动补位和长期稳定运行的可行性：不足。**

首版方向已经收缩为：

- 玩家和 AI 只使用 [`assets/decks/缪预组.yaml`](../../assets/decks/缪预组.yaml) 与 [`assets/decks/绿莲-6弹ver.yaml`](../../assets/decks/绿莲-6弹ver.yaml) 两套受控卡组；准入和认证绑定规范化卡组内容哈希，不只依赖文件名。
- 产品上提供独立 AI 对战入口，实现上复用正式联机的权威对局、玩家投影、命令、记录、聊天和共享桌面；参赛者从双 USER 收缩为 USER + SYSTEM。
- 决策契约只作为现有规则查询、pending / active effect 和命令校验的 typed read model，不建设新的通用卡效 DSL、AST 或步骤解释器。
- 模型负责战术选择；连续协议错误只让当前步骤使用保守选择，供应商超时、不可用或达到单局预算时，服务端通过 Phase 1B 已落地的专用 `SYSTEM_NOTICE` 聊天消息发送去重提示，并将本局切换到具备最小推进和有界活性政策的保守确定性策略。
- “保守操作”不等于永久空过：仍需按审查过的优先级执行最小推进、结束阶段、跳过低价值可选项、确认强制步骤或使用合法 witness，并在无进展达到阈值时安全终局。
- 正式 SYSTEM 席位已经通过无 LLM 整局回归与 Phase 4 真实模型/普通玩家入口验证；下一步先完成 Phase 4.5 的语言推理质量闭环，再进入 Phase 5 的公共牌桌补位和生产级多实例治理。

## 2. 需要先澄清的概念边界

### 2.1 AI 对战不等于现有对墙打

当前 `GameMode.SOLITAIRE` 的职责是让单人测试可以推进，而不是让对手进行战术决策。它会自动完成对手不换牌、跳过主阶段、跳过表演或确认结算等动作，也已经能通过通用 responder 处理一部分不需要卡牌策略知识的效果窗口：纯确认、可选操作默认不发动、强制单选、简单选项/槽位选择，以及受限的隐藏手牌单选或有序多选。遇到复合输入、数字输入、站位编排、特殊费用或其他复杂决策时仍会安全停止自动处理。

现有服务端对墙打虽然把系统对手显示为“对手 (AI)”，但该名称不代表它已经具备 AI 决策能力。相关事实位于：

- [`src/application/mode-automation.ts`](../../src/application/mode-automation.ts)
- [`src/server/services/solitaire-match-service.ts`](../../src/server/services/solitaire-match-service.ts)
- [`docs/battle-mode-purpose-and-boundaries.md`](../battle-mode-purpose-and-boundaries.md)

真正的 AI 对手应当像真人一样完成换牌、主阶段出牌、起动能力、LIVE 设置、同一时点效果顺序、目标选择、可选费用、成功 LIVE 选择等决策，而不是由 `SOLITAIRE` 策略替它跳过。现有 responder 不应整套升级成战术 AI，但其中的确认、默认跳过、盲选 token 和连续自动推进可以抽取为 AI 调度器中的确定性决策层。

在接入 LLM 前，还应先实现一个只消费统一合法决策契约的随机合法机器人。它不负责打得好，只负责在所有必要窗口中选出结构合法、仍然有效的动作，并反复完成整局。这个机器人既是最早可用的非真人参赛者，也是区分“基础设施不完整”和“模型策略不好”的关键验收工具。

### 2.2 AI 公开身份不等于普通登录账号

用户看到的是稳定的 AI 身份：名称、头像、简介、专属卡组和风格。

系统内部还需要区分它是否是可登录的普通账号，还是不可登录、只能由服务端驱动的系统参赛者。Phase 3 以 `ai-battle.system-participant-identity/v1` 冻结了不可登录身份、精确卡组哈希、Phase 0 认证版本、决策契约/命令适配器版本与无 LLM 策略版本；Phase 4/4.5 按停机升级原则追加 Prompt、输出 schema、provider、模型、决策与调用政策版本，当前 v7 绑定实际 observation、strategy context、model strategy context 与 semantic decision context 版本。卡牌规则代码和发布卡牌数据继续随项目版本统一发布并由 Phase 0 与 focused tests 验证；全局机器调度只接受 `ONLINE + AI_BATTLE + 单一完整认证 SYSTEM binding`，未绑定或认证字段被篡改的 SYSTEM 不能进入调度。

从现有架构看，更自然的方向是保留 `SYSTEM` participant 语义，并为其增加不可登录的公开身份、专属卡组和策略版本配置；不应把 AI 做成持有密码、登录令牌和普通用户权限的账号。玩家侧稳定 Persona 与服务端执行身份可以绑定，但不能靠预先注册几个普通用户解决。

### 2.3 Prompt 负责策略，不负责裁判

压缩规则、完整卡组组成、当前局面、合法动作和逐动作后果共同构成 AI 的决策知识。通用打法优先让模型从这些事实中推理，不维护按卡牌编号硬编码的线上最优策略。

Loveca 本身适合被建模为语言理解与推理问题：规则引擎精确提供费用、槽位、卡文、合法动作和已确定后果，LLM 负责理解这些事实之间的关系，比较保留/替换、当前资源/后续用途和短期展开/获胜路线。服务端不应因为游戏复杂就再建设一套通用收益值、后悔值、搜索树或按卡牌编号维护的“最佳动作”规则；这种简化策略引擎很容易成为另一套不完整的 Loveca。

但 Prompt 不能代替以下权威规则：

- 当前动作是否合法。
- 费用能否支付以及实际支付哪些资源。
- 卡效是否触发、有哪些候选目标。
- 隐藏信息能否查看。
- 同一时点是否必须先处理其他 pending。
- 卡牌移动、判定、分数和胜负结果。

这些事实必须继续由游戏引擎决定。否则模型即使理解了卡文，也可能因为幻觉、规则版本漂移或上下文遗漏而制造非法状态。

介于规则事实和模型选择之间，还需要一层权威派生的语义表达：每个合法动作应独立说明来源卡、目标、实际支付、替换/保留对象、动作后公开场面和能力归属。服务端可以拒绝建立在错误事实上的理由，但不应以自己的启发式分数否决一个事实一致且合法的策略选择。

### 2.4 独立入口不等于独立对局实现

AI 对战应在产品和导航层提供独立入口，让玩家明确知道对手是 AI、当前只支持受控卡组，并能看到模型故障后的系统提示。但服务端不应另建 AI 专用状态机或桌面：

- AI 对局继续由 `GameSession` / `GameService` 维护权威状态。
- 真人席位继续通过正式联机 snapshot / command 管线操作。
- AI 使用不可登录的 `SYSTEM` 席位，由服务端内部调度器代表该席位提交现有 `GameCommand`。
- 双方继续读取各自的 `PlayerViewState`，历史记录继续保存参与者、卡组快照、timeline、checkpoint 和 decision record。
- 前端继续复用 `GameBoard` / `PlayerArea` 和现有局内聊天窗口。

`GameMode.SOLITAIRE` 可以提供确定性 responder 的复用来源，但不应成为 AI 对战的规则自动化模式；AI 对局仍需要完整双人规则流程。

## 4. 玩家可见信息一致性是否可实现

可以实现，而且现有 `PlayerViewState` 已经是联机玩家视角的权威可见性来源。面向模型的调用链不需要、也不应另建一套区域可见性、卡面可见性或隐藏信息规则；但前端视图不是模型出站协议，不能把完整 `PlayerViewState` 原样放进 Prompt。

需要明确区分可信服务端层和模型侧。可信的 AI 调度器、决策契约生成器与命令适配器可以读取 `GameState`，以复用费用计算、候选查询、窗口判断和最终命令校验；它们承担与现有投影层相同的服务端信任责任。Prompt 构造器、上下文管理器、启发式/LLM 策略和第三方模型调用则不得读取 `GameState`、对手 private events、sealed audit、对手卡组顺序或其他只存在于服务端的完整事实。模型只获得以下允许信息：

- 从自己座位 `PlayerViewState` 复制出的明确允许字段。
- 自己正常知道的完整初始卡组构成；按卡号与张数表达，不包含洗牌顺序或实例 ID。
- 双方正常可见的公共事件与公开历史。
- 精选的、正常对该座位可见且仍对当前策略有价值的关键历史。
- 当前允许行动的窗口和合法决策候选。

现有投影已经能按玩家座位区分 `FRONT`、`BACK`、`NONE`，并让自己的手牌可见、对手手牌只显示张数。它也能投影 active effect 的候选卡、槽位、选项和输入范围。这部分基础成熟度较高，应直接复用。`AiObservation` 只复制 `FRONT` 或该座位依法可见的身份；隐藏区域只提供合法数量/摘要，模型候选使用当前决策内稳定的临时 ID，不暴露真实对象 ID、隐藏顺序或可跨视图关联里侧对象的字段。

首版局内聊天不属于模型上下文来源。玩家昵称等确需呈现的用户可控文本也只能作为明确标记的数据字段传入，不得拼接到规则 Prompt、完整卡组知识或其他系统指令段。

仍有三个需要特别注意的缺口。

第一，`PlayerViewState` 适合前端渲染，但不是适合模型消费的出站协议。当前实现用只读、字段 allowlist、版本化适配器从 `PlayerViewState`、决策契约和允许公开给该座位的精选历史生成紧凑 `AiObservation`；该适配器只能删减、归纳和重排模型有权获得的事实，不能回读 `GameState` 或补入投影之外的信息。本方完整卡组属于赛前已知的独立可信知识，放在 system 消息并按同编号张数压缩，不混入当前牌库状态。防泄漏快照覆盖实际发送给模型的完整 request envelope、修复重试提示、日志和错误摘要，而不只是中间局面对象。完整卡组会增加固定输入 token，因此仍需通过真实 provider 用量持续评估，但不能用缺失卡文换取表面上的短上下文。

第二，`permissions.availableCommands` 目前主要是命令类型、作用域和少量参数提示，不等于“所有可直接提交的具体合法决策”。例如主阶段可能只告诉客户端可以使用 `PLAY_MEMBER_TO_SLOT`，却没有完整表达每张手牌可用的槽位、费用/换手约束和构造参数。前端仍会结合本地交互逻辑构造 payload，最终依赖服务端拒绝非法输入。这个边界不适合让 LLM 自由猜命令。

第三，AI 知道自己的初始卡组构成是正常玩家知识，但不能从服务端权威状态额外取得玩家投影之外的当前牌库事实。上下文必须明确区分“初始卡组有哪些牌”“当前投影中实际可见什么”与“服务端实际下一张是什么”，不能因为 AI 运行在后端就使用权威卡组实例映射或洗牌顺序。基础版本也不需要维护包含全部历史的知识账本；只保留对当前策略仍有价值的少量公开事实即可。

## 5. 初始缺口复盘与当前剩余边界

> 5.1 至 5.3 保留初始分析时的设计推导，但对应基础设施已分别由 Phase 1A、1B、1C 落地；5.4 起仍是当前待完成边界。

### 5.1 历史缺口：面向机器决策的统一决策契约（Phase 1A 已解决）

这是初始分析中最重要的基础设施缺口。Phase 1A 已按下述边界落地 typed contract；本节保留其设计理由。

初始版本的 `GameCommand` 已经定义了如何提交动作，服务端也会校验动作，但系统当时还不能统一输出“在当前 authority revision 和决策窗口下，AI 可以做哪些决策、候选是什么、输入约束是什么，以及该选择如何安全转换为命令”。只提供命令名称或允许操作的对象范围不足以安全驱动 LLM。

这一层不应通过扁平枚举所有多选、排序和站位组合来建立第二套规则引擎，也不应建立任意卡效 AST 或通用步骤解释器。更合适的边界是认证卡组实际可达窗口上的 typed 决策契约：

- 无参数动作可以直接成为候选。
- 单选、选项和槽位输入提供当前合法候选。
- 多选、排序、数字和站位编排提供候选集合、数量范围、顺序要求和其他结构化约束。
- 每个决策契约绑定对局 authority revision、席位、语义窗口签名和稳定决策 ID。
- 模型只返回候选 ID 或满足约束的结构化选择，由服务端适配器生成 `GameCommand`。
- 每个暴露的结构化选择都必须有与最终命令校验共源的选择校验器；强制窗口必须能够提供至少一个已经通过该校验器验证的合法样例选择（witness），随机策略通过同一契约的合法选择生成器（sampler）或 witness 生成选择，不自行解释卡效约束。
- 最终命令继续经过现有 `GameSession` 校验；决策契约不能成为绕过权威规则的捷径。

契约类型应从现有确认、单选、多选、效果选项、数字、槽位、排序和站位等真实交互面逐步建立。复杂约束仍由原有 workflow 或领域函数拥有，AI 模块只引用候选、约束结果和共源校验能力，不复制卡效规则。

缺少这一层会产生几个直接问题：

- 模型需要自行拼接复杂 command payload。
- 模型可能选择看似合理但当前不可支付或时机非法的动作。
- 只能依靠反复提交、读取错误再重试，污染命令记录并增加延迟。
- 同一卡效的多选、排序、数值、站位历史等输入很难稳定生成。
- 无法明确区分“可选跳过”“必须选择”“当前只需确认”和“可以结束阶段”。
- 若另写一套独立合法动作判断，还会与现有命令政策和规则查询逐渐漂移。

因此，在没有与现有权威校验共源的机器决策契约前，LLM 只能做实验性建议者，不能成为稳定的权威对局参赛者。

### 5.2 历史缺口：AI 行动时机和决策调度（Phase 1B 已解决单实例范围）

初始系统知道活跃玩家、等待玩家、子阶段、窗口和 pending，但没有后台 AI 调度器消费这些事实。Phase 1B 已在单实例、默认关闭的受控范围落地下述调度边界；多实例 fencing 仍属于后续阶段。

AI 对战至少会遇到以下调度问题：

- 双方可同时提交的换牌、LIVE 设置和分数确认。
- 同一命令结算后立即出现新的 AI pending。
- 人类在 AI 思考期间完成了另一个并行窗口，使旧决策过期。
- 卡效自动推进多次后，AI 已经不再是等待玩家。
- LLM 超时、重试或重复回调导致同一动作提交多次。
- 公开展示 deadline 到期后，原决策窗口自动变化。
- 一次 AI 行动触发另一串效果，必须逐步重新读取，而不能一次生成整回合脚本。

初始普通命令支持幂等键，但普通对局命令没有像撤销请求那样强制携带 `expectedRevision`。对真人 UI 来说，服务端逐条校验通常足够；对可能思考数秒的异步模型来说，当时还缺少明确的过期决策保护。

这里的 revision 不是 Git revision，而是权威局面的单调版本语义。Phase 1B 已将现有联机 `remoteRevision` 与统一单局串行执行器一并提升，使其成为 match runtime 内唯一的 authority revision 所有者；如果后续改名或迁移，应一次性替换，不保留双计数或 dual-read。AI 在 revision 42 开始思考，若玩家、AI、撤销、自动规则、deadline 或恢复接管使局面进入 revision 43，基于 42 返回的结果必须作废。每次机器决策同时绑定：

- `matchId`。
- AI 席位。
- `authorityRevision`。
- 由窗口种类、pending / active effect 身份和生命周期代际组成的语义窗口签名。
- decision lease。

换牌、LIVE 设置和分数确认等双方可并行输入应按席位分别识别窗口；首版采用安全优先的粗粒度策略，任何权威状态变化都会使旧 AI 结果失效并从最新 `PlayerViewState` 重新决策。

这不能只依赖“提交前分别检查几次”。单实例阶段也需要一个内部机器决策提交临界区，将 lease 所有权确认、authority revision 与窗口比较、结构化选择校验、命令适配、`GameCommand` 执行、revision 增长和 lease 消耗作为一次不可插入其他对局写入的操作。该入口必须与真人命令、撤销、deadline 和恢复接管共享同一个单局串行执行器，而不是建立 AI 专用锁。该入口属于可信服务端内部能力，不需要把 lease 字段扩散到真人使用的公开 `GameCommand` 协议。多实例阶段再将同一语义提升为数据库锁、租约记录或带 fencing token 的单局 owner。

调度器也不应把每个窗口都交给 LLM。现有对墙打 responder 已证明一部分窗口可以确定性处理。合理的调用层级是：

1. 只有一个合法动作、纯确认或规则强制输入时直接执行。
2. 明确配置的低风险默认策略由确定性/启发式策略执行。
3. 只有存在实际战术分支时才调用 LLM。

这样可以同时减少延迟、费用和非确定性，并保留与真人相同的命令校验边界。

Phase 1B 也已将公开展示 deadline 从“客户端按投影倒计时后请求推进”升级为有服务端 owner 的权威调度：写入 deadline 时登记任务，确认、撤销、窗口替换和终局时取消，到期任务进入同一个单局串行执行器，恢复后从最新状态重新扫描。客户端仍可发送幂等请求改善体验，但不能成为 headless 或 SYSTEM 席位继续运行的前提。

### 5.3 历史缺口：随机合法机器人和整局 playout（Phase 1C 已解决认证范围）

Phase 1C 在接入 LLM 前先实现了一个只依赖统一决策契约的随机合法机器人。它不需要理解卡组战术，也不追求胜率；它只需要在当前契约中选择一个满足数量、顺序、槽位、数值和可跳过约束的合法输入，并继续从最新局面处理下一窗口。

随机合法机器人至少应验证：

- 换牌、主要阶段、LIVE 设置、效果顺序、目标选择、可选费用、成功 LIVE 选择和结算都存在机器可消费的合法入口。
- 唯一动作和纯确认可以确定性推进，存在真实分支时可以随机选择。
- 一次行动产生新的 pending 或 active effect 后，会重新读取最新投影和决策契约，不生成整回合脚本。
- 旧 authority revision、旧窗口或旧 lease 的结果不会在新状态上执行。
- 在首版选定的固定 AI 卡组和测试对手卡组范围内，可以反复完成整局，不依赖 `FREE`，不会永久卡死。

这一步是 AI 基础设施的首个端到端验收。若随机合法机器人仍会卡死，问题属于规则覆盖、候选生成、调度或命令适配，而不是 LLM 策略质量。后续确定性 responder、启发式策略和 LLM 都应复用同一决策契约与调度边界。

要让该验收能够稳定复现，必须同时控制两类随机性：

- 机器人在合法决策中的策略选择。
- 引擎内部的初始洗牌、换牌后洗牌、牌库刷新和卡效洗切等规则随机事实。

初始引擎洗牌直接读取系统随机源，因此“记录机器人种子”本身不足以重现对局。Phase 1C 已引入可注入的规则随机源：测试使用 seeded RNG；生产继续使用安全随机源，同时把重放所需的随机事实写入审计。失败 artifact 记录规则事实与分席策略事实，并覆盖策略选择完成后被权威命令拒绝的严格重放路径。

### 5.4 面向 LLM 的对战上下文

Phase 2 已完成无 LLM 策略使用的上下文构造器，当前随 Phase 4.5 停机升级为 `ai-battle.observation/v3` / `strategy-context/v4`：它只从对应席位 `PlayerViewState` 与脱敏 typed decision contract 构造紧凑局面和合法决策摘要，并以代表性/盲选快照锁定不输出 match/player/authority object ID、隐藏卡牌身份、聊天和权限提示。`strategy-context/v4` 在其上组合 `compact-rules/v4`、`deck-knowledge/v1`、内部保守 witness 使用的固定卡组 playbook，以及 `selected-history/v4` 的按席位定长精选可见历史。完整卡组知识按卡号合并张数，包含卡名、卡文和印刷数值，但不含洗牌顺序或实体 ID；压缩规则同时明确 `[E]`、冒号前复合费用、完整支付、可选不发动与换手费用差额的卡文语法。历史只从已脱敏 observation 和权威接受后的结构化决策产生。Phase 4.5 已将模型边界停机升级为 `model-request-envelope/v7` / `model-strategy-context/v6` / `model-decision-output/v3`，接入固定服务端 provider、脱敏调用事实审计与故障处理。已有 `PlayerViewState` snapshot、public events 和 match record 仍是后续恢复与正式审计的正确数据来源，但目标不是维护一套包含全部历史事实的知识账本，而是持续为模型构造直观、版本化的决策输入。

真实对局说明“字段正确”仍不等于“语言语义足够”。代表性回归中，中心位已有 `PL!HS-bp5-008-R` 费用 4「桂城泉」，左右槽为空；手牌中的 `PL!HS-sd1-012-SD` 费用 4「百生吟子」可以支付 4 能量登场到空槽，也可以通过换手以实际支付 0 替换中心成员。模型选择了合法的中心换手，但把「桂城泉」的检索能力归给无卡文能力的「百生吟子」，随后又把仍有两个空槽的舞台描述为已满。复盘确认 observation、费用计划、目标槽位和 typed actions 都正确，缺口是同一动作的语义分散在手牌、舞台和 payment preview 等不同对象中，模型必须自行跨对象拼接，而且现有校验只检查 action ID 合法。

Phase 4.5 因此不增加复杂收益计算，而是把上下文升级为“权威事实 + 逐行动后果”的语言接口：

- 当前局面按卡牌身份、公开卡文、槽位、方向、资源和阶段组织为可读事实。
- 每个合法动作独立说明实际支付、目标槽位、被替换/保留对象、动作后占位与依法已知的卡效来源。
- 同一张成员登场到空槽与换手覆盖已有成员时，直接并列展示两条路线的真实差异。
- 权威局面事实、权威行动事实、完整卡组/规则事实和模型结论分层，后者不能覆盖前者。
- 模型只必须返回结构化 typed selection，简短取舍和下一步计划可以省略；服务端从通过契约校验的选择派生事实审计引用，但不判断唯一最佳动作。
- `selected-history` 只从权威接受结果和相邻可见投影生成事实；模型自由文本摘要不再被当作下一窗口的事实来源。

一份可用的模型上下文由四层组成。

第一层是稳定的规则 Prompt。它应使用适合决策的压缩语言说明回合与阶段、成员登场、费用与换手、能量、LIVE 设置与成功、主要能力时点、隐藏信息边界和 pending 优先处理等核心规则；同时明确模型只能选择决策契约提供的合法决策 ID 或结构化输入，不能自行构造命令、裁定规则或补做卡效。规则 Prompt 帮助模型理解选择的意义，但不取代 `GameSession` 和决策契约。

第二层是与固定 AI 卡组绑定的完整卡组知识。system 消息按卡号与张数列出编号、名称、类型、卡文、费用、BLADE、HEART、LIVE 分数、必要 HEART 和其他公开归属字段，让模型能从真实卡牌组合推理当前与未来空间；它不包含洗牌顺序、实体 ID 或“某卡必须这样用”的硬编码策略。卡文被明确标为游戏数据，不能改写系统指令。

压缩规则、完整卡组知识和输出契约共同组成稳定 System Prompt。当前局面、合法决策、逐动作后果与精选历史属于每次调用重新构造的 user 上下文，不写死在 System Prompt 中。固定 playbook 只保留给模型失败后的内部保守 witness，不进入实际模型请求。

第三层是从最新 `PlayerViewState` 派生的当前局面摘要，至少包括：

- 当前回合、阶段、子阶段、行动席位、等待席位和正在处理的效果。
- 双方分数、成功 LIVE、公开资源和距离胜利的差距。
- 自己的手牌、舞台、能量、LIVE 区、休息室和剩余牌库数量。
- 对方当前公开的舞台、能量、LIVE、成功区和休息室。
- 当前持续修正、方向状态、关键次数限制和本窗口相关资源。
- 用卡名、费用/分数和战术含义表达的重要对象，避免要求模型自行解释大量内部对象 ID。

第四层是当前合法决策和精选关键历史。合法决策应在上下文中显著呈现，说明稳定决策 ID、动作含义、目标、费用、数量/顺序约束和必要的规则层结果预览，并进一步给出逐动作的保留、替换、支付和动作后场面。精选历史只保留对当前策略仍有价值且能由权威接受结果或相邻可见投影证明的信息，例如最近的关键登场、LIVE、卡效与资源支付，对方公开过的重要卡牌，已消耗的核心组件和每回合能力使用情况。模型上一次生成的摘要或计划不是局面真值；首版可以不回灌，若未来保留也必须以单独的低可信结构标记。纯确认、自动移动和无战术意义的逐步流水不需要反复发送给模型。

因此，模型每次决策时应能直接回答四个问题：

1. 现在场面是什么情况。
2. 当前轮到我处理什么。
3. 当前有哪些合法操作。
4. 根据规则、完整卡组和当前/后续动作空间，应该选择哪一个。

当前场面始终以最新 `PlayerViewState` 为准，决策可行性始终以最新决策契约为准，历史只作为策略辅助而不是状态真值。进程重启、调用超时或 lease 过期后，应丢弃旧模型结果，从最新玩家投影、固定版本的规则/完整卡组知识和仍保留的精选可见历史重新构造输入；不需要恢复模型正在生成的私有推理，也不需要完整重放全部历史才能继续对局。局内聊天不进入这份精选历史。

Phase 4.5 已把 Phase 4 的摘要/指标调试轨迹替换为管理员专用的“模型上下文检查器”：按 system prompt、完整卡组知识、当前权威事实、逐行动后果、精选历史、输出约束/repair 指令和解析后结构化结果分区展示实际规范化请求内容。展示与运行时共用 `buildAiModelProviderRequest` 生成 provider-neutral system/user 消息，不维护一份可能与真实请求漂移的调试文案；调用指标只作为辅助信息。

这不是普通参与者功能。实际上下文可能包含 AI 席位的手牌等私有信息，只允许在开发环境开关开启、管理员完成认证且进入管理员 AI 测试会话时查看；普通玩家即使是对局参与者也不能读取，生产环境强制关闭。启用后该局明确属于非公平开发测试。上下文不进入聊天或持久审计，并继续排除 API key、认证 header、供应商内部 payload、原始 provider 响应、服务端错误、权威对象 ID 和模型私有思维链。

### 5.5 AI 身份、专属卡组和 Prompt 治理

初始分析时，数据库只有普通用户、资料和用户卡组，对墙打使用一个硬编码系统身份和配置路径指定的默认 YAML。当时尚不存在：

- 多个稳定 AI 身份及其公开资料。
- AI 身份与专属卡组的正式绑定。
- 卡组变更后的版本关系。
- 完整卡组知识与规则 Prompt 的版本绑定。
- Prompt 的审核、启停、版本和回滚状态。
- 一局对战实际使用的 AI 身份、卡组版本和 Prompt 版本快照。
- 模型或 Prompt 升级后，旧对局仍可解释的版本记录。

完整卡组知识由实际认证卡组快照生成，避免手写策略说明与卡组内容漂移；只修改卡组却不更新内容认证和卡效覆盖，仍会造成模型知识与规则能力脱节。

Phase 3/4 已用一套受版本控制的系统 AI 配置绑定固定身份、固定卡组、规则 Prompt、provider、模型参数和调用政策，并在每局 SYSTEM 身份快照中记录实际版本；Phase 4.5 从认证卡组快照生成完整卡组知识。内部 playbook 只属于模型失败后的保守 witness，不是模型输入。基础版本仍不建设多 AI 管理后台或复杂 Prompt 数据库；Prompt 质量后续通过固定场景和对局评测持续改进，版本变化必须重新验证。

### 5.6 首版固定卡组的规则覆盖

当前项目仍明确处于“已登记自动化能力 + 规则模式语义化命令 + 自由模式兜底”的阶段，不是全卡池完整自动裁判。首版也不需要追求覆盖所有卡效或任意 AI 卡组；只要少量官方提供的固定卡组能够稳定与玩家完成整局，并表现出清晰、有趣的卡组玩法，就已经可以形成足够好的基础体验。

真人联机可以协商切换到 `FREE`，手动落实尚未自动化的复杂效果；AI 自动匹配不能把这种协商和人工裁定作为正常依赖。Prompt 也不能安全地让 AI 自己移动任意卡牌来“补做”未实现效果。

因此，基础 AI 对战成立的规则目标应收缩为：

- 玩家和 AI 首版只使用 [`assets/decks/缪预组.yaml`](../../assets/decks/缪预组.yaml) 与 [`assets/decks/绿莲-6弹ver.yaml`](../../assets/decks/绿莲-6弹ver.yaml) 两套卡组。
- 认证单位是由版本化 canonical schema 产生的规范化卡组内容哈希；同名 YAML 内容变化后必须重新认证。
- 补齐这些卡组实际使用到的卡效、费用、触发与决策窗口。
- 验证两套卡组在双方席位和允许的对局组合中都能在 `RULES` 中完成本局所需裁定。
- 确保玩家卡效施加给 AI 的目标选择、可选费用和其他输入也能由统一决策契约表达。
- 通过随机合法机器人和聚焦场景验证这些有限组合可以完成整局。

首版的卡组角色组合是“两个玩家卡组选择 × 两个 AI 卡组选择”共四种；每种组合还必须至少覆盖 AI 先手和后手，因此最低是八个基础验证单元。若第一轮仍需缩小，可以先验证 μ's 预组玩家对绿莲 AI 的先、后手两个单元，再逐项扩展。随着新卡组和卡效逐步加入，再扩展准入清单。关键标准是“本局双方实际使用的卡牌可以由引擎裁定”，而不是“整个卡池已经完成”。

认证不能只保存一个永久布尔值，也不能成为第二个卡效完成登记册。卡效完整/部分状态仍以 [`existing_module_map.md`](../card-effect-reuse-audit/existing_module_map.md) 为唯一主登记册；AI 卡组认证只记录精确内容哈希、canonical schema 与哈希算法版本、依赖的基础编号和能力段、主登记册引用、准入对手卡组、规则引擎版本、卡牌数据版本、决策契约版本和场景矩阵版本。任一输入发生影响语义的变化时，旧认证必须失效并重新验证。静态能力/窗口覆盖、聚焦交互测试和随机 playout 应分别记录：playout 是重要回归证据，但不能单独证明所有可达交互已经完整覆盖。

### 5.7 对战用 LLM 服务能力

项目已经有一个用于管理端卡图文字提取的 DashScope/Qwen 调用：

- [`client/src/lib/aiService.ts`](../../client/src/lib/aiService.ts)

这条链路是浏览器侧管理辅助能力，使用固定 Prompt 调用多模态接口，不参与对局或规则判定。它不能直接视为 AI 对战基础设施，也不应复用其通用代理作为对战调用边界；对战接口必须在服务端固定模型能力、输入 schema、认证、限额和可记录字段，不能允许客户端自由构造供应商请求。

Phase 4 已提供版本化 provider-neutral 请求、严格结构化输出解析和 typed contract 复验，并接入固定的服务端 DashScope `qwen3.7-flash` provider profile。凭据只存在于服务端环境；模型等待移出按局临界区，返回后重新检查 lease、revision、窗口和选择。单次调用具有 12 秒超时和最多两次协议尝试，对局状态变化会取消旧调用；全站、账号和单局并发、每分钟请求、单局请求/token/估算费用都有限额。模型返回为空、格式或选择协议错误经有限修复仍失败时，只在当前步骤使用保守选择；供应商不可用、超时或单局预算拒绝才让本局剩余时间固定切换到保守策略。

调用记录只保留版本、请求哈希、结构化选择、单行短摘要、结果类别、延迟、token、估算费用和哈希化 provider request id，不保存完整原始响应、供应商错误、凭据或聊天。Phase 5 仍需增加跨实例容量、生产告警、聚合看板和自动熔断；这些不改变 Phase 4 已完成的单实例安全边界。

为便于本地验证，设置 `AI_BATTLE_DEBUG_TRACE_ENABLED=1` 后，管理员可在自己进入的 AI 测试对局中使用实际模型上下文检查器，查看真正生效的 system prompt、动态语义上下文、输出契约和严格解析结果；轨迹仅在当前服务进程内存中保留。生产环境仍强制关闭，普通参与者无权读取；即使在开发环境，也不把私有思维链、原始无效 provider 响应、供应商内部 payload 或凭据变成调试接口。

LLM 应负责在合法策略选项中做判断，而不能成为规则引擎、随机源或状态写入入口。

供应商失败不能让对局永久停在 AI 窗口。首版应准备一个覆盖认证卡组全部强制窗口的保守确定性策略：

- 可选卡效和可选费用默认不发动。
- 换牌默认不换。
- 主阶段按审查过的稳定优先级执行最低风险推进动作；没有可用推进动作时结束阶段。
- LIVE 设置存在稳定合法候选时按确定性优先级设置；只有没有可用候选或策略矩阵明确允许时才确认空设置。
- 纯确认、规则分数确认和结算继续推进。
- 强制单选、多选、排序、数字或站位输入使用契约提供的稳定合法 witness。

连续协议失败时，服务端通过局内聊天 UI 发布仅针对当前步骤的去重结构化系统提示，立即使用保守选择推进该步，下一步重新请求模型。供应商不可用、超时或预算拒绝时，另行发布一次整局降级提示，并将本局剩余时间固定为保守策略。Phase 1B 已落地真正的 `SYSTEM_NOTICE` schema 和服务端专用追加入口，而不是让 SYSTEM 席位发送一条看似普通玩家消息；消息具有独立类型、稳定去重键和前端样式，并独立于玩家身份、屏蔽词与玩家发送限流。提示不得泄漏供应商、密钥、错误堆栈或内部重试信息。

单个 witness 只证明当前窗口可合法提交，不证明整局一定结束。保守策略还必须记录连续无进展回合、降级持续时间或等价活性指标；达到开局前冻结的阈值后，应由 SYSTEM 认输或进入明确、可审计且玩家可见的异常终局。供应商故障不应立即被标记为基础设施失败，但也不能以“继续对局”为名永久空过。

### 5.8 公共牌桌 AI 补位和赛前流程

当前公共牌桌 Beta 已经具备持久候场票据、FIFO 原子配对、双方确认、封闭房间引导、猜拳、先后手选择和正式联机对局复用。AI 对战不需要另建一套自动匹配系统，应优先复用这条现有链路。

现有公共牌桌仍是普通用户之间的双人流程。要实现“玩家在公共候场中匹配到 AI”，还缺少：

- 真人优先还是 AI 补位的产品规则。
- 等待多久后允许 AI 补位，以及玩家是否可选择不匹配 AI。
- AI 身份、卡组和允许对战卡池的选择规则。
- AI presence、并发容量和单局决策 worker 占用。
- 当前双方确认模型在 AI 席位下如何收敛，AI 是否免确认或由服务端自动确认。
- AI 如何自动完成卡组锁定、准备、猜拳和先后手选择。
- AI 对局是否计入普通历史、胜率、任务、奖励或未来排位。
- 玩家在进入候场前或匹配成功后如何明确知道对手是 AI。
- AI 席位如何处理撤销、重开、离开、超时和供应商故障。

这些不是 LLM 策略问题，而是在现有公共牌桌和正式联机生命周期上新增系统参赛者语义。正式 SYSTEM 席位和内部授权入口应先以确定性/启发式策略接入正式联机 runtime，验证身份、记录、聊天、撤销、刷新和异常终局，再接入 LLM。首版玩家产品入口应独立于公共牌桌；公共牌桌 AI 补位在受控入口稳定后再建设。排位体系仍属于未纳入当前交付范围的独立能力，不应与基础 AI 补位捆绑。

Phase 3 的管理员入口验证了较窄的受控赛前：版本化解析器标记 USER/SYSTEM 准备完成，复用真人房间的共享猜拳胜负函数，由确定性获胜的 SYSTEM 选择请求的先后手，然后直接创建 `OnlineMatch`。Phase 4 已在同一路径上提供登录玩家可用的独立入口，但仍不创建临时双 USER 房间或公共候场 presence。无房间 AI match 的聊天由 match participant 授权，普通真人对局仍要求 room presence；公共牌桌生命周期属于 Phase 5。

### 5.9 运行态持久化和恢复

`OnlineRoomService` 和 `OnlineMatchService` 的房间、对局及相关状态目前主要保存在进程内存中。对局记录、authority checkpoint 和回放已经落地，但正式联机在服务进程重启后恢复进行中对局尚未闭环；当前只有服务端可记录对墙打具备较窄的 checkpoint 恢复能力。

AI 对战还会额外产生以下恢复要求：

- 当前是否存在未完成的 decision lease，以及它对应哪个 revision 和决策窗口。
- 请求是否已经发出、返回或提交。
- 重启后必须使旧 lease 和旧模型结果失效。
- 当前局面摘要、固定 Prompt 版本和精选关键历史如何从玩家视角事实重建。
- Prompt、模型和卡组版本如何保持与开局一致。

如果这一边界缺失，单纯把上下文放在内存里会让服务重启、部署、超时回调和多实例运行都可能造成卡局或重复行动。基础 headless 和受控入口阶段可以在重启时使旧 lease 全部失效，并对无法重建的对局明确、安全地终止；正式进行中恢复和多实例接管属于生产阶段门槛。无论处于哪个阶段，都不能让旧模型回调在新运行态上继续提交动作。

### 5.10 AI 决策审计和复盘

Phase 4 已把 AI 专属调用事实接入 match record，当前 `strategy-decision-record/v4` 在既有命令、窗口和权威 checkpoint 基础上，额外关联模型请求哈希、版本、结构化选择、服务端派生事实引用、可选单行取舍/计划、调用结果、延迟、token、估算费用和哈希化 provider request id。完整 decision record 与确定性重演在整个项目范围内仍是阶段性闭环，但已不再缺少当前模型协议所需的调用事实。

为了定位“模型为什么没有行动”“是否看到了不该看的信息”“为什么选择了非法目标”这类问题，至少需要能够关联：

- 对局 authority revision 和决策窗口。
- decision lease、决策契约及其 schema/适配器版本。
- 当时提供给 AI 的规范化结构化输入 envelope 哈希，以及按受限保留策略保存的实际可见输入。
- 当时的合法候选集合。
- 最终选择、执行结果和失败原因。
- 使用的 AI 身份、卡组、Prompt 和模型版本。
- 机器原子提交结果，以及与该决策关联的规则随机事实引用。
- 调用耗时、重试、降级和 token/费用摘要。

不需要、也不应依赖保存模型的私有思维链。当前普通与受限记录都只保存规范化输入 envelope 哈希、schema/version、候选、结构化选择、执行结果和调用摘要，不保存完整模型输入、完整原始响应或供应商错误；出站边界由 allowlist 构造与专项测试证明，而不是依赖长期保存敏感 payload。

Phase 4.5 的管理员上下文检查器不改变这一持久化政策。它只在开发测试会话的当前进程内展示实际规范化模型请求，帮助管理员定位语义构造、Prompt、模型选择和服务端事实审计缺陷；system prompt 与动态上下文不会因此写入普通历史、聊天或长期审计。

当前另行提供生产可用但仍是内存态的 `reflection-history/v2`。它不保存完整请求，而是把 allowlist 语义局面、服务端结构化战略目标、合法选择、显式短取舍/计划、最终选择和权威执行状态组织成带自动复盘摘要、决策速览和完整审计附录的 Markdown；管理员可在自己参与的 AI 对局中途导出快照，交给 agent 做复盘或版本对比。该文档仍可能包含 AI 席位当时依法可见的私密局面，因此保持管理员授权和 `private, no-store`；它排除完整 Prompt、原始响应、聊天、凭据、权威对象 ID 与私有思维链，也不回灌到在线决策上下文。首版最多保留最近 1024 次决策，随对局运行态删除而消失，尚未替代数据库 match record 或长期归档。

### 5.11 安全、隐私和公平性

AI 运行在服务端会天然接近完整权威状态，因此必须用边界和测试证明 Prompt 构造器、上下文管理器、策略实现和第三方模型调用只读取玩家投影及经过脱敏的决策契约，不能只靠调用方自觉。可信调度器和契约生成器可以读取权威状态，但不得把投影外事实带入模型输入。

需要重点防范：

- 把完整 `GameState`、sealed audit 或对手 private events 误传给模型。
- 从卡组实例 ID、服务端日志或调试字段推断牌库顺序。
- 在错误日志、模型观测日志中长期保存双方隐藏信息。
- 把局内聊天发送给模型，或把玩家昵称、房间文本等用户可控字符串当作 Prompt 指令。
- 第三方模型服务接收不必要的账号、房间或个人信息。
- 供应商超时导致大量对局 worker 堆积。
- 模型通过自由文本构造未授权命令或尝试切换 `FREE`。
- AI 账号被当作普通账号登录、领取奖励、访问卡组管理或历史授权。

当前投影层解决玩家视角下“可以给什么”的权威边界；Phase 2/4 已用独立 observation/context 类型、出站 forbidden-key 检查、严格结构化返回、日志脱敏和专项测试证明首版 LLM 调用链只消费该投影派生数据。后续仍需随 observation 字段、卡组范围和 provider 能力扩展持续增加泄漏与 Prompt injection 回归。

## 6. 可行性成立的最低条件（非规范摘要）

本节只摘要可行性成立所依赖的能力，不作为第二份验收规范；精确职责、门槛和验证矩阵以[设计与实施草稿](design-and-implementation.md)为准。在不要求任意卡组、排位和高水平策略的前提下，一版基础 AI 对战至少应满足以下条件：

1. 首版只允许 μ's 预组与绿莲 6 弹两个由版本化 canonical schema 生成的精确内容哈希进入该入口，并在至少八个基础验证单元中于 `RULES` 完成本局所需裁定，不依赖人工 `FREE` 处理；不要求全卡池完整。
2. Prompt 构造器、上下文管理器和策略模型只接收由单一字段 allowlist 适配器从对应座位 `PlayerViewState` 派生的 `AiObservation`、固定卡组知识、精选可见历史和脱敏决策契约，不直接序列化完整视图，也不建立第二套可见性真值。
3. 现有联机 `remoteRevision` 与统一单局串行执行器一并被提升为 match runtime 内唯一的 authority revision；每次机器决策都只面对绑定当前 revision、席位、语义窗口签名和 decision lease 的结构化决策契约，而不是自由生成原始命令。
4. 强制决策契约能够提供经共源校验器验证的合法 witness，随机策略可以通过同一契约能力生成合法输入，而不复制卡效规则或试提交命令。
5. 规则随机源可在测试中固定，生产权威随机事实记录在正式 SYSTEM 席位接入前落地；一个不依赖 LLM 的随机合法机器人能够连续处理所有必要窗口，并按设计文档冻结的数值门槛完成和复现整局。
6. 机器决策通过与真人命令、撤销、服务端 deadline 和恢复接管共享的单局原子提交边界执行；决策过期、模型超时、输出非法或供应商不可用时，不会重复行动、泄漏信息或永久卡局。连续协议错误只降级当前步骤；供应商、传输或预算故障会通过服务端专用 `SYSTEM_NOTICE` 告知玩家，并切换到覆盖认证窗口且具备有界活性政策的保守确定性策略。
7. LLM 每次都能获得包含压缩规则、完整卡组组成、最新局面、逐行动语言化后果和精选关键历史的直观上下文；当前合法列表明确表示眼前完整选择空间，模型不依赖按卡号硬编码的线上最佳动作规则。权威事实与模型结论严格分层，局内聊天不进入首版模型上下文，其他用户可控文本也与系统指令隔离。
8. AI 的命令继续经过与真人相同的 `GameSession` / `GameCommand` 校验和记录。
9. AI 身份、卡组、规则 Prompt、模型和规则版本在单局内固定并可追溯，同时允许后续持续评测、替换和回滚 Prompt。
10. 玩家明确知道对手是 AI，AI 不伪装成真人账号。
11. AI 对战运行态和上下文可以在合理故障边界内恢复；模型供应商故障不立即终止本局，而是先由保守策略继续。保守策略达到冻结活性阈值，或权威对局运行态本身无法恢复时，按各自明确且可审计的政策安全终止。自动化验证覆盖隐藏信息、非法动作、超时、重复回调、多步卡效、服务端 deadline、保守降级和整局无卡死。

缺少第 1～6 项中的任何一项，都更接近“LLM 操作桌面的演示”；缺少第 7 项则只能证明模型会提交合法动作，不能证明它理解了动作。两类缺口都不应进入公共 AI 补位。

## 7. 缺口优先级判断（非规范摘要）

以下分组只用于说明依赖优先级；实施阶段以设计文档为准。

### 阻断机器参赛者闭环的缺口

- μ's 预组与绿莲 6 弹两个精确卡组哈希及其认证席位组合的有限规则闭环。
- canonical deck schema、稳定哈希算法和至少八个基础验证单元。
- 与权威规则共源的机器决策契约。
- 契约作为现有规则查询的 typed read model，不建立第二套卡效 DSL。
- 强制窗口合法 witness、共源选择校验器和契约 sampler。
- AI 行动时机、连续决策、服务端 deadline owner、唯一 authority revision、共享单局串行提交和过期保护。
- 可注入规则随机源、正式 SYSTEM 席位前落地的生产权威随机事实记录，以及只依赖决策契约的随机合法机器人和数值化整局 headless playout。
- 确定性 responder、具备最小推进和有界活性的保守策略。

### 玩家受控入口完成状态

Phase 3 已完成 SYSTEM 席位内部授权、正式联机 runtime、复用共享猜拳规则但不创建临时真人房间的受控自动赛前、身份/固定卡组/Phase 0 与策略版本绑定、canonical YAML 内容认证、按真人串行的管理员内部入口、无房间 AI match 聊天、刷新/撤销/自由模式/重开/离开政策、异常终局和八单元无 LLM 真实链路验证。Phase 4 已完成此前阻断普通玩家入口的能力：

- 首页和独立 AI 对战页明确告知对手身份、固定卡组范围、隐藏信息边界与异常处理。
- Prompt、输出 schema、provider、模型、决策政策和调用政策按局绑定，并以真实 provider 固定场景评测。
- 服务端 provider 等待不占按局临界区，返回后重新检查 lease、revision、窗口和选择。
- LLM 只处理 `HEURISTIC` 选择；机械窗口继续直接处理。
- 超时、有限重试、取消、调用事实审计、预算/限流、专用 `SYSTEM_NOTICE`、整局保守策略切换和活性终局均已接线。

### 当前优先缺口：语义决策与服务端事实审计

Phase 4 已证明模型可以安全地进入真实对局并提交合法选择，但尚未证明模型始终正确理解每个合法动作的完整含义。Phase 4.5 先于公共牌桌补位，重点补齐：

- 从 allowlist 局面与 typed contract 生成逐动作的语言化事实和后果。
- 明确卡牌能力归属、空槽/占用槽、实际支付、换手替换和动作后公开场面。
- 模型只必须输出 typed selection，简短取舍和计划可以省略，不输出私有思维链。
- 服务端从已通过权威契约校验的选择派生事实审计，不建设复杂收益值或后悔值引擎。
- 精选历史不再把模型自由文本摘要晋升为状态事实。
- 管理员开发调试窗口直接展示实际 system prompt 与动态模型上下文，普通参与者和生产环境不可访问。
- 用固定语义场景、真实 provider 和真人抽样对局作为进入公共候场前的策略质量门槛。

### 阻断公共牌桌 AI 补位的缺口

- Phase 4.5 的语义上下文、服务端事实审计与策略质量回归。
- 真人优先、等待阈值、玩家拒绝权和双方确认政策。
- AI presence、并发容量和公共房间生命周期。
- 多实例决策互斥与公共候场故障恢复。

### 阻断生产稳定性的缺口

- 正式联机运行态及 AI 上下文恢复。
- 多实例并发与单局决策互斥。
- 跨实例 LLM 容量、自动熔断、告警和聚合监控。
- 更长周期的模型/Prompt 对局质量评测与回滚运营。
- 持续扩展隐藏信息与 Prompt injection 专项回归。
- 长局、复杂卡效链和供应商故障压测。

### 可以在基础对战后继续提升的能力

- 多难度、多模型或动态思考预算。
- 长期对手建模和更强的局势记忆。
- 自动生成或自动优化卡组战术 Prompt。
- 基于历史对局的 AI 复盘和策略训练。
- 排位、奖励、AI 胜率平衡和更复杂的匹配策略。

## 8. 主要风险

### 8.1 规则覆盖风险

最严重的风险不是模型水平低，而是模型进入一个引擎无法完整裁定的局面。首版不需要覆盖所有卡效，但不能只检查 AI 一侧：μ's 预组与绿莲 6 弹在玩家席位时仍可能向 AI 施加选择、费用或状态变化。应对已认证的卡组席位组合和真实交互路径做聚焦验证，并在规则范围扩展前继续使用随机合法机器人跑整局回归。

### 8.2 合法动作不完整风险

如果决策契约漏掉一个应有动作，AI 会被错误限制；如果多给一个非法动作，模型可能选择它并卡住流程。该边界需要尽量复用现有命令政策、规则查询和候选生成能力，并始终保留最终 `GameSession` 校验，不能形成第二套分叉规则。多选、排序和站位编排应表达约束，不应预先展开全部笛卡尔积。

### 8.3 延迟和成本风险

一局卡牌对战会出现大量小决策。若每次确认、跳过或强制单选都调用大模型，延迟和费用会迅速累积。应优先用确定性 responder 处理无策略分支窗口，再用启发式策略处理明确默认项，只把真实战术分支交给模型。上下文过长还会降低模型对当前窗口的注意力。Phase 4 已取得固定真实场景的延迟/token 样本并设置单局预算，但尚无长周期生产分布，仍不能据此推断典型整局成本。

### 8.4 非确定性和模型漂移风险

相同局面可能得到不同选择，供应商升级后行为也可能变化。对娱乐型 AI 这不一定是缺点，但它会增加回归和线上问题复现难度，因此版本与输入事实必须可追溯。

随机合法不等于适合生产降级。任意合法动作仍可能支付高价值资源、放弃关键窗口或让对局体验明显失真。生产降级使用单独的保守确定性策略：跳过低价值可选动作，按审查过的优先级执行最小推进，并在强制窗口使用已经审查的稳定合法 witness。随机合法策略的首要用途仍是 headless 验收和故障定位。

局部合法也不等于整局有活性。如果保守策略永久不登场、不设置 LIVE 或只做纯确认，它仍可能让对局无限空转。生产降级必须额外具备审查过的最小推进规则、无进展监测和有界 SYSTEM 终局政策。

另一类风险是把策略漂移误判为需要更复杂的服务端评分。Loveca 的组合空间使通用收益值、后悔值或卡牌特例很难长期与真实卡文同步；它们容易变成一套不可审计的第二策略引擎。当前方向是改善语言事实接口和模型评测，只对事实矛盾做机器拒绝，不把启发式偏好升级为线上价值裁决。

### 8.5 上下文失真风险

只发原始当前快照会让模型难以快速理解场面和卡组目标；发送过多历史又会淹没当前决策。上下文构造器必须以最新玩家投影和决策契约为真值，用稳定模板解释当前场面，只追加少量仍有战术价值且能由权威接受结果或相邻可见投影证明的历史。若它错误压缩数量、卡牌身份、费用或效果窗口，比模型本身判断失误更危险，因此应对上下文生成结果做结构校验和代表性局面快照测试。

当前实测进一步证明，即使各字段分别正确，语义仍可能因跨对象拼接而失真。若动作没有直接说明“谁被替换、谁仍在场、能力属于谁、节省的资源接下来能否使用”，模型会用语言补全缺口并产生看似合理的幻觉。Phase 4.5 应让每个动作成为可以独立阅读和比较的语义单元，并对模型引用的事实做一致性校验。

模型生成的摘要还会形成自我强化风险：如果自由文本被写入精选历史，第一次能力误归属可能在后续窗口被当成既有事实。历史必须以权威接受结果和可见投影为来源，模型计划只能保持低可信标记或完全不回灌。

### 8.6 测试耦合与演进成本风险

AI 对战同时包含 observation、语义上下文、精选历史、模型 envelope、SYSTEM binding、调度和整局运行链路。若每个测试都手写完整跨层 payload、版本字符串和 fake model 分支，一次协议升级就会迫使大量本来只验证行为的测试同步修改；这会提高重构成本，也会让开发者倾向于保留已经不合适的内部结构。

应把领域场景、语义行为、出站协议、运行时集成和真实模型评测分层。协议版本由生产清单统一导出，公共 builder 只为对应层提供合法默认值，完整 snapshot 只冻结少量真实 provider-neutral 边界；fake model 通过 typed selection contract 生成通用合法返回，不复制卡效规则或完整策略。开发分支不需要为减少测试修改而保留旧协议兼容，停机升级只更新当前 builder 和对应契约测试。精确规范见[设计与实施草稿 11.5 节](design-and-implementation.md#115-测试架构与变更隔离)。

### 8.7 用户体验风险

AI 长时间无响应、反复非法操作、机械地逐个确认、持续空过或在明显必输时拖延，都会让匹配体验变差。模型服务异常时，局内聊天应只显示一次去重的系统提示，并让本局稳定切换到保守策略；不能沉默卡住，也不能用连续错误消息刷屏。达到冻结活性阈值后的 SYSTEM 认输或异常终局也必须向玩家明确展示。玩家还需要知道 AI 是否会接受撤销/重开。

## 10. 最终判断

当前项目最适合把 AI 对战理解为：在现有权威对局之上新增一种受严格玩家视角约束的“服务端参赛者”，而不是新增一套 AI 专用桌面或让模型直接操作完整游戏状态。

底层规则、命令、投影和记录基础已经让这个方向具备良好可行性；相比许多只有前端牌桌的项目，Loveca 已经跨过了最关键的权威状态与隐藏信息门槛。

Phase 0～4 已完成首版受控 AI 对战的规则、调用、合法性、故障治理和玩家入口闭环：登录玩家可以在独立入口选择双方固定卡组与 AI 先后手，模型只在合法选择范围内行动；连续协议错误仅让当前步骤改用保守选择，供应商不可用、超时或预算拒绝才会让本局剩余时间固定为保守策略。但真实对局已经证明，进入公共匹配前还需要补齐语言语义和事实落地质量；当前剩余工作不只是扩大使用范围：

1. **规则与机器输入闭环**：冻结 canonical deck schema、两个精确卡组内容哈希和至少八个基础验证单元，补齐认证范围的规则覆盖，并建立与权威校验共源的 typed 决策契约、选择校验、witness 和 sampler。
2. **可复现机器参赛者闭环**：将现有 `remoteRevision` 与统一串行执行器共同提升为唯一 authority revision，完成服务端 deadline、decision lease、具备有界活性的确定性策略、可注入规则随机源和整局 headless playout。
3. **正式 SYSTEM 链路闭环**：以不可登录身份和精确认证卡组进入标准联机 runtime，复用规则命令、投影、聊天、记录与共享猜拳规则；无 LLM 整局、内部授权、原子审计和生命周期政策均已由 Phase 3 验证。
4. **模型与玩家产品闭环**：Phase 4 已在脱敏上下文上接入服务端结构化 LLM 调用、超时/重试/取消/预算治理、专用 `SYSTEM_NOTICE`、整局保守策略切换和玩家独立入口。
5. **语言推理质量闭环**：Phase 4.5 用权威派生的语义局面与逐行动后果、从合法 selection 派生的服务端事实审计、纯净精选历史和管理员上下文检查器补齐“合法但依据错误”的缺口，不建设通用后悔值/收益值引擎。
6. **公共补位与生产治理**：Phase 5 再建设公共牌桌补位、presence、多实例互斥、进行中恢复、跨实例容量和运营监控。

具体职责、阶段门槛和验证矩阵以[设计与实施草稿](design-and-implementation.md)为唯一规范来源。Phase 4 的机器可读完成状态见 `src/server/ai-battle/phase-four-baseline.ts`；Phase 4.5 当前仍在实施，公共牌桌仍不会自动把等待中的玩家替换为 AI。

Phase 0 已完成，内容身份、规则/权威卡牌数据/场景/证据版本键、逐 `baseCardCode + abilityId` 行为证据、真实卡牌数据八单元 smoke、确定性保守排序、双层进展语义和数值门槛见 [`phase-0-baseline.md`](phase-0-baseline.md)。Phase 1A 已完成认证范围 typed 决策契约与 v2 可达窗口矩阵；Phase 1B 已完成共享单局执行器、lease、服务端 deadline、保守策略、活性终局和去重 `SYSTEM_NOTICE`。Phase 1C 已完成安全/seeded/replay 规则随机事实、随机合法策略、失败 tape 与严格回放、8 局固定 smoke 和 256 局专用回归。Phase 2 已完成 allowlist observation、压缩规则、两个内容哈希绑定 playbook、精选可见历史、strategy context、三层可解释策略、哈希化执行审计和 64 局策略质量回归。Phase 3 已完成不可登录 SYSTEM 身份、canonical YAML 内容认证、共享猜拳赛前、标准联机投影/聊天/历史和八个真实 USER + SYSTEM 整局。Phase 4 已完成 SYSTEM 身份的模型版本绑定、服务端结构化模型选择、调用治理与脱敏审计、故障切换、独立玩家入口和浏览器真实链路验证。Phase 4.5 当前已落地通俗语义上下文、服务端派生事实审计、纯净历史、简化模型输出与管理员上下文检查器，仍需更广语义与真实模型质量收束；`SOLITAIRE` 仍明确排除在战术机器调度之外。

> 文档类型：专题说明
> 适用范围：管理员 AI 对战的单步费用、整局费用记录与 DashScope 用量解析
> 当前状态：已进入开发基线；北京价格、现有协议与定价结构固定，生产迁移另行执行
> 调研日期：Qwen 价格核对于 2026-09-11；GLM-5.2 与 DeepSeek-V4.1-Flash 追加核对于 2026-09-14

## 当前范围

在现有 AI 决定观察框中，每个模型决定旁显示一个小金额；悬停时显示“输入 + 缓存输入 + 缓存创建 → 输出”的 token 数。本局顶部显示累计费用，结束后仍能从历史对局记录读取。

费用定义为**上游实际返回的用量 × 本局冻结的公开原价**，显示“预估”或 `≈`。这是模型调用成本统计，不是向玩家扣款，也不是阿里云现金账单。免费额度、优惠券、套餐抵扣、限时活动与合同折扣不进入首版计算；公开模型页也明确区分原价与控制台活动价。[Max 模型价格](https://help.aliyun.com/zh/model-studio/qwen3-8-max)、[Flash 模型价格](https://help.aliyun.com/zh/model-studio/qwen3-8-flash)

第一版沿用当前请求的隐式缓存方式，正确记录缓存命中；同时定义显式缓存创建的计量口径。启用显式缓存是另一个会改变请求内容和费用结构的优化，不作为展示费用的前置条件。

### 缓存与输出的含义

- 隐式缓存自动启用，没有额外创建费；未命中部分仍按普通输入计价。实际命中数以上游响应为准，不能把本地重复文本或固定资料大小当作已命中数量。
- 显式缓存通过 `cache_control` 开启，当前为 5 分钟有效期，命中会续期。创建部分、命中部分与普通输入分别计价；一次请求只适用显式或隐式中的一种模式。上述规则来自[上下文缓存说明](https://help.aliyun.com/zh/model-studio/context-cache)。
- 本次核对的模型专属价表未单列按 token × 小时收取的缓存存储费；首版不增加这项费用，也不套用其他供应商的 1 小时缓存价格。
- 输出取 `completion_tokens`；`reasoning_tokens` 是其细分信息，不再次相加。当前客户端关闭思考，仍必须按实际返回用量计算，不能用 `max_tokens` 或回答字符数代替。[Chat Completions 返回契约](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)

## 计算与采集口径

### 把输入拆成互不重复的费用项

当前使用 OpenAI 兼容 Chat Completions，字段映射如下：

| 上游字段                                                  | 用途                                     |
| --------------------------------------------------------- | ---------------------------------------- |
| `usage.prompt_tokens`                                     | 本次输入总量，包含命中及创建部分         |
| `usage.prompt_tokens_details.cached_tokens`               | 缓存命中输入；按本次实际缓存模式选择单价 |
| `usage.prompt_tokens_details.cache_creation_input_tokens` | 显式缓存创建输入                         |
| `usage.completion_tokens`                                 | 输出总量                                 |
| `usage.prompt_tokens_details.cache_type`                  | 显式缓存的响应标识，可与请求方式核对     |

字段依据 [Chat Completions 契约](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)。缓存文档的 OpenAI 示例也用“总输入减创建减命中”计算普通输入。[官方计算示例](https://help.aliyun.com/zh/model-studio/context-cache)

设 `P` 为总输入、`H` 为缓存命中、`W` 为创建、`O` 为输出：

```text
普通输入 U = P - H - W
单次费用 = (U × 普通输入价 + H × 本次缓存命中价
           + W × 缓存创建价 + O × 输出价) / 1,000,000
单步费用 = 本决定全部调用尝试的已知费用之和
整局费用 = 本局全部调用尝试的已知费用之和
```

缓存创建价是该部分的完整单价，不能先对全部 `P` 收取普通输入费，再额外加一笔创建费。隐式请求没有创建行为，`W=0`；不得把 `P-H` 全部误标为创建缓存。

规范化用量只需要五个互斥桶：普通输入、隐式命中、显式命中、显式创建、输出。界面把两个命中桶合并成“缓存输入”，计算层保留单价区别。`text_tokens` 与 `total_tokens` 都不作为新增收费项；`cache_creation.ephemeral_5m_input_tokens` 是创建细分，不与创建总数相加。

五项价格以整数“分／百万 token”保存，计算用 BigInt；最小计量单位为 10⁻⁸ 元，API 返回八位小数金额字符串。逐步显示可四舍五入，整局必须从未舍入用量计算，不能把四位小数的界面金额相加。

### 哪些调用计入

| 场景                                                   | 计费展示                                                 |
| ------------------------------------------------------ | -------------------------------------------------------- |
| 正常模型选择、效果对象或顺序选择                       | 按该决定所有实际调用的用量累计                           |
| 模型回答格式错误、引用非法、输出到长度上限、命令被拒绝 | 已取得有效用量的调用仍计入；执行失败不等于没有调用成本   |
| 服务重试                                               | 每次尝试分别记录，决定行显示合计；详情可查看每次尝试     |
| 过期或取消后仍收到有效响应                             | 计入原决定及原对局，继续拒绝过期游戏命令                 |
| 等待、机械确认、没有调用模型的兜底                     | 显示 `—`，悬停可说明“未调用模型”                         |
| 模型失败后使用规则兜底                                 | 保留此前模型尝试的成本，不能因最终来源为 FALLBACK 而清零 |
| 网络中断、取消、响应读取截断、缺少关键用量             | 标记用量未确认，不能当作免费或零 token                   |
| 组装失败或明确在发送前取消                             | 未调用模型，不新增模型费用                               |

用量解析与 `choices` / `selection` 校验分开：只要收到可验证的用量，就先记录消耗。token 应为非负整数，并满足 `H + W ≤ P`；矛盾数据标为用量未确认，不用截零掩盖错误。未启用显式缓存时缺少创建字段可确定为 0；缺少缓存命中字段不能依据文本重复程度补数。

未确认用量通过持久计数 `attempts` 与 `reportedAttempts` 的差值显式暴露：`reportedAttempts < attempts` 即存在未确认用量。计费视图与投影另提供派生字段 `unreportedAttempts`（= attempts − reportedAttempts，其中仍在途的部分由 `pendingAttempts` 单独区分）；该字段只在投影时计算，不写入 `match_records.ai_billing`，旧记录随时可由两个持久计数重算，保持 JSONB 向后兼容。`estimatedCny` 只累计已报告用量；展示端必须依据该差值标注未确认次数，不能因金额为零或仅为已知金额而把统计当作完整。

“用量未确认”表示缺少足以计价的响应事实；当前允许创建的模型均有固定单价。无法确认的 HTTP 错误也不自行推断为扣费或免单。取消请求无法保证上游停止生成，精确现金扣款需以供应商账单核对。

## 观察框与历史展示

### 每一步的小金额

在现有决定行的状态旁增加右对齐的弱强调金额，详情标题也可显示同一金额。沿用现有字体与日夜主题，数字使用等宽数字特性，字号约 12px；主要视觉仍留给动作与执行结果。

| 状态                     | 行内示意        | 悬停内容                                                     |
| ------------------------ | --------------- | ------------------------------------------------------------ |
| 已得到完整用量           | `≈¥0.3866`      | `输入 29,797 + 缓存输入 17,408 + 缓存创建 0 → 输出 81 token` |
| 正在调用                 | `统计中`        | 请求结束后显示用量                                           |
| 重试中，已有一笔已知金额 | `≈¥0.3866…`     | 已返回用量的四项合计；另标“1 次待统计”                       |
| 存在无法确认的消耗       | `已知 ≈¥0.3866` | 四项已知合计；另标“1 次用量未确认”                           |
| 从未调用模型             | `—`             | `未调用模型`                                                 |

默认提示只有一行四项 token 数；有异常或重试才加一条短说明。普通价格规则、请求 ID、原始 usage 留在现有详情中，不塞进 hover。极小但非零的价格显示 `<¥0.0001`，避免四舍五入成免费。

同一内容支持键盘聚焦；触屏点击金额查看，Esc／点击外部关闭，不影响选择决定和当前对局。复用现有提示层，并处理观察框滚动区裁剪与窄屏换行。

“一步”按现有 `decisionId` 定义，不按游戏回合合并。起动、支付选择、检视选择可以分别有价格；一个 HTTP 回答产生多个规则效果仍只计一次，纯机械后续没有新增费用。

### 一场对局的总费用

观察框顶部显示 `本局 ≈¥5.2995`；有未确认尝试时显示 `本局 已知 ≈¥5.2995`，提示中注明未确认次数。在途请求以“待统计”区分。这里的 5.2995 仅是界面示意，不能将上述不完整旧日志直接当成完整实测局费。

总额包含被筛选隐藏、已淘汰、失败和过期调用。搜索、查看历史决定、关闭观察框或重复轮询不会改变总额。当前选中决定的小金额仍只属于该决定。

AI 会话列表显示本局累计。超过当前会话的一小时保留期后，从管理员历史对局详情读取持久记录；即使回放已经清成 `METADATA_ONLY`，仍显示该局费用与统计完整性。计费字段只投影给有权查看该 AI 调试局的管理员，不进入普通 `PlayerViewState`。

导出中区分 `decisionBilling` 与 `matchBilling`：单决定导出也可携带整局累计，但必须显式标注范围。重材料不完整与计费统计不完整分别报告，不能用同一个缺失标记代替。

## 最小持久化与生命周期

### 复用对局根记录

只在 `match_records` 增加一个可空的 `ai_billing` JSONB，承载本局计价事实，不建立独立账单／流水表。金额由该字段中的冻结价格和累计用量直接计算。

| 内容                                   | 当前读取者               | 为什么需要保存                                                       |
| -------------------------------------- | ------------------------ | -------------------------------------------------------------------- |
| 本局价格快照：模型、核价日期及五项单价 | 费用计算与历史详情       | 当前代码价格可能变化，旧对局费用不能随当前价格重算；配置正文也会过期 |
| 五项累计 token 数                      | 会话总额、历史详情和导出 | 旧决定／正文会淘汰，无法从现有长期规则记录还原上游用量               |
| 发起尝试与取得完整用量的计数           | 统计完整性展示           | 中断和缺失响应不能被当成 0 元；正常游戏动作数不等于模型调用数        |
| 计费快照 revision                      | 持久写入边界             | 防止较旧的异步保存覆盖包含迟到响应的新累计值                         |

不再持久化一个可由这些事实计算的 `totalPrice`，也不另外保存每回合汇总、价格历史表或每次完整 prompt。每步用量和缓存模式作为现有 trace 决定的轻量元数据保存，在决定保留期间不依赖正文解析；决定淘汰后，整局累计仍在根记录中。

地域与币种固定为北京 CNY，不重复存入业务字段。价格表放在服务端 `billing.ts` 中，首版登记本文两个精确模型与明确的北京人民币口径，开局时冻结。当前一局只使用一个模型和一套价格，不提前实现局中混合模型、汇率换算或价格管理后台。

### 写入顺序与中断

1. 创建 AI 对局后、启动驱动前初始化计费记录；写入失败则不开始模型调用。
2. 每次准备实际发送前登记一次待统计尝试；本地发送前取消可撤回该待统计项。数据库提交与网络发送之间若进程崩溃，只能保留“未确认”，不声称一定已发送或一定免费。
3. HTTP 客户端取得有效用量时，以原 `matchId + taskId + attempt` 完成一次计量，更新累计快照并落盘，再独立处理诊断材料和模型选择。无有效用量则保留未确认数量。每次尝试以当前 HTTP 回调闭包保持完成标记；在途计数属于当前调用运行态，不新增持久请求状态表。
4. 用量采集必须覆盖 `requestWithDeadline` 已返回之后的迟到响应，不能只挂在“命令接受”或 driver 的 `Promise.race` 胜出分支上。计费回调闭包绑定原对局，旧决定淘汰也不丢弃整局用量。
5. 同一尝试的用量至多累计一次。数据库写入保存带 revision 的绝对累计快照，同版本重写幂等，旧版本不能覆盖新版本；重试写库不会重发模型请求或重复执行游戏命令。
6. 自然结束、主动结束和失败停止都保留已发生费用。结束时保存当前累计；尚有本地在途请求显示待统计，之后的有效迟到用量继续更新原局。没有 usage 的中断调用始终保留不完整标记，不无限等待取消确认。

计费存储出错时，界面标明保存失败，保留内存累计，每次保存最多尝试两次；下次准备请求时先重试保存，仍失败则本次请求不发送，按可重试服务错误进入既有重试与连续失败停止政策，而不是当作部署适配错误立即永久停止。已经成立的游戏动作与胜负不回滚，也不把计费保存失败当作模型选择失败。HTTP 在队列外执行，观察读取不触发保存、重算上游用量或唤醒驱动。

这保证已落盘的累计在浏览器断线、关闭观察框、会话过期和服务重启后仍可读取；外部响应在崩溃时丢失的部分只能标为未确认，不能承诺恢复供应商未返回的准确费用。

### 历史数据

停机迁移增加字段，旧记录保持 `NULL`，定义为“未采集计费事实”。新建 AI_DEBUG 对局必须初始化当前结构。历史页显示“未记录”，不能通过旧日志大小、回合数或现在的平均费用填出整局价格；读取路径不做旧格式 fallback 或懒回填。

本轮的旧日志计算只作为离线样例，不写回数据库。首版也不承诺永久保留每一步用量明细；用户要求的长期记录是整局累计。若以后明确需要逐调用长期对账，再增加相应事实存储。

## 实现入口与验证

`configuration.ts` 读取平台持久 URL/Key，并在开局时冻结；配置更新只影响新局。使用现有加密与出站校验，不新增配置表或环境变量备用路径。

- `src/server/ai-battle/billing.ts`：固定单价、互斥分桶、精确金额及每局累计；`model-client.ts` 在每次 HTTP 回包处独立计量。

- `AiBattleService`：创建时初始化、结束时刷新累计；`GET /api/admin/ai-battle/records/:matchId/billing` 从数据库读取，不依赖会话/日志保留期。路由继续要求当前 `rules.manage` 与原局真人归属。

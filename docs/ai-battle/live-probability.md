# LIVE 成功率参考

AI 在 `LIVE_SET` 请求的 `decisionBrief.liveSet.probabilityReference` 自动获得组合比较摘要，Codex 和 API 模型共用。自动基线无需额外模型调用；模型另可在同一窗口申请一批条件查询，收到结果后再用一次模型调用提交最终选择。无需新增 HTTP 接口、数据库迁移或环境开关。更新后端进程后，新建对局即可使用。观察面板与归档中的真实 `REQUEST` 包含该字段，原 `SAMPLE.input` 不包含派生的 decisionBrief；当前没有独立前端概率控件。

## 计算口径

`live-probability.ts` 是纯数值组合计算器：将单张卡的全部印刷 HEART 作为一个整体无放回抽取，按总量和所需指定色分组进行 BigInt 组合计数，最终复用现有 `HeartPool` 判断。DRAW 不增加声援，SCORE 不当 HEART；多个 LIVE 合并一次判断。失败划分为“总心不足”和“总心足够但指定色不足”两个互斥类别。

`live-probability-summary.ts` 只读取冻结的己方构筑和当前按席位脱敏的观察，扣除己方可见手牌、舞台及叠放成员、LIVE、成功区、休息室、除外和结算区域，核对结果与主卡组张数。既不读取真实牌库身份/顺序，也不读对手手牌或卡组。扣除无法闭合、己方正面不完整、仍有检视区域占用时，返回 `UNAVAILABLE`，不猜缺失数据、不停止对局、不删除合法候选。

当前有效舞台心/刀、投影中已经成立的玩家 HEART、需求修正和判心变色会参与计算；只消费数值，不解释卡文。现有 `context.knownDeckTop` 的一张已知顶牌先按盖牌补抽时点消费；其余牌按均匀混合估算。**未重建洗成员回底等历史牌群，因此结果是条件参考，不能称为真实牌序下的精确成功率。** 函数内的精确组合计数不消除输入假设造成的误差。

覆盖三曲以内组合，并对各组合可以搭配的不同成员盖牌和最终盖牌数计算范围。先补抽，再将成员盖牌送入休息室，再声援；至多处理一次刷新。如果补抽耗尽旧牌库，尚未揭示的成员盖牌不能提前进入那次刷新池。`successProbabilityRange` 是不同盖牌完成方案产生的最小／最大条件概率，**不是置信区间，也不是可以套给任意盖牌的统一概率**。两个失败类别的范围端点不要求互相加和为 1，因为端点可能来自不同完成方案。

每次摘要最多展示 24 种 LIVE 组合，单曲／双曲／三曲交错枚举，超过部分以 `omittedCombinations` 明示；全部摘要共享 150,000 次 DP 转移预算。超出算力、设置额度超过三张、候选超过 24 张或所需牌量超过一次刷新能力时，相关计算返回 `UNAVAILABLE`。未展示/无法计算的组合仍可合法选择，不能按缺少概率判为劣势。

## 未结算卡效与决策职责

基线不自动应用未来的小鸟补心、三曲加分、六色加分、追加／重做声援等能力。`printedScore` 只是 LIVE 印刷分数之和，模型仍须核对可实际兑现的卡效、费用和时点。基线概率为 0 或 1 不代表最终卡效结算必败或必成。

内部 `estimateAiLiveSet(input, ownDeck, finalSetRefs, assumptions)` 可针对一组完整盖牌做数值条件分析；批量入口 `estimateAiLiveSets` 共用一次观察准备和 150,000 次 DP 转移预算。`additionalHearts`、`additionalCheer` 随返回值保留，表示“假设这些条件已兑现”。函数不验证额外能力能否合法发生，不修改权威状态。

## 模型只读批量查询

`live-probability-query.ts` 接入 Codex 与 API 两条客户端。在 `LIVE_SET` 模型可以直接提交原动作，也可以先输出下面这种 JSON（候选引用为示意）：

```json
{
  "tradeoff": "比较两种补心配色",
  "selection": {
    "kind": "LIVE_PROBABILITY_QUERY",
    "scenarios": [
      {
        "id": "two-pink",
        "cardRefs": ["c1", "c2", "c3"],
        "additionalHearts": [{ "color": "PINK", "count": 2 }],
        "additionalCheer": 0,
        "assumptionNote": "假设小鸟补两粉的条件与费用均能兑现"
      },
      {
        "id": "two-yellow",
        "cardRefs": ["c1", "c2", "c3"],
        "additionalHearts": [{ "color": "YELLOW", "count": 2 }],
        "additionalCheer": 0,
        "assumptionNote": "假设小鸟改选两黄且条件与费用均能兑现"
      }
    ]
  }
}
```

每窗口最多一批、每批 1—8 组。各组的 `cardRefs` 必须是当前窗口的完整最终盖牌组合，至多三张，按原 min/max/group 约束校验；不能直接传牌库、对手状态或任意命令。额外各色心与声援次数均为 0—120 的整数；颜色不能重复，`GRAY` 只补总量，`RAINBOW` 表示 ALL，不能把“可选一种颜色”当成 ALL。只填写尚未计入当前观察的增量。每组保留 `assumptionNote`，不判断其真实性；盖牌补抽后才知道的新信息不能预先用于选牌。

返回每组输入假设、成功概率、总量不足/指定色不足两类概率、印刷分数和是否跨刷新，或具体 `UNAVAILABLE` 原因；`assumptionsVerified=false` 明示能力未验证。不能计算不代表该动作非法。无效请求返回原因后只允许最终回答，不继续修复查询；二次查询或非 LIVE 设置窗口的查询交回原无效输出处理，绝不转为游戏命令。

这是服务端拦截 JSON 的只读查询，不开放 Codex 的文件、网络或 shell 工具，也不改变玩家公开协议或权威命令。Codex 同线程只追加结果；无状态模式或查询后恰好换线程则重带当前观察、查询与结果。输出 schema 跨窗口和查询轮次保持一致。API 保留原消息前缀，追加 assistant 查询与计算结果。两次真实模型请求分别计费；Codex 在最终回答前重新检查累计预算，查询不绕过原登录、取消、上下文和预算保护。整段往返共用原窗口的超时，失败或失效不会重开整批查询；最终选择仍由原解析、freshness 和 command 链校验。

观察面板与归档增加 `LIVE_PROBABILITY_QUERY`、`LIVE_PROBABILITY_RESULT` 和拒绝原因，保留两次请求/响应及 `queryRound=0/1`。查询后的回答会增加一次模型调用；已有自动基线足够时应直接决策，不要求每轮必查。

概率只回答“唱成的机会”。模型须比较可实现分数、对手公开终结威胁、双方成功区及后续资源；不能总选最高成功率，也不能因为追加 LIVE 存在失败可能就一概排除。留后续歌源须以有合理机会进入下一轮为前提。通用提示词要求同时比较唱成后的赢分机会、失败后果与平局续战价值：稳健低分方案说明公开威胁与续局优势，高风险方案说明额外分数改变的胜负结果；不默认对手最强组合、不编造隐藏持牌概率，不以固定必赌阈值或成功率乘分数取代判断。只在现有预算结论中简述，不增加回复轮次或卡组专属分支。

## 离线验证与试玩

单元测试用独立小牌库排列穷举核对无放回、同卡多心、ALL 分配、已知顶牌、补抽和刷新边界，并检查冻结构筑扣除、隐藏字段不访问、选择约束和不可计算时不改变候选。T4 的简化条件案例与 Sider 原计算器的组合结果一致。

2026-09-20 对本地归档 `8477ca56` 的窗口 126（T4）与 184（T5）重新计算：均覆盖 7 个组合，无省略或计数错误。最终代码各重复 8 次，T4 约 2.4–9.6 ms，T5 约 10.4–14.4 ms，新增摘要分别 2,669／2,640 UTF-8 字节。此测量是本机两个窗口的计算开销，不是 token 数或模型整体延迟承诺；已知牌群未纳入，结果仍按所列假设解释。

首次接入定向回归为 11 个文件、240 项测试通过（包括纯计算、查询输入与失效边界、Codex/API 往返与计费、上下文轮换、原模型输入、AI 决策和 Like a Treasure 规则闭环）；共享、服务端与前端 TypeScript，Prettier 和 `git diff --check` 通过。该开发验证未进行真实模型调用或服务器重启；后续用户试玩见下文。

下一局检查 LIVE 设置的 REQUEST 是否出现 `probabilityReference`，以及 RESPONSE 是否比较不同组合的分数与失败原因、正确另计尚未结算的卡效。T4 实际归档窗口也经过新的批量查询往返离线验证：用额外补一粉的纯数值假设、统一盖三抽三（不表示小鸟可只补一粉），5／6／7 分分别得到 95.960%／95.956%／82.731% 的条件成功率，单次本机处理约 5 ms；不是新增真实模型对局，也不是忽略历史牌群后的真实胜率承诺。新增批量查询测试还覆盖两种模型运输、逐次计费、预算中止、失效、重复查询拒绝、跨线程恢复及查询不改变真实 GameSession。后续用户 Astra low 对局归档已确认自动基线进入请求，T5 真实执行一批四组条件查询，比较双曲约 99.90% 与三曲约 69.68% 的条件唱成率；该局 T6 因公开历史旧容量停止，扩容后的完整自然局及本次通用提示词修订仍待试玩。不将查询成功或离线测试通过等同于策略强度改善。

# 赛季管理员角色

> 文档类型：专题说明
>
> 适用范围：固定平台角色、后台授权、用户角色管理与赛季管理员的当前上线边界
>
> 当前状态：开发基线；赛季写操作的持久审计、破坏性操作原因、完整负向矩阵与 E2E 验收完成前，不得向真实运营账号分配 `season_admin`

> 权威关系：产品目标以 [项目总体需求](../PROJECT_REQUIREMENTS.md) 为准，系统全景与关键代码路径以 [系统设计](../system-design.md) 为准；本文只维护赛季管理员的权限、接口、运行边界与未完成上线门槛。

## 当前模型

平台使用固定单角色模型：

| 角色值         | 中文名称   | 当前职责                                                                                             |
| -------------- | ---------- | ---------------------------------------------------------------------------------------------------- |
| `user`         | 普通玩家   | 使用玩家功能，不进入后台。                                                                           |
| `season_admin` | 赛季管理员 | 运营排位、排位卡组分类、主题赛季与赛季入口显示，不拥有平台、卡牌、游戏规则或构筑合法性规则管理能力。 |
| `admin`        | 平台管理员 | 拥有全部后台能力，并包含赛季管理员的全部权限。                                                       |

角色类型与能力矩阵的单一实现位于 `src/shared/auth/permissions.ts`。角色之间不通过字符串、数组顺序或数值比较推断权限；每条受保护路由声明所需的 `ManagementPermission`，由 `hasPermission` 与 `requirePermission` 统一处理。

| 能力                             | `user` | `season_admin` | `admin` |
| -------------------------------- | :----: | :------------: | :-----: |
| `season.ranked.manage`           |   否   |       是       |   是    |
| `season.deck_classifier.manage`  |   否   |       是       |   是    |
| `season.theme.manage`            |   否   |       是       |   是    |
| `season.entry_visibility.manage` |   否   |       是       |   是    |
| `platform.manage`                |   否   |       否       |   是    |
| `cards.manage`                   |   否   |       否       |   是    |
| `cards.sync`                     |   否   |       否       |   是    |
| `rules.manage`                   |   否   |       否       |   是    |
| `users.list`                     |   否   |       否       |   是    |
| `users.roles.manage`             |   否   |       否       |   是    |

## 授权与会话边界

认证链路、JWT 和前端 `Profile` 均接受三种正式角色。`profiles.role` 由 `0028_add_season_admin_role.sql` 的数据库约束限制为 `user | season_admin | admin`；迁移、停机检查和回滚边界见 [`drizzle/migration-notes/season-admin-role.md`](../../drizzle/migration-notes/season-admin-role.md)。

特权请求不能只信任 access token 内的角色。`requirePermission` 先以 token 角色做允许列表检查，再查询 `profiles` 验证当前角色仍与 token 一致且仍具有该能力：

- 低权限 token 在提升后不会自动获得新权限，必须重新登录或刷新会话；
- 降权后的旧特权 token 在下一次受保护请求得到 `AUTHORIZATION_STALE`；
- 角色变更事务会删除目标用户的全部 refresh token；
- 前端收到 `AUTHORIZATION_STALE` 后会清除会话状态、离开后台并提示重新登录。

`requireAdmin` 是 `requirePermission('platform.manage')` 的窄别名。原本只允许平台管理员的卡组越权访问、管理员回放、联机房间、维护公告、快捷表情和壁纸处置仍使用该平台能力，不会因新增角色而下放。

## 已获能力

| 路由                                                      | 所需能力                         | 当前范围                                                   |
| --------------------------------------------------------- | -------------------------------- | ---------------------------------------------------------- |
| `/api/admin/ranked/**`                                    | `season.ranked.manage`           | 排位赛季、运营概览、对局处理、结算重试及既有评分修订流程。 |
| `/api/admin/deck-classifier/**`                           | `season.deck_classifier.manage`  | 卡组分类名称、样板、规则、发布、重分类和人工复核。         |
| `/api/admin/theme-table/**`                               | `season.theme.manage`            | 主题赛季、预组、组合、分配与既有运营统计。                 |
| `PUT /api/site-announcements/admin/player-battle-entries` | `season.entry_visibility.manage` | 单独维护排位与主题赛季的玩家入口显示。                     |

赛季管理员在管理中心只看到“赛季运营中心”中的排位、排位卡组分类、主题赛季和玩家赛季入口设置。平台管理员使用同一批页面，但还能看到平台、卡牌、游戏规则和用户管理模块；页面不为两类角色分叉实现。卡组“识别规则”只是对长期卡组观察做统计分类的受限数据条件，不是卡牌效果规则、对战规则或构筑合法性规则。

入口显示只控制玩家大厅与对局准备页的发现性，不会改变赛季生命周期、开放时段或候场运行态。隐藏入口不会暂停已开放的匹配，暂停仍需在对应赛季页面执行。

### 用户管理与角色分配

用户管理只属于平台管理员：

| 路由                                | 能力                 | 行为                                                                            |
| ----------------------------------- | -------------------- | ------------------------------------------------------------------------------- |
| `GET /api/admin/users`              | `users.list`         | 按注册时间倒序、ID 稳定排序的服务端分页；支持用户名、显示名称、邮箱和角色筛选。 |
| `PUT /api/admin/users/:userId/role` | `users.roles.manage` | 修改三种正式角色，使用 `expectedRole` 做乐观并发校验。                          |

列表只返回用户 ID、用户名、显示名称、邮箱、邮箱验证状态、角色、卡组数量和注册时间；不会返回密码摘要、refresh token、验证 token、JWT 或其他认证秘密。每页默认 50 条、最大 100 条，不会把全量账号下载到浏览器后再分页。

角色变更在一个事务中锁定当前平台管理员集合与目标用户。过期的 `expectedRole` 返回 409；角色不变时不写入也不撤销会话；降级最后一个 `admin` 返回 409。通用 `PUT /api/profiles/:id` 已不接受 `role`，避免绕过这些约束。当前角色变更不写入 `management_audit_logs`，也不要求填写原因或二次确认。

## 明确隔离的能力

`season_admin` 被服务端拒绝以下范围：

| 领域       | 排除范围                                                                 |
| ---------- | ------------------------------------------------------------------------ |
| 平台运行   | 维护状态、限制新对局、公告、全局联机房间、管理员观战与管理员回放。       |
| 卡牌与资源 | 卡牌草稿/未发布数据、卡牌 CRUD、导入导出、发布状态、卡图和卡效 AI 配置。 |
| 构筑与内容 | PT 限制表、快捷表情目录、壁纸处置。                                      |
| 用户与权限 | 用户列表、其他玩家档案、角色授予或撤销。                                 |
| 私有数据   | 其他玩家的私有卡组、认证秘密、全局隐藏对局信息。                         |
| 发布运维   | 生产发布、数据库迁移、卡牌同步、密钥与对象存储管理。                     |

赛季管理员仍可使用普通玩家的公开卡牌读取和本人云端卡组；主题预组使用云端卡组时仍只允许读取操作者本人的卡组。不得为了后台卡牌选择而开放 `/api/cards/admin`、`/api/cards/export` 或 `/api/cards/status-map`。

## 数据库与审计现状

迁移 `0028_add_season_admin_role.sql` 同时创建 `management_audit_logs` 骨架，包含操作者、操作者角色、scope、action、目标、request ID、结果、原因与脱敏前后摘要的字段，以及 actor、scope/target 和时间索引。当前表还未接入赛季写操作，不能被描述为完整审计能力。

当前排位部分实体已有 `created_by` / `updated_by` 或专用评分修订记录；主题赛季的管理动作主要保留结构化应用日志。这些机制不足以支持向真实运营账号委派赛季管理员。

## 上线前必须完成的门槛

在分配任何真实 `season_admin` 前，必须完成并验证：

1. 所有排位、主题赛季和入口显示写操作在同一权威事务中写入追加式持久审计。
2. 排位草稿删除、主题预组退休及其他破坏性赛季操作通过窄请求体提交非空原因；赛果更正和评分修订继续保留既有原因、预览签名、状态和并发保护。
3. 为每类平台、卡牌、规则、用户和赛季路由补齐完整的服务端正负权限矩阵；前端仅作为体验层，不能代替服务端断言。
4. 完成用户管理、即时失权、最后管理员保护、赛季后台与直接 URL 访问的 E2E 验收。
5. 在停机窗口完成数据库迁移、应用与前端切换。迁移前确认至少存在一名可登录的 `admin`；不增加旧角色格式的运行时 fallback 或 dual-read。

权限拒绝、输入失败和事务冲突当前写入结构化安全日志，不得伪装为已成功提交的业务审计。若未来需要长期保存失败尝试，应使用独立安全事件存储，而不是在会回滚的业务事务中写入成功形态的审计行。

## 验证边界

当前自动化测试覆盖三角色权限矩阵、JWT、迁移约束、排位/主题/入口/用户管理的授权核心路径，以及分页、字面搜索转义、角色并发冲突、refresh token 撤销、最后管理员保护和 profile 接口拒绝角色修改。

尚未覆盖的上线门槛以“上线前必须完成的门槛”为准，尤其是完整负向矩阵、持久审计接线和真实浏览器 E2E。

## 非目标

当前模型不包含自定义角色、任意权限勾选、按单赛季分配负责人、双人复核、玩家封禁/聊天审核、删除用户、代改密码或查看用户会话。新增这些能力需要独立定义权限、持久化与审计边界，不能通过扩大 `season_admin` 的现有权限隐式实现。

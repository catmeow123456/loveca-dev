# Loveca 联机对局快捷表情需求与设计

> 文档类型：设计文档
> 适用范围：普通房间联机、休闲公共牌桌、赛季排位，以及这些对局的授权观战视图
> 当前状态：首版核心链路已实施；公共牌桌、排位与多主题扩展仍待持续验收
> 更新日期：2026-08-02

## 1. 背景

当前正式联机对局已经提供按 `matchId` 隔离的轻量文字聊天：对局双方可以发送简短纯文本，授权观战者只读；消息支持刷新和短暂断线后的游标补拉，但不进入权威对局状态、数据库、历史记录或回放。

文字聊天可以表达完整信息，但在实际打牌时存在三个不足：

- 输入会打断玩家查看卡牌、结算效果和思考行动；
- “我还在思考，请稍等”这类高频状态需要反复输入；
- 公共牌桌和排位中的陌生玩家更需要低压力、低歧义的礼貌交流方式。

因此在现有聊天能力上增加一组服务端白名单控制的快捷表情。第一版不是开放式贴图平台，也不是任意 Unicode Emoji 面板，而是数量有限、含义明确、视觉统一的 Loveca 对局表情。

## 2. 产品目标

### 2.1 核心目标

- 玩家可在不离开对局桌面的情况下，用一次或两次点击发送常用状态和礼貌表达。
- 必须提供醒目且不催促对手的“深度思考中…”表情，帮助玩家说明当前仍在线、正在阅读或计算。
- 普通房间、公共牌桌和排位复用同一套表情能力与权限规则。
- 表情到达时可被对手及时感知，但不得遮挡关键卡牌、效果处理、合法目标或主要操作。
- 通过固定表情目录、统一限频和现有静音入口，降低刷屏、嘲讽和骚扰风险。

### 2.2 成功信号

首版上线后可以关注以下不包含聊天正文的聚合信号：

- 有效联机对局中的表情使用率；
- 各表情的发送占比，尤其是“深度思考中…”和“谢谢！”；
- 表情发送被限频的比例；
- 玩家开启“静音对手”的比例是否异常上升；
- 表情发送失败率和游标补拉异常率。

这些信号用于判断表情集是否实用，不用于评分、匹配、处罚或对局胜负判定。

## 3. 非目标

第一版不包含：

- 玩家上传、自定义或从外部链接加载表情；
- GIF、视频、带声音贴图或全屏特效；
- 给具体聊天消息添加回应；
- 观战者发送表情；
- 房间准备阶段、公共候场阶段或排位候场阶段的大厅聊天；
- 表情商城、稀有度、收藏、解锁或付费表情包；
- 将表情写入 `GameState`、公共对局日志、历史记录、回放、积分账本或裁判事件；
- 使用表情代替撤销、重开、认输、自由操作模式切换或其他需要明确命令/双方确认的行为。

## 4. 产品定义

### 4.1 系统形态

第一版产品名使用“快捷表情”，技术模型使用 `emote`。每个表情由稳定的 `emoteId`、中文可访问名称和本地静态资源组成。客户端只能发送服务端当前允许的 `emoteId`，不能提交任意图片地址、任意显示文字或自定义动画参数。

表情作为现有单局聊天流中的一种结构化条目，与文字消息共用：

- `matchId` 生命周期；
- 参与者鉴权和当前房间成员校验；
- 服务端递增序号与客户端幂等提交标识；
- 游标分页、刷新补拉和有界内存保留；
- 授权观战者只读链路；
- 对手静音和同步失败反馈；
- 重开、双方离开或服务重启后的清理边界。

不为普通房间、公共牌桌和排位建立独立表情服务。三种来源在进入正式 `ONLINE` 对局后使用同一实现。

### 4.2 首发表情目录

首版固定提供 6 个表情，以控制选择负担并方便观察真实使用情况：

| `emoteId`                   | 玩家可见名称 | 主要场景                                 | 设计语气                     |
| --------------------------- | ------------ | ---------------------------------------- | ---------------------------- |
| `DEEP_THINKING`             | 深度思考中…  | 阅读卡文、计算费用或规划行动，请对手稍候 | 专注、认真，不显得慌乱或敷衍 |
| `THANK_YOU`                 | 谢谢！       | 对手配合操作、接受等待或完成友好交流     | 真诚、克制                   |
| `NICE_TO_MEET_YOU`          | 请多指教！   | 开局问候                                 | 友好、对等                   |
| `NICE_PLAY`                 | 漂亮！       | 肯定对手的操作或组合                     | 欣赏，不夸张嘲讽             |
| `GOOD_GAME`                 | 好局！       | 对局结束或精彩阶段后                     | 有体育精神                   |
| `SORRY_TO_KEEP_YOU_WAITING` | 抱歉，久等了 | 思考结束或临时停顿后                     | 简短、礼貌                   |

目录评审原则：

- 优先保留能说明对局状态或增进礼貌的表达；
- 不加入大笑、愤怒、挑衅、质疑、哭闹、催促等容易被反向使用的表情；
- 不加入“同意”“拒绝”“可以”“收到”等可能被误认为规则确认的文案；
- 不依赖特定角色、团体或卡牌梗，避免对新玩家造成理解门槛；
- 表情含义必须仅凭图形与短标签即可理解，不要求玩家记忆编号。

## 5. 体验需求

### 5.1 入口

- 保留参与者现有的“局内聊天”顶层按钮，点击后直接打开完整文字聊天，不增加“交流 → 打开文字聊天”的中间步骤。
- 在己方身份标识旁提供独立的“快捷表情”图标按钮。它与文字聊天共享消息流、未读、静音和请求状态，但不共享入口层级。
- 点击“快捷表情”后直接看到 6 个表情，点击表情立即发送；从桌面发出任一表情仍只需要两次点击。
- 表情菜单在桌面端锚定于己方身份附近，使用 3 列 × 2 行轻量弹层；移动端使用 2 列 × 3 行、适配安全区的轻量面板。单个点击目标不得小于 44 × 44 CSS px。
- 点击某个表情后不增加二次确认。发送中的表情项显示局部等待状态，并临时禁止重复触发。
- 发送成功后关闭表情菜单；发送失败时保留菜单，并在表情网格附近显示可重试的内联错误。
- 完整聊天面板只负责文字输入和共同时间流，不再内嵌第二套表情入口，避免同一功能出现两个层级不同的启动方式。
- 不使用长按、双击或悬停作为表情主入口；这些方式发现性较弱，也不适合键盘和触屏用户。
- 不提供“单击直接重发上次表情”，避免误触和排位对局中的刷屏。
- 观战者继续显示“观战聊天”只读入口，不显示身份旁的快捷表情按钮，聊天面板内也不显示表情发送控件。

推荐布局草图：

```text

工具栏 [房间] [日志] [局内聊天 2]           工具栏 [局内聊天 2]

己方身份 [玩家 A] [表情]                    己方身份 [玩家 A] [表情]
                   │                                           │
                   ▼                                           ▼
      ┌────────────────────────┐             ┌──────────────────────┐
      │ [思考中] [谢谢] [请多指教] │             │ [思考中] [谢谢]        │
      │ [漂亮]   [好局] [久等了]   │             │ [请多指教] [漂亮]      │
      └────────────────────────┘             │ [好局]   [久等了]      │
                                              └──────────────────────┘

点击“局内聊天”后
┌──────────────────────────┐
│ 局内聊天          静音 关闭 │
├──────────────────────────┤
│ 消息与表情时间流           │
│                          │
├──────────────────────────┤
│ 输入本局消息          [发送] │
└──────────────────────────┘
```

表情菜单是轻量临时层，不把表情选择覆盖到对局桌面中央；文字聊天与表情分别保持最短路径，同时复用同一个通信运行态。

### 5.2 对话流中的展示

- 文字消息与表情共用同一时间顺序和消息列表。
- 表情条目使用比普通文字气泡更宽松的留白，展示表情图、固定名称、发送者和时间。
- 自己发送的表情与普通自己的消息一样靠右；对手表情靠左；观战视图继续用双方席位颜色帮助区分来源。
- 表情名称必须以真实文本存在于可访问树中，不把关键信息只画在图片里。
- 聊天面板已经打开时，新表情只进入消息列表并正常滚动，不额外在棋盘上叠加提示。

### 5.3 聊天关闭时的即时反馈

- 收到未静音对手的新表情时，在发送者身份标识旁展示一次轻量表情浮层，使“谁发出的”无需依赖聊天面板即可被识别；不新增全屏动画。
- 浮层建议显示 72–88 px 的表情图、发送者名称和表情名称，约 3.5 秒后自动消失；点击浮层打开聊天面板。
- 同时到达多个表情时只展示最新一个，不在棋盘上堆叠；所有条目仍保留在聊天列表中。
- 浮层不得覆盖效果选择、Public Reveal Dwell、判定面板的主操作、手牌选择网格或系统错误提示。若高优先级覆盖层正在显示，应延后或仅计入未读数。
- 自己发送成功后不在自己的棋盘上播放大型浮层，以消息列表落位和按钮完成态作为反馈。
- 第一版无声音、震动和页面标题闪烁。

### 5.4 “深度思考中…”的标志性表现

“深度思考中…”是首版的主表情，不只是通用的 `🤔` 字符。建议制作原创、非角色化的透明底贴图：以卡牌/牌套轮廓、思考气泡和缓慢移动的三个思考点构成，使用项目既有主强调色与次强调色，不使用官方角色肖像或未经授权的卡图。

动态效果由 CSS 或轻量矢量层完成：思考点依次淡入，整体保持原位，不旋转、不弹跳、不覆盖其他区域。开启 `prefers-reduced-motion` 时显示静态终态，仅做极短淡入淡出。其他表情原则上保持静态，避免整套表情同时争夺注意力。

### 5.5 静音与未读

- 现有“静音对手”同时作用于文字消息和表情。
- 静音后不显示对手文字预览、表情浮层或新增未读红点；打开聊天面板后仍可主动查看完整交流记录。
- 不为文字和表情提供两套静音开关，避免玩家误判当前状态。
- 静音开关继续位于完整聊天面板，不塞入快捷表情菜单；表情菜单只承担发送表情。
- 观战者维持现有只读未读逻辑，不展示棋盘表情浮层。

### 5.6 对局阶段与模式

- 只要当前正式联机 `matchId` 仍有效且玩家仍是该局参与者，即可发送表情；是否处于自己的操作时点不影响发送资格。
- 已完成但尚未离开/清理的对局可继续发送礼貌类表情，支持使用“好局！”和“谢谢！”。
- 双方确认重开后，新 `matchId` 使用新的空交流流，旧表情不延续。
- 公共牌桌和排位不额外禁用表情；其固定目录和限频规则与普通房间一致。

## 6. 视觉与资源要求

- 表情必须延续现有产品视觉 token，不另建一套高饱和社交应用风格。
- 视觉关键词：卡牌桌、专注、友好、轻量；避免“直播打赏特效”“二次元聊天贴纸墙”和系统原生 Emoji 拼盘感。
- 每个表情使用本地矢量资源并提供静态降级表现，不依赖外部图片地址；后续若改用透明 WebP，应重新评估包体、清晰度和主题适配。
- 同一资源在 1×/2× 屏幕上应清晰，在浅色和深色主题中均有足够轮廓对比。
- 不把固定中文烘焙进唯一图片资源；界面另行渲染名称，便于无障碍、缩放和未来本地化。
- 表情浮层层级低于规则确认、效果处理、公开展示和关键错误，高于普通桌面背景。
- 视觉验收至少覆盖桌面与移动端、浅色与深色主题、普通动画与 reduced-motion。

## 7. 数据与接口设计

### 7.1 共享条目模型

局内聊天条目使用判别联合类型，继续复用现有 `/chat/messages` 读写入口：

```ts
type OnlineMatchChatEntry =
  | {
      readonly kind: 'TEXT';
      readonly messageSeq: number;
      readonly senderSeat: Seat;
      readonly senderDisplayName: string;
      readonly text: string;
      readonly sentAt: number;
    }
  | {
      readonly kind: 'EMOTE';
      readonly messageSeq: number;
      readonly senderSeat: Seat;
      readonly senderDisplayName: string;
      readonly emoteId: OnlineMatchEmoteId;
      readonly sentAt: number;
    };

type SendOnlineMatchChatEntryInput =
  | {
      readonly kind: 'TEXT';
      readonly clientMessageId: string;
      readonly text: string;
    }
  | {
      readonly kind: 'EMOTE';
      readonly clientMessageId: string;
      readonly emoteId: OnlineMatchEmoteId;
    };
```

实现时按项目的停机迁移原则一次性切换客户端和服务端类型，不在业务读取路径中保留旧 payload 的 dual-read 或 fallback。聊天本来就是内存运行态，部署切换时不需要数据库数据迁移。

### 7.2 服务端校验

- `kind: 'EMOTE'` 只能携带白名单 `emoteId`，拒绝额外图片 URL、文案、颜色或动画字段。
- 服务端返回的可见名称由客户端内置目录映射；服务端日志与协议以稳定 ID 为准。
- 幂等键继续由 `userId + clientMessageId` 构成。同一提交标识改发不同 `kind`、正文或 `emoteId` 时返回冲突。
- 表情与文字共用当前 500 条单局保留上限、100 条分页上限和递增 `messageSeq`。
- 观战读取继续校验 token、session、room generation 和 attachment generation；不新增观战发送端点。

### 7.3 限频与防打扰

- 表情和文字共用现有每用户综合窗口：1 秒最多 3 条、10 秒最多 5 条。
- 在综合窗口之上，表情额外增加每用户 2 秒一次的发送冷却，避免视觉浮层连续闪现。
- 所有限频均由服务端裁定并返回结构化 `retryAfterMs`；客户端倒计时只用于反馈，不能作为安全边界。
- 被拒绝的发送不追加序号、不进入列表，也不触发表情浮层。
- 表情目录的固定文案不走敏感词过滤；任意文字消息继续保持原过滤规则。

## 8. 权限、隐私与规则边界

- 只有当前 `ONLINE` 对局的两名有效用户参与者可以发送表情；已退出房间或失去本局资格的迟到请求必须拒绝。
- 普通观战者和管理员观战者只能读取与其当前授权单局绑定的表情。
- 表情不携带隐藏卡牌、当前选择、手牌数量或客户端本地状态，不经过 `projector` 暴露额外游戏信息。
- 表情不是权威命令，不调用 `GameSession` / `GameService`，不改变阶段、计时、优先权、操作模式或任何卡牌状态。
- “深度思考中…”只是一条交流信息，不暂停对局、不延长排位断线期限，也不阻止服务端执行现有超时政策。
- 表情不进入历史对局与回放。若未来确有举报或竞技审计需求，应单独评审持久化期限、告知文案和数据权限，不能借本需求顺带写库。

## 9. 异常与反馈

| 场景                   | 玩家反馈                                            | 状态处理                              |
| ---------------------- | --------------------------------------------------- | ------------------------------------- |
| 发送成功               | 表情进入消息列表，关闭身份旁的表情菜单              | 使用服务端返回序号去重                |
| 发送限频               | 在身份旁的表情菜单附近显示“发送太快，请 N 秒后重试” | 保留当前选择层，不制造本地假消息      |
| 网络失败               | 显示“表情发送失败，请重试”                          | 保留当前选择层，可用相同幂等标识重试  |
| 表情 ID 已下线或非法   | 显示“这个表情暂时不可用”并刷新/关闭当前选择层       | 不降级成文字消息                      |
| 拉取短暂失败           | 沿用聊天现有“正在自动恢复”反馈                      | 保留最后一份有效列表和游标            |
| 对局已失效或玩家已退出 | 关闭发送能力并提示本局已结束/不可发送               | 不触摸或复活旧房间成员                |
| 观战切换到下一局       | 清空旧局表情列表并等待新 `matchId`                  | 不跨 attachment generation 混入旧消息 |

## 10. 无障碍与输入方式

- “局内聊天”和“快捷表情”必须具有独立、稳定的可访问名称；快捷表情按钮公开展开状态，打开后焦点进入第一个表情。
- 每个表情按钮的可访问名称采用“发送表情：深度思考中”等明确结果文案。
- 快捷表情菜单支持键盘 Tab/方向键移动、Enter/Space 发送、Escape 关闭；关闭后焦点返回身份旁入口。
- 表情图必须有等价名称；装饰性动画层标记为不可访问，避免屏幕阅读器重复播报。
- 到达提示使用现有温和的 `aria-live` 策略，不因动画反复播报。
- 不只依靠颜色、位置或动画区分六个表情。
- 页面缩放至 200% 和窄屏时，表情名称不能被完全截断，托盘不能挡住发送错误与关闭操作。
- 遵守 `prefers-reduced-motion`；不加入自动声音或必须依赖听觉的反馈。

## 11. 测试与验收

### 11.1 服务端 focused tests

- 六个白名单 `emoteId` 均可发送，未知 ID 和额外自定义内容被拒绝。
- 文字与表情共用递增序号、分页、500 条裁剪、游标截断和幂等冲突规则。
- 表情 2 秒冷却与现有综合限频同时生效，并返回正确 `retryAfterMs`。
- 非参与者、已退出成员和观战者不能发送；有效参与者双方可读取。
- 授权观战者按当前 token/session/代际读取，重开后不读取旧 `matchId` 表情。
- 普通房间、公共牌桌、排位创建的正式联机对局均走同一表情运行态。
- 表情不会写入权威状态、公共事件、历史记录、回放或积分结算。

### 11.2 前端 focused tests

- 参与者从己方身份旁点击“快捷表情”后可以直接选择并发送，完整路径不超过两次点击。
- 顶层“局内聊天”保持一次点击打开文字聊天，聊天面板内不重复提供表情入口。
- 文字与表情共用的未读数显示在“局内聊天”按钮，打开完整聊天后正确清零。
- 观战视图继续使用“观战聊天”只读入口，没有身份旁的快捷表情发送控件。
- 表情条目按发送者席位正确排列，并展示名称、时间与发送者。
- 聊天关闭时只对未静音的对手新表情在发送者身份旁显示一次浮层；聊天打开或静音时不显示。
- 多条到达时浮层不堆叠，未读和游标仍准确；刷新补拉不会把旧表情当成新到达重复播放。
- 发送失败保留可重试状态，成功响应与后续轮询不会生成重复条目。
- 键盘操作、焦点返回、`aria-label` 和 reduced-motion 行为符合要求。

### 11.3 E2E 与视觉验收

- 双浏览器完成“玩家 A 发送‘深度思考中…’—玩家 B 收到浮层—玩家 B 打开聊天查看—玩家 B 回复‘谢谢！’”完整路径。
- 在普通房间、公共牌桌和排位各验证至少一局，最终以双方看到相同有序条目为结束条件。
- 授权观战浏览器能看到双方表情但没有发送控件。
- 在效果选择、卡牌检视、公开展示和移动端底部操作同时出现时，表情浮层不遮挡关键交互。
- 为桌面/移动端、浅色/深色、普通动画/reduced-motion 建立针对性截图审查；不以普通说明文案存在代替功能结果验证。

## 12. MVP 验收标准

同时满足以下条件才视为第一版完成：

1. 对局参与者可从己方身份旁的“快捷表情”入口用两次点击发出六个固定表情中的任意一个，其中包含“深度思考中…”和“谢谢！”，无需先打开完整聊天面板；“局内聊天”仍可一次点击打开。
2. 普通房间、公共牌桌和赛季排位使用同一协议、服务和共享 UI，不出现模式分叉。
3. 对手在聊天关闭且未静音时能在发送者身份旁及时看到不遮挡规则操作的表情浮层；打开聊天后能按顺序查看完整条目。
4. 授权观战者只读可见，不能发送。
5. 服务端完成白名单、参与者身份、幂等和综合/表情冷却校验。
6. 表情不改变权威对局状态，不进入数据库、历史、回放或竞技结算。
7. 静音、断线补拉、重开隔离、移动端、键盘和 reduced-motion 均通过 focused tests 或针对性验收。
8. 表情资源不使用未经授权的角色肖像、卡图或外部动态 URL。

## 13. 实施状态与剩余验收

- 已冻结 6 个首发表情的稳定 `emoteId`、中文名称和本地矢量表现，其中“深度思考中…”提供克制的思考点动画。
- 已完成 `TEXT | EMOTE` 判别联合、内存运行态、幂等比较、游标读取、综合限频、表情冷却，以及参与者和观战鉴权复用。
- 已完成共享桌面交互：文字聊天保持顶层直达，快捷表情从己方身份旁发出，文字与表情进入同一时间流，对手表情预览锚定发送者身份。
- 已覆盖桌面、移动端、授权观战和 reduced-motion 的双浏览器 E2E；公共牌桌、排位真实流程及更多主题组合仍需持续验收。
- 上线后应观察不含聊天正文的聚合使用率、限频率、静音率与失败率；若 6 个表情不足，再基于真实场景评审目录扩展。

## 14. 已确认的首版决策

1. 首发保留 6 个表情，并维持单个轻量面板完整展示。
2. “深度思考中…”采用原创卡牌轮廓意象，不建立角色设定或引入角色肖像授权负担。
3. 对手表情浮层展示约 3.5 秒，锚定发送者身份，层级低于关键规则覆盖层。
4. 已结束但尚未清理的对局允许继续发送，以支持“好局！”和“谢谢！”，但不延长房间或排位运行态生命周期。

## 15. 与现有实现的对应关系

当前实现主要涉及：

- 共享类型：`src/online/chat-types.ts`；
- 内存消息、分页、幂等、过滤与限频：`src/server/services/online-match-chat-runtime.ts`；
- 参与者与观战鉴权：`src/server/services/online-match-service.ts`、`src/server/services/online-room-service.ts`；
- REST 输入与错误映射：`src/server/routes/online.ts`；
- 客户端请求：`client/src/lib/onlineClient.ts`；
- 普通房间、公共牌桌、排位和观战共享通信入口：`client/src/components/game/MatchChat.tsx`，组件内部管理身份旁表情菜单、完整聊天面板、预览、轮询和消息状态；
- 身份定位锚点：`client/src/components/game/GameBoard.tsx`、`client/src/components/game/PlayerArea.tsx`，只声明当前真实可见的席位身份 DOM 锚点，不承载具体表情逻辑；
- 当前聊天 focused tests：`tests/unit/online-match-chat-runtime.test.ts`、`tests/integration/online-room-service.test.ts`、`tests/integration/online-route-error-handling.test.ts`。

具体表情目录、发送和展示逻辑不得写入 `GameBoard` / `PlayerArea`；这两个组件只提供席位身份锚点。公共牌桌或排位不得复制另一套聊天组件。

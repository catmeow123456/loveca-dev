# 游戏资产目录与公共资源读取

> 文档类型：需求与设计
> 适用范围：公共游戏资产目录、资源读取及后续上传迁移
> 当前状态：只读目录已实现；revision 模型、上传发布与迁移流程为后续设计

## 1. 目标与原则

本功能为公共游戏资源提供一个可查、可追踪、可迁移的目录，并继续通过同源 `/images/*` 提供读取。首期目标是：

1. 管理员能找到资源、查看当前版本、历史版本和业务引用。
2. 新资源使用对象存储，读取可以接入 CDN，前端不需要改成第三方域名。
3. 迁移可以暂停、重试和回退，不要求一次搬完全部仓库资源。

实现遵循以下原则：

- 业务服务仍是“资源在哪个业务对象上生效”的权威；资产目录是公共的文件目录和引用索引，不替代卡牌、活动、表情或音乐的业务发布规则。
- 数据库保存业务可查的元数据，对象存储保存文件内容；浏览器不持有 MinIO/S3 凭证。
- revision 创建后不可修改。需要换文件时创建新 revision，并由业务明确切换引用。
- 首期只做能支持现有业务和迁移的能力，不提前建设通用文件管理器、细粒度角色或私有资源 CDN。

现有 MinIO 的 bucket、代理和 `/images/*` 约定仍以 [MinIO 对象存储需求与设计](../minio-requirements.md) 为准；本文件只补充资产目录和迁移规则。

### 当前实施阶段

当前实现卡图、候场音乐和其他图片资源的只读目录，不实现上传、替换、发布、退役或删除 UI，也不新增资源角色。卡图目录直接读取现有 `cards.image_filename`、卡牌状态和 `source_flags`；音乐目录复用 `matchmaking_bgm_tracks` 的既有曲库服务和公共 URL；图片目录复用快捷表情目录、排位／娱乐活动的封面与徽章接口，以及前端公共图片 manifest。首期不新增资产表，因此不会出现第二份业务资源事实。卡图目录复用 `cards.manage`，音乐和其他图片目录复用现有平台或赛季管理权限。

当前可用入口为管理中心的“公共资产目录”分支：卡图目录接口为 `GET /api/admin/card-images` 和 `GET /api/admin/card-images/:cardCode`，音乐目录复用 `GET /api/matchmaking-bgm`，图片目录复用 `GET /api/match-emotes/admin/catalog`、排位／娱乐活动管理接口和 `src/shared/public-static-assets.ts`。卡图盘点脚本为 `pnpm assets:inventory:card-images`；需要读取对象内容时追加 `--verify-content`，可用 `--output <path>` 保存 JSON 报告。

目录支持逐文件下载：卡图提供已有的三种尺寸，静态图片提供当前文件，快捷表情区分静态图与动图，活动封面提供宽屏版、紧凑版和母图，活动徽章和候场音乐也可下载。公共文件直接读取目录中的同源 URL；封面母图继续通过带鉴权的既有管理接口读取。下载控件共用读取和错误反馈，不改变业务引用、文件格式或资源内容；请求失败或返回页面内容时不会保存为图片／音乐。

管理中心只保留一个“公共资产目录”入口，管理员默认打开卡图，赛季管理员默认打开图片，各目录可直接切换。表情管理和曲库管理分别从对应目录进入，返回时回到原目录。目录页面和卡图详情支持浏览器前进、后退；搜索与筛选只接受仍有效的请求结果。卡图内容校验在 10 MiB 文件、3600 万像素和 10 秒解码上限内完整解码 WebP，不以文件头可读作为校验成功。活动封面或徽章查询失败时显示具体活动的读取失败状态，相关统计暂显示“—”，刷新成功后恢复；只有成功查询且没有资源时才显示“未设置”。图片目录入口和页面共用平台／排位／娱乐赛季权限判定，业务资源仍按各自权限读取。

当前阶段不需要配置 CDN 域名：页面和接口继续使用现有同源 `/images/*` 与 `/music/*`。以后接入 CDN 时，只需让 CDN 回源现有公共资源代理并配置 DNS/TLS，前端 URL 和权限边界不变。

## 2. 范围

首期目录包含以下公共资源：

- 卡牌图片：`thumb`、`medium`、`large`。
- 公共静态资源：卡背、牌堆图标、应用公共图标等。
- 活动封面和活动徽章。
- 快捷表情的静态图和动图。
- 候场音乐及其封面。

玩家壁纸继续使用现有私有 bucket 和鉴权读取接口，不进入公共资产列表、公共 CDN 或本期公共资产 `kind`。目录可以单独统计私有对象数量和孤儿扫描结果，但不能展示其内容。

以下内容不在首期范围：

- 浏览器直接操作 MinIO/S3 的文件管理器。
- 一次性清理所有 Git、旧 bucket 和业务表中的历史对象。
- 公共资源以外的私有 CDN、临时授权 URL 和跨用户共享。
- 新的资源专用角色。

## 3. 权限与入口

资产管理使用独立前端入口（例如 `/admin/assets`），复用现有管理员登录态和后端会话。它可以有自己的页面结构，但不能直接访问对象存储或绕过业务 API。

服务端按现有管理员权限校验以下操作：

| 操作                     | 规则                                                       |
| ------------------------ | ---------------------------------------------------------- |
| 查看目录、预览已发布资源 | 现有管理员权限                                             |
| 上传和创建 revision      | 现有管理员权限；服务端校验资源类型和文件内容               |
| 发布 revision            | 由对应业务服务执行或确认，目录 API 不替业务决定生效对象    |
| 退役                     | 无新业务引用时允许；保留历史记录                           |
| 删除/回收对象            | 二次确认；有引用时禁止；只允许回收已退役且超过保留期的对象 |

普通用户和未登录用户只能读取已发布的公共 URL。预览未发布 revision 只通过管理员 API 返回，不能让对象存储公开读取。

## 4. 目录模型

未来进入上传和发布阶段时，才考虑两张目录表和一张引用表。字段采用实际查询需要的最小集合：

```text
game_assets
  id                  -- 稳定逻辑 assetId
  kind                -- 受控枚举
  source              -- 业务来源，例如 card、activity、emote
  status              -- ACTIVE / RETIRED
  created_by
  created_at
  updated_at

game_asset_revisions
  id
  asset_id
  revision             -- 同一 asset 内单调递增
  object_key
  content_hash         -- 处理后实际文件的 hash
  mime_type
  width
  height
  bytes
  processing_status    -- UPLOADING / PROCESSING / READY / FAILED
  failure_reason
  created_by
  created_at
  published_at
  retired_at

game_asset_references
  asset_id
  revision_id
  owner_type           -- 例如 CARD、ACTIVITY、EMOTE
  owner_id
  created_at
```

约束：

- `asset_id + revision`、`object_key`、`content_hash + mime_type` 分别建立唯一性约束或查询索引。
- 业务对象需要可复现时，必须保存 `revision_id`，不能只保存 `asset_id`。`asset_id` 只表示逻辑资源，不能代表历史时刻的文件。
- `game_asset_references` 是引用索引，不取代业务表的正式外键；业务删除或替换时必须同步更新它。
- `kind` 首期只允许 `CARD_IMAGE`、`STATIC`、`ACTIVITY_COVER`、`ACTIVITY_BADGE`、`EMOTE`、`MATCHMAKING_BGM`。
- 不把任意客户端传入的 object key 写入数据库。object key 由服务端根据 `assetId`、revision 和处理结果生成。

目录详情至少显示文件属性、当前已发布 revision、历史 revision、引用来源、处理失败原因和不可变读取地址。首期不要求全文搜索；按 `kind`、状态、hash、时间、来源和是否有引用筛选即可。

## 5. 后续上传、处理和发布

以下流程不属于当前只读阶段，作为后续实现边界保留。

上传由应用 API 接收，应用使用服务端凭证写入对象存储。对象存储和数据库不共享事务，因此流程必须按以下规则实现：

1. 创建 `UPLOADING` revision，生成幂等键（客户端请求 ID 或原始内容 hash）。
2. 校验声明 MIME、实际文件类型、大小、尺寸和资源类型规则。
3. 图片按资源类型处理；卡图生成规定的三种尺寸，其他图片保留业务规定的尺寸和透明/动画属性。音频校验编码、时长和大小。
4. 处理结果按不可变 `object_key` 写入对象存储，再更新为 `READY`。失败写入 `FAILED` 和可读的 `failure_reason`。
5. 重试使用同一幂等键；已存在且 hash、处理参数一致的结果直接复用，不重复创建对象。
6. 业务服务将 revision 绑定到业务对象后，调用发布操作；只有 `READY` revision 才能发布。
7. 发布前执行一次可读性检查，确认代理能读到文件；发布后记录操作者和时间。

对象写入成功而数据库更新失败时，由补偿任务根据 `object_key` 和幂等键重试或标记为孤儿对象；数据库记录存在而对象不可读时，revision 不能进入 `READY` 或 `PUBLISHED`。孤儿对象只报告，不立即删除；超过保留期且确认无目录记录后才允许回收。

“重复内容”只表示同一 `content_hash + mime_type` 的处理结果可复用物理对象；是否属于同一个逻辑资产仍由业务决定。

## 6. URL、存储和缓存

生产公共读取链路固定为：

```text
浏览器 -> CDN（可选） -> Nginx/图片代理 -> MinIO 或兼容 S3
```

本地开发继续使用现有 `/images/*` 调试代理。生产 API 不直接承担静态文件下载，具体代理边界遵循 MinIO 文档。

新目录资源返回不可变 URL，例如：

```text
/images/assets/{assetId}/{revision}/file.webp
```

这个 URL 中包含 revision，可以设置较长的 `Cache-Control: public, max-age=31536000, immutable`。现有卡图、静态资源等兼容 URL 继续按当前业务规则提供；切换资源时由业务更新其引用，不依赖 CDN purge。目录 API 同时返回 `assetId`、`revisionId` 和 `url`，前端不自行拼接 object key。

响应至少设置正确的 `Content-Type`、`ETag` 和 `Cache-Control`；音频支持范围请求。CDN 是否启用属于部署配置，不能改变权限规则或 URL 语义。

## 7. 业务接入边界

业务服务负责：

- 判断资源是否符合业务规则；
- 选择哪个 revision 对业务对象生效；
- 在业务快照、回放或审计数据中保存不可变 `revisionId`；
- 删除业务对象时解除引用。

资产目录负责：

- 统一记录文件、revision、处理状态和操作者；
- 提供引用查询、孤儿扫描和公共 URL；
- 执行通用的格式、大小、对象存在性和权限校验。

UI 图标和极小、随前端版本发布的图标可以继续由 Vite 打包。需要运行时替换、多页面共享或体积较大的资源才进入目录。

## 8. 迁移与发布

迁移分三步，每一步都可以独立部署和回退：

1. **盘点**：扫描现有 MinIO/S3 对象、仓库 manifest 和业务表，按 hash、尺寸、字节数建立导入报告；只创建目录记录，不改变用户可见 URL。
2. **导入**：以幂等任务导入对象和引用，旧对象与新 revision 并存。每批记录成功、失败、跳过和孤儿清单，失败可重试。
3. **切换**：先让代理支持新不可变 URL，再由单个业务逐步切换引用。观察读取错误、带宽和缓存指标后再处理重复对象。

切换失败时，业务引用可以恢复到旧 revision，旧对象和旧 URL 在保留期内不得删除。迁移完成的判定是 hash、尺寸、字节数、可读性和业务引用全部一致，不以“仓库中没有旧文件”为条件。

发布只包含应用、迁移脚本和配置变更；CDN 配置、bucket 策略和数据迁移分别记录版本并可单独回退。生产环境不在本功能内自动创建 bucket、修改防火墙或删除旧对象。

## 9. 后续上传与迁移阶段的监控与验收

至少记录：上传/处理/发布/退役/回收审计、处理失败数、孤儿对象数、对象读取 4xx/5xx、CDN 命中和回源、公共 bucket 匿名读取范围。日志不得包含对象存储密钥或私有对象路径。

首期验收：

- 管理员可以按类型、状态、来源和引用状态查询目录，并查看 revision 和引用。
- 非法格式、超限文件和不符合资源类型的文件会被服务端拒绝，并返回明确原因。
- 同一幂等请求或同一处理结果重复执行不会产生无意义的重复对象。
- `READY` revision 可读，未发布 revision 不会通过公共 URL 暴露。
- 业务切换到新 revision 后，新请求使用新 URL；旧 revision 在保留期内仍可读取。
- 有业务引用的 revision 不能删除；孤儿扫描可重复执行且结果稳定。
- 迁移重复执行不会丢引用，校验报告能定位失败对象，并可以恢复到旧 revision。
- 本地代理、生产代理和 CDN 使用同一套逻辑 URL，差异只在部署层。

上线后关注公共资源 CDN 命中率、源站带宽、资源读取错误、处理失败率、孤儿对象数量和管理员定位资源所需时间。首期完成标准是目录可用、公共读取稳定、revision 可追踪、迁移可回退。

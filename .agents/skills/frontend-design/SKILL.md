# Frontend Design

默认开发者使用能力强的 agent 与 harness。自主决定调研、实现和验证方式；本 skill 聚焦设计目标、关键取舍与产品约束，不规定执行步骤或组件形式。

## 设计目标与关键判断

让目标用户在真实使用情境中正确、顺畅地完成任务，同时获得清晰、可控、舒适且符合产品气质的体验。判断时考虑用户经验、任务频率、内容密度、设备与输入方式；以下维度用于发现问题和权衡方案，按当前任务确定重点，不要求逐项写报告。

| 维度             | 设计目标与需要考虑的关键点                                                                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 任务有效性       | 用户能发现入口、理解选项、完成目标并确认结果。关键规则、状态与操作后果准确可见；关注任务成功与错误，而不只看页面是否渲染。                                             |
| 效率与认知负担   | 减少不必要的搜索、记忆、反复阅读、输入和上下文切换。用层级、分组与适当的信息密度支持扫描和比较；在需要时提供说明与详情，保留影响决定的信息。                           |
| 可学性与一致性   | 名称、图形、位置和操作语义形成可理解的心智模型。兼顾新用户的发现与熟练用户的操作节奏；模式变化明确，常用位置与焦点稳定，同类控件协调且角色可辨。                       |
| 交互反馈与控制感 | 操作是否被接受、正在进行还是已完成应有及时反馈。预防误操作，提供符合业务规则的取消、返回、修正或撤销；失败可恢复，保留有效输入，让原因和下一步出现在用户看得见的位置。 |
| 视觉与情感体验   | 字体、色彩、间距、比例、对齐、图形和动效形成有层级的整体，兼顾可读性、审美、信任与使用乐趣。延续用户认可的风格，以内容和产品身份支持特色；视觉强调与信息重要性相称。   |
| 无障碍与情境适应 | 在目标视口、主题、文字缩放与输入方式下保留主要任务。关注实际背景对比度、语义控件、焦点、键盘、读屏、触控和动效敏感性，遵循适用的 WCAG 要求；状态表达不只依赖颜色。     |
| 性能与稳定性     | 内容及时可用，输入和状态更新及时响应，布局、焦点与操作位置保持可预测。结合真实设备、网络和数据量判断加载、卡顿、跳动与资源成本；等待和失败也属于体验。                 |
| 工程可持续性     | 尊重已有组件、语义 token、状态与权限边界，保持实现可理解、可维护、可验证。正确处理异步、重复操作和状态切换，避免为了外观增加重复状态或没有实际收益的依赖与抽象。       |

这些目标可能冲突。依据用户当前任务和产品定位取舍，保持业务正确性、权限与适用的无障碍要求；不要把最少点击、最少文字、最大留白、最强装饰或最高参与度当作所有页面的统一目标。美观、感知易用和实际任务表现应分别判断。

## 产品语境与设计取舍

- 延续已有产品语言与组件体系，允许有依据的演化。一致性包含外观、语义和行为，不只是共用 token；复用与抽象服务于实际需求，局部修改的范围与收益应相称。
- **任务结构与操作成本**：按新增决策、必要上下文或风险控制判断独立页面、步骤和确认的价值。流程本身造成重复阅读或往返时，重新审视任务结构，避免只压缩文案或统一控件。
- 轻快不等于轻淡，统一不等于均质。兼顾局部控件与整页构图，让视觉重心、分组和空间关系支持任务；不以删减表达或增加装饰作为默认答案。
- 信息密度、文字与图形、交互反馈的体量与持续性，由任务和使用情境决定。表达应清楚、适度且可访问，保留关键后果与恢复路径，不套用固定视觉模板。
- **信息层级与渐进式披露**：按当前任务安排常驻信息与按需解释，压缩重复表达；影响判断的限制与后果直接可见。权衡常驻信息的扫描负担与展开内容的发现、访问成本，同时保持操作位置与焦点可预测；正文展开可以自然重排，频繁预览不应使操作目标跳动。
- **语义可辨识性**：根据含义的清晰程度选择文字、图标与颜色，权衡扫描效率、理解准确性和学习成本，避免让用户依靠猜测或记忆理解界面。
- 本仓库按需查阅[产品视觉系统](../../../docs/ui-design/product-visual-system.md)和[前端规范](../../../docs/ui-design/standard.md)。对战命令、隐藏信息与模式边界遵守对应领域约定。

## 复杂问题与研究

用户要求调研，或遇到复杂、反复修改仍难收敛、直觉与证据冲突的 UI 问题时，主动查阅相关学术研究与工业实践。研究可以帮助重新定义问题、比较候选方案或发现已有方法；检索范围与深度由当前不确定性决定。

优先原论文、标准正文、作者材料和官方产品／设计系统。学习它们如何定义问题、优化什么、怎样评估以及适用条件，将机制转化为符合当前用户、数据和产品风格的方案。区分规范要求、经验启发、实验发现与自己的推论，不把个别实验或产品外观当作通用答案。

需要确定评价维度、选择研究方向或核对依据时，参阅[设计目标与研究依据](references/design-objectives.md)。它是按需使用的参考，不是每次任务的必读清单。

## 证据与完成质量

证据应对应当前设计目标与真实使用情境，兼顾任务结果、主观体验和工程质量。没有用户研究时，不把 agent 自评或自动化通过写成已证明的用户体验提升。

UI 修改以真实浏览器中的画面和行为为依据，覆盖与问题相关的角色、内容和状态。围绕方案的主要风险选择对照状态，关注关键操作前后的变化；布局与交互改动需比较位置、遮挡和焦点，内容增长或短视口可能影响结果时补充相应证据。视觉与行为证据互补，局部与整页质量都应成立；测试通过不能替代审美判断。评审也要判断重复信息的占位价值、压缩后能否直接做出判断，以及按需说明是否容易发现；不只检查对齐、溢出和控件是否可用。

需要评审实际截图时，可使用项目内的 [ui-screenshot-review](../ui-screenshot-review/SKILL.md)。

验证深度与改动风险相称，具体工具和顺序由 agent 把控。交付说明实际变化、关键取舍、已验证内容与未覆盖边界。临时截图、录屏和报告留在本地验证目录，暂存、提交及视觉基线更新遵循用户要求与仓库约定。

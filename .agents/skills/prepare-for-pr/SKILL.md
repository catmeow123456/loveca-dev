# PR 检查与准备

围绕实际 PR 差异完成审查、必要准备和可供评审的说明。沿用仓库 `AGENTS.md` 的授权、工作树保护与验证原则。

## 根据请求确定范围

- 只要求审查、判断能否合入或起草 PR 文案时，保持只读；检查现有基线、代码、文档和已有验证材料，报告问题，不自动改文件、切分支、rebase、stage 或发布。
- 要求完整准备 PR 时，完成范围内必要修正、基线同步、可确定的冲突处理、相关验证和文案；已有授权不逐项重复询问。用户限制为检查、排除同步或给定特定基线时优先遵守。
- 推送、创建／更新 PR、重写远端历史与合并按本次及既有具体授权执行。“准备 PR”本身不授权这些外部写操作；已明确要求“开 PR”时继续完成其所需推送和创建，不停在提供文案。

## 差异与分支

从当前 checkout 根目录读取实际分支、暂存／未暂存／未跟踪状态。目标仓库和 base 分支先取用户指定值或已有 PR 信息；普通 Loveca PR 默认以作者仓库 `main` 为目标，但不能把名为 `origin` 的 fork 或未经核实的本地 `main` 当成作者最新基线。

明确本次比较的 base ref/SHA、HEAD 与 merge-base，按 `git diff <base>...HEAD` 检查分支改动；另列尚未进入提交的相关修改，不混入 PR diff。只读审查未同步远端时说明使用的已有 ref，不声称它是最新远端状态。

需要同步基线、判断／处理合并冲突或使用作者 main 独立副本时，读[分支同步](references/branch-sync.md)。不固定要求 Git 恰好等于某一版本；按实际命令能力选择检查方式。冲突、命令不支持和仓库错误分别报告，不把所有非零退出码当成冲突。

## 代码、文档与验证

完整检查或准备时，按[改动检查与验证](../prepare-for-git-commit/references/change-review.md)检查实际差异；只起草文案无需额外加载该参考。只读命中主题的规范和文档，不以通读整套需求、设计、登记册或全量测试为默认前置。

- 涉及卡效、卡文或卡效提交说明时，使用 [loveca-card-effect-governance](../loveca-card-effect-governance/SKILL.md)；数据源沿用用户指定导出及其治理要求，不由 PR 流程改选 `cards.json`、API 或“最新文件”。
- 涉及持久格式、checkpoint 复水或公开协议兼容时，读[兼容边界](references/compatibility-boundaries.md)，核对迁移和现有窄例外。
- 有可修正的问题且处于完整准备范围时，修复后只重查受影响内容；只读审查则给出定位、影响和建议。确定失败或需要用户决策的事项只阻塞相关步骤，独立审查和 PR 文案继续完成。

## PR 文案与交付

以最终 diff 起草中文标题和描述，优先遵循仓库现有 PR 模板。先写具体问题及改变后的行为，再写有助于评审的实现取舍、实际验证和必要限制；范围变化后同步重写，不保留聊天过程、已放弃方案或无关检查记录。

即使存在阻塞，也提供当前可核对的草稿并标明未解决项，不把草稿写成已验证通过。只要求文案时，不为了填写“测试通过”而自动运行整套检查或修复代码。

完整交付说明本次审查基线、结果、实际验证及遗留项；若已获授权并完成发布，附 PR 链接。多行描述通过结构化参数或临时正文文件提交，保留真实换行；创建 PR 不包含合并或正式发布。

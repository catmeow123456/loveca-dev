# 玩家可见操作文案规范

本 reference 适用于 definition / activated UI 的卡文正文与标题，以及 `activeEffect` 的
`stepText`、`selectionLabel`、`confirmSelectionLabel`、`skipSelectionLabel`、
`selectableOptions[].label` 和数字输入按钮。

## 核心原则

- 当前普通玩家 `/api/cards` 的 `card_text_cn ?? card_text_jp` 是玩家实际看到的卡文事实。
- `definition.effectText` 使用对应能力时点的完整 API 段落；
  `activatedUi.text` 在源码中直接复用该 effectText 常量，正文不得总结、缩写或改写。
- `activatedUi.title` 可以概括操作，不能替代正文，也不能作为 effectText 的来源。
- 按钮写点击后立即执行的游戏动作，不写界面机制。
- 优先复用同类既有 workflow 的稳定字面量；新增前先用 `rg` 搜索相同目的区域和动作。
- 使用玩家语言，不出现 `source`、`pending`、`stale`、`payload`、`eventId`、`trigger` 等内部术语。
- `确认` 只用于没有更具体游戏动作的纯确认步骤。能写 `加入手牌`、`登场`、`放置于卡组顶` 时，不写 `确定`、`确认选择`、`确定分配`、`选择` 或 `继续处理`。
- 同一 shared family 和同批同型卡使用一致文案；差异必须来自真实规则动作。

## 字段职责

| 字段                        | 应表达的内容                              | 示例                                            |
| --------------------------- | ----------------------------------------- | ----------------------------------------------- |
| `definition.effectText`     | 普通玩家 API 中对应能力时点的完整卡文段落 | `【起动】……` 的完整段落                         |
| `activatedUi.text`          | 直接复用对应 `effectText` 常量            | 与 `effectText` 同一源码常量                    |
| `activatedUi.title`         | 可概括本次起动操作                        | `支付[E][E]，回收1张LIVE卡`                     |
| `stepText`                  | 当前要做什么以及必要的规则结果            | `请选择至多1张放置于卡组顶，其余放置入休息室。` |
| `selectionLabel`            | 候选区选择目标                            | `选择要放置于卡组顶的卡`                        |
| `confirmSelectionLabel`     | 提交选择后执行的动作                      | `放置于卡组顶`                                  |
| `skipSelectionLabel`        | 不提交选择时的真实规则分支                | `不发动`、`不加入`、`全部放置入休息室`          |
| `selectableOptions[].label` | 玩家可选的规则动作或结果                  | `发动`、`获得[BLADE]`                           |

## 玩家可见卡文三层一致性

- 按基础编号读取普通玩家 API 的全部当前印刷，使用每个印刷实际选择的
  `card_text_cn ?? card_text_jp`。不同罕度结果不同时报告罕度漂移，不静默选一个版本。
- 按 `【起动】`、`【登场】`、`【自动】`、`【LIVE开始时】`、`【LIVE成功时】`、
  `【常时】` 等能力时点切分段落。不要把整张多能力卡文与一条 definition 比较。
- 只允许规范化 CRLF/LF 和整段首尾空白。不得按含义、关键词、标点或 token 做近似合并。
- 同一时点只有一段时可直接映射；同一时点有多段时，仅当 effectText 与其中一段完全相等时
  自动映射，否则报告“同类多段无法自动映射”。
- API 不可用、字段缺失或映射有歧义时停止该项治理；不得回退到 `cards.json`、Excel、
  `cards_cn.json` 或人工翻译。
- 已确认的 API 错误只能进入窄的显式例外清单。每项必须记录卡号、错误字段、错误值、正确值、
  正确依据和原因；禁止按系列、前缀或错误类型全局跳过。
- 联网审计使用独立只读脚本，不放入普通 Vitest。focused test 使用代码内独立完整字符串，
  同时精确断言 effectText 和 activatedUi.text；只断言二者相等或使用 `toContain`
  都不能证明玩家卡文没有被省略。

## 常用动作标准词

| 效果形状                | `selectionLabel` 示例      | 主按钮                                          |
| ----------------------- | -------------------------- | ----------------------------------------------- |
| 卡加入手牌              | `选择要加入手牌的卡`       | `加入手牌`                                      |
| 公开后加入手牌          | `选择要公开并加入手牌的卡` | `公开并加入手牌`                                |
| 卡放置入休息室          | `选择要放置入休息室的卡`   | `放置入休息室`                                  |
| 卡放置于卡组顶          | `选择要放置于卡组顶的卡`   | `放置于卡组顶`                                  |
| 卡放置于卡组底          | `选择要放置于卡组底的卡`   | `放置于卡组底`                                  |
| 多张卡按选择顺序放置    | `按放置顺序选择卡片`       | `按此顺序放置于卡组顶` / `按此顺序放置于卡组底` |
| 成员从区域登场          | `选择要登场的成员`         | `登场`                                          |
| 选择登场槽位            | `选择登场区域`             | `登场`                                          |
| 成员变为待机            | `选择要变为待机状态的成员` | `变为待机状态`                                  |
| 成员变为活跃            | `选择要变为活跃状态的成员` | `变为活跃状态`                                  |
| 成员移动槽位            | `选择移动后的区域`         | `站位变换`                                      |
| 选择卡支付费用          | `选择要用于支付费用的卡`   | `支付费用`                                      |
| 选择 Heart/BLADE 等结果 | `选择要获得的效果`         | `获得[赤ハート]`、`获得[BLADE]`                 |
| 公开卡牌的定时展示      | `本次公开的卡牌`           | 不显示按钮；到期自动继续                        |

卡组顶/底统一使用“放置于”，不要在新增文案中混用“放到”“放回”作为按钮动词。`stepText` 可按卡文说明“放回”，但提交按钮仍描述最终动作，例如 `放置于卡组顶`。

## 能量费用与能量卡操作

- 玩家可见文本中的能量费用统一使用 `[E]` token。固定费用按实际数量重复：1 点写 `支付[E]`，2 点写 `支付[E][E]`，依此类推。
- 禁止 `支付1能量`、`支付1张能量`、`支付2张活跃能量`、`支付1[E]`、`支付2个[E]` 等数字、量词与 token 混合写法；“每支付4个”也应写成“每支付[E][E][E][E]”。
- 动态费用在运行时按实际数量展开 `[E]`。数量为 0 时使用明确的 `支付0个[E]`；数量未知的 definition 文本使用“支付与该卡分数相同数量的[E]”等规则描述，不伪造固定数量。
- 费用按钮直接描述本次支付，例如 `支付[E][E]`。步骤提示使用 `可以支付[E][E]，……`；资源不足提示仍应包含对应费用 token，例如 `当前活跃能量不足，无法支付[E][E]，可以不发动。`
- `[E]` 只表示支付费用，不替代实体能量卡、区域、数量或状态。`将2张能量变为活跃状态`、`从能量卡组放置1张能量`、`自己的能量为10张以上`、`将能量放回能量卡组`、`成员下方的能量` 等文本保留“能量”。
- 特殊能量选择窗口必须同时说明费用和候选卡状态。`stepText` 按实际费用写成 `请选择用于支付[E][E]的活跃能量卡。`，`selectionLabel` 使用 `选择用于支付费用的能量卡`，提交按钮使用 `支付费用`；不要简化成无法表达候选状态的“请选择要支付的[E]”。
- 文案调整不得改变通用能量操作底座的自动处理、特殊能量选择、候选数量、稳定顺序、非法输入或 continuation 语义。

## 可选与跳过

- 整个效果可不发动：正向 option 使用 `发动`，跳过按钮使用 `不发动`。
- 固定来源自身作为成本或动作时，不展示唯一来源卡供玩家选择；使用 `发动 / 不发动`，确认发动后重新校验并直接处理来源。
- 可选择不把卡加入手牌：使用 `不加入`。
- 可选择不放置卡：使用 `不放置`；如果不选会让所有已检视卡进入休息室，应写真实结果 `全部放置入休息室`。
- 不要把负向选项同时放进 `selectableOptions` 和 `skipSelectionLabel`，避免双重跳过按钮。
- 不要使用 `取消` 表示规则上的“不发动”或“不处理”；`取消` 只适合真正撤回尚未提交的界面操作。

## 多步骤窗口

- 每一步只保留本步骤需要的选择字段。进入下一步时清理旧的 `selectableCardIds`、选择数量、确认按钮和跳过按钮。
- 第一步按钮描述第一步动作，不提前概括整个效果。例如先弃手再抽牌时，第一步使用 `放置入休息室`，不要使用 `发动效果`。
- 普通 confirm-only 窗口可使用 `确认`；Public Reveal Dwell 不显示确认按钮，只展示状态 `公开展示中，即将自动继续`。只要存在更具体动作，就使用具体动作。

## 检视与公开结果

- “检视”默认是私密查看：检视者看到正面，对手只看到检视区牌背。未被选中或未被卡文明示公开的牌，不得为了展示方便全部加入 `revealedCardIds`。
- “公开”要求双方看到正面。`inspectTopCards(..., { reveal: true })` 只改变可见性，不会自动生成玩家可阅读的停留窗口；若公开后会立即移动卡牌、判断条件、发放奖励或打开下一交互，必须先建立 shared Public Reveal Dwell。
- dwell 的 `stepText` 应说明本次实际公开张数、与卡文直接相关的条件结果以及展示结束后的规则去向；使用“展示结束后”，不要写“确认后”“继续处理后”或内部状态说明。界面统一显示 `本次公开的卡牌` 与 `公开展示中，即将自动继续`，不渲染 `selectionLabel` / `confirmSelectionLabel` 按钮。
- deadline 前，公开卡应保持双方可见，且不得执行基于公开结果的移动、奖励或 pending continuation；此前已经合法支付的费用、已经发生的区域移动与记录的 ability use 保持不变。到期后由原 workflow 重验并结算；这不是让玩家重新选择公开卡，也不得与 public-card-selection / public-effect-choice 自动展示重复嵌套。
- 普通检视选1流程中，主按钮仍描述真实动作，例如 `公开并加入手牌`；不选会使全部检视牌进入休息室时，跳过按钮写 `全部放置入休息室`。无合法目标时也应让玩家看完适用的检视结果，而不是直接关闭窗口。

## 审查与测试

- focused test 至少断言关键 `selectionLabel`、主按钮和跳过按钮的精确文本。
- 涉及检视/公开结果时，focused test 还应断言双方 projector 的 FRONT/BACK 差异、deadline 前卡牌仍在检视区且尚未结算、双方到期推进只结算一次、旧 generation 不生效，以及条件失败/无目标路径不会直接跳过适用展示。
- 能量支付文本测试至少覆盖固定 1 点、固定复数、动态 0/1/复数，以及特殊能量选择窗口按实际费用展开 `[E]`；同时确认普通能量操作文本不会被费用文案治理误报。
- 检查按钮是否描述实际规则动作，尤其拒绝 `确定分配`、无上下文的 `确定`、无动作结果的 `选择`。
- 检查可选效果是否出现两个负向按钮，固定来源是否被错误渲染成单卡选择。
- 触及这些字段后，运行 focused workflow test、`card-effect-tokens.test.ts` 和 `card-effect-text-governance.test.ts`。
